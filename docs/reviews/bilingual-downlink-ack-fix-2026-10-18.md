# 长译音挤压 ACK 的网关修复与 BT04 跟踪

用户此前确认在 **0.3.0-work.7、荣耀 300 / Android 16** 上仍出现长句 BT11，另一次出现 BT04。上一版修复了界面线程耦合，本轮补充下行发送修复后，用户反馈复测通过、问题未再复现；本次长句 BT11 验收已关闭，BT04 单独保留。

## 现场证据与原因

- 保留的节点轮转日志中，20:09:18 对应错误为 `language_detection_unavailable`。方向识别依赖发生临时失败，当前网关强制 `max_failures=1`，按既有策略立即结束会话；该故障与长句译音挤压 ACK 分开登记。
- 20:11 的长句在源文最终确认前积累译音，20:11:17 开始集中发出，20:11:22 连接中断。模型已产生译文和音频不代表手机收齐，更不代表完成播放。
- 旧网关虽然按半秒音频分包，却会在方向/原文校验放行后连续突发发送整个缓冲。音频与 ACK 共用 WebSocket/TCP 下行，ACK 会排在已经发出的音频字节后面；将手机 ACK 处理移到后台线程无法越过这段传输积压。

## 修复与验证

网关 `aliyun-dev` 产品提交 `145de46473af4fed915256621dbaae1707ec63e1`：新增有界音频发送队列（最多 60 秒原始 PCM、256 个事件），首段立即发送并保留少量播放提前量，之后按 PCM 时长推进。ACK 和译文绕过音频队列，睡眠不持有 socket 锁；音频结束标记保持顺序。正常结束等待音频队列排空，撤销或断线立即取消未发送尾音。供应商完成仍限 25 秒，音频排空另限 65 秒，且不得超过业务准入截止时间；客户端原有 95 秒结束限制覆盖这两阶段。五秒 ACK 超时、输入窗口和采集缓冲均未放宽；新增的是独立且有界的服务端媒体队列。

真实回环 WebSocket 在 120000 B/s 下行对照中，禁用新发送队列时 ACK 最大延迟 7090 ms；启用产品实现后为 528 ms。该对照没有真实模型或手机，因此又补做了以下生产链路测试：

| 条件与结果 | 旧网关 | 新网关 |
| --- | --- | --- |
| 手机、主 APK | 同一 OPPO / Android 12，work.7 | 主 APK SHA-256 完全相同 |
| 输入与连接 | 通用出行长句的两次连续合成录音，共 12.320 秒；自动方向、Tina、真实生产 API/模型 | 相同测试输入和选项 |
| 下行 | 75000 B/s 的 CONNECT 字节转发；端到端 TLS 与主机名校验保持正常 | 相同 |
| 输入发送 / 收到 ACK | 179 / 130 帧 | 349 / 349 帧 |
| 结果 | BT11；仅播放 120000 样本，未收齐音频结束标记 | 收到译文、完整音频结束和 finished；播放及回放均无错误 |

候选版即时播放与回放合计写入 387840 样本（每次约 8.08 秒），测试正常结束。模型输出有随机性，此对照保持相同输入与限速配置，未声称两轮模型输出字节完全相同。它验证真实 Android 传输与 AudioTrack 完整排空，不替代荣耀自然语音、语义和人工听感验收。

Windows 与无网络、无主机挂载的不可变 Linux 镜像各通过 **174 项**回归，新增发送公平性、队列上限、尾音结束顺序、断线、撤销和截止时间覆盖；产品代码与新增测试 Ruff 通过。原有真实 socket 测试曾因“译文可先于音频”的新顺序触发旧断言，现允许二者先后任意，仍强制 `audio_end` 与 `finished` 不越过尾音。产品提交的四项 Release guard 均通过。
