# 任务与任务清单权限设计审查

> 本文保留审查时的基线行为。对应实现已续接并验证，最终规则、验证结果与后续发布注意事项见 [任务 UX 优化收尾记录](tasks-ux-implementation-2026-09-12.md)。

基线：`fix/contacts-ux@e3a62a57`，2026-09-12。范围：任务、任务清单的查看、编辑、删除，以及影响这三类权限的共享、归档、移动和所有权。任务分组/清单分组仅作为关联规则参考。

方法：对照后端查询范围、序列化能力字段、写接口、前端入口和已有测试。未修改业务代码、未提交或推送本报告，未运行真实账号权限场景或后端测试。下面是静态审查确认的代码行为与由此推导的产品影响，不宣称已完成动态漏洞复现。

## 结论

基础规则大体一致，但完整权限设计尚未自洽。当前实现使用“各角色授权取并集”的模型，而界面只展示“可查看 / 可编辑 / 所有者”。编辑还隐含删除任务、调整清单成员权限、移动任务等能力；这些能力的影响范围与生命周期没有在界面中充分表达。

应保留“任务权限不等于清单权限”的区别，同时明确任务内容编辑、任务迁移、任务删除、清单成员管理四种独立动作。不要通过让所有查看者一律只读或给管理员一律全量访问来掩盖边界问题。

## P1：应优先明确或修正的边界

### 1. “可编辑”的说明与实际授予的权力不一致

**已确认：**共享提示只说“可查看成员只能浏览；可编辑成员可以新增、修改、完成任务及归档清单”。实际上编辑者还可删除清单内其他人创建的任务、邀请成员、提升查看者为编辑者、降低或移除其他编辑者。后端和前端都允许这些操作，不是单纯按钮误显。

同样，“可查看成员只能浏览”对同时担任任务负责人或创建者的人不成立。已有后端测试明确验证查看者成为负责人后可以编辑，但仍不能仅凭负责人身份删除。

**风险：**分享人以为只授予内容协作能力，实际还授予永久删除和授权管理能力。两个编辑者可互相移除，但界面没有“清单管理员”这一概念。

**建议：**默认把成员授权管理保留给所有者，或者增加明确的清单管理员角色；将删除任务能力单独表达。如果决定保留当前编辑者权限，共享提示必须明确“可删除任务、管理成员权限”，并说明任务直接角色会叠加。

证据：`src/frontend/src/locales/zh/tasks.json:182`；`src/frontend/src/features/tasks/components/TaskListDialogs.tsx:143`；`src/backend/core/api/serializers.py:807`、`:1007`；`src/backend/core/api/tasks.py:1182`、`:1234`、`:2068`；`src/backend/core/tests/tasks/test_api_task_lists.py:150`。

### 2. 任务内容编辑权可以改变清单的访问边界

**已确认：**任务负责人或创建者通过普通 PATCH 即可修改 `task_list_id`。指定非空目标时检查目标清单的编辑资格；设为 null 时直接通过，没有要求管理源清单。界面也把“所属清单”作为普通 `can_edit` 字段开放。

**具体场景：**A 拥有清单，B 在其中创建任务并指派 C。C 只有任务负责人权限，没有清单编辑权。C 将任务移入默认清单后，A 如果没有该任务的创建/负责/关注或其他授权，就不再能看到任务。任务未删除，但从 A 的管理视角消失。

**判断：**这不是绕过现有接口限制，而是规则本身把内容编辑与授权边界修改合并了。若任务清单定位为轻量项目，这个能力应当被明确约束。

**建议：**单列 `can_move`；移出共享清单须满足源清单的迁出规则，移入另一个清单须满足目标写权限。迁移前展示会失去访问的成员范围，不能只把它当作普通分类变更。

证据：`src/backend/core/api/tasks.py:629`、`:1839–1863`；`src/frontend/src/features/tasks/components/TaskSidePanel.tsx:1047`；`src/backend/core/services/task_hierarchy.py:303–308`。

### 3. 删除清单时的附加删除范围与文案不一致

**已确认：**勾选项是“同时删除只属于该清单、无负责人的任务”，但后端只检查任务属于该清单且单/多负责人均为空，没有检查创建者、关注者、会话分享、独立分组、父子关联等。被选中的任务会进入真实删除和附件清理流程。

**具体场景：**一个无负责人任务仍有其他人的关注、评论或会话分享，也会被此选项删除。“无负责人”并不等于“没有其他协作或访问关系”。这是已有无负责人数据或人员变化后数据的边界场景，不是说正常新建任务默认没有负责人。

**建议：**要么严格定义“只属于清单”的判定并实现，要么准确改成“删除该清单中所有无负责人任务”，展示实际受影响数量与预览，并说明关注/分享关系及附件会失效。默认取消勾选是正确的，应保留。

证据：`src/frontend/src/locales/zh/tasks.json:199`；`src/frontend/src/features/tasks/components/TaskListDialogs.tsx:223`；`src/backend/core/api/tasks.py:1168–1179`、`:247–263`。

### 4. 所有者不可退出、不能转让，缺少离职接管路径

**已确认：**所有者不能退出，共享接口不能改动 owner，也只接受 viewer/editor；清单更新不能修改 creator。组织管理员没有清单自动访问/删除权限。当前离职资源盘点也没有任务清单。

**影响：**所有者离职或账号不可用后，其他编辑者仍能修改任务和归档，但没有产品内的删除清单或正式接任所有者入口。若所有者之外没有清单协作者，清单更难恢复管理。

**建议：**增加所有者转让，保证至少一个有效所有者；离职盘点纳入清单。为管理员提供受审计的接管流程，而非默认读取所有私有清单。用户删除或注销前也应有同样的处理。

证据：`src/backend/core/api/tasks.py:1197–1219`、`:1243–1270`、`:1313–1318`；`src/backend/core/api/serializers.py:854`；`src/backend/core/services/offboarding.py:71–103`。这是当前仓库中未找到接管实现，不排除仓库外人工运维手段。

## P2：前后端能力与入口不一致

### 5. 编辑所属清单时，把只读目标显示为可选

**已确认：**详情和表格编辑器将所有可见清单作为候选，没有筛选可写清单；后端却只接受可编辑、未归档的目标。因此“有权编辑任务，但目标清单只可查看”的用户可选中目标，提交时才失败。

新建任务窗口已经按 `can_create_tasks` 筛选，编辑入口没有采用相同边界。当前清单因只读而不在可写候选中时，仍需保留它的只读显示，不能让控件看起来像任务已无清单。

**建议：**统一候选来源，禁用不可写目标并解释原因；结合上一条独立迁移能力，分别检查源与目标，不要仅用一个 `can_edit`。

证据：`src/frontend/src/features/tasks/routes/TasksRoute.tsx:498`、`:853`；`src/frontend/src/features/tasks/components/TaskSidePanel.tsx:1063`；`src/frontend/src/features/tasks/components/TaskList.tsx:1433`；`src/backend/core/api/tasks.py:629–648`。

### 6. 归档不是只读，但归档清单缺少完整查看与退出入口

**已确认且本身合理：**当前归档定义是“默认隐藏且不能新建任务”，不是冻结。已有测试明确允许修改归档清单中的已有任务。不能将“归档后可编辑”直接当成权限漏洞。

**不一致部分：**归档清单侧栏名称只是文本，只给有编辑权的人提供“取消归档”。查看者虽然仍有读取权限，却不能从此入口打开清单，也无法退出。任务列表按清单筛选又固定要求 `is_archived=False`，不能简单补一个点击事件就解决。其任务可能仍从全部任务/直接链接访问，形成同一对象不同入口体验。

另一个能力冲突是 `can_create_subtasks` 只检查任务编辑权与层级数量，没有检查默认继承的清单是否归档。前端新建子任务默认携带父任务清单，提交时会被清单归档校验拒绝。用户能否在另一个活跃清单下创建子任务应另行定义，不应被一个笼统布尔值混在一起。

**建议：**已归档清单可打开、可查看；非所有者仍可退出；明确既有任务可否编辑。对“在归档清单下新建子任务”提前禁用或要求选择有效目标。详情对象的查找应与清单列表的 archived 筛选参数分开。

证据：`src/frontend/src/features/tasks/components/TaskWorkspaceNavigationNodes.tsx:190–231`；`src/backend/core/api/tasks.py:515–523`、`:1120`；`src/backend/core/api/serializers.py:1091–1103`；`src/backend/core/tests/tasks/test_api_task_lists.py:306–336`；`src/frontend/src/features/tasks/components/TaskForm.tsx` 的父任务清单初始值和提交 payload。

## 需要写清，但不应误判为后端漏校验的规则

- **退出/移除清单成员不等于撤销所有任务权限。**任务创建者、负责人、关注人仍通过各自角色保留访问；降为 viewer 也不会消除直接任务编辑资格。撤权对话框应提示残留权限来源。若产品要实现“完全撤权”，应另外处理这些关系，不能仅删除一条清单共享记录。
- **任务删除与清单删除不同。**直接删除任务仅删除该任务，子任务保留并脱离父任务；默认删除清单则保留任务并清空 task_list。只依赖清单授权的人可能无法继续访问保留任务，应在确认中解释。不能把“看不见”与“已删除”混为一谈。
- **子任务协作默认授予祖先读取，不授予编辑。**这是显式配置，不是前端误显；但分配子任务/加入关注人时宜说明上层信息可见范围。会话分享另有祖先链限制。
- **组织管理员不自动读取业务清单是合理选择。**不要把清单分组中管理员可管理的规则错误套到清单本体；接管与日常查看是两种动作。

## 建议的规则收敛顺序与验收

1. 明确 editor 是否允许删除任务、管理授权，优先修正文案与高影响动作边界。
2. 分离内容编辑、移动、删除、管理成员等能力；校验与序列化能力复用同一政策函数。
3. 补 owner 转让/接管、归档查看与退出、撤权后残留授权说明。
4. 用同一组角色数据验证页面能力、API 能力字段和 HTTP 操作结果。

重点验收场景：

| 场景 | 应明确的验收结果 |
| --- | --- |
| viewer 同时是负责人 | 内容可编辑、删除资格单独判断，界面解释来自负责人身份 |
| editor 删除其他人创建的任务 | 与分享时授予范围完全一致，有永久删除说明 |
| editor 管理另一个 editor | 按最终政策允许或拒绝，前后端相同 |
| 负责人移出只读共享清单 | 校验源清单规则，并说明迁移带来的可见性变化 |
| 编辑任务选择只读目标 | 无可成功提交的误导入口 |
| 删除清单中的无负责人但有关注人的任务 | 预览、文案、实际删除集合一致 |
| viewer 打开/退出归档清单 | 仍可查看和退出，不需要先请求编辑者取消归档 |
| 归档父任务创建子任务 | 默认目标与能力字段一致，无点开后才发现无法提交 |
| 清单撤权但任务仍有直接角色 | 正确保留或明确撤销各项独立授权，不制造“撤权完成”的假象 |
| owner 离职 | 有有效接任者或受审计的管理员接管路径 |

建议先处理第 1–4 项权限语义与生命周期问题，再统一编辑候选和归档交互。当前没有证据支持“普通无关用户可以任意编辑/删除任务”的笼统结论。
