## 1. 结论摘要

设计整体质量高：信任边界划分（LiveKit 只传媒体与消息、服务端管身份与授权、B 本机持有最终执行开关）正确；§6.3 的两层状态（业务 PAUSED / CAPTURE_SUSPENDED）、§7.2 的 `closeAndRelease` 独立安全路径、§9.1 的 guardian 兜底与"不确定窗口"保守释放，都是对上一轮评审问题的正确修复方向；§17 的能力边界声明（不承诺端到端保密、不承诺撤销零延迟、不承诺任意系统界面可控）也符合工程诚实性要求。

本轮核对中，**§2 引用的 14 条源码路径与能力声明全部属实**，依赖版本（`livekit-client` 2.17.1、`@livekit/components-react` 2.9.19）与基线 commit `e95c6ebb8` 一致。

需要区分两类问题：

- **必须补齐的实施契约**（F-01、F-04、F-05、F-07、F-11、F-12）：这些是文档尚未定义、实现时必然踩到的东西。F-01 是其中唯一影响"授权是否可信"的一条，须在 P1 授权实现前关闭。
- **表述与口径的澄清**（F-02、F-03、F-06、F-08、F-09、F-10、F-13、F-14）：不影响总体架构，但会直接影响验收项的写法与测试能否构造，应在文档修订时一并改掉。

**不存在需要阻止 P0 技术验证的问题。** SDK 去重语义、共享源绑定细节、原生确认的最终形态都属于 P0 应当产出的结论，不应阻碍技术验证；P1 的授权与协议实现则应等待 F-01 的契约补齐。

## 2. 问题清单（按处理优先级）

### F-01（P1 阻断项）可信密钥绑定与本机确认机制未定义

- 文档位置：§5（第 117、119 行）、§6.2（`prepare`/`approve`，第 156–157 行）、§6.1（`target_public_key`，第 138 行）、§9.2（第 319–321 行）、§16（第 450 行）。
- 问题方向：文档主张服务端"无法替 B 点击同意"、`approve/` 由"B 主进程流程"提交。核对到 B 端 Renderer 与主进程使用的是同一套用户级凭据（`src/desktop/src/main.ts:94-124` 的主进程也是取 `auth.access()` 的 Bearer token 调 `/api/v1.0/...`），因此服务端无法从认证层面区分 `prepare/approve` 的提交者是主进程还是被攻陷的 Renderer。
- **但初版推导不成立**：即便要求提交签名，只要 B 的公钥本身可以凭普通用户凭据在 `prepare` 时提交，被攻陷的 Renderer 完全可以自行生成密钥并自签。服务端只能证明"提交者持有该私钥"，**不能证明它来自可信原生进程，也不能单凭签名证明是真人操作**。
- 因此不能表述为"已存在确定的 P0 越权漏洞"。原方案的主进程本地确认与"本机主进程持有最终执行开关"仍然有效——真正的缺口是**这条确认与这把密钥从来没有被写进协议**。
- 需要补齐的三件事：
  1. **激活条件写进契约**：主进程只能激活与自己生成的密钥、可信采集实例及本地确认记录三者完全匹配的许可；许可中的 `share_instance_id` / `track_sid` / `display_binding_hash` 与本地记录不一致即拒绝激活（不接受"服务端签发的就一定对"）。
  2. **签名覆盖范围明确**：签名须覆盖不可变申请摘要、服务端一次性挑战、绑定信息、用途（audience/scope）和有效期，防止被替换与重放；挑战为一次性且与 `state_version`/`epoch` 绑定。
  3. **如要求服务端也能验证原生来源**：需引入可信设备密钥登记或等价证明机制（设备注册、硬件绑定或平台证明），临时自签公钥不足以承担该职责。这条应作为**决策项**写入 §16，而不是默认"签名即证明"。
- 处理建议：列为 **P1 授权实现前阻断项**；文档修订时同步修正 §5、§6.1、§6.2、§9.2 的措辞，避免读者把"产品流程约定"读成"协议保证"。

### F-02（P3，表述澄清）接收端不依赖 destination 字段

- 文档位置：§7.1 第 205 行。
- 核对到的事实：`livekit-client@2.17.1` 的 `RoomEvent.DataReceived` 实际参数是 `(payload, participant, kind, topic, encryptionType)`（`dist/livekit-client.esm.mjs:26085`），`UserPacket` 虽定义了 `destination_identities`（同文件 4721 行），但未透出给 JS。
- 初版误读纠正：该行的接收端校验清单为 topic、room、session、身份、签名、大小、版本，**并未要求读取 destination**；"每次必须显式设置唯一 `destinationIdentities`"是对发送端的要求，成立且必要（该字段为空即广播给全房间）。
- 需要的修正：仅补一句"接收端无法读取 destination 字段，身份与授权完全依赖 `participant.identity/SID` + 服务端绑定公钥 + 逐条签名"。可作为 §13 P0 的核对项之一，但它不构成阻断。

### F-03（澄清，保留原验收）SDK 去重与应用 seq 是两套序号，缺口检测仍然有效

- 文档位置：§7.1 第 209 行、§7.3 第 251 行。
- 核对到的事实：`handleDataMessage`（`dist/livekit-client.esm.mjs:19796-19821`）按 `(participantSid, sequence)` 做接收侧去重：`if (lastSeq && dp.sequence <= lastSeq) return;`，`reliableReceivedState` 为 `TTLMap`。即 Receiver 会在到达 JS 前静默丢弃重复/乱序包。
- **撤回初版结论**："前向缺口用例无法确定性构造"不成立。SDK 序号与应用层输入 seq 相互独立：SDK 丢弃某包后，若后续仍有应用输入到达，应用层就会看到 seq 缺口；若没有后续输入，则由待确认输入超时检测。
- 需要保留并写清的三点：
  1. **拒绝跳号执行**是核心保护，不能取消：它避免遗漏 key-up/button-up 后继续控制（正是上一轮 P1 修复的同一类风险）。
  2. 文档应说明两套序号的职责分工：SDK 序号负责通道去重，应用 seq 负责防重放与拒绝跳号执行；"可靠通道不等于可靠交付"的定性仍然成立。
  3. 验收用例可确定性构造：在模拟 transport 中投递**有效签名的 seq=1 与 seq=3**（或拦截 seq=2 后继续投递 seq=3），断言关门、作废代次、释放台账并终止，且后续 heartbeat 不能重新开启输入。

### F-04（采纳 + 补充）更换 F12，并明确组合拦截与命中测试

- 文档位置：§3.3 第 75 行、§8.2 第 287 行、§9.2 第 315 行。
- **采纳设计方补充：当前 `Ctrl+Alt+Shift+F12` 候选应直接更换。** Windows 官方说明 F12 保留给调试器，不应注册为热键；这比"远程注入可能触发热键"更直接，属于设计修订项而非实现细节。
- 初版一处表述纠正：A 注入该组合触发的是"停止控制"，属**安全方向的动作，不是授权绕过**；文档的问题在于组合拦截策略与产品表述必须一致，而不是"这构成越权"。
- 需要写清：
  1. 替换后的候选组合，以及 `RegisterHotKey` 失败时"本次不开放被控能力"的行为保留；
  2. 该组合在注入层的拦截粒度（按键级还是组合级）及对目标应用合法使用的影响，作为产品说明的一部分；
  3. "原生命中区域拒绝远程指针"从设计意图变为可测契约：命中区域随控制条位置、DPI、多显示器变化，需 §14 用例覆盖。

### F-05（采纳）申请 TTL 与原生模态确认框的交互

- 文档位置：§3.1 第 58–60 行、§6.2 第 155–157 行、第 172 行。
- 问题：原生模态框（既有写法见 `src/desktop/src/main.ts:373-386`）阻塞到用户点击，而申请 TTL 30 秒、准备 TTL 60 秒；B 犹豫超过 30 秒后点"允许本次控制"会拿到服务端过期，界面此前无任何倒计时或失效反馈。
- 需要的修正：定义到期时原生框的禁用/自动关闭行为、迟到确认的明确拒绝与用户提示（不是静默失败），并在 §10 生命周期表补一行"确认框超时"。

### F-06（表述纠正 + 建议保留）"插入输入流"不等于"目标应用完成操作"

- 文档位置：§7.3 第 255 行、§9.1 第 304 行、§10 第 338–342 行。
- **事实纠正**：初版写"UIPI 拦截下可能返回成功"不准确。UIPI 阻止时 `SendInput` 调用失败、返回 0，只是返回的错误信息不足以明确识别失败原因。正确的边界是：返回数量表示事件被插入输入流的数量，**不证明目标应用完成了操作**——`ACK 表示注入 API 已处理，不保证目标应用完成业务动作`（§7.3 第 255 行）这句本身已经正确。
- 仍然成立的空白：安全桌面（UAC 提示、锁屏、登录界面）切换期间，"插入成功但未到达目标应用"无法从返回值区分。建议保留原修正：**该期间一律按不确定状态处理——作废代次、保留候选台账直到 B 本地确认、禁用被控能力直至 B 本地检查**，并与 §9.1 第 311 行的阻断规则统一表述。
- 另需在文档中避免使用"注入成功即已生效"的措辞，防止实现者据此提前清理台账。

### F-07（采纳）整屏绑定的落地路径与既有实现不一致

- 文档位置：§2 第 42 行、§8.1 第 263 行、§12 第 365 行。
- 核对到的事实：`src/desktop/src/main.ts:388-417` 现有的 `setDisplayMediaRequestHandler` 把屏幕与窗口混在一个原生对话框，`slice(0, 20)` 截断，按 `source.name` 展示，且不保存任何 `display_id`。
- 需要写清：
  1. 远控只在"整块显示器"源上成立，需在共享路径上区分源类型并提供专门的整屏选择入口（或明确的降级提示）；
  2. 20 个源的上限在多显示器 + 多窗口场景下的行为；
  3. `source.display_id` / `source.id`（`screen:x:y`）如何成为 `display_binding_hash` 的输入，必须实测，不得默认与 Win32 物理显示器一一对应；
  4. 屏幕采集权限系统弹窗失败/拒绝时的处理；
  5. 混合源下的映射失败降级：只允许查看，不建立可执行绑定。
- §13 P0 增列"多显示器 + 窗口源混合下 source↔display 映射验证"。

### F-08（采纳）状态命名口径统一

- 文档位置：§3.3 第 76 行。
- 需要的修正：在首次出现处直接写"业务 PAUSED（见 §6.3）"，与第 77 行的 `CAPTURE_SUSPENDED` 明确区分，避免被实现成本地输入 → CAPTURE_SUSPENDED → A 可自助恢复（正是 §6.3 禁止的路径）。

### F-09（部分采纳）客户端不可用与断线重申请的体验代价

- 文档位置：§3.1 第 60 行、§6.2 第 164 行、§10 第 335 行。
- 已有充分覆盖的部分（无需改动）：端能力检查与"不因 Web 端缺少 native capability 而弹出无效批准流程"（§12 第 374 行）；断线/重连需新申请、新密钥、新 epoch（§10 第 335 行）。
- 需要补齐的仅是提示与已知代价：B 未安装/未运行桌面客户端时申请只能到期，应有明确 UI 提示；连接替换或短暂断线后的重申请应作为**已知 UX 代价**写入 §3 或 §16 决策表，避免 P2 验收时才暴露。

### F-10（部分采纳）停止新注入与释放既有按键是两个上界，不能合并

- 文档位置：§6.2 第 174 行、§10 第 336 行、§15 第 435 行。
- **采纳设计方修正**：初版建议合并为"撤销的双重上界"是不准确的。二者语义不同：
  - **停止新注入**的上界由许可租约（15 秒）与心跳（3 秒）约束；
  - **释放既有按键**依赖原生监督与候选台账路径（§9.1），其成功与否不由租约决定。
- 需要的修正：文档分别写明这两条上界各自的覆盖范围与失败表现（`RELEASE_FAILED` 与阻断新授权），避免读者以为 15 秒覆盖按键释放。

### F-11（采纳，调整落地建议）新增专用远控 HTTP 请求封装

- 文档位置：§9.2 第 319–321 行、§12 第 365 行。
- 调整后的建议（初版只说改正则，不充分）：**不应复用 `localCloudRequest` 的正则白名单**——该函数还硬编码了 Work / AI Platform 的路径前缀（`/api/v1.0/work/`、`/api/v1.0/ai-platform/`，见 `src/desktop/src/main.ts:95-96、102`）。应新增**专用远控请求封装**，并保持既有纪律：
  1. 独立端点白名单（固定端点、无用户输入拼接）；
  2. 登录 epoch 校验（复用 `auth.epoch` 的既有模式，`main.ts:98-100、116`）；
  3. 响应体大小上限与超时（对齐既有的 2.1 MB / 8 秒约束）；
  4. 错误码只回传白名单化的稳定 code，不回传服务端原始信息。
- 同时补认证口径：`LiveKitTokenAuthentication`（`src/backend/core/authentication/livekit.py:41-44`）在找不到 `sub` 对应 User 时返回 `AnonymousUser` 而不是拒绝，远控接口须**显式检查真人账号**（`user.is_authenticated and user.is_active and user.sub`，可与 `src/backend/work/api.py:29`、`src/backend/ai_platform/api.py:51` 对齐），否则"匿名访客首期不开放"只是文字承诺。
- 附带证据：`DisconnectReason.DUPLICATE_IDENTITY` 已被现有前端处理（`src/frontend/src/features/rooms/components/Conference.tsx:350`），§3.3/§14 关于"连接替换终止旧许可"的假设与现状一致，建议在 §2 增补此行便于实现者定位。

### F-12（采纳）文本提交键与 composition 事件的隔离

- 文档位置：§3.1 第 61 行、§8.2 第 284–285 行、§7.2 `keyboard.text`。
- 需要的修正：明确输入框的 Enter 提交、按钮点击、以及输入法 composition 事件**均不得进入远程键盘流**，避免"文本 + 回车"重复注入或非预期换行；纳入 §14 键盘用例。

### F-13（版本协商采纳，改名可选）topic 命名与协议版本共存
