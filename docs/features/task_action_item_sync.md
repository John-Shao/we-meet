# 任务与会议行动项状态联动

## T3.1 目标

会议行动项负责确认会议结论，任务负责跟进执行。T3.1 先建立从任务到来源行动项的单向、可解释状态联动，同时保留人工决策的最高优先级，避免双向自动更新形成循环或覆盖会议管理员的判断。

## 联动规则

仅带有 `source_action_item` 的会议任务参与联动：

| 任务变化 | 来源行动项当前状态 | 结果 |
| --- | --- | --- |
| 待处理/进行中 → 已完成 | 已确认 | 自动改为已完成，并记录本次任务动态为同步来源 |
| 待处理/进行中 → 已完成 | 已完成 | 保持不变，记录已经一致；人工完成不会被标记为任务驱动 |
| 待处理/进行中 → 已完成 | 待确认/已驳回 | 保持人工状态，记录同步冲突 |
| 已完成 → 待处理/进行中 | 上次由任务自动完成 | 自动恢复为已确认，并清除同步来源 |
| 已完成 → 待处理/进行中 | 人工完成 | 保持已完成，记录人工覆盖 |
| 已完成 → 待处理/进行中 | 已确认 | 保持不变，记录已经一致 |
| 已完成 → 待处理/进行中 | 待确认/已驳回 | 保持人工状态，记录同步冲突 |

任务状态流转不允许从已完成直接进入已取消，因此不需要额外定义“已完成 → 已取消”的行动项行为。个人任务和没有来源行动项的任务不执行任何同步。

## 人工优先与来源标记

`ActionItem.task_status_sync_activity` 仅保存最近一次真正改变行动项状态的任务动态。它不是通用的“最后修改人”字段，而是判断任务重新打开时是否有权恢复行动项的内部来源标记。

会议管理员或行动项负责人手工修改行动项状态时，服务端会清除该标记。此后即使任务重新打开，也不会覆盖人工完成、待确认或驳回状态。部署前已经处于已完成状态的历史行动项没有来源标记，按人工完成处理，不会因任务重新打开而自动恢复。

## 审计

任务状态变化动态的 `changes.source_action_item_sync` 记录行动项 ID、同步前后状态、结果和可选原因。结果包括：

- `updated`：联动实际修改了行动项。
- `already_aligned`：双方状态已经一致。
- `skipped_manual_override`：人工完成优先，未执行回退。
- `skipped_conflict`：行动项处于待确认或已驳回等冲突状态，未覆盖。

来源行动项发生人工状态变化时，关联任务新增 `source_action_item_changed` 动态，记录原状态、新状态以及是否覆盖了任务同步结果。任务页面会把上述结果展示在操作历史中，便于解释任务状态和行动项状态为何一致或不一致。

## 本阶段边界

T3.1 不包含：

- 行动项状态自动反向修改任务状态。
- 标题、说明、负责人或日期的双向同步。
- 为联动结果发送额外 IM 通知。
- 自动修复历史任务与行动项的状态差异。

后续阶段如增加行动项到任务的反向同步，需要先定义事件来源、幂等键、冲突版本和循环抑制规则。

## 部署与验收

部署后端前执行迁移 `0117_action_item_task_status_sync`，并同时发布前端以展示新增的时间线文案。建议至少验收：

1. 已确认行动项的任务完成后，行动项自动完成，任务历史显示同步成功。
2. 同一任务重新打开后，行动项自动恢复为已确认。
3. 人工完成行动项后再完成并重新打开任务，行动项仍保持已完成，历史显示人工优先。
4. 待确认或已驳回行动项对应的任务完成时，行动项不变，历史显示同步冲突。
5. 任务自动完成行动项后，再人工修改行动项状态，任务历史显示来源行动项的人工变化；随后重新打开任务不会覆盖该状态。
6. 普通个人任务的状态流转保持原有行为。
