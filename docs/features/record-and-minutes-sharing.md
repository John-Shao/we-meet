# 会议实录与智能纪要：独立分享及协作者管理

日期：2026-09-22。依据用户提供的两组飞书移动端截图（会议实录七张、智能纪要六张）、聊天卡片截图及明确说明。已在后端、Web 与 Android 实现，本次未部署。下文保留截图分析与实施前差异，最终实现范围见文末。

## 核心边界

会议实录与智能纪要是两个独立的授权对象。两者可以复用分享、选人、角色选择等 UI 组件，但必须分别保存和校验所有者、协作者、角色、链接分享及权限设置。某一侧的邀请、移除、角色调整、所有权转移或链接设置变更，不得改变另一侧的授权。

实录页面内的概要（参考截图中的“纪要”标签）、章节、文字记录、发言人属于实录。独立的智能纪要文档是另一对象，不能因标签名相似而共用纪要文档权限。产品内继续使用“概要”以区分二者。

从实录打开智能纪要、从智能纪要打开实录，都需要校验目标对象权限；内容关联本身不授予访问权限。

## 本产品确定的入口与分享范围

用户补充要求：会议实录与智能纪要均将“分享”和“协作者管理”设为两个独立入口，分享方式仅支持“发送至会话”和“复制链接”。以下产品规则优先于后文的飞书截图参考。

| 入口 | 内容与操作 |
| --- | --- |
| 分享 | 仅展示“发送至会话”“复制链接”，作用于当前实录或当前纪要文档 |
| 协作者管理 | 查看协作者、邀请协作者、调整角色、设为所有者、移除；链接访问范围和权限设置归入此入口 |

两个入口在当前内容页面分别可达，协作者管理不以先打开分享面板为前提。分享面板不混入邀请、成员名单或权限管理；协作者管理不混入转发渠道。链接访问设置与“复制链接”分别处理，发送至会话和复制链接本身不自动新增协作者或扩大访问范围。

分享不设置“其它”渠道分组，不展示微信、朋友圈、QQ、加密链接、图片分享，也不通过系统分享菜单引入额外渠道。这些截图中的能力仅作为参考记录，不进入本次产品范围。

## 会议实录截图确认的交互

1. 实录详情的“更多”打开操作底部面板，显示内容标题、所有者及“分享”等操作。
2. “分享”打开独立底部面板，包含“邀请协作者”“协作者”“链接分享”“权限设置”，底部提供分享渠道及“复制链接”。
3. 邀请协作者进入全屏选择页：搜索用户、群或部门；支持组织架构、多人选择、已选展示，底部显示已选数量和“下一步”。
4. 下一步进入邀请确认页：逐项设置被邀请对象的角色，可添加备注和选择“发送通知”，最后点击“邀请”。截图中的初始角色是“可阅读”。
5. 角色选择使用底部面板，提供“可管理”“可编辑”“可阅读”。“可管理”的说明为“可以编辑、分享内容和修改权限设置”。邀请阶段的“删除”仅从本次待邀请名单删除。
6. 已有协作者页显示人数、所有者及其他协作者，右上角可以继续邀请。成员角色面板提供角色调整、“设为所有者”和“移除”。所有者在列表中单独标识。
7. 截图中链接分享未开启，提示“仅添加的协作者可通过链接打开内容”。复制或转发链接与开放链接访问是不同动作。

## 智能纪要补充截图确认的交互

1. 智能纪要以独立文档页展示，顶部标题栏直接提供分享按钮，页面标题为“智能纪要：中国老板”。本组展示的是从文档顶部直接进入分享的路径。
2. 分享底部面板同样分为“邀请协作者／协作者”和“链接分享／权限设置”两组，协作者行右侧展示头像。
3. 本次纪要截图的链接分享提示为“组织内获得链接的人可阅读”；前一组实录截图为“链接分享（未开启）”。两者可以处于不同的分享状态。截图只能确认当前示例状态，不能推断两类内容的新建默认值。
4. 邀请选择页的搜索提示为“搜索用户、群组、部门、用户组或智能体”，比实录截图展示的搜索范围更广。两者均有组织架构入口、已选展示、已选数量和“下一步”。搜索提示不代表这些主体具有完全相同的授权语义。
5. 邀请确认页、备注、“发送通知”、邀请按钮及角色底部面板与实录相似。截图先展示“可阅读”，随后展示选中“可编辑”；“可管理”说明相同，邀请阶段提供“删除”。
6. 补充的已有协作者管理截图同样展示所有者标识、角色调整、“设为所有者”和“移除”。
7. 纪要分享栏可见“发送至会话”“复制链接”“加密链接”“图片分享”“微信”。实录分享栏可见“发送至会话”“复制链接”“微信”“朋友圈”“QQ”。这些是截图可见项目，不代表完整渠道清单，也不能据此断言另一对象不支持某项能力。

## 共用结构与对象差异

| 项目 | 会议实录截图 | 智能纪要截图 |
| --- | --- | --- |
| 展示的分享入口 | 实录详情 → 更多 → 分享 | 独立纪要文档 → 顶部分享按钮 |
| 分享面板结构 | 邀请协作者、协作者、链接分享、权限设置、分享渠道 | 相同结构 |
| 当前链接状态 | 未开启，仅添加的协作者可通过链接打开 | 组织内获得链接的人可阅读 |
| 邀请搜索范围 | 用户、群、部门 | 用户、群组、部门、用户组、智能体 |
| 角色 | 可管理、可编辑、可阅读 | 相同角色名称和选择方式 |
| 已有协作者操作 | 改角色、设为所有者、移除 | 相同操作结构 |
| 分享栏可见差异 | 朋友圈、QQ | 加密链接、图片分享 |

实现时复用选人、邀请确认和角色管理交互，按本产品要求拆分分享与协作者管理入口，不照搬截图中的合并分享面板。各入口固定绑定当前实录或当前纪要文档，名单、角色、链接和设置只作用于该对象。面板内不提供切换“纪要／原文”授权对象的选项。选人范围按对象及实际接入能力配置，分享动作固定为发送至会话和复制链接；相同角色名称不意味着两种内容的编辑操作完全相同。

Web 的「选择联系人」面板（[`DirectoryMultiPicker`](../../src/frontend/src/features/contacts/components/DirectoryMultiPicker.tsx)）是日历「添加参与者」、云文档「邀请成员」与会议资料「邀请协作者」共用的同一块左搜索勾选／右已选面板。邀请协作者因此收敛为**一个弹窗、两个视图**（成员名单 ↔ 选人），并在选人视图里用**一个角色下拉作用于本批所有人**：截图里的「下一步 → 逐人配置角色 → 添加备注 → 邀请」四步合并成「勾人 → 选角色 → 邀请」三步，个别角色差异在邀请完成后于成员名单里单独调整（与云文档邀请成员一致）。「添加备注」「发送通知」跟随角色下拉放在同一底部动作区，不再独占一页。

**该收敛已由用户确认（2026-09-22）为最终方案，Web 与 Android 两端同构**：Android `MaterialActions.kt` 原来是「成员名单 → 选人 → 邀请确认」三步加逐人角色底部弹层，现同样改为一个对话框两个视图，整批共用一个角色。两端共用同一份后端契约。成员行两端都画头像：后端 `collaboration/<scope>/` 的成员行给出 `avatar_url`（与目录接口同一套 presigned URL），用户行取 `avatar_key`，部门与用户组没有头像字段、回落成首字色块。

「邀请确认页」中每个被邀请对象逐项设置角色、以及邀请阶段的「删除」是截图能力，实现改为本批统一角色，理由同上：逐人配置需要多一次页面切换，而常用路径是「一批人给同一权限」。改角色在两端都**直接提交**（不再弹「确认修改此协作者的角色？」），因为它是可逆操作、有保存回执，且服务端按 `expected_revision` 挡住过期写入；只有移除、设为所有者与链接访问范围改动保留先确认后提交。成员行两端都直接给出角色入口与移除入口，不再把「转移／移除」藏在角色选择弹层里。

两组截图均未展开“链接分享”和“权限设置”子页；已确认纪要存在“组织内获得链接的人可阅读”这一示例状态，但完整访问范围、其他链接角色、有效期、下载/复制限制等选项仍未确定。“加密链接”和“图片分享”已排除在本产品范围外。

## 当前实现的差异

| 位置 | 当前行为 | 目标 |
| --- | --- | --- |
| Android `RecordSharing.kt` | 同一面板通过 FilterChip 切换纪要与原文，共用返回名单 | 每个对象分别提供分享入口和协作者管理入口 |
| Web `SummaryMembersDialog.tsx` | 同一协作者弹窗显示两类阅读授权，可切换授权范围 | 当前对象内完成邀请与管理 |
| Web `SummarySharingControl.tsx` | 同一组件承载转发与协作管理，纪要分享入口复制 `/meeting/records/{id}` | 拆分两个独立入口；分享仅有发送至会话和复制链接，链接打开对应对象 |
| 后端 `MeetingRecordAccess` | 同一记录、用户行保存 `read_summary` 和 `read_transcript` 两个布尔值 | 按独立对象表达协作者角色、所有者及设置 |
| 后端 `meeting_summary_sharing.py` | 两个 scope 共用 `can_manage`，经 `can_export` 使用实录所有者或会议管理权限 | 按被管理对象的当前角色校验管理权限 |
| 后端分享接口 | 从 `read_summary` 可见记录出发，返回共用授权名单 | 独立查询当前对象的协作者、可用操作与设置 |
| 实录概要 | 现有设计和实现仍依赖 `read_summary` | 实录阅读权限控制概要，不依赖独立智能纪要权限 |
| 邀请能力 | 当前分享接口选择用户，操作为 grant/revoke，未表达截图中的完整角色体系 | 补齐角色及主体类型契约；实录参考用户、群、部门，纪要还展示用户组和智能体，按实际支持能力接入 |

现有两个阅读布尔值允许单独授予和撤销阅读权限，但不足以表示两套完整的协作管理体系。仅替换面板文案或把面板复制两份不能完成该需求。

## 建议实现顺序

1. 明确实录与纪要文档的资源标识和角色能力；分别建模所有者、成员、链接与设置。纪要的历史版本归属同一文档，版本选择不应产生越权入口。
2. 后端提供按对象授权的读取、邀请、角色变更、移除、所有权转移接口；实录概要、原文、播放资源和纪要内容分别采用所属对象的权限检查。
3. 明确旧数据迁移映射。现有原文授权不会授予媒体访问，不能直接把 `read_transcript` 映射成包含媒体的完整实录阅读权限；现有房间权限继承也需明确兼容策略。迁移不得静默扩大授权。
4. Android 与 Web 分别提供分享和协作者管理入口，复用两类对象各自的交互组件。分享仅支持发送至会话和复制链接；协作者管理承载邀请、成员角色和权限设置。各入口固定传入目标对象，查询缓存、邀请草稿、幂等请求、未确认回执与通知目标都包含对象标识。
5. 分享链接和聊天卡片显式区分实录与纪要；只拥有其中一个对象权限时，仍能正常使用该对象自身的分享入口与允许的操作。

角色的具体编辑能力、谁能邀请、所有权转移后原所有者的角色、群/部门/用户组成员变化如何生效、智能体授权边界、通知投递失败处理及链接分享子页规则，需要在接口契约中明确。以上是实现建议，不是截图已证明的飞书行为。

## 验收场景

- 实录和纪要页面均能分别进入分享与协作者管理；打开协作者管理无需经过分享面板。
- 两类对象的分享面板均只提供“发送至会话”“复制链接”，没有其他渠道、系统分享扩展入口或协作者管理操作。
- 发送至会话或复制链接不新增协作者、不改变角色或链接访问范围；权限设置从协作者管理入口操作。
- 在目标对象没有其他有效授权（例如组织内链接访问）的前提下，仅邀请用户阅读实录：用户可访问被授予的实录内容，但不能打开独立智能纪要；反向场景同样成立。
- 同一用户在实录“可阅读”、在纪要“可管理”：各自显示正确操作，服务端分别校验权限。
- 移除一侧协作者、变更一侧角色或所有者、关闭一侧链接分享：另一侧的状态不变。
- 纪要开启组织内链接阅读、实录关闭链接分享时，未被单独邀请的组织成员可按链接规则阅读纪要，但不能因此访问实录；移除显式协作者不等于撤销其通过其他有效授权获得的访问。
- 两侧协作者名单及人数独立、包含各自所有者；不能用未筛选的共用名单或当前分页长度代替总人数。
- 邀请页后退保留已选对象与角色；确认前从待选列表删除对象不影响其已有授权。Web 邀请页的「返回」回到成员名单并清空本次草稿（尚未提交，不产生授权）；Android 的返回键行为相同。
- 邀请流程走「一个弹窗两个视图」：从成员名单进入选人后，勾选、本批角色、备注、发送通知与「邀请协作者」同屏可达，中间不出现逐人配置页；已直接授权的人不出现在候选里。
- 邀请提交后成员名单立即反映新成员与本批角色；个别成员改角色时不再出现二次确认对话框，移除／设为所有者／链接范围改动仍然先确认后提交。
- 复制实录链接打开实录；复制纪要链接打开纪要；无目标权限时不泄露目标内容或自动授予权限。
- 只获实录权限的用户能够阅读实录概要；只获纪要权限的用户不能通过概要、引用定位、原文或媒体接口绕过实录权限。
- 群/部门授权、旧权限迁移、撤权后的缓存、重复提交与跨对象请求均有服务端验证。

实录概要和章节现在使用 `read_transcript`；独立智能纪要继续使用 `read_summary`。

## 本次落地契约

- 独立的 `MeetingCollaboration`（对象、所有者、链接范围、修订号）、个人与团队角色。实录范围为 `record`，纪要为 `minutes`，请求、缓存及未确认操作按范围隔离。历史纪要与人工修订归属同一纪要授权对象。
- `GET/POST /meeting-records/{id}/collaboration/{scope}/` 提供成员和权限操作；`candidates/` 按 `kind`（用户／部门／用户组）搜索并按 `next_cursor` 分页，行上给出 `id/name/avatar_url`，直接喂给共享选人面板，调用方不需要把目录 id 翻译成 ACL key；`preview/` 读取当前查看者的聊天预览；`notifications/retry/` 重试邀请通知。
- 阅读者可以阅读和分享已有链接；编辑者增加当前对象内容编辑；管理者增加邀请、角色、移除及链接范围设置；只有该对象所有者可以转移所有权。转移后原所有者为管理者。实录新邀请包含媒体阅读，历史 `read_transcript` 授权仍只读文字，不静默增加媒体权限。
- 可邀请主体按现有目录能力接入：两侧均支持用户、部门；智能纪要另支持用户组。部门和用户组按当前有效成员关系求值。聊天群和智能体未接入 ACL；发送至会话可以选择已有聊天目标，但转发不授予权限。
- 链接范围为“仅协作者”或“组织内获得链接的人可阅读”；无匿名公开链接。移除个人授权后，团队或组织链接仍可能提供阅读权限。
- 邀请备注和通知采用持久化投递记录，仅在 IM 与会议助手配置可用时显示通知选项。投递前重新核对双方权限；失败可重试，重试不重新授权。消息正文在外部投递前冻结，同一通知沿用相同幂等键。
- 实录卡片显示音视频预览与时长，智能纪要卡片显示文档摘要，底部按查看者权限显示“你可阅读／编辑／管理”。消息本体仅包含对象标识、范围和标题快照，正文与媒体 URL 在阅读时鉴权获取。旧无 scope 的 Web 卡片保留纪要入口。
- 原始录音设备控制权不随协作角色转移。整体记录回收站操作仍属于原存储所有者，且要求同时持有两侧所有权；转移任一侧后不能通过整体删除影响另一方内容。恢复不会恢复旧分享。上传媒体沿用已有的有时效签名 URL，已签发的 URL 在过期前仍可能有效。

后端独立授权、成员变化、旧授权兼容、通知幂等、媒体访问、回收站与相关纪要测试通过。Web 工作区、邀请确认修订号、网络不确定重试、撤权和聊天预览测试通过；Android 编译、设计规范及链接／分享仓库测试通过。

`scripts/check-material-collaboration-ui.mjs` 使用本地模拟数据验证两个分享渠道、分开的协作者入口、手机宽度邀请流程、卡片跳转与撤权。截图输出至 `src/frontend/test-results/material-*.png`。未向真实会话发送测试消息，未执行生产迁移或部署；Android 真机及真实通知投递仍需发布环境验收。
