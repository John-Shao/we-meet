# 任务模块功能缺口与增量路线图

> 盘点日期：2026-08-26
> 事实来源：当前代码、数据库迁移和 `docs/features/task_*.md`。竞品资料只用于识别用户预期，不作为本仓库已经实现的依据。

## 结论

任务模块已经具备可上线的团队任务闭环：任务创建、多人负责人、关注人、清单协作、列表/看板/统计、表内编辑、日期与优先级、评论附件、通知提醒、会话分享、操作历史，以及会议行动项状态双向同步。

下一阶段不应直接复制完整项目管理套件。建议先补齐四类高频能力：

1. **搜索、保存视图与批量操作**：解决任务量上升后的查找和维护效率。
2. **有界递归子任务/检查项**：已支持五级拆解、独立状态、父链可见性和整树影响确认。
3. **重复任务**：覆盖周会准备、值班、巡检、报表等稳定高频场景。
4. **提醒偏好**：在现有可靠通知账本之上，允许用户控制提前量和关闭单条提醒。

依赖、里程碑、甘特图、工作量和自动化规则应作为后续成套能力建设；在需求量未被验证前，不建议先做组合复杂、维护成本高的重型项目管理功能。

## 增量路线图

### P0：规模化使用的基础体验

#### P0.1 保存视图与批量操作（全局任务搜索已完成）

目标：先解决任务数量从几十条增长到数百条后的操作成本，不新增复杂领域模型。

- 已完成：Ctrl/Cmd+K 全局搜索支持标题/说明检索、相关性排序、创建人/负责人/关注人/状态/截止日期筛选和任务详情深链，并保持组织和可见性约束。
- 保存个人视图：范围、状态、日期、优先级、清单、排序、显示列；允许重命名和删除。
- 列表增加多选，首批支持批量完成/重开、修改负责人、优先级、清单和删除。
- 批量接口逐条执行权限判断，返回成功项和失败项；禁止前端假定整批权限相同。
- 对搜索查询、批量上限和查询数设置基准，避免随着负责人和清单关联增长出现 N+1。

验收：可在 500 条可见任务中快速定位目标；50 条以内批量修改具有部分失败反馈、操作历史和通知去重；刷新后保存视图仍可恢复。

#### P0.2 有界递归子任务/检查项（已完成）

目标：支持工作拆解，同时控制层级、权限、统计和通知复杂度。

- 数据模型使用递归 `parent_id`，默认允许根任务以下五级子任务，深度上限可通过服务端配置提升。
- 每个父任务最多 100 个直接子任务，单棵任务树最多 500 个节点；循环引用和跨组织挂载由服务端拒绝。
- 子任务使用完整任务能力，可单独设置负责人、日期、状态和优先级。
- 父任务展示完成进度，但默认不因全部子任务完成而自动完成；后续可通过显式设置扩展。
- 父子节点独立鉴权并校验完整父链，禁止子任务通过清单或会话分享扩大父任务数据的暴露范围。
- 搜索和筛选命中子任务时展示完整父链；统计提供“仅顶层任务”和“包含子任务”的明确口径。
- 删除或移动父任务前展示并确认整棵子树影响。
- 同一父任务下的子任务可就地排序，服务端原子校验完整同级快照；并发创建和互相移动由稳定事务锁保护。

收尾验收：PostgreSQL 后端层级与任务回归测试 `84 passed`，相关前端单元测试 `45 passed`，真实 OIDC + Chromium E2E `3 passed`。

迁移 `0112_task_parent` 曾加入 `parent`，又在 `0124_remove_task_parent` 删除。本次通过新的前向迁移重新引入，并由 [ADR-0001](../adr/0001-bounded-recursive-task-hierarchy.md) 明确层级、删除、权限、统计和行动项同步语义。

#### P0.3 重复任务

目标：覆盖每日、每周、每月和自定义周期的稳定重复工作。

- 使用“重复规则 + 当前实例”的模型；完成当前实例后生成下一实例，避免无限预生成。
- 复制标题、说明、负责人、关注人、清单、优先级、日期跨度和附件引用策略；不复制评论和操作历史。
- 修改规则时明确“仅本次 / 本次及以后 / 全部”范围。
- 生成过程使用幂等键和事务，重复执行调度任务不能产生重复实例。
- 删除、人员离职、清单归档和时区变化必须有确定行为。

#### P0.4 提醒偏好

目标：让用户控制提醒噪音，同时复用现有 `TaskImDelivery` 幂等与重试能力。

- 首期支持关闭单条任务提醒，以及截止日前 0/1/3 天提醒。
- 提醒偏好按用户存储；多人负责人可以有不同设置。
- 逾期提醒仍保持一次性，暂不引入每日催办。
- 截止“具体时刻”和稍后提醒需要改变当前纯日期语义，单独立项，不与偏好设置捆绑。

### P1：轻量项目管理增强

1. **清单模板**：从会议待办、发布检查、入职、巡检等真实场景沉淀模板；复制字段和分组，不复制成员和历史数据。
2. **自定义字段与高级筛选**：先支持清单级文本、数字、日期、单选、人员字段；统一字段定义、权限、统计和 API，不先恢复孤立标签模型。
3. **依赖 + 里程碑 + 时间线 MVP**：先实现 `blocked_by`、阻塞校验、里程碑和只读时间线，再评估可拖拽排期；不要单独上线“只有图没有约束”的甘特图。
4. **日历视图与日历联动**：复用现有日历模块，提供按开始/截止日期查看任务以及受控的日程映射，避免复制两套日期编辑器。
5. **会议行动项字段同步扩展**：在当前状态双向同步稳定后，按字段逐项评估标题、负责人和截止日期；保留人工覆盖优先和冲突审计。

### P2：经需求验证后再建设

- 自动化规则、表单收集和审批节点。
- 工作量、容量、工时和人员排期。
- 多清单归属、跨项目组合、目标与项目集。
- 外部协作者和跨组织负责人。
- 日历订阅、第三方任务导入导出和开放 Webhook。

## 暂不建议直接跟进

- **不设规模边界的递归子任务**：会让权限、统计、排序、删除和通知成本失控；当前使用可配置深度与 100/500 节点配额。
- **先做甘特图外观**：没有依赖、里程碑和排期约束时只能提供有限价值。
- **立即恢复标签**：迁移 `0119_task_labels` 引入标签后，`0121_remove_task_labels` 已明确移除；若重新建设，应由实际筛选场景驱动，并评估统一自定义字段模型。
- **完整项目组合/目标管理**：偏离当前“会议、IM、任务闭环”的产品优势，且需要独立的权限和汇总模型。
- **所有字段自动双向同步**：会议行动项与任务存在不同生命周期，应逐字段定义来源优先级和冲突策略。

## 配套质量门槛

每个 P0 特性除单元和后端测试外，至少补充以下浏览器或契约验证：

- 两个真实用户分别以负责人、关注人、清单 viewer/editor 身份验证权限矩阵。
- 批量操作的部分成功、重试幂等、通知去重和操作历史。
- 子任务的父子权限、删除、统计和完成/重开行为。
- 重复任务的时区、月末、幂等、规则修改和失败恢复。
- 任务附件、会话分享和会议行动项转换的真实 E2E。
- 500/5,000 条任务规模下的列表查询、统计查询和首屏性能基准。

## 推荐实施顺序

1. `P0.1 保存视图 + 批量操作`（全局任务搜索已交付）
2. `P0.2 有界递归子任务/检查项`（已交付）
3. `P0.3 重复任务`
4. `P0.4 提醒偏好`
5. 根据使用数据决定进入 `P1 自定义字段`，还是 `P1 依赖/里程碑/时间线`

第一项对现有模型侵入最小、能立即改善规模化体验，也能为后续子任务和重复任务提供统一的查找与批量管理入口。
