# 任务时间提醒与逾期管理（T2）

## 目标

在最小任务闭环上补齐日期驱动的执行提醒，让负责人能够看到今天开始、今天截止和已经逾期的任务，并由任务助手可靠投递一次对应提醒。

## 日期语义

任务的 `start_date` 和 `due_date` 都是日期，不包含具体时刻。系统按当前负责人的 `User.timezone` 解释“今天”：

- 开放任务在 `start_date` 当天产生 `starting` 提醒。
- 开放任务在 `due_date` 当天产生 `due_today` 提醒。
- 开放任务在 `due_date` 之后产生一次 `overdue` 提醒。
- `completed` 和 `canceled` 任务不产生时间提醒，也不显示时间状态。
- 开始日期与截止日期为同一天时，只发送优先级更高的“今天截止”，避免同一分钟连续发送两张卡片。
- 逾期提醒是一次性状态提醒，不在最小阶段按天重复催办。

## 投递与幂等

时间提醒复用 `TaskImDelivery`、任务助手和既有 Celery 重试链路，不建立第二套消息账本。`reference_date` 保存触发提醒的任务日期，`task + recipient + event + reference_date` 唯一约束保证定时扫描可安全重跑。

每分钟运行的 `send_due_reminders` 同时扫描日程和任务日期。新提醒记录提交后立即入队；已有待投递记录由同一命令恢复。临时 IM/Broker 故障沿用五次退避重试。

投递前再次校验任务仍处于开放状态、接收者仍为当前负责人且日期没有变化。任务转交、完成、取消或改期后，旧的待投递提醒会标记为 `superseded`；新负责人或新日期满足条件时生成新的幂等记录。

## 改期即时通知（T2.1）

创建人实际修改开放任务的开始日期或截止日期后，任务助手立即通知当前负责人。通知关联不可变的 `TaskActivity` 日期变更记录，并展示修改人以及每个变化日期的“原值 → 新值”，因此 IM 或 Broker 故障后的重试不会丢失改期快照。

- 创建人与负责人是同一人时保持静默。
- 请求值与原日期相同，不创建活动或通知。
- 日期与负责人在同一次请求中修改时，只向新负责人发送包含新日期的转交通知，避免连续两张卡片。
- 同一任务连续改期时，尚未投递的旧改期通知会变为 `superseded`，只重试最新快照。
- 改期会立即淘汰日期已经失效的待投递开始、截止和逾期提醒；新日期仍按原定时规则触发。
- 完成或取消任务时不发送改期通知。

## 进度状态即时通知（T2.2）

任务实际流转到待处理、进行中、已完成或已取消后，任务助手立即通知未执行本次操作的当前协作者。通知关联对应的 `TaskActivity` 状态变更记录，展示“原状态 → 新状态”和操作人，并沿用现有持久化账本、幂等消费及退避重试。

- 负责人推进任务时通知创建人；创建人操作时通知不同人的当前负责人。
- 父任务协作者按继承权限推进一级子任务时，通知子任务创建人和负责人，并自动排除操作者及重复接收人。
- 创建人与负责人为同一人、请求没有实际状态变化时保持静默。
- 状态与负责人在同一次请求中修改时，只发送包含当前任务信息的转交通知，避免新负责人连续收到两张卡片。
- 同一任务连续流转时，尚未投递的旧状态通知会变为 `superseded`；投递前还会校验接收者仍是当前协作者且活动目标状态仍是任务当前状态。
- 任务完成或取消时，尚未投递的改期通知、开始提醒、截止提醒和逾期提醒会立即作废。

## 查询与展示

任务列表增加 `time` 查询参数：

- `all`
- `starting_today`
- `due_today`
- `overdue`

日期筛选只返回开放任务，并继续叠加原有的 `scope` 权限范围。任务序列化结果包含只读 `time_state`，前端用它展示“今天开始”“今天截止”“已逾期”状态，其中逾期使用危险色强调。

## 本阶段边界

- 不支持用户自定义提醒时间或提前天数。
- 不提供每日重复催办、稍后提醒或关闭单条提醒。
- 不通知标题、描述等普通内容变更；即时变更通知仅覆盖日期和任务状态。
- 不向创建人额外发送提醒；创建人同时是负责人时会正常收到。
- 不新增 Celery Beat，继续使用生产已有的 Kubernetes CronJob。

## 验收要点

1. 不同时区的负责人按各自本地日期收到提醒。
2. 开始日、截止日和逾期提醒均只创建一次，重复扫描不重复投递。
3. 同日开始并截止只发送截止提醒。
4. 完成、取消、改期和转交后旧提醒不再发送。
5. IM 临时故障保留记录并可靠重试。
6. 列表时间筛选和任务时间状态与服务端日期口径一致。
7. 创建人改期后，非同一人的当前负责人收到包含原日期和新日期的可靠通知。
8. 无实际变化、自分配、关闭任务和同请求转交均不会产生重复改期卡片。
9. 负责人推进状态后创建人收到可靠通知，创建人操作时不同人的负责人收到通知。
10. 快速连续流转、任务转交或关闭后的旧通知不会迟到投递；个人任务不会通知操作者本人。
