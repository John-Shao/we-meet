# 一对一通话 P1 —— 呼叫信令详细设计

> 状态:设计评审中
> 日期:2026-07-10
> 前置:P0(单聊通话入口,we-meet-android `99fecc5`)已上线
> 范围:**App 在线双方**的飞书式振铃通话(语音/视频)。离线推送唤醒(P2)、
> 系统级来电 UI/Telecom(P2)、拨打电话手机号(P3)均不在本期。

## 0. 一句话架构

**信令走 jusi-light-im WS 新增的 `call` 帧(瞬时、不落库、按 uid 定向投递);
媒体复用 LiveKit:主叫建 `trusted` 房拿 slug,slug 随 invite 发给被叫,
被叫接听后 `GET /rooms/{slug}/` 自己换 token 进房。Django 本期零改动。**

涉及仓库:

| 仓库 | 改动 | 部署 |
|---|---|---|
| `jusi-light-im`(Go 服务) | 新增 call 帧类型 + handler(~200 行) | 需重新部署 |
| `jusi-light-im/sdk/android`(composite build) | 新增 calls flow + sendCall(~80 行) | 随 App 构建 |
| `we-meet-android` | CallController 状态机 + 呼出/来电两屏 + 导航 | 发版 |
| `we-meet`(Django) | **无** | 无 |

## 1. 已验证的事实依据(实勘结论)

设计建立在以下已核实的代码事实上,不再是假设:

1. **定向投递管道现成**:`Hub.byUID: map[string]map[*Conn]struct{}`(多端)
   + `dispatchToUID`(hub.go:381)+ broker `user:{uid}` 频道(已订阅
   `user:*`,hub.go:152)。跨节点也通。
2. **瞬时不落库定向帧有先例**:`notifyRemoved`(admin/conversations.go:134)
   —— system 帧 `Publish(UserChannel(uid))`,零落库。call 帧照此模式。
3. **身份不可伪造**:conn 的 uid 在 WS 握手时从 JWT `sub` 固化
   (hub.go:183-207),所有 handler 用 `c.uid`,不信任 payload。
4. **被叫一次 GET 直接进房**:后端默认 `access_level=trusted`
   (settings.py:886),serializer 对「trusted + 已登录」直接发 livekit token
   (serializers.py:207-257),不进等候室。**不需要改 Django。**
5. **已知短板**(设计必须补偿):Redis Pub/Sub at-most-once、conn 发送缓冲
   32 满即静默丢帧(conn.go:120)、无端到端 ACK、无 offline outbox。
6. **房间无自动回收**:不显式 end 会留僵尸房;`end` 是 owner-only。
7. **在线判定可用**:`PresenceStore.Get(uid)`(presence.go:81,TTL 90s)
   已存在,但 Hub 的 `PresenceOps` 接口未暴露 `Get`,需补一行接口方法。

## 2. 信令协议

### 2.1 帧格式

复用现有 `Frame{type, ts, server_ts, payload}` 信封,新增类型 `call`:

```json
{
  "type": "call",
  "ts": 1720500000000,
  "payload": {
    "event": "invite",
    "call_id": "c7a1…uuid,主叫生成",
    "cid": "两人 direct 会话 id(授权依据)",
    "from": "服务端覆写为发送 conn 的 uid",
    "to": "对端 uid",
    "media": "audio | video",
    "room_slug": "83920417(仅 invite 携带)",
    "room_name": "与李梓昂的通话(仅 invite 携带)",
    "reason": "timeout | declined | busy | unreachable(可选,终态帧携带)"
  }
}
```

### 2.2 事件集

| event | 方向 | 语义 |
|---|---|---|
| `invite` | 主叫→被叫 | 发起呼叫,带 room_slug |
| `ringing` | 被叫→主叫 | 收到 invite 的回执(应用层 ACK,主叫 UI 可显示「等待接听」) |
| `accept` | 被叫→主叫 | 接听。双方进房 |
| `reject` | 被叫→主叫 | 拒接(reason=declined) |
| `cancel` | 主叫→被叫 | 主叫取消 / 60s 超时(reason=timeout) |
| `hangup` | 双向 | 通话中挂断,让对端 UI 立即收敛(媒体层兜底见 §6.4) |
| `busy` | 被叫→主叫 | 被叫忙线(本地状态非 Idle 时自动回,reason=busy) |
| `unreachable` | 服务端→主叫 | 服务端发现被叫全端离线,立即回告(P1 提示「对方不在线」;P2 改为触发推送) |

### 2.3 状态机

**主叫**:

```
Idle ──startCall──> Creating(POST /rooms/) ──ok──> Inviting(发 invite,启动 60s 总超时)
Inviting ──ringing──> Ringing(「等待接听」)
Inviting/Ringing ──accept──> InCall(进房)
Inviting/Ringing ──reject/busy/unreachable/超时──> Ended(超时时发 cancel + endRoom)
Inviting/Ringing ──用户点取消──> Ended(发 cancel + endRoom)
InCall ──hangup/对端离房──> Ended(主叫 endRoom)
```

**被叫**:

```
Idle ──收到 invite──> Ringing(来电页 + 铃声振动,60s 本地超时)
Ringing ──用户接听──> Joining(发 accept → GET /rooms/{slug}/ → 进房)──> InCall
Ringing ──用户拒接──> Idle(发 reject)
Ringing ──收到 cancel / 60s 超时──> Idle(UI 显示「未接听」)
非 Idle 状态收到新 invite ──> 自动回 busy,不打扰当前状态
```

幂等规则:所有事件按 `call_id` 收敛;对已终结的 call_id 收到任何帧一律忽略。

### 2.4 可靠性补偿(针对 §1.5 的短板)

- **invite 重发**:主叫发出 invite 后 3 秒内未收到 `ringing`,重发同
  `call_id` 的 invite,最多 3 次;被叫按 call_id 幂等去重。补偿缓冲丢帧
  与 Pub/Sub 抖动。
- **总超时**:主叫 60s 未获终态 → 发 `cancel(timeout)`、endRoom、UI 收敛。
  被叫来电页同样 60s 自动消失。两端时钟独立,不依赖对方。
- **终态双投**:服务端把 accept/reject/cancel/hangup/busy **同时投给
  from 和 to 两个 user 频道**。作用:①多端收敛(手机接听了,平板的来电页
  收到同 call_id 的 accept 自动消失,显示「已在其他设备接听」);②发送方
  自己也收到回声,可当作弱 ACK。
- **不落库、不重放**:接受 P1 的限制 —— WS 断开期间的 invite 永久丢失
  (被叫不知道有人呼过)。P2 由离线推送补上;P1 主叫会收到 unreachable
  或超时,体验闭环。

## 3. Go 服务改动(jusi-light-im)

### 3.1 `internal/api/ws/frame.go`

```go
const TypeCall = "call"    // 加入 frame type 注册表

type CallPayload struct {
    Event    string `json:"event"`
    CallID   string `json:"call_id"`
    CID      string `json:"cid"`
    From     string `json:"from"`
    To       string `json:"to"`
    Media    string `json:"media,omitempty"`
    RoomSlug string `json:"room_slug,omitempty"`
    RoomName string `json:"room_name,omitempty"`
    Reason   string `json:"reason,omitempty"`
}
```

### 3.2 `internal/api/ws/hub.go`

- `handle` switch(hub.go:302)加 `case TypeCall: h.handleCall(c, f)`。
- `PresenceOps` 接口(hub.go:64)补 `Get(ctx, uid) (string, error)`
  (底层 `PresenceStore.Get` 已存在)。

### 3.3 新文件 `internal/api/ws/handlers_call.go`

服务端**无状态**——不存呼叫会话,只做校验 + 转发。状态机全在客户端。

```
handleCall(c, f):
  1. 解析 CallPayload;校验 event ∈ 事件集、call_id/cid/to 非空
  2. payload.From = c.uid                      // 覆写,防伪造
  3. 授权:Members.IsMember(cid, c.uid) && Members.IsMember(cid, payload.To)
     且 cid 会话类型为 direct(拒绝群聊 cid)
  4. event == invite:
       node := presence.Get(payload.To)
       if node == "":  回投 unreachable 帧给 c(写回 c 自身,不经 broker)
       else:           Publish(UserChannel(payload.To), frame)
  5. 终态帧(accept/reject/cancel/hangup/busy):
       Publish(UserChannel(payload.To), frame)
       Publish(UserChannel(payload.From), frame)   // 终态双投,见 §2.4
  6. ringing:仅投 UserChannel(payload.To)
```

安全性小结:第 2 步杜绝「A 伪造成 B 呼叫」;第 3 步保证只能呼有 direct
会话关系的人,且群聊 cid 不可用于骚扰群成员。

### 3.4 明确不做

- 不落库、不建 outbox、不做服务端呼叫状态机、不改 push webhook(P2)。

## 5. 客户端改动(we-meet-android)

### 5.1 CallController(feature-im,新文件)

挂在 `ImSession` 上的进程级单例(ImSession 已是单例,直接持有):

```kotlin
sealed interface CallState {
    data object Idle : CallState
    data class Outgoing(val info: CallInfo, val waitingAnswer: Boolean) : CallState  // Inviting/Ringing
    data class Incoming(val info: CallInfo) : CallState
    data class Connecting(val info: CallInfo) : CallState   // accept 后拉房间信息中
    data class InCall(val info: CallInfo) : CallState        // 已交给 Room 界面
    data class Ended(val info: CallInfo, val reason: EndReason) : CallState  // 瞬态,展示 toast 后回 Idle
}
```

职责:

- 收 `client.calls`,跑 §2.3 状态机(含 call_id 幂等、busy 自动回、
  invite 3s×3 重发、60s 超时)。
- `startCall(cid, peerUid, peerName, media)`:调 app 层注入的
  `createRoom` → 发 invite → 进 Outgoing。
- `accept()/reject()/cancel()/hangup()`。
- 房间创建/结束不属于 feature-im(RoomRepository 在 app 模块),通过
  **宿主注入的接口**(照 `ImDeps` 模式加 `CallHost`:`suspend createCallRoom(name): CallRoom`、
  `suspend endCallRoom(roomId)`)完成,feature-im 不感知 Retrofit。

### 5.2 UI(两个全屏页,对照飞书截图)

**OutgoingCallScreen(主叫呼出页)**:居中头像 + 姓名 +「正在发起语音/视频
通话…」/「等待接听…」+ 扬声器切换胶囊 + 底部红色取消按钮;视频通话时背景
为本地相机预览(复用 preview 包 `CameraPreview`),左上角返回=取消。

**IncomingCallScreen(被叫来电页)**:居中头像 + 姓名 +「邀请你进行语音/视频
通话」+ 底部左红(拒接)右绿(接听)双按钮;铃声
(`RingtoneManager.TYPE_RINGTONE`)+ 振动,页面存续期间播放。
P1 仅处理 **App 在前台** 的来电;App 在后台但进程活着时发一条
high-importance 通知(点击进来电页),**全屏 intent 留 P2**。

### 5.3 导航与进房

- `AppNav` 顶层 collect `CallState`:Outgoing/Incoming → navigate 到对应
  路由(单例 launchSingleTop);Ended → pop + toast。
- 接通进房:**跳过 Preview**,直接 `Routes.room(roomId, url, token, …,
  mic=true, cam=(media==video))`。被叫的 url/token 来自 accept 后
  `RoomRepository.getRoom(slug, username)`(trusted 房直接有 livekit 字段,
  见 §1.4);主叫的来自 createRoom 响应。
- `CallOptionsSheet` 的语音/视频两项从「进 Preview」改接
  `CallController.startCall`(P0 的 createPreview(audioOnly) 路径仅保留给
  群聊快速会议)。ChatViewModel 需在 `ChatUiState` 补 `peerUid` 字段
  (refreshConversationShape 里已算出,顺手暴露)。

### 5.4 房间生命周期(防僵尸房,§1.6)

- 主叫(owner)在 cancel/timeout/reject/busy/unreachable/通话结束时一律
  `endRoom`。
- 被叫无权 end,仅 disconnect。
- 已知残留:主叫进程在 Inviting 期间被杀 → 房间无人 end。P1 接受
  (trusted 房无人时无媒体成本),P2 配合后端加清理。
- 通话房会出现在主叫的「历史会议」列表(名字「与X的通话」)。P1 接受,
  P2 可用 `configuration` 标记 + 列表过滤。

## 6. 边界与竞态(评审重点)

1. **双方同时互拨**:两端各处于 Outgoing,收到对方 invite 时本地非 Idle
   → 各自动回 busy → 两边都收 busy 收敛到 Idle,提示「对方忙」。简单、
   对称、无脑,代价是「心有灵犀反而打不通」,可接受。
2. **接听与取消竞态**:被叫 accept 与主叫 cancel 在网上交错 —— 被叫可能
   进了房但主叫已收敛。兜底:被叫进房后 **15s 内房内无对端则自动挂断**,
   提示「通话已取消」。主叫侧收到迟到的 accept(状态已 Ended)直接忽略。
3. **多端**:invite 天然广播到被叫所有在线端(dispatchToUID 遍历 byUID);
   任一端接/拒后,其余端靠「终态双投」收到同 call_id 终态而收敛(§2.4)。
4. **通话中 WS 断开**:媒体不受影响(LiveKit 独立连接)。hangup 帧可能
   收不到 → 兜底用 LiveKit `ParticipantDisconnected` 事件:1v1 房里对端
   离开即视为挂断,退房。**此兜底是必做项,不是可选**。
5. **被叫收到 invite 时正在会议中**:CallController 状态虽为 Idle,但
   RoomViewModel 在会 → busy 判定需含「当前在任意 LiveKit 房间」。通过
   宿主接口暴露 `isInMeeting(): Boolean` 查询。
6. **铃声焦点**:来电铃声申请 audio focus(transient),避免与正在播放的
   语音消息叠音。

## 7. 测试计划

- **Go 单测**:handleCall —— 伪造 from 被覆写、非 direct cid 拒绝、
  非成员拒绝、离线回 unreachable、终态双投。
- **双机实测矩阵**(2 台真机):
  接听 / 拒接 / 主叫取消 / 60s 超时 / 忙线(被叫在会中)/ 双方互拨 /
