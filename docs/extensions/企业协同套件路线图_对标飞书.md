# we-meet 企业协同套件路线图 — 对标飞书 (to-B)

> 立项日期：2026-06-22 · 范围由产品负责人拍板 · 详细设计来自两份地基/协同面深入推演

## Context（为什么做这件事）

we-meet 已经是一个 **会议 + AI + IM** 三强俱全的产品：LiveKit 音视频会议、录制/转写/字幕、AI 会议纪要+待办、房间内/跨会议 RAG 问答、实时 AI agent，加上刚完成 P0-P6 的自研 jusi-light-im（私聊/群聊/历史/已读）。但定位要从"带 AI 的会议工具"升级为**面向企业（to-B）的协同套件**，对标字节飞书。

对照飞书核心支柱，we-meet 当前最大的缺口是：

1. **没有组织架构** —— `User.get_teams()`（`core/models.py:248`）是 stub 返回 `[]`，企业里"谁在哪个部门、谁是谁的主管"完全没建模。这导致 @部门、审批路由、通讯录选人、成员开通、按部门共享 全都无从谈起。**这是 to-B 的地基，必须先建。**
2. **没有协作文档 / 日历 / 知识库 / 审批** —— 协同面只有 IM 和会议，缺飞书最日常的几块。

好消息是地基**可扩展不重写**：`BaseAccess` 已同时支持 user 与 team（string）两种访问行，`BaseAccessManager.filter_user`（`core/models.py:528`）已是 `Q(user=user) | Q(team__in=user.get_teams())`，团队访问控制全链路已就绪，**只差 `get_teams()` 填真值 + 组织数据建模**。

### 用户已拍板的范围（2026-06-22）

| 决策 | 选择 |
|---|---|
| 首要攻坚方向 | **组织架构地基优先** |
| 协作文档 | **集成 La Suite Docs**（`suitenumerique/docs`，同源同 Keycloak，不自建 CRDT） |
| 纳入支柱 | 组织架构（地基）+ 日历/日程 + 协作文档 + 知识库/Wiki + 审批/工作流 |
| 明确排除 | 多维表格/Bitable、OKR、邮箱 |

预期产出：先打通"组织/通讯录/管理后台"地基，再依次铺开日历、文档、知识库、审批，最终形成"组织为骨、会议+IM+AI 为核、文档+日历+审批为面"的飞书式企业协同闭环。

### 对标总览

- **会议 + AI = 核心竞争力**：会议支柱几乎全 ✅，AI 线（实时 agent、跨会议 RAG）**部分领先飞书**——这是 we-meet 的护城河，不是追赶项。

> 粗略计分（约值）：✅ 约 18 项 · 🟡 约 14 项 · ⛔ 约 26 项 · 🚫 4 项。结论：**核心会议/AI 已成型，企业协同面整体待建**——路线图正是为补齐 ⛔/🟡 而设。

## 载荷决策（贯穿全程，先定不再讨论）

这些是各阶段都依赖的架构选择，来自两份深入设计推演：

1. **组织数据 app-native，Keycloak 只管认证。** 部门树/职位/主管/排序/软删/审计这些产品数据用 Keycloak group 建模很别扭，且改部门要走 IdP admin 往返太慢。现状本就把 Keycloak 当纯 OIDC（只镜像 `sub`/email/name 到 `User`），组织结构属授权/产品数据，归 app 侧。仅保留一个**可选、单向（Keycloak→app）、默认关**的 `groups` claim 导入口做开通便利，绝不作结构权威。
2. **`team_key` 用不可变的 `dept:<uuid8>`** 写进 `BaseAccess.team`（CharField **100** 上限，`core/models.py:542`）—— 绝不用人类可读 path（会超长、改名即断权限）。
3. **`get_teams()` 返回用户的直属部门 `team_key` 列表**（MVP 不含子树，避免隐式越权），按请求 memoize（可加短 TTL Redis 缓存）。填真值后，部门共享的录制/资源**零改 viewset 即生效**。
4. **多租户写进 schema、单租户运营。** 现在就给组织级表加 nullable `organization` FK，bootstrap 一个默认 org，查询一律 org-aware；但不建租户路由中间件/realm 切换。等真出现第二家租户再做隔离。
5. **通讯录 API 服务端解析 `User.sub → im_uid`**（缓存列 + 批量解析）—— 这是打通 IM 的关键：现有 `POST /im/conversations/direct {peer_uid}` 客户端拿不到 peer_uid，通讯录把 im_uid 直接给前端就闭环了。
6. **会议纪要自动流转链路已是生产代码**（`Transcript → Summary/ActionItem → _push_summary_to_im → MeetingConversation`，`core/services/meeting_summary.py`）。文档/日历/提醒都**克隆这条 pattern**：纪要也推一份成 Doc、提醒走 IM 推送。

## 分阶段路线图

依赖顺序：组织地基 → 日历 → 文档 → 知识库 → 审批。日历强依赖会议核心（最快出价值），知识库建在文档之上，审批依赖组织做路由。

### P1 — 组织架构地基（组织/部门/通讯录/管理后台）【地基，必须先行】

**目标**：企业能建部门树、开通成员、按部门管权限；通讯录可搜人选人并直连 IM。

**数据模型**（均继承 `BaseModel`，`db_table = "meet_*"`，新建于 `core/models.py`）：
- **Organization**：`name`、`slug`(unique)、`primary_domain`、`is_active`、`settings`(JSON)。bootstrap 一行，挂全部存量用户。
- **Department**（邻接表 + 物化路径，**不引 MPTT 依赖**）：`organization` FK、`parent` self-FK、`name`、`path` CharField(1024) 建索引、`depth`、`head` FK User、`sort_order`、`is_active`、`deleted_at`，以及关键的 **`team_key` CharField(100) unique = `dept:<uuid8>`**（写进 `BaseAccess.team`）。`path` 支持 `path__startswith` 子树展开。
- **Membership**（user↔dept）：`organization`、`user`、`department`(null=组织级)、`title`(职位)、`is_primary`、`org_role`、`employee_no`、`status`(active/invited/suspended/left)、`joined_at`。约束：unique(user, department)；每用户每 org 仅一个 primary。`org_role` 与 `ResourceAccess.role` 区分——共用 RoleChoices 重合值（member/administrator/owner）并加 `dept_admin`；管理后台权限看 `org_role`，单资源 ownership 仍走 `ResourceAccess`。

**`get_teams()` 实现**（改 `core/models.py:248`）：返回用户直属、active 的部门 `team_key`，按请求 memoize。

**通讯录 API**（新建 `core/api/directory.py`，`IsAuthenticated` + org-scoped，**替换** `ALLOW_UNSECURE_USER_LISTING` 的不安全 listing）：
- `GET /directory/departments/`（`?parent=` 懒加载 / `?tree=true` 嵌套）
- `GET /directory/departments/{id}/members/`（`?include_subtree=true`，分页）
- `GET /directory/members/?q=&department=`（name+email trigram，复用现有搜索；拼音后置）
- `GET /directory/members/{user_id}/`
- `DirectoryMember` 形如 `{id, sub, full_name, avatar_url(presigned, 复用 UserSerializer), title, department{...}, im_uid, is_self}`，**`im_uid` 服务端解析**。

**管理后台 API**（新建 `core/api/admin_org.py`，`IsOrgAdmin`）：
- 部门 CRUD（move 时 `save()` 重写子树 path/depth；软删非空部门需 `?reassign=`）
- 成员邀请 `POST /admin/members/invite/ {emails[], department_id, title, org_role}` → 建 `Membership(status=invited)`；**`post_get_or_create_user`（`core/authentication/backends.py`）在首次 OIDC 登录时按已验证 email 关联待定 Membership**，无需调 Keycloak Admin API。
- 角色分配复用 RoleChoices + "保底 ≥1 owner" 不变式。

**前端**（`src/frontend/src/features/`）：新增 `org`/`contacts` feature——通讯录浏览/搜索、管理后台（部门树编辑、成员开通）。Header（`src/layout/Header.tsx`）加"通讯录"入口。IM「+ 新建会话」从 `window.prompt(peer_uid)` 升级为**通讯录选人**（拿 im_uid 调 `conversations/direct`）。

**迁移路径**：① 加表（不动 access 模型）② 数据迁移建默认 Organization + 给每个 User 建 primary Membership，staff 提 ORG_ADMIN ③ 实现 `get_teams()` ④ 可选 `directory_groups` ArrayField ⑤ User 加缓存 `im_uid` 列（首次 `issue_token` 时回填）。每步可回滚。

**验收**：建三层部门树→把成员挪部门→该部门共享的录制对成员可见（零改 viewset）；通讯录搜人→选中→直接发起 IM 私聊。

**MVP vs later**：MVP = 单 org + 部门树 + Membership + 真 `get_teams()` + 通讯录(含 im_uid) + 部门 CRUD + 邮件邀请→OIDC 关联。Later = 子树授权展开、虚线汇报、Keycloak group 导入、拼音搜索、SCIM/CSV 批量导入、真多租户隔离。

### P2 — 日历/日程

**目标**：建日程、邀人、RSVP、会前提醒、一键进会，与现有会议核心深度联动。

**模型**（新建，复用 Resource/ResourceAccess RBAC + `Room.scheduled_at`）：
- **CalendarEvent(BaseModel)**：`title`、`description`、`organizer` FK、`start_at`/`end_at`、`timezone`(复用 User 的 TimeZoneField pattern)、`all_day`、`room` FK(SET_NULL，进会目标，`Room.scheduled_at` 镜像 `start_at`)、`recurrence`(RRULE 字符串，**MVP 仅单次**)、`recurrence_parent` self-FK、`status`、`visibility`、`reminders`(JSON 提前量)。
- **EventAttendee(BaseModel)**：`event` FK、`user` FK(nullable)/`email`(外部)、`rsvp`(needs_action/accepted/declined/tentative)、`role`(organizer/required/optional)。

**Free/busy**：`GET /calendar/free-busy?users=&from=&to=`（MVP 仅本人，跨人后置）。
**提醒**（FCM 国内不可用，已搁置）：**新增 Celery beat**（当前 Celery 仅事件驱动，无调度器）定时扫到期提醒，走现有 `JusiImAdminClient.post_message` 推到用户 IM + 站内通知。
**前端**：`ScheduledMeetingsList.tsx` 演进为日程 agenda；加建日程表单——保存即建 Room、设 `scheduled_at`、预建 IM 群（复用 ensure-group）。attendee 选人复用 P1 通讯录。

**MVP vs later**：MVP = 单次事件 + RSVP + 建日程联动 Room/IM + agenda 视图 + IM 提醒。Later = RRULE 周期+例外、跨人 free/busy、周/月网格、OpenExchange/CalDAV 同步、审批挂钩。

### P3 — 协作文档（集成 La Suite Docs）

**目标**：用上 Notion 式协作文档；会议纪要自动落成 Doc（飞书"妙记"体验）。

**策略**：**集成 `suitenumerique/docs`，不自建编辑器。** 它是同源姊妹项目，Django + Yjs/BlockNote 已解决 CRDT 协同编辑（整条路线图最大隐藏成本），且共用同一 Keycloak OIDC 栈（用户已按 `sub` 存在）。Docs 后端 + 协同 ws 服务独立部署、独立 PG/S3，Keycloak 注册 `docs` client 实现真 SSO，we-meet 加 `/docs` iframe 路由深链。

**前置 spike（1-2 天，做 MVP 前必须）**：验证 ① Keycloak 跨子域 SSO（iframe cookie/CORS）② Docs server-to-server 建文档 API 是否够用。**这一项成败决定文档轨。**

**we-meet 侧薄接入**：新增 **MeetingDoc** 链接模型（**镜像 MeetingConversation**）：`room` OneToOne(SET_NULL，doc 比 room 长寿)、`doc_id`、`doc_url`、`pushed_at`。**CRDT/正文不进 we-meet 库，Docs 持有。**
**妙记自动流转**：扩 `core/services/meeting_summary.py`——`Summary` SUCCESS 后在 `_push_summary_to_im` 旁加 `_push_summary_to_doc`：调 Docs 建文档 API 写纪要 markdown + 待办（+可选转写），存 MeetingDoc，把 doc 链接也发进 IM，复用同一 `pushed_at` 幂等守卫。

**MVP vs later**：MVP = `/docs` iframe + MeetingDoc + 纪要→Doc + doc 链接进 IM。Later = 房间内文档侧栏、按事件建文档模板、Room 权限→Docs 权限同步。

### P4 — 知识库/Wiki

**目标**：团队文档库/空间/目录树，沉淀组织知识。

建在 P3 文档之上：La Suite Docs 本身有文档树/空间能力，优先复用其 Wiki/空间形态，we-meet 侧仅做**空间↔组织/部门的权限映射**（复用 P1 的 Department `team_key` + ResourceAccess team 行）与入口。若 Docs 空间能力不足，再评估补轻量目录层。**依赖 P3 spike 结论**，细节在 P3 落地后细化。

### P5 — 审批/工作流

**目标**：请假/报销式审批，按组织架构做审批路由。

依赖 P1 组织架构（审批人=主管/部门 head/指定 org_role）。模型草案：**ApprovalTemplate**（表单 schema + 流程定义）、**ApprovalInstance**（发起人/当前节点/状态）、**ApprovalNode/Task**（审批人、动作、时间）。审批人解析走 Membership/Department.head。通知与催办复用 IM 推送（同 P2 提醒通道）。@部门/@人复用 P1 通讯录。MVP = 串行单链审批 + IM 通知；Later = 条件分支/会签/抄送/委托。

## 跨阶段风险（排序）

1. **协作文档自建 CRDT 成本** —— 由"集成 Docs"消除；但替换为 **Docs server 建文档 + iframe SSO 可行性**（P3 spike 必须先验，决定文档轨成败）。
2. **`get_teams()` 性能/缓存陈旧** —— 强制请求 memoize + Membership 写时失效；审计全部调用点。
3. **`team_key` 改名稳定性** —— 不可变 `dept:<uuid8>`。
4. **子树隐式越权** —— MVP 仅授直属，子树展开做成显式可见选项。
5. **邀请↔OIDC email 误关联** —— 按已验证 email 匹配、用 `sub` 对账，复用现有 `MultipleObjectsReturned`→SuspiciousOperation 处理。
6. **多租户泄漏** —— 通讯录/后台所有 queryset 从第一天就按 org 过滤（哪怕只有一个 org）。
7. **Celery beat 是新基建** —— 当前 Celery 仅事件驱动，提醒需加调度器到部署。
8. **运营负担** —— 集成 Docs 多两个服务（Docs 后端 + 协同 ws），小团队需评估。
