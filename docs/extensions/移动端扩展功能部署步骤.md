# 移动端功能部署步骤（阿里云）

> 配套文档：[移动端App客户端支持方案.md](移动端App客户端支持方案.md)、[移动端上线检查清单.md](移动端上线检查清单.md)
> 适用场景：在**已运行的 we-meet 阿里云部署**上，升级发布移动端 Part A（OTP 登录 / 房间 8 位数字 slug / 个人资料）。
> 首次全新部署请走 [../installation/aliyun.md](../installation/aliyun.md) 全流程。

## 本次发布的改动

| 改动 | 影响 |
|------|------|
| 后端 Part A 代码（`mobile_auth.py`、房间 8 位数字 `slug`/`end`、个人资料、迁移 `0020`/`0021`/`0022`） | 需重建 **backend 镜像** |
| `pyproject.toml` + `uv.lock`（新增 `volcengine`/`tenacity`） | 同上（`uv sync --locked` 构建时拉取） |
| `values.meet.yaml` / `values.secrets.yaml`（OSS 迁移、`MOBILE_AUTH_*`、`VOLC_SMS_*`） | `helm upgrade` 时注入，无需重建镜像 |
| Keycloak `compose.yaml`（`KC_FEATURES`） | aliyun-zlm 重建 Keycloak 容器 |

frontend / summary / agents 镜像**无需重建**——它们只受 `values` 的环境变量变更影响，由 `helm upgrade` 自动滚动。

拓扑回顾：`aliyun-sjy`（4C8G，K3s 主节点，meet 全栈）+ `aliyun-zlm`（2C2G，Keycloak）。

## 步骤 1 — Keycloak 启用 token-exchange（aliyun-zlm）

OTP 登录依赖 Keycloak Token Exchange。`bootstrap-mobile.sh` 已创建 `meet-service` 客户端；还需让 `KC_FEATURES` 生效。

```bash
# 把改动后的 compose.yaml 同步到 aliyun-zlm（git pull 或 scp deploy/aliyun/keycloak/compose.yaml）
ssh aliyun-zlm
cd <repo>/deploy/aliyun/keycloak
docker compose up -d                 # 重建 keycloak 容器，加载 KC_FEATURES
docker compose logs -f keycloak      # 看到 "started in" 即就绪
```

验证 token-exchange 已开启：

```bash
curl -s https://id.we-meet.online/realms/meet/.well-known/openid-configuration \
  | jq '.grant_types_supported' | grep token-exchange
```

## 步骤 2 — 同步配置到主节点（aliyun-sjy）

把改动后的 `values.meet.yaml` 与 `values.secrets.yaml`（OSS endpoint / 区域 / 桶名、`MOBILE_AUTH_*`、`VOLC_SMS_*`、OSS 的 AK/SK）同步到 aliyun-sjy 仓库：

- `values.meet.yaml` 已入库 → 在 aliyun-sjy `git pull`
- `values.secrets.yaml` 为 gitignored → 用 `deploy/aliyun/sync-customer-config.sh` 或手动 `scp`

确认阿里云 OSS 三个桶已就绪且**均为私有**：`we-meet-video`（主）、`we-meet-avatar`、`we-meet-cover`。

## 步骤 3 — 构建并推送 backend 镜像（PC）

移动端代码全在 backend，只重建 backend 一个模块。镜像 tag 用默认的 `latest`
（**不改** `values.meet.yaml`）。

```bash
# === VPN ON：构建（需直连 PyPI / Docker Hub）===
bash deploy/aliyun/build.sh backend

# === 关 VPN：推送（走国内 CR；凭据自动从 values.secrets.yaml 读）===
bash deploy/aliyun/push.sh backend
```

> ⚠️ **后端代码改动必须经此步重新 `build.sh` + `push.sh`。**
> 在 ECS 上 `git pull` 只更新仓库里的配置与源码，**不会更新 registry 里的镜像**；
> 步骤 4 的 `rollout restart` 只是让新 Pod 去拉 `latest` —— 若没先推送新镜像，
> 拉到的还是旧的。（历史教训：漏掉本步导致 `openid` 修复始终没生效。）

## 步骤 4 — 升级 Helm 并强制滚动 backend（aliyun-sjy）

本项目采用「`latest` 标签 + 手动 rollout」：不改 `values.meet.yaml` 的 `image.tag`，
每次推完新镜像后手动强制滚动 backend。

```bash
ssh aliyun-sjy
cd <repo>
git pull                       # 同步 values / chart / 源码

# ① 应用配置变更（values.meet.yaml / values.secrets.yaml）
sudo -E env KUBECONFIG=/etc/rancher/k3s/k3s.yaml \
  helm upgrade meet ./src/helm/meet -n meet \
  -f src/helm/env.d/common.yaml.gotmpl \
  -f src/helm/env.d/aliyun-prod/values.meet.yaml \
  -f src/helm/env.d/aliyun-prod/values.secrets.yaml \
  --wait --timeout 15m
```

> ⚠️ **`helm upgrade` 不会更新 backend 镜像。** `image.tag` 是 `latest` 没变 →
> Deployment 的 Pod 模板字节不变 → helm 认为没改动 → 不滚动 backend Pod
>（`pullPolicy: Always` 只在 Pod **新建**时拉新，不会让在跑的 Pod 重新拉）。
> 所以只要步骤 3 重建过 backend 镜像，下面的强制滚动 **必做**：

```bash
# ② 强制 backend 重建 Pod —— 新 Pod 会拉到步骤 3 刚推送的新 latest
kubectl -n meet rollout restart deploy/meet-backend
kubectl -n meet rollout status  deploy/meet-backend --timeout=5m

# ③ 应用数据库迁移 —— helm 的 migrate hook 不一定用到新镜像，从新 Pod 手动跑最稳
kubectl -n meet exec deploy/meet-backend -- python manage.py migrate --no-input
```

验证 backend 确实是新镜像：

```bash
kubectl -n meet get pods | grep meet-backend       # AGE 应为秒级
kubectl -n meet exec deploy/meet-backend -- \
  python manage.py showmigrations core | tail -4    # 应见 0020 / 0021 / 0022 [X]
```

> 仅改 `values.*`（环境变量、未动 backend 代码）时，env 变化会让 helm 自动滚动
> backend，可跳过 ②；但只要跑过步骤 3 的 `build.sh`/`push.sh`，② 就**必做**。

## 步骤 5 — 部署后冒烟验证

按 [移动端上线检查清单.md](移动端上线检查清单.md) §7 逐接口验证，并对照 [移动端API接口文档.md](移动端API接口文档.md)。最小冒烟：

```bash
# 1. OTP（demo 手机号或真实短信）
curl -s -X POST https://meet.we-meet.online/api/mobile/auth/send-otp/ \
  -H 'Content-Type: application/json' -d '{"phone":"13800000000"}'
# → {"success": true, "expires_in": 600}

# 2. 校验验证码取 access_token，之后：
#    建房 POST /api/v1.0/rooms/ → 拿 slug（8 位数字会议号）
#    GET /api/v1.0/rooms/{slug}/ → 含 livekit token
#    POST /api/v1.0/rooms/{id}/end/ → 结束后再 GET 应无 livekit 块
# 3. 个人资料三步上传 upload-url → PUT → profile-image
```

## ⚠️ 关键风险（部署后立即测）

| 风险 | 说明 / 应对 |
|------|------|
| **阿里云 OSS 的 S3 兼容性** | 三步上传的预签名 PUT/GET 走 SigV4，阿里云 OSS 无独立 S3 兼容 endpoint，未必接受。**部署后第一时间测上传流**；若不通需改用 OSS 原生 SDK |
| **`pytest` 未跑全量** | 本机无 Postgres，后端回归测试未执行。建议在 CI 或带 Postgres 的环境先跑一遍再上生产 |
| **demo 账号** | `MOBILE_AUTH_DEMO_PHONES/OTP` 若为联调启用，正式对外前确认已在 `values.meet.yaml` 注释/移除 |

## 回滚

```bash
# 镜像 / 配置回滚
helm -n meet rollback meet            # 回上一个 release
# 迁移回滚（如必要；0021/0022 加/删列，0020 加列，回滚风险低）
kubectl -n meet exec deploy/meet-backend -- python manage.py migrate core 0019
```
