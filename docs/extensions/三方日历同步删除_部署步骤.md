# 三方日历同步删除 — 部署步骤

> 适用于 `we-meet` `aliyun-dev` 分支 `fc741c5e` 及以上版本、
> `we-meet-android` `main` 分支 `73ae78b` 及以上版本。
>
> 本次删除 Google Calendar 与 Microsoft 365 / Outlook.com 日历同步。
> Outlook Add-in 只是向 Outlook 日程插入 We Meet 会议链接，不属于同步功能，不受影响。
>
> 若从未部署过包含三方同步的 `361fa2eb`，不要为了“补步骤”先部署旧版本。
> Django 会按顺序建立统一日历 Schema，再由 `0098` 删除仅属于三方同步的部分；
> `0098` 已显示 `[X]` 时，直接执行 4.3 开启保留的 P0/P1/P2 能力即可。

## 1. 变更与风险

本次需要发布 backend、frontend 和 Android，并执行迁移
`0098_remove_external_calendar_sync`。生产 values 同时开启统一日历、分享和导出
开关，因此需要在迁移完成后执行 `helm upgrade`；不需要配置任何 Google/Microsoft
Client ID、Secret 或 Webhook。

`0098` 会永久删除 We Meet 本地保存的：

- 第三方账号及加密 OAuth 令牌；
- 远端日历绑定、同步游标和 Webhook 元数据；
- 本地镜像日历及镜像日程；
- 同步 Outbox、冲突状态、相关 ContentType 和权限元数据。

Google/Microsoft 远端日历和日程不会被删除。迁移的数据清理不可通过
`migrate core 0097` 恢复；完整回滚必须同时恢复发布前 PostgreSQL 备份和旧镜像。

## 2. 发布前检查与备份

1. 通知管理员本地镜像数据将在本次升级中永久清除。
2. 确认代码已推送：

   ```bash
   # 开发机
   cd /mnt/d/workspace/jusi-meet/we-meet
   git fetch origin aliyun-dev
   git merge-base --is-ancestor fc741c5e origin/aliyun-dev

   cd /mnt/d/workspace/jusi-meet/we-meet-android
   git fetch origin main
   git merge-base --is-ancestor 73ae78b origin/main
   ```

   两条命令均应返回退出码 `0`。

3. 在生产 ECS 创建 PostgreSQL 完整备份：

   ```bash
   install -d -m 700 /opt/backups
   PG_POD=$(kubectl -n meet get pod \
     -l app.kubernetes.io/instance=postgresql,app.kubernetes.io/component=primary \
     -o jsonpath='{.items[0].metadata.name}')
   test -n "$PG_POD"

   BACKUP="/opt/backups/meet-before-0098-$(date +%Y%m%d-%H%M%S).dump"
   kubectl -n meet exec "$PG_POD" -- \
     pg_dump -U meet -d meet -Fc > "$BACKUP"
   test -s "$BACKUP"
   kubectl -n meet exec -i "$PG_POD" -- \
     pg_restore --list < "$BACKUP" | head
   echo "backup=$BACKUP"
   ```

4. 记录当前工作负载和迁移状态：

   ```bash
   kubectl -n meet get deploy | grep -E 'meet-(backend|frontend|celery-backend)'
   kubectl -n meet exec deploy/meet-backend -- \
     python manage.py showmigrations core | grep -E '0095|0096|0097|0098'
   ```

## 3. 构建并推送镜像

## 4. 生产发布顺序

本次使用“新代码先行、破坏性迁移随后”的专用顺序。新 backend 能兼容迁移前的旧
Schema；迁移后的 Schema 不兼容旧 backend。

### 4.1 拉取代码并先更新 backend/worker

```bash
# 生产 ECS
cd /opt/we-meet
git pull --ff-only origin aliyun-dev
git rev-parse --short HEAD

kubectl -n meet rollout restart deploy/meet-backend
kubectl -n meet rollout status deploy/meet-backend --timeout=180s

# 若该 Deployment 存在，必须在迁移前一起更新，避免旧同步任务继续访问旧表。
if kubectl -n meet get deploy/meet-celery-backend >/dev/null 2>&1; then
  kubectl -n meet rollout restart deploy/meet-celery-backend
  kubectl -n meet rollout status deploy/meet-celery-backend --timeout=180s
fi
```

确认新后端已不再暴露同步接口：

```bash
BASE=https://meet.we-meet.online/api/v1.0
curl -sS -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $TOK" "$BASE/external-calendar-accounts/"
# 期望：404
```

### 4.2 执行并确认迁移

```bash
kubectl -n meet exec deploy/meet-backend -- \
  python manage.py migrate core 0098 --no-input

kubectl -n meet exec deploy/meet-backend -- \
  python manage.py showmigrations core | grep 0098
# 期望：[X] 0098_remove_external_calendar_sync
```

该迁移为非原子清理迁移，用于避开 PostgreSQL 级联删除产生的延迟外键触发器。执行
时间很短，但不能人为中断；如果失败，不要继续发布前端，应保留日志并根据第 8 节
从备份回滚。

### 4.3 应用日历开关并发布 frontend

日历导出依赖 Docs `0e0d78d3` 的原生表格创建接口。先做无凭据探测：

```bash
curl -sS -o /dev/null -w '%{http_code}\n' -X POST \
  https://docs.we-meet.online/api/v1.0/documents/create-table-for-owner/
# 期望：401/403（接口存在但未认证）；404 表示需先发布 we-meet-docs 0e0d78d3+
```

接口就绪后应用生产开关：

```bash
helm upgrade --install meet ./src/helm/meet \
  -n meet \
  -f ./src/helm/env.d/common.yaml.gotmpl \
  -f ./src/helm/env.d/aliyun-prod/values.meet.yaml \
  -f ./src/helm/env.d/aliyun-prod/values.secrets.yaml \
  --wait --timeout 15m

# 环境变量变化会滚动 backend/worker；0098 已执行，migrate hook 此时是空操作。
kubectl -n meet rollout status deploy/meet-backend --timeout=180s
if kubectl -n meet get deploy/meet-celery-backend >/dev/null 2>&1; then
  kubectl -n meet rollout status deploy/meet-celery-backend --timeout=180s
fi

# latest 标签内容变化不会自动触发 frontend 更新，仍需显式重启。
kubectl -n meet rollout restart deploy/meet-frontend
kubectl -n meet rollout status deploy/meet-frontend --timeout=180s
```

这里的 `helm upgrade` 必须放在 4.2 的手动 `0098` 之后。若提前执行，migrate hook
会先删除同步 Schema，仍在运行的旧 backend/worker 可能访问已删除的表。生产配置
生效后，`/api/v1.0/config/` 的 `calendar` 应返回三个开关均为 `true`。

## 5. 数据库验收

```bash
PG_POD=$(kubectl -n meet get pod \
  -l app.kubernetes.io/instance=postgresql,app.kubernetes.io/component=primary \
  -o jsonpath='{.items[0].metadata.name}')

kubectl -n meet exec "$PG_POD" -- psql -U meet -d meet -P pager=off -c "
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public'
  AND (table_name ILIKE '%external%calendar%'
       OR table_name ILIKE '%calendar%sync%'
       OR table_name ILIKE '%event%mirror%');

SELECT table_name, column_name
FROM information_schema.columns
WHERE table_schema = 'public' AND column_name = 'sync_status';

SELECT count(*) AS external_calendar_rows
FROM meet_personal_calendar
WHERE kind = 'external';

SELECT app_label, model
FROM django_content_type
WHERE model IN ('externalcalendaraccount', 'externalcalendarbinding',
                'externaleventmirror', 'calendarsyncoutbox');
"
```

验收标准：表、字段和 ContentType 三个查询均返回 `0` 行，
`external_calendar_rows` 返回 `0`。

## 7. 外部配置与授权清理

仓库内已不再使用以下变量。若生产环境通过额外 values、Kubernetes Secret 或外部
密钥系统注入它们，应删除后再滚动 backend/worker：

```text
EXTERNAL_CALENDAR_SYNC_ENABLED
GOOGLE_CALENDAR_CLIENT_ID
GOOGLE_CALENDAR_CLIENT_SECRET
MICROSOFT_CALENDAR_CLIENT_ID
MICROSOFT_CALENDAR_CLIENT_SECRET
EXTERNAL_CALENDAR_TOKEN_KEYS
EXTERNAL_CALENDAR_WEBHOOK_BASE_URL
EXTERNAL_CALENDAR_TIMEOUT_S
```

可先检查 Deployment 中是否仍有注入：

```bash
kubectl -n meet get deploy meet-backend -o yaml | grep -E \
  'EXTERNAL_CALENDAR|GOOGLE_CALENDAR|MICROSOFT_CALENDAR' || true
```

最后在 Google Cloud Console 和 Microsoft Entra 管理中心删除专用于本功能的 OAuth
客户端，或撤销相应用户授权。数据库迁移只删除本地令牌，无法替你撤销云端授权；
已有 Provider Webhook 会自然过期，但删除 OAuth 应用可完成最终收口。

## 8. 回滚

迁移前：可直接停止发布并回滚 Deployment。

迁移后：禁止只执行 `migrate core 0097` 或只回滚 backend；旧代码依赖已经删除的表和
字段。完整回滚步骤为：

1. 停止 backend 和 `meet-celery-backend` 接收新流量/任务；
2. 恢复第 2 节 PostgreSQL 完整备份；
3. 将 backend、worker、frontend 回滚到上一版镜像；
4. 恢复上一版 Android APK；
5. 验证旧迁移状态、同步表和主要日历链路后再恢复流量。

若不需要恢复本地镜像数据，优先修复新版本并重跑 `0098`，不要回退 Schema。
