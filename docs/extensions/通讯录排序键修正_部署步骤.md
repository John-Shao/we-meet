## 1. 为什么必须改（实测证据，用于验收时判断「有没有真修好」）

1. **`#` 桶排到了名册最前面。** `0143` 用 `'~'` 当前缀把「分不出首字母」的人压到最后，
   但生产的 `datcollate` 是 `en_US.utf8` —— 这个 collation 在**主比较级别忽略标点**：

   ```sql
   SELECT '~1001' < 'abao';   -- 生产上实测为 t（期望 f）
   ```

   `~` 被忽略后比较的是 `'1001'` 与 `'abao'`，数字当然排在字母前。改用数字前缀后
   `'0zhangsan' < '1zhangsan'` 恒成立（数字是真实比较级别，不会被忽略）。

2. **`CASE` 排序让索引完全失效。** 5001 行、warm cache 实测（同一份数据、同一条
   `?ordering=pinyin&page_size=20`）：

   | 写法 | 计划 | 耗时 |
   |---|---|---|
   | `ORDER BY CASE … , full_name_pinyin, full_name` | `Limit → Sort (5001 rows)` | **3.627 ms** |
   | `ORDER BY full_name_pinyin, full_name` | `Limit → Index Scan using meet_user_pinyin_name_idx` | **0.112 ms** |

   首列是表达式时 btree 用不上，必须把整个组织物化再排序 —— 32× 的差距，且随组织
   规模线性恶化。

3. **`full_name_initial` 上的索引一次都没被用过**：字母表的 `GROUP BY` 走 HashAggregate，
   `?from_initial=#` 只是 pkey 扫描上的 Filter。它只有约 28 个不同值，留着就是每次保存
   用户多维护一条索引（Postgres 上 `db_index=True` 还会额外建一条 `varchar_pattern_ops`
   的，给 LIKE 用，而我们从不 LIKE 这一列）。

4. 顺带说明**为什么不用 `.only()` 收窄投影**：实测每页只省约 0.6 ms，而会把
   `full_name` / `department` 变成 deferred load —— 一行一次查询的地雷换 0.6 ms，不划算。

## 2. 迁移画像

`core/migrations/0144_pinyin_sort_key_bucket.py`，四步：

1. `AlterField` ×2：去掉两列的 `db_index=True`（→ 删掉四条自动索引）；
2. `RunPython(recompute_sort_keys)`：**整表**重算 `full_name_pinyin` 与
   `full_name_initial`（`bulk_update`，500 一批）。只有 `#` 桶的键真的会变，但整表重算
   比按前缀筛更简单也更不容易漏；
3. `AddIndex`：`(full_name_pinyin, full_name)` → `meet_user_pinyin_name_idx`。第二列是
   翻页稳定需要的次序键。**放在回填之后**：先建索引再改数据等于建完就让它失效。

### ⚠️ 迁移窗口的「漂移行」

迁移在**滚动更新之前**跑完，而这段时间**旧 backend Pod 仍在服务**：任何一个用户在这个
窗口里被保存（改昵称、改部门、OIDC 登录同步 profile、管理端调整），旧代码会把
`full_name_pinyin` 写回**旧格式**（字母桶没有前缀，其他桶是 `~` 前缀）。

后果是**有限的**：这些行会排在名册末尾（`'0…'` < `'z…'`），直到它们再被保存一次；
数据不丢、`initial` 不受影响（那一位的规则没变，新旧代码算出来一样）。所以：

- [ ] 挑低峰时段发布（窗口本来就是一次 rollout 的时间，通常 1–2 分钟）；
- [ ] 发布后按第 3 节那条「前缀合法性」SQL 检查，非 0 就按第 3.1 节的命令收敛一次。
      收敛命令是**幂等**的，多跑几次没有副作用。

## 5. 回滚预案

| 对象 | 方式 |
|---|---|
| 后端 | `kubectl -n meet rollout undo deploy/meet-backend` |
| 前端 | `kubectl -n meet rollout undo deploy/meet-frontend` |
| **迁移 0144** | **不回滚**。键是纯派生值；回滚后旧代码的 `CASE` 只认 `~` 前缀，而库里的键已经是 `0`/`1` 开头 → `#` 桶会排到名册最前面。那正是本次要修的缺陷，所以「回滚后端」= 回到已知缺陷，**不要**用「改数据」来回滚 |

## 7. 未交付项（别在验收时找）

- **拼音搜索**（全拼 / 首字母缩写 / 工号）：仍是 `p10-org-structure-deepening.md` §4.3 的
  M3。本次的 `?q=` 只多认了职位与部门名，不做拼音匹配。
- **虚拟化与「页」的关系**：虚拟化只对**已加载**的行生效，滚动条高度也按已加载行算；
  上千人的名册要滚到底才会把页加载完。要做「总量占位的假滚动条」是另一件事。
- **筛选与索引起点的组合**：`?q=` 与 `?from_initial=` 可以同时生效（服务端两个条件都认），
  但前端没有专门的组合入口 —— 点字母会清掉筛选框（反之亦然），这是有意的克制。
- **部门视图不含子部门**：与 `departments/{id}/members/`（不带 `include_subtree`）一致，
  子部门在树里是独立的一行。要「连子部门一起看」是另一个决定（后端已支持
  `?include_subtree=true`）。
