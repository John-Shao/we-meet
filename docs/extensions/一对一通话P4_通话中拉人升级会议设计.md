# 一对一通话 P4 —— 通话中拉人升级会议详细设计

状态:M1+M2 已上线并实测通过(2026-07-17:M1 宫格/动态回落/自动结束/多方通话记录双端验证;M2 邀请广播 chips 含头像、视频「第三人进房才切会议页」时机、owner rename 均实测通过;P2 冷杀推送来电 V4 待真机验证)
背景:竞品差距分析(`docs/research/competitor-gap-feishu-wecom-2026-07.md` §四/§五)确认本项为最划算差距——飞书有(1:1 拉第三人自动升级会议)、企微没有;我方通话与会议同为 LiveKit 房间同栈,升级路径天然存在。
原则:只扩展不修改;jusi-light-im 侧只列需求与接口约定(立项 **p19**),其实现须按惯例在 jusi 仓先出 `docs/phases/p19-meet-invite-kind.md` 再开干。
已拍板(2026-07-17):①等 p19 一起上,不做无 kind 字段的降级先行版;②通话双方都可拉人;③升级后**双形态**——语音保留极简页(多人头像宫格),视频切完整会议页。
二次拍板(2026-07-17 实测后,现状模型):**语音全程通话语义**——形态跟随房内人数动态切换(≥3 宫格、=2 回落 1:1、剩 1 人自动结束,与 1:1 现状一致;有邀请响铃中时不自动结束);**视频升级后为会议语义**——单向锁存,不回落、不自动结束。原「语音单向锁存不回落」方案作废。

## 0. 一句话架构

通话房=会议房,升级不换房:A 在 1:1 通话中经「A↔C 的 direct 会话」发一条带 `kind:"meet"` 的标准 P1 invite(`room_slug`=当前通话房间),C 收到**响铃入会呼叫**,接听后按 `media` 分流——语音进极简多人宫格页、视频进完整会议 UI;A 发出首个邀请即升级本端形态,B 以「远端参会者≥2」自动跟随;「对端离房 1.5s 自动挂断」随升级解除。Django 零新接口,jusi 仅 +1 可选字段。

## 1. 已验证的事实依据(实勘结论,2026-07-17)

1. **通话房间在后端就是普通会议房间**:同一 Django `Room`(8 位数字 slug,`generate_unique_slug` `models.py:521-539`),trusted 访问级;LiveKit room name=Room UUID(`utils.py:141-182`);token 经 `RoomSerializer.to_representation` 对 trusted+已登录直接下发(`serializers.py:209-259`);trusted+已登录绕过大厅候场(`lobby.py:106-122`)。**被拉人接听后一次 `GET /rooms/{slug}/` 即拿 token 进房,无候场、无新接口。**
2. **通话 vs 会议的区别只在客户端渲染**:Web 分叉点 `Conference.tsx:310`(`callPeer ? <CallStage/> : <VideoConference/>`,callPeer 来自 `history.state`,**非响应式,刷新即丢**);Android 分叉点 `RoomScreen.kt:222`(`callPeerUid != null` → `MinimalCallHost`)。
3. **唯一运行时语义差别**:「对端离房 1.5s 防抖自动挂断」——Web `CallStage.tsx:91-107`(`useRemoteParticipants` + `peerSeenRef` + 1.5s setTimeout),Android 同构语义(见极简页设计 §4)。升级后必须解除。
4. **P1 信令是严格 1:1 的**:jusi WS 瞬时 `call` 帧,服务端无状态校验中继,handleCall 强制 `cid` 为 direct 会话且双方为成员(拒绝群聊 cid),from 覆写防伪造;invite 3s×3 重发、60s 双端超时、终态双投、`call_id` 幂等(P1 §2/§3)。`CallPayload` 是 Go 类型化 struct——**加字段必须动 Go + 双端 SDK**,未知字段不透传。
5. **双端 CallController 均为单通道状态机**:`startCall` 要求 `Idle && !isInMeeting`(Android `CallController.kt:80`,Web `callController.ts` 同构);接通后 Web 立即 `finishQuietly` 回 idle,通话中状态由 LiveKit room 承载——「**房间成员状态是真相源**」是既有设计哲学。→ 拉人不能复用 `startCall`,需独立子状态机(§4.1)。
6. **direct 会话幂等懒建**:`POST /im/conversations/direct {peer_user_id}`(`im.py:289-364`),`cid=uuid5("direct:lo:hi")` 确定性,返回 `{cid, members, self_uid}`——客户端由此拿到 peer 的 jusi uid,**不接触裸 sub,不需要新的 uid 映射**。A 与 C 从未聊过也无感。
7. **P2 离线链路四透传点**:jusi 离线 webhook → Django `notify_call` → 个推双通道 payload/深链 `wemeet://call?payload=...` → Android `CallSeed.fromJson`(宽松 JSON 解析,加可选字段零成本)。ts 新鲜度 55s 校验不变。
8. **可复用组件**:选人器 Web `GroupPicker.tsx`(Multi+已选 chips)、Android `core-directory/ContactPicker.kt`(Multi、`excludeUserIds`/`preselectUserIds`);头像/名字目录解析 Web `MemberAvatar`、Android `UserDirectory`(跨组织解析不到退字母头像,数据边界非 bug)。
9. **群聊多人通话不存在 call 信令**:群=「快速会议」路径(P1 §6 明确保留)。本设计不动群聊入口。

## 2. 方案对比与选型

### 2.1 拉人信令通道(3 选 1)

| 方案 | 说明 | 判定 |
|---|---|---|
| **A. 复用 P1 的 1:1 invite(选定)** | A 拉 C = 沿「A↔C direct cid」发标准 invite,`room_slug` 填当前通话房;拉 N 人 = N 路并行 1:1 invite | ✅ jusi 校验天然通过(direct+双方成员);busy/unreachable/60s 超时/终态双投/**P2 离线推送**全部免费复用;Go 侧改动最小 |
| B. 新增群呼 call 信令 | 新事件集 + 群 cid 授权模型 | ❌ 等于再设计一个 P1 体量的协议;群 cid 授权会打开「骚扰群成员」口子(P1 明确拒绝过) |
| C. 纯服务端邀请(REST+推送) | Django 发个推通知,点击进房 | ❌ 丢掉响铃三态/忙线/超时收敛语义,「入会呼叫」退化成普通通知,不符合需求 3 |

### 2.2 「会议邀请」标识(3 选 1)

| 方案 | 说明 | 判定 |
|---|---|---|
| **A. CallPayload 加可选字段 `kind`(选定)** | `kind:""|"meet"`,invite 携带,服务端不校验原样中继 | ✅ 被叫来电页文案与接听后进房形态都发生在**进房前**,必须靠字段区分;向后兼容(老端忽略) |
| B. 无字段,接听后按房内人数推断 | 进房后数人头再切形态 | ❌ 来电页文案无法区分;接听瞬间形态抖动;人数在进房前不可得 |
| C. room_name 文案嗅探 | 靠「邀请你加入」字样判断 | ❌ 脆弱 hack,i18n 即碎 |

降级故事:老客户端收到带 `kind` 的 invite → 忽略字段按普通 1:1 来电响铃 → 接听进极简 1:1 页 → 「远端≥2」判据兜底切多人形态。降级路径完整可用,`kind` 是体验保障而非功能前提——但已拍板等 p19 一起上,不发布无 kind 版本。

### 2.3 升级后形态(已拍板:双形态)

| 场景 | 升级后形态 | 理由 |
|---|---|---|
| **语音通话拉人 → 语音会议** | **保留极简页**,单 peer 布局改为**多人头像宫格**(微信群语音式),可继续拉人 | 会议网格 UI 为视频/共享设计,纯语音下满屏空瓦片突兀;极简形态保住「通话很轻」的心智;B 端升级无页面跳变(只是头像+1) |
| **视频通话拉人 → 视频会议** | **切完整会议页**(`VideoConference`/`RoomContent`) | 多人视频天然需要网格;复用现成组件零 UI 成本,白得共享/字幕能力;微信群视频同为宫格,跳变可接受 |

被拉人接听后的形态由既有 `media` 字段决定:`audio` → 极简语音多人页;`video` → 完整会议页。`kind` 只标识「这是多人邀请」。

落选方案「语音也切会议网格」:实现最省(零新 UI),但语音体验降级明显,已被否。

### 2.4 升级触发与锁存

- **拉人者**:选人确认、发出首个 invite 的瞬间,本端立即升级形态(飞书同款——不等被邀人接听)。
- **在房其他人**(未参与拉人):以「远端参会者≥2」为升级判据——与「房间成员是真相源」哲学一致,零信令成本。M2 补 LiveKit data message(`topic:"call-upgrade"`)让拉人动作即时广播,消除竞态窗口(§6 #9)。
- **锁存口径(二次拍板修订)**:仅**视频**升级单向锁存(会议语义,不回落);**语音**不锁存——宫格 ↔ 1:1 完全跟随房内人数(通话语义),被邀人拒绝/超时只是 chips 消失,形态自然回落。

## 3. 信令与协议扩展(jusi p19 需求清单,只列约定)

### 3.1 CallPayload 新增可选字段

```
kind: "" | "meet"    // invite 携带;非 invite 帧忽略;服务端不校验、原样中继
```

### 3.2 meet-invite 帧示例

```json
{ "type": "call", "ts": 1721180000000,
  "payload": {
    "event": "invite", "kind": "meet",
    "call_id": "全新 uuid(每路邀请独立)",
    "cid": "A↔C 的 direct 会话 id(授权依据,不是通话房的会话)",
    "from": "服务端覆写为 A 的 uid", "to": "C 的 uid",
    "media": "audio | video(当前通话的媒体类型,决定 C 接听后形态)",
    "room_slug": "当前通话房间的 8 位 slug(不新建房)",
    "room_name": "{A 的显示名} 邀请你加入通话"
  } }
```

### 3.3 p19 立项范围(全部向后兼容,老端忽略)

| 触点 | 改动 |
|---|---|
| Go `internal/api/ws/frame.go` | CallPayload struct +1 字段 `kind`(omitempty) |
| Go 离线 webhook 请求体 | 透传 `kind` |
| Android SDK `CallPayload` | +1 可选字段 |
| JS SDK(`@jusi/light-im-sdk`)类型 | +1 可选字段 |

**明确不做**:无新事件、无新校验、无服务端状态、不动 handleCall 的 direct-only 授权。

### 3.4 完整复用不变的机制

invite 3s×3 重发、60s 双端独立超时、终态双投(from+to 双频道多端收敛)、`call_id` 幂等表、busy 自动应答(被邀人在通话/会议中)、unreachable→P2 离线推送(webhook 带 kind,深链 payload 带 kind,55s 新鲜度不变)。

### 3.5 Django 改动(1 行级)

`notify_call` 构造个推透传/深链 payload 时透传 `kind`。无新表、无新接口。

## 4. 状态机与 UI 形态

### 4.1 邀请方:MeetInviteTracker(新,双端同构)

独立于主 CallController 的轻量子状态机(Web 新文件 `meetInviteTracker.ts`;Android 放 `CallController.kt` 同文件或伴生类),与主状态机**并存**(主状态机接通后已回 Idle,不冲突),共享 WS client 与 finishedCallIds 幂等表。

```
per-invitee(每路独立 call_id):
Inviting ──ringing──▶ Ringing ──accept──▶ Accepted(等其进房,以房内名单为准)
   │                     │
   └──── reject / busy / unreachable / 60s 超时 ────▶ 终态 chip(可重邀,新 call_id)
```

职责边界:只做发帧 + 3s×3 重发 + 60s 超时 + 状态 chip 展示;**不建房、不导航、不写 call-log**。
拉人流程:选人确认 → 逐人 `POST /im/conversations/direct {peer_user_id}` 取 `cid`+peer uid → 逐路发 meet-invite → 本端升级形态(若尚未升级)。
拉人者离房时:对所有未终态邀请补发 `cancel`(尽力而为;失败靠对端 60s 超时 + 接听时 `resolveCallRoom` 判活兜底)。

### 4.2 被邀方:完全复用 P1 被叫状态机,仅两处分支

1. **来电页文案**:`kind=meet` → 「{from} 邀请你加入语音/视频通话」(按 media);其余(响铃/三态按钮/多端收敛/busy 自动应答)不变。
2. **接听后导航**:`kind=meet` → 进房**不带** peer 参数;`media=audio` 追加「极简多人形态」标记(Web router state / Android route query),`media=video` 直接完整会议 UI。

### 4.3 在房两端:升级判据与形态切换

```
语音(无锁存):宫格 := 远端参会者 ≥ 2 ∥ 有邀请在响铃;否则 1:1 布局(对象=房内剩余那人,经 resolve-subs 解析,可能已不是原 callPeer)
视频(单向锁存,三次拍板 2026-07-17):会议UI := 以 meet 身份进房 ∥ 远端参会者 ≥ 2——即第三人**真正进房**才切会议页,发邀/响铃期间双方都留在 1:1 视频页(App 方案统一)
```

- **语音**:极简页内宫格 ↔ 1:1 动态切换(同组件,无路由跳转);「他人走光 1.5s 自动结束」全程武装,仅邀请响铃期间挂起(自动结束会 cancel 被邀人)。
- **视频**:锁存触发后卸载 CallStage/MinimalCallHost,渲染 `VideoConference`/`RoomContent`(无 LiveKit 重连);「对端离房自动挂断」解除,离房=leave(会议语义)。
- **实现要点(Web)**:`callPeer` 来自 `history.state` 非响应式(`Room.tsx:34`)——升级状态需引入响应式 store(valtio 或 Conference 内 state),分叉条件改为 `callPeer && !upgraded`;人数判据在 `Conference` 层用 `useRemoteParticipants` 取(它在 LiveKitRoom context 内)。
- **实现要点(Android)**:`RoomViewModel` 观察 remote participants 维护 `upgraded` StateFlow;`RoomScreen.kt:222` 分叉条件加 `!upgraded`;audio/video 分流决定切 `MinimalCallHost 多人形态` 还是 `RoomContent`。

### 4.4 极简语音多人页(本期 UI 主体工作量)

- 由现有极简语音页(Web `CallStage.tsx`、Android `MinimalVoiceCallScreen.kt`)改造:单 peer 头像 → **按 LiveKit 房内成员渲染头像宫格**(含自己),自适应至 3×3,超出折叠「+N」。
- 头像/名字按 participant identity 走目录解析(Web `MemberAvatar` / Android `UserDirectory`);跨组织解析不到退字母头像(既有兜底,数据边界非 bug)。
- 操作区维持极简:静音 / 挂断 / 扬声器(Android)或摄像头切换钮**移除**(语音会议不提供开摄像头)+ **「添加成员」**。
- **只渲染音频+头像,忽略远端视频轨**:有人从会议链接开着摄像头进来也不自动跳视频页,保持形态确定性(§6 #14)。不提供共享/字幕/AI 入口,保持轻。
- M2 加分项:isSpeaking 描边高亮。

### 4.5 挂断语义(二次拍板修订)

- **语音(通话语义)**:与 1:1 一致——他人全部离开后 1.5s 自动结束本端;唯一例外是还有邀请在响铃(此时保持,等接听/终态后再按人数判定)。
- **视频升级后(会议语义)**:任何人离开不结束;自己挂断=leave;剩 1 人不自动结束(对齐视频会议现状 9);房间人走光由 LiveKit 空房自动关,Django Room 留存(owner 仍可 end)。
- **被拉人通话记录(2026-07-17 实测后补)**:被拉人接通后,由**被拉人**在「与拉人者的 direct 会话」写一条 `completed` + 自己在房时长的 call-log(该会话内单一写入方,拉人者同会话可见);未接通终态(拒接/超时/忙线/取消)仍不写,避免「未接来电」误导。MeetInviteTracker 本身始终不写记录。
- 主持人口径:**room owner 固定为最初主叫 A,不转移**(token `room_admin` 既有逻辑零改动);任何在房成员可拉人(对齐企微「任何成员可拉人」;与飞书「拉人者成为主持人」的差异在此记录)。被拉进来的人拿普通成员 token,无需后端改动。

## 6. 边界与竞态(评审重点)

| # | 场景 | 行为 | 依据 |
|---|---|---|---|
| 1 | C 拒接 | A 见 chip「已拒绝」,可重邀;A/B 不回落 | §2.4 锁存 |
| 2 | C 忙线(在别的通话/会议) | C 端自动 busy(P1 复用);A 见「忙线」 | P1 §2.3 |
| 3 | C 全端离线 | unreachable→P2 推送(kind 随深链);55s 新鲜度不变 | P2 |
| 4 | C 60s 未接 | 双端超时收敛;A 可重邀(新 call_id) | P1 §2.4 |
| 5 | A 在 C 响铃期间离房 | A 对未终态邀请发 cancel;C 来电页消失(失败靠 60s 超时+resolveCallRoom 兜底) | §4.1 |

## P4.1 群语音通话与会议拉人(2026-07-17,基建复用)

两个延伸功能,零协议/后端改动,纯双端客户端编排:

**A. 群聊语音通话**
- 入口:群聊顶栏语音按钮(Web header / App 顶栏+「+」面板)→ **群成员多选器**(roster 范围,默认全选、排除自己、跨组织解析不到的隐藏;拍板:默认全选)。
- 编排:建房(房名「{群名}的语音通话」)→ 以 `callMeet+audio` 直落语音宫格 → `sendMeetInvites` 对选中成员并行 kind=meet 响铃(成员 jusi uid 经 resolve 的 `.id` 即 tracker 需要的 userId,邀请引擎零改动)。
- 不进 Outgoing 状态机:宫格响铃 chips 即等待 UI,「独自+无响铃邀请→自动结束」收敛一切结局。
- 通话记录:接受者各自写「与发起人 direct 会话」的 completed(P4 机制自动);**群会话不落卡片**(微信式「进行中卡片可点击加入」留待后续)。

**B. 视频会议拉人**
- 入口:Web=参会者面板顶部「添加成员」(拍板);App=底部「更多」面板「邀请成员」格子。
- 选人:目录多选;Web 用 resolve-subs 的 `.id` 排除已在房者(App M1 不排除,已在房被邀自动 busy 兜底);确认 → `sendMeetInvites(media='video', roomSlug=当前会议房)`,被拉人响铃接听直落完整会议页(P4 callMeet+video 路径)。
- 会议 UI 内不渲染响铃 chips(M3 项);拉人对 restricted 房不做兜底提示(M1 边界)。

**联动修正**:M2 owner rename 收紧为**仅 1:1 升级场景**(有 callPeer/callPeerUid 才触发)——群语音房名「{群名}的语音通话」不被覆盖。

## 8. 开放问题(待拍板,附建议)

1. **A 离房时对响铃中邀请发 cancel(建议)vs 邀请随房间存活**:建议 cancel——房间 owner-only end 意味着 A 离房后房间可能只剩 B 甚至空房,C 接听进空房体验差;B 想邀 C 自己再发即可。(M1 已按建议实现,可复议)
2. **房间 rename(M2)**:不 rename 则会议历史列表里躺着「与B的通话」却是三人记录;建议做。连带确认:A↔B 的 1:1 call-log 时长按 A 在房总时长记(现状零改动,升级后轻微失真)是否接受。
3. **语音多人宫格上限口径**:3×3+「+N」在 ≥10 人时信息密度不足;是否给极简语音页加「查看全部成员」列表入口(轻抽屉),还是接受「+N」不展开(建议先接受,M3 再议)。(M1 实现为 3 列宫格超高滚动,未做「+N」折叠)
