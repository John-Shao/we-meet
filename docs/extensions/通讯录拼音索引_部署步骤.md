# 通讯录拼音索引（A–Z 首字母索引 + 拼音排序）— 部署步骤

> ⚠️ **本篇之后还有一个增量**：[通讯录排序键修正_部署步骤.md](./通讯录排序键修正_部署步骤.md)。
> 那一篇修的是本篇引入的一个真实缺陷 —— 「`#` 桶排最后」用 `~` 前缀实现，而生产的
> `en_US.utf8` collation 会忽略标点，于是 `#` 桶反而排到了名册**最前**；同时把
> `CASE` 排序换成索引排序（5001 行实测 3.6 ms → 0.11 ms）。**两篇一起看**再决定发布包。

> 配套文档：[../phases/p10-org-structure-deepening.md](../phases/p10-org-structure-deepening.md)
> （§4.3 是拼音**搜索**的 M3 计划，与本次不是同一件事）、
> [../installation/aliyun-release-runbook-cn.md](../installation/aliyun-release-runbook-cn.md)（日常发布 Runbook）
> 用法：逐项打勾，带命令的可直接复制执行。
>
> ⚠️ **本次有迁移**（`0143_user_name_pinyin`：给 `meet_user` 加两列 + **回填存量用户**），
> 并且**新增了一个 Python 依赖 `pypinyin`**。这两件事都**不需要额外的手工步骤**：
>
> - 依赖在**构建 backend 镜像时**装（Dockerfile 的 `uv sync --locked` 读 `src/backend/uv.lock`，
>   锁文件已同步）——`deploy/aliyun/*` 里**不需要**也不要加 `uv sync`：生产宿主机上没有 venv
>   可同步，`release-meet.sh` 只做 `helm upgrade`，在部署阶段装依赖等于去改运行中的容器，
>   与这套「不可变 tag」模型冲突（`IMAGE_TAG=latest` 都是明令禁止的）。
> - 迁移由 Helm 的 migrate hook 在 `helm upgrade` 时自动跑（见第 1 节）。
>
> ⇒ **本次要做的动作只有：重建并发布 `backend` 镜像，再发布 `frontend` 镜像。**

## 0. 本次变更范围

| 仓库 | 分支 @ 提交 | 变更 | 部署动作 |
|---|---|---|---|
| `we-meet` | `aliyun-dev` @ `c361003e`（后端 `74ec8b13`） | **后端**：`pyproject.toml` + `uv.lock` 加 `pypinyin`；`User` 加 `full_name_pinyin` / `full_name_initial` 两列（`save()` 维护）；迁移 `0143` 建列 + 回填；成员列表支持 `?ordering=pinyin`、`?from_initial=L`；新增 `GET /directory/members/alphabet/`；成员卡片（含离职墓碑卡）多返回 `initial`。**前端**：通讯录左栏重排（分组 / 计数 / 角标 / 最近访问 / 可收起）、选择状态落到 URL、右栏浮层（窄屏）、成员列表虚拟化 + A–Z 索引条（**仅简体中文界面**）。**前端零新依赖** | build + push `backend frontend` → `release-meet.sh backend` →（冒烟）→ `release-meet.sh frontend` |
| `we-meet-android` | — | 无变更。App 今天不调用 `ordering=pinyin` / `from_initial` / `alphabet`，默认排序也没改 | **无需操作** |
| `jusi-light-im` | — | 无变更 | **无需操作** |

**顺序：建议后端先、前端后，但不是硬约束**（比 M2.1 那次宽松）：

- 「新前端 + 旧后端」→ 前端会发 `?ordering=pinyin`（旧后端忽略未知参数，只是退回编码序）
  和 `GET /directory/members/alphabet/`（旧后端 404）。前端把这两种情况都当**降级**处理：
  不画索引条、不画悬浮字母头，页面照常用。开发模式下控制台会有一次 404 记录，属预期。
- 「新后端 + 旧前端」→ 纯新增字段与参数，完全安全。

所以先后端只是为了「冒烟时索引条是能用的」，而不是为了不报错。

## 1. 依赖与迁移画像

**依赖**（`src/backend/pyproject.toml`）：

```
"pypinyin==0.55.0",   # 通讯录 A–Z 索引：中文姓名没有拼音序
```

纯 Python、无 C 扩展，只在 `User.save()` 这条写路径上执行（实测：拉丁名 4 µs、中文名 11 µs、
100 个汉字 441 µs）。`uv.lock` 里来源仍是 `pypi.org/simple`——**不要**给它设国内 mirror，
`uv sync --locked` 会因 source 不一致拒绝继续（见 `installation/aliyun.md` §12.1）。

**迁移**：`core/migrations/0143_user_name_pinyin.py`。两列 + 一次分批回填
（`bulk_update`，500 一批）。算法在迁移里是**冻结副本**，与 `core/services/pinyin.py` 一致——
有测试逐名字比对两份实现，漂移会红。

- [ ] 上线前自证「模型与迁移一致」：

  ```bash
  cd d:/workspace/we-meet/we-meet
  docker compose run --rm --no-deps -e DJANGO_CONFIGURATION=Test app-dev \
    python manage.py makemigrations --check --dry-run
  # 期望：No changes detected
  ```

- [ ] **迁移是怎么跑的**（不需要手动执行，知道就好）：`src/helm/meet/templates/backend_job_migrate.yaml`
  是一个 Helm `pre-install,pre-upgrade` hook（`hook-weight: -5`），命令是
  `python manage.py migrate --no-input`。`helm upgrade --wait` 会**等它跑完**才继续滚 Pod，
  所以 0143 一定先于新代码生效。

- [ ] ⚠️ **只发前端不会跑 0143**：migrate hook 用的是**本次发布里 backend 镜像的 tag**，
  而未选模块会沿用「正在运行的 tag」（`release-meet.sh` 的 `module_tag()`）。想让迁移执行，
  就必须把 `backend` 纳入本次发布。

## 4. 后端冒烟（约 2 分钟）

```bash
TOK=<access_token>
BASE=https://meet.we-meet.online/api/v1.0

# 1) 字母表：每个字母各有多少人，'#' 排最后
curl -s -H "Authorization: Bearer $TOK" "$BASE/directory/members/alphabet/" \
  | python -m json.tool | head -20

# 2) 拼音序：前 5 个姓名应与「不加参数」时不同（除非该组织本来姓名字母序就等于拼音序）
curl -s -H "Authorization: Bearer $TOK" "$BASE/directory/members/?ordering=pinyin" \
  | python -c "import sys,json;print([m['full_name'] for m in json.load(sys.stdin)['results'][:5]])"
curl -s -H "Authorization: Bearer $TOK" "$BASE/directory/members/" \
  | python -c "import sys,json;print([m['full_name'] for m in json.load(sys.stdin)['results'][:5]])"

# 3) 从 L 开始：列表里的姓名不应再出现 L 之前的字母
curl -s -H "Authorization: Bearer $TOK" "$BASE/directory/members/?ordering=pinyin&from_initial=L" \
  | python -c "import sys,json;print(sorted({m['initial'] for m in json.load(sys.stdin)['results']}))"

# 4) 成员卡片带 initial
curl -s -H "Authorization: Bearer $TOK" "$BASE/directory/members/?ordering=pinyin" \
  | python -c "import sys,json;print(sorted({m['initial'] for m in json.load(sys.stdin)['results']}))"

# 5) 部门成员端点同样支持
curl -s -o /dev/null -w "%{http_code} dept-pinyin\n" -H "Authorization: Bearer $TOK" \
  "$BASE/directory/departments/<dept_uuid>/members/?ordering=pinyin"
```

- [ ] 1) 返回 `{"letters":[{"letter":"A","count":n},…]}`；2) 两次顺序不同或可解释；
      3) 只出现 L 及之后的字母；4) `initial` 全是 A–Z 或 `#`；5) 200

- [ ] **老客户端不受影响**（必查，Android 走的就是不带参数的默认序）：
      `GET /directory/members/` 不带任何新参数时的顺序与上线前一致

## 6. ⚠️ 本次最大的回归面：全员通讯录的**顺序变了**

这是本次唯一对所有用户可见的行为变化，很容易被当成 bug 报上来：

- 中文姓名从**编码序**（张 U+5F20 → 李 U+674E → 王 U+738B，看起来是乱序）变成**拼音序**；
- 拉丁姓名从**区分大小写的码点序**变成**不区分大小写的字母序**（`Zoe` 不再排在 `alice` 前面）。

- [ ] 上线前先跟客户 / 客服说一句「通讯录列表顺序会变成字母顺序」；
- [ ] `?ordering=pinyin` 只对 Web 生效：Android 端仍是不带参数的默认序（如果客户拿两端对比，
      顺序不同是**预期**的，等 App 侧跟进后再统一）。

**顺带变化的还有 `User.save()`**：每次保存用户都会多算一次拼音（微秒级）。冒烟一次：

- [ ] 设置页改一次昵称 → 保存成功；
      `SELECT full_name, full_name_pinyin, full_name_initial FROM meet_user WHERE full_name = '<新昵称>';`
      拼音两列应跟着变（改昵称走的是 `save(update_fields=["full_name"])`，最容易漏的一条路径）

## 7. 观察面（上线后 24h）

- [ ] `/directory/members/alphabet/` 的 5xx 与耗时：它是一次 `GROUP BY`（代码里显式
      `.order_by()` 清掉默认排序，否则排序字段会进 GROUP BY 把分组打碎）；大组织留意响应时间
- [ ] `?ordering=pinyin` 的耗时：`full_name_pinyin` 有索引，排序还带一个 `CASE`（把 `#` 桶推到最后）
- [ ] 拼音两列的空串计数（第 3 节那条 SQL）——回填是否完整，之后也可以当巡检项
- [ ] 前端控制台若出现 `/directory/members/alphabet/` 404，说明后端镜像没更新到位：
      表现是「索引条不出现」，不是页面报错

## 8. 回滚预案

| 对象 | 方式 |
|---|---|
| 后端 | `kubectl -n meet rollout undo deploy/meet-backend` |
| 前端 | `kubectl -n meet rollout undo deploy/meet-frontend` |
| **迁移 0143** | **不回滚**。两列留在库里，旧代码不读它们，行为与上线前一致；已回填的值是纯派生数据，留着无害 |
| 顺序 | 与上线相反：**先回前端，再回后端**（旧前端配新后端也安全） |

- 只回前端 = 索引条、悬浮字母头、虚拟列表、语言门槛一起消失，列表退回编码序，其余照旧。
- 只回后端 = 新前端降级（不画索引条/字母头），页面可用。

## 9. 未交付项（别在验收时找）

- **拼音搜索**（全拼 / 首字母缩写 / 工号 / 职务一次命中）：那是 `p10-org-structure-deepening.md`
  §4.3 的 M3（`core/services/directory_index.py` 的 `Membership.search_key` + `gin_trgm_ops`），
  **本次没做**。本次的搜索仍是姓名 / 邮箱子串匹配（就地筛选走客户端、Ctrl+K 走服务端）。
  两处拼音（`User.full_name_pinyin` 与将来的 `search_key`）的折叠规则要保持一致，否则同一人
  在两个功能里会落在不同桶里。
- **星标联系人没有 A–Z 索引**：星标走的是另一个端点（不支持拼音序），而且它本来就是短名单。
- **非拉丁、非汉字文字**（西里尔 / 日文假名 / 韩文 / 希腊文 / 阿拉伯文）统一进 `#` 桶并按该桶
  排在最后；日文汉字按**中文读音**归档（山田 → S，而非日语读音的 Y）。要做就得给每种文字一套
  首字母映射，属于独立功能。
- **虚拟化的代价**：屏幕外的行不在 DOM 里，浏览器「页内查找」与 Tab 顺序只看得到当前窗口
  （窗口总是覆盖整屏再多几行，不是更激进的一屏内）。
- **部门级「发起群聊」只拉直属成员**，不含子部门——整棵子树拉进来往往是几十人的大群，那是另一个决定。
