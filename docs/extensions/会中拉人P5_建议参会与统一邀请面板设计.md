# 会中拉人 P5 —— 参会人页对标飞书:建议参会 + 统一邀请面板详细设计

状态:已交付待实测(2026-07-19)——M1 后端 `356d0ace`(we-meet)、M2 Web `dd2ebb59`(we-meet)、M3+M4 App `453a9e2`(we-meet-android),全部编译/测试通过,APK 已打。2026-07-21(周一)实测。拍板记录:①方案整体通过;②M4 本期做(实勘后缩水为广播补 userId——dataChannel 收发 P4-M3 已有);③POST 上报权限=参会者皆可。
⚠️ 发布注意:M1 含迁移 0061_roominvitee,生产必须 helm upgrade 走 migrate hook,不能只换镜像。
背景:P4.1 已交付「会中拉人振铃」引擎(双端 `MeetInviteTracker` + 选人器 + kind=meet 信令),但 UX 信息架构与飞书差距明显:Android 参会人页零拉人入口(藏在「更多」第二排)、双端「分享链接」与「振铃拉人」两条独立路径、无「建议参会」概念。本设计对标飞书参会人页(截图实勘 2026-07-18),把已有引擎重新组织成飞书式信息架构。
原则:只扩展不修改;jusi-light-im 零改动(纯复用 P4 信令);Django 只增不改(1 新模型 + 1 新端点)。
已拍板(2026-07-18):①做到档3(完整对标飞书:建议参会 tab + 统一邀请面板 + 参会人页搜索);②呼叫交互保留「多选后确认」,建议参会页另有单人「呼叫」按钮(飞书同款)。

## 0. 一句话架构

「建议参会」= **房间受邀名单 − 已在场者**:受邀名单 = `ResourceAccess` 成员(日历预约会创建时已镜像,零改动白得) ∪ 新表 `RoomInvitee`(群发起会/会中拉人时由客户端幂等上报);已在场者用返回体自带的 `sub` 与 LiveKit participant identity 直接做差集(**免 resolve-subs**)。双端参会人页改为「搜索框 + 邀请按钮 + 全部/建议参会两个 tab」,建议参会行内单人呼叫复用 P4 `sendMeetInvites` 单目标调用;「邀请」按钮打开统一邀请面板(振铃选人 + 复制链接/会议号合一)。

## 1. 飞书语义基线(需求方 2026-07-18 给定,三场景)

| 场景 | 建议参会来源 | 我方数据链路 |
|---|---|---|
| 1. 日程预约会议 | 创建日程时添加的全部参会人(未入会者) | ✅ **今天就有**:`calendar.py perform_create` 建 Room 时把 invitee 既写 `EventAttendee` 又镜像 `ResourceAccess(member)`(实勘 2026-07-18) |
| 2. 群聊发起的会议 | 当前群内所有群成员 | ⚠️ 半有:发起端持 `groupCid`(Web `callController.ts:250` `groupCall={cid,slug}`;Android `CallController.kt:159` `GroupCallSession(cid,slug)`),且群里落了 `group-call` 消息绑定 slug↔群;但 **Django 不知道**这层关联 → 由发起端把选中群成员上报 `RoomInvitee` 补齐 |
| 3. 纯即时快速会议 | 无,恒为 0 | ✅ 天然成立:instant 房只有 owner 一条 `ResourceAccess`,owner 在场即被减掉 → 空列表 |

补充规则(同需求方给定):名单里的人**进入会议即从「建议参会」移到「全部」**(前端按 sub 差集实时计算,零信令);主持人/参会者可在建议参会页对单人**一键呼叫**。

## 2. 已验证的事实依据(实勘结论,2026-07-18)

1. **振铃引擎双端完备,纯复用**:Web `meetInviteTracker.ts`(`sendMeetInvites/cancelPendingMeetInvites`,valtio `meetInviteStore`)、Android `MeetInviteTracker.kt`(`ImSession.meetInvites`);逐人状态机 INVITING/RINGING/ACCEPTED/REJECTED/BUSY/UNREACHABLE/TIMEOUT/CANCELED/FAILED,3s×3 重发 + 60s 超时,未接落 call-log。本设计**不动这套状态机**。
2. **选人器双端完备**:Web `MeetInvitePicker.tsx`(搜索 + 多选 + `excludeUserIds`)、Android `core-directory/ContactPicker.kt`(Multi、300ms 防抖、`excludeUserIds`)。
3. **入口现状不对称**:Web 参会人面板已有「邀请成员」按钮(`ParticipantsList.tsx:93-131`)+ 通话舞台加人钮(`CallStage.tsx:345`);**Android 参会人 Sheet(`RoomScreen.kt:1422 ParticipantsSheet`)零拉人入口**,唯一入口在「更多」面板第二排(`RoomScreen.kt:2009`),另有通话升级入口(`RoomScreen.kt:527 showEscalatePicker`)。
4. **分享链接与振铃拉人两条独立路径**:Web `InviteDialog.tsx`(复制链接/电话 PIN,建会自动弹) vs `MeetInvitePicker`;Android `InviteSheet.kt`(二维码/复制/系统分享,顶栏会议号触发) vs `ContactPicker`。互不共享代码,用户心智割裂。
5. **User.sub 可下发**(`models.py:149`):LiveKit identity == OIDC sub(P4 §1 已证),suggested 返回体带 `sub` 即可与 `useParticipants()`/RoomScreen participants 直接差集,**免去 Web 现有 `resolve-subs` 往返**(现 `ParticipantsList.tsx:67-75` 为算 excludeUserIds 每次都要 POST resolve-subs)。
6. **Room 无 invitee 字段**:参会人建模只有 `ResourceAccess`(owner/administrator/member);`POST /rooms/` instant 房仅写 owner 一条(`viewsets.py:753`)。`/resource-accesses/` 管理接口仅 admin 可列,不适合做建议参会读取口。
7. **Django 无 call-log 落库、无「最近联系人」聚合口**;jusi 侧会话数据不在 Django。→ 首期建议参会**不做**「最近协作推荐」,仅按三场景规则(见 §7 不做清单)。
8. **跨端邀请可视化仅 Web 有**:Web 经 LiveKit dataChannel `MEET_INVITES_TOPIC` 广播「谁在被呼叫」(`Conference.tsx CallOrMeeting`),房内全员可见响铃 chip;Android 只显示本端发起的邀请(`RoomScreen.kt:247` collect `imSession.meetInvites`)。→ Android 补广播列 M4 可选项。

## 3. 方案对比与选型

### 3.1 「受邀名单」持久化载体(3 选 1)

| 方案 | 说明 | 判定 |
|---|---|---|
| A. 全走 `ResourceAccess` | 群发起/会中拉人也写 member 角色 | ❌ 副作用大:被拉人房间列表被污染(GET /rooms/ 列出相关房间)、白得房间权限;非 owner 参会者将有权给房间加成员,越权面扩大 |
| **B. 新表 `RoomInvitee` + 读取时 union(选定)** | 日历会走既有 ResourceAccess(零改动),群发起/会中拉人写新表;GET 端点 union 两表 | ✅ 只扩展不修改;新表无权限语义,纯「建议名单」;unique(room,user) 幂等;删房级联清理 |
| C. 客户端本地拼(不落库) | 发起端内存 groupCid + 群成员现拉 | ❌ 中途入会者(被振铃进来的人)拿不到群上下文,建议列表因人而异;刷新即丢;与飞书「全员一致可见」不符 |

### 3.2 「已在场」差集计算位置(2 选 1)

| 方案 | 说明 | 判定 |
|---|---|---|
| **A. 客户端差集(选定)** | GET 返回全量受邀名单(含 sub),客户端拿 LiveKit participants identity 集合实时相减 | ✅ 进房/离房即时反映(LiveKit 事件驱动),零轮询零信令;服务端无需感知在场状态 |
| B. 服务端差集 | 端点接收当前 identities 或查 LiveKit API | ❌ 服务端多一次 LiveKit 往返或信任客户端上报;实时性差(需轮询) |

### 3.3 统一邀请面板收敛策略(2 选 1)

| 方案 | 说明 | 判定 |
|---|---|---|
| **A. 渐进收敛(选定)** | M2/M3 新建统一面板(选人器 + 底部链接区),参会人页/舞台/「更多」入口全部指向它;建会自动弹的 `InviteDialog`/`InviteSheet` **暂保留原样**,待统一面板稳定后下线 | ✅ 建会自动弹时机在 IM client 未必就绪(picker 依赖目录/IM),强行合一有竞态;渐进无回归风险 |
| B. 一步到位全替换 | 所有入口含自动弹一次性换新面板 | ❌ 触碰建会首弹链路(`Conference.tsx:359 showInviteDialog` / `HomeScreen.kt:199`),回归面大,违背只扩展不修改 |

## 4. 后端设计(M1,唯一有迁移的阶段)

### 4.1 新模型 `RoomInvitee`

```python
class RoomInvitee(BaseModel):          # core/models.py 末尾新增
    room = models.ForeignKey(Room, on_delete=models.CASCADE, related_name="invitees")
    user = models.ForeignKey(User, on_delete=models.CASCADE, related_name="room_invites")
    invited_by = models.ForeignKey(User, null=True, on_delete=models.SET_NULL, related_name="+")
    source = models.CharField(max_length=16, choices=[("group","group"),("manual","manual")])
    # 日历来源不写本表(走 ResourceAccess),choices 不含 calendar
    class Meta:
        unique_together = [("room", "user")]
```

迁移注意:**生产发布必须 helm upgrade 走 migrate hook,不能只换镜像**(踩坑记录:只换镜像会漏迁移报 relation does not exist 500)。

### 4.2 新端点(挂 `RoomViewSet` `@action`,detail=True)

**`GET /api/v1.0/rooms/{id_or_slug}/suggested-participants/`**
权限:`IsAuthenticated` + 能 retrieve 该房间(复用现有房间访问判定)+ 组织隔离(`get_caller_organization`,跨组织成员不返回)。
返回(无分页,上限 200,超出截断):

```json
{ "suggestions": [
  { "id": "django-user-uuid", "sub": "oidc-sub", "full_name": "张三",
    "avatar_url": "signed-url-or-null", "title": "工程师", "department": "技术部",
    "source": "member | group | manual" }
] }
```

实现:`ResourceAccess.objects.filter(resource=room)`(source=`member`——房间成员表无法区分「日历镜像」还是「管理员手加」,统一诚实标 member;日历预约会即此来源)∪ `RoomInvitee.objects.filter(room=room)`;同人两表都有时 member 优先;人卡字段经「user_id 反查本组织 ACTIVE `Membership`」复用 `DirectoryMemberSerializer`——组织隔离与头像签发一并解决,无本组织成员身份者自然不出现。

**`POST /api/v1.0/rooms/{id_or_slug}/suggested-participants/`**
body `{"user_ids": ["..."], "source": "group|manual"}`;逐条 `get_or_create` 幂等;权限同 GET(参会者皆可上报——与「会中人人可拉人」口径一致,骚扰面由 P4 振铃侧 busy/reject/60s 超时天然兜底);同组织校验:非本组织 user_id 静默丢弃。

不动:`/resource-accesses/`、`calendar.py`、`/rooms/{id}/invite/`(邮件邀请)、jusi。

## 5. Web 设计(M2)

### 5.1 参会人页改造(`ParticipantsList.tsx`,结构重排)

```
┌ 参会人 ────────────────────┐
│ [🔍 搜索或呼叫____] [邀请]   │  ← 新:搜索框(本地过滤两 tab)+ 邀请按钮(开统一面板)
│ 〔全部 (N)〕〔建议参会 (M)〕  │  ← 新:tab 切换,数字实时
├─ 全部 tab ─────────────────┤
│ (现状三段:等待区/举手/参会者,│  ← 原封不动,仅包进 tab;搜索时按名字过滤
│  MuteEveryone 等 action 保留) │
├─ 建议参会 tab ──────────────┤
│ 👤 李四  产品部      [呼叫]  │  ← 未呼叫:单人立呼(sendMeetInvites 单目标)
│ 👤 王五  技术部   呼叫中⋯[✕] │  ← 自己发起:meetInviteStore 状态,可取消
│ 👤 赵六  设计部     响铃中⋯  │  ← 他人发起:MEET_INVITES_TOPIC 广播,置灰只读
│ 👤 钱七  市场部  未接听[再呼] │  ← rejected/timeout/busy 终态:可再次呼叫
│ (空态:「暂无建议参会人」)     │
└────────────────────────────┘
```

- 数据:`useQuery(['rooms', roomId, 'suggested-participants'])`,`staleTime 60s`;展示行 = suggestions − participants(按 `sub`===identity 差集,`useParticipants()` 驱动实时移除)− 自己。**删除现有 resolve-subs 查询**(§2.5,excludeUserIds 直接由 suggestions∩在场 + 在场者 sub 推得?否——picker 的 excludeUserIds 仍需全量在场者 id,保留 resolve-subs 仅供 picker 打开时懒查)。
- tab 徽标:全部 (N)=participants.length;建议参会 (M)=差集后行数(含呼叫中/未接,不含已入会)。
- 单人〔呼叫〕= `sendMeetInvites([target], {media:'video', roomSlug, roomName})`——P4 状态机原样,一人也是一路。
- 行状态映射:`meetInviteStore.invites` 按 userId 匹配 → inviting/ringing=呼叫中(可取消 `cancel`);终态 rejected/timeout/busy/unreachable=未接听/已拒绝/忙线 +〔再次呼叫〕;他端广播(MEET_INVITES_TOPIC)同 userId → 置灰「响铃中」。

### 5.2 统一邀请面板(新组件 `UnifiedInvitePanel.tsx`,features/rooms/components)

= `MeetInvitePicker` 内容(搜索+多选+确认振铃)+ 底部固定区:会议号、复制链接、(启用电话网关时)电话+PIN——即 `InviteDialog` 信息合入。确认振铃后追加 fire-and-forget `POST suggested-participants {user_ids, source:'manual'}`(失败静默,不阻塞振铃)。

- `startGroupVoiceCall`(`callController.ts:230`):建房成功后 fire-and-forget `POST suggested-participants {user_ids: targets, source:'group'}`——群发起会全员进建议名单(含未勾选的?**否**,按飞书语义应为「当前群内所有群成员」;但发起 picker 默认全选群成员,实际相等;若发起人手动取消勾选某人,该人仍属群成员应进建议——M2 简化为「以 picker 打开时的全量群成员列表上报」,GroupVoiceCallPicker 已持有该列表)。

## 7. 不做清单(本期明确出局)

1. **「最近协作/常邀对象」智能推荐**——Django 无 call-log 落库、jusi 无聚合口(§2.7),且三场景规则已覆盖飞书语义;后续真要做,走独立只读聚合端点另立项。
2. **建议参会「一键全呼」**——飞书无此钮(逐人呼/邀请面板多选已覆盖);防误触群体骚扰。
3. **「请求全员开麦」对标**(截图5 底栏)——非拉人范畴,另立项。
4. **忙闲(freebusy)显示**——日历侧有接口但参会人页首期不集成。
5. **25 人上限文案/加人卡**——商业化文案,无对应计费体系。
6. **自动弹窗换统一面板**——§3.3 渐进收敛,本期保留 InviteDialog/InviteSheet 首弹。

## 9. 风险与开放问题

1. **建议名单可见性口径**:选定「任何能进房者可见受邀名单」——受邀人姓名/职务对同组织参会者本就可见(通讯录公开),风险低;跨组织已隔离。
2. **POST 上报是客户端行为**:恶意端可塞名单——但仅影响建议列表展示(无权限授予),且限同组织,可接受;后续如需收紧改 owner-only。
3. **`ResourceAccess` 中日历受邀人退出日程**:日历侧删 attendee 会同步删 ResourceAccess(既有逻辑),建议列表自动一致;不一致场景留观察。
4. **Android ContactPicker 抽内容 composable**:需回归群聊建群/转发等既有调用方——加默认参数保证零行为变化,重点自测。
5. **建议参会 tab 与等待区(waiting)的关系**:waiting 是「敲门中」实体在场前状态,仍留在「全部」tab 顶部段(现状),不与建议参会混排——飞书同款分区。
