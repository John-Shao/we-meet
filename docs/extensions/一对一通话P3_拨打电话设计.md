# 一对一通话 P3 —— 拨打电话(系统拨号)

> 状态:设计评审中(隐私可见性待拍板,见 §7)
> 日期:2026-07-11
> 前置:P0 单聊通话面板已上线,「拨打电话」行当前置灰(`peerPhone=null`)。
> 范围:把对方手机号带到 App,点「拨打电话」拉起**系统拨号盘**(预填号码,
> 用户确认后拨出)。
> 不在本期:App 内 VoIP 直拨、Feishu 式「已通知对方呼叫请求」、Web 展示手机号
> (可选,见 §6)。

## 0. 一句话架构

**手机号权威副本在 Keycloak(`phoneNumber` 属性);登录时由
`post_get_or_create_user` 按 `User.sub` 反查并落到新增的 `User.phone`
(幂等自愈);经 serializer 按可见性策略下发;App 用 `ACTION_DIAL` 拉起
系统拨号盘。不碰 LiveKit、不发信令 —— 这是「跳转系统电话」,不是网络通话。**

涉及仓库:

| 仓库 | 改动 |
|---|---|
| `we-meet`(Django) | 迁移 `0056_user_phone` + 登录同步 + 2 个 serializer + 可见性 |
| `we-meet-android` | MemberDto.phone + 单聊拨号 + 资料页拨号 + `ACTION_DIAL` |
| `we-meet`(前端 Web) | 可选:资料/通讯录展示手机号(§6) |
| Keycloak | 无(phone 已在,登录时读取) |

## 1. 已验证的事实依据(实勘结论)

1. **手机号只在 Keycloak**:`User` 表无 phone 列;权威副本是 Keycloak 用户的
   `phoneNumber` 属性。OTP 登录时 Django 自发自验 OTP,**短暂持有明文
   phone**,但此刻 `User` 行常还不存在(OIDC 惰性创建)。
2. **读取范例现成**:`qr_login._get_keycloak_user_attrs(sub, sa_token)`
   已实现「按 sub 读 Keycloak 用户 dict(含 attributes.phoneNumber)」;
   底座 `_admin_realm_url` + `_get_service_account_token` 在 mobile_auth.py。
3. **落库点**:`OIDCAuthenticationBackend.post_get_or_create_user`
   (backends.py L49-74)此处已有 `User` 实例 + `sub`,与
   `ensure_default_org_membership` 同款「每次登录自愈」套路,是最稳的写入点。
   (verify-otp 处明文 phone 在手但 User 行未建,不适合。)
4. **User↔Keycloak 关联**:`User.sub` == Keycloak UUID。`im_uid` 是 jusi
   内部 uid,与 Keycloak 无关,**不能**用来读 phone。
5. **可见性零基础**:无好友模型、无字段级隐私、无用户自主开关。通讯录唯一
   边界是**同组织可见**(`get_caller_organization` + active `Membership`),
   外加 `is_self`。`Membership.org_role`(member/dept_admin/administrator/
   owner)是唯一可复用的角色抓手。
6. **Web 不展示手机号**:后端加 phone 字段不会破坏 Web(多余字段被忽略);
   要显示需 Web 同步(§6)。

## 2. 后端改动(Django)

### 2.1 模型 + 迁移
```python
# core/models.py User
phone = models.CharField(_("phone"), max_length=32, blank=True, default="")
```
迁移 `0056_user_phone`(default="" 避免 `BaseModel.save()` 的 full_clean 报错)。
`max_length=32` 容纳 `+86` 前缀与分隔符。

### 2.2 登录同步(权威读取)
`core/authentication/backends.py` `post_get_or_create_user`:
```
try:
    sa = _get_service_account_token()
    attrs = _get_keycloak_user_attrs(user.sub, sa).get("attributes", {})
    phone = (attrs.get("phoneNumber") or [""])[0].strip()
    if phone and phone != user.phone:
        user.phone = phone
        user.save(update_fields=["phone"])
except Exception:
    logger.warning(...)  # 静默:拿不到 phone 不能挡登录
```
- 幂等:每次登录自愈,Keycloak 改号后下次登录同步。
- **失败不挡登录**(phone 是增值信息,不是登录必需)。
- 复用 mobile_auth/qr_login 的 helper —— 需把 `_get_keycloak_user_attrs`
  从 qr_login 提到共享位置(或 backends 直接 import,注意循环依赖)。

### 2.3 序列化出口
- **`UserSerializer`**(serializers.py,GET `/users/me/`):加 `phone`。
  本人看自己,**无隐私问题**,恒返回。
- **`DirectoryMemberSerializer`**(directory.py,列表+详情共用):加
  `phone = SerializerMethodField()`,`get_phone` 按 §7 拍板的策略返回
  (本人恒可见;他人视策略,不可见时返回 `""` 或 `None`)。

## 3. Android 改动

### 3.1 数据
`MemberDto`(core-directory)加 `val phone: String? = null`
(对应 `DirectoryMemberSerializer.phone`)。读取侧 `getMember(userId)` 已有,
无需改接口。

### 3.2 单聊通话面板拨号
[ChatScreen.kt](../../../we-meet-android/.../ui/chat/ChatScreen.kt) 当前
`CallOptionsSheet(peerPhone = null, onDialPhone = {})`:
- 打开面板时用 `directoryRepository.getMember(peerUid)` 解析对方 `phone`
  (可在进会话时预取并缓存到 ChatUiState,避免点开面板才拉)。
- `peerPhone = 解析到的号码`(拿不到则仍置灰,面板不变)。
- `onDialPhone = { phone -> context.startActivity(Intent(ACTION_DIAL,
  Uri.parse("tel:" + Uri.encode(phone)))) }`。

### 3.3 资料页拨号(顺带)
[MemberDetailScreen.kt](../../../we-meet-android/.../ui/contacts/MemberDetailScreen.kt)
已用 InfoRow 展示 email/title:加一行「手机号」+ 一个拨号 affordance
(点号码或右侧电话图标 → `ACTION_DIAL`)。号码为空则不显示该行。

### 3.4 为什么用 `ACTION_DIAL` 而非 `ACTION_CALL`
- `ACTION_DIAL`:拉起系统拨号盘并预填号码,**用户确认后才拨**,
  **无需 `CALL_PHONE` 运行时权限**,合规、体验与飞书截图一致(弹「呼叫 +86…」)。
- `ACTION_CALL`:直接拨出,需危险权限,不采用。

## 4. 号码规范化
- 落库时存 Keycloak 原值(通常已是 11 位或带 `+86`)。
- 拨号前统一成可拨格式:去空格;`tel:` scheme 交给系统解析,`+`/`-` 系统能处理。
- 展示时可做 `138****1990` 脱敏(资料页看策略;拨号确认页由系统展示完整号)。

## 5. 边界
1. **对方无手机号**(设备账号、邮箱注册、Keycloak 无 phoneNumber):
   phone 为空 → 面板「拨打电话」保持置灰,资料页不显示手机行。
2. **对方不可见手机号**(§7 策略拒绝):后端返回空 → 同上,置灰。
3. **本机无电话能力**(平板/无 SIM):`ACTION_DIAL` 无 Activity 处理 →
   `try/catch` toast「设备不支持拨号」。
4. **老用户存量**:phone 靠登录同步,存量用户**下次登录**才有号;不做一次性
   回填脚本(可选:后续加 management command 批量拉 Keycloak)。

## 6. Web 同步(可选,产品决定)
后端出 phone 后,Web 要显示需:`ApiUser` / `DirectoryMember` 两个 interface
加 `phone`;AccountTab / 通讯录卡片加展示位。**App-first 需求,Web 可暂不做**
(不影响后端)。Web 无系统拨号,展示为「可复制的号码」即可。

**⚠️ 已知后续项 — Web 端 `phone-viewed` 号主渲染**:若号主在 **Web** 上,
Android 揭示其号码后投递的 `phone-viewed` 系统消息,Web 前端当前不识别该
content_type,会渲染为「[不支持的消息]」。两端都在 App 时无此问题。补齐需在
Web 前端消息渲染 switch 加 `phone-viewed` 分支(方向渲染「对方查看了你的手机
号码」/「你查看了对方的手机号码」),与 P1 call-log 的 web 渲染同款。已在
Android 侧完成对应渲染([MessageContent.kt] PhoneViewed)。

## 7. 可见性策略(已拍板 2026-07-11)

**同组织可见 + 默认掩码 + 显式揭示 + 揭示即通知号主。**

- **同组织可见**:同一 organization 的成员互相可见对方手机号(`is_self`
  恒可见);非同组织 / 无号 → 空,拨打置灰。
- **默认掩码**:通讯录 / 资料页 / 通话面板拿到的是**掩码号**
  `138****1990`(前 3 后 4 明文,中间 4 位 `*`);全号**不随列表下发**。
- **显式揭示**:用户点【显示】(或点「拨打电话」——拨号需全号,等同揭示)才
  取全号。
- **揭示即通知**:一次成功揭示,**服务端**经 jusi 桥接往两人**直聊**投一条
  `phone-viewed` 系统消息,sender = 查看者;号主一侧渲染「对方查看了你的
  手机号码」。

### 7.1 掩码 / 揭示 / 通知机制

**掩码(serializer 侧)**:`DirectoryMemberSerializer.get_phone` 与
`UserSerializer` 对**他人**一律返回掩码;本人(`is_self`)返回全号。掩码函数:
保留前 3 后 4,中间统一 4 个 `*`(号长不足则整体掩码)。→ 全号在批量列表里
**永不出现**,杜绝 curl 拉全组织通讯录导出号码库。

**揭示端点(全号唯一出口)**:
```
POST /api/v1.0/directory/members/{user_id}/reveal-phone/
  权限: 已登录 + 与目标同组织(复用 get_caller_organization)
  行为:
    1. 校验同组织,取目标 User.phone(全号);无号 → 404/空
    2. 经 jusi 桥接投递系统消息(见下),失败不阻断返回(通知是尽力而为)
    3. 返回 { "phone": "<全号>" }
```

**通知(服务端发,可靠)**:复用 `core/services/jusi_im.py`:
- `create_direct(cid=det_cid, owner_uid, peer_uid)` 确定性 cid(排序 im_uid),
  create-or-get 直聊会话;
- `post_message(cid, body, content_type="phone-viewed")`,**sender = 查看者的
  im_uid**;body 可空(文案由端上按类型渲染)。
- 号主端 IM 收到该消息 → 按 `content_type=phone-viewed` + **isOwn 方向**渲染:
  号主(接收方)显示「对方查看了你的手机号码」;查看者(发送方)显示「你查看
  了对方的手机号码」或隐藏。**与 P1 call-log 同款方向渲染**,加一个
  `MessageContent.PhoneViewed` 变体即可。
- 该类型加入 `NON_BUMPING`(不顶会话列表、不计未读——它是提示不是对话)。

> 揭示口径:**任何取到全号的动作都通知**(点【显示】或点「拨打电话」)——
> 通知语义是「有人访问了你的完整号码」,拨号本身就需要全号,故一并计入。
