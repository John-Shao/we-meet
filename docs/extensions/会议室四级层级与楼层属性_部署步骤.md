# 会议室四级层级与楼层属性 — 部署步骤

## 发布前

- 备份 PostgreSQL，重点确认 `meet_meeting_room_node`、`meet_meeting_room` 和 `meet_meeting_room_booking` 可恢复。
- 告知管理员：升级会物理删除现有会议室、会议室预订和整棵会议室层级树，上线后需要重新创建层级和会议室。
- 记录仍在使用的会议室名称、编号、容量、设施和预订策略，便于升级后重建。

## 数据迁移

先执行 Django migration `0088_retire_legacy_meeting_room_hierarchy`，再执行 `0089_meeting_room_floor_attribute`。`0089` 会物理删除全部现有会议室（预订随外键级联删除）和整棵会议室层级树，然后为会议室增加必填的 `floor` 属性；日历事件保留。

该迁移不提供反向恢复。需要回滚数据时应恢复发布前数据库备份，不能只执行 `migrate` 回退。

## 上线后重建

1. 进入 `/admin/meeting-rooms`，从空态开始创建国家/地区。
2. 依次创建城市、园区、建筑；城市必须选择 IANA 时区。
3. 选中第 4 级建筑后添加会议室，填写必填楼层，并恢复编号、容量、设施和预订策略。
4. 员工端验证层级树、会议室搜索、可用性、时间轴和日历预订。

## 验收查询

```sql
SELECT depth, count(*)
FROM meet_meeting_room_node
WHERE deleted_at IS NULL
GROUP BY depth
ORDER BY depth;

SELECT count(*)
FROM meet_meeting_room r
JOIN meet_meeting_room_node n ON n.id = r.node_id
WHERE r.deleted_at IS NULL AND n.depth <> 3;
```

第一条查询仅应出现 `0` 至 `3`；第二条必须返回 `0`。再确认所有新会议室的 `floor` 均为非空。升级前的会议室和会议室预订已不可恢复，除非还原发布前数据库备份。
