# 一对一通话 P2 —— 离线推送来电 + 全屏来电 + 回铃音

> 状态:设计评审中
> 日期:2026-07-10
> 前置:P1 已上线并跨端验证通过(Go `340d046` / SDK alpha.9 / web `e0b2ad2e` / android `a05d5f2`)
> 范围:被叫 **Android App 离线(WS 断)时也能收到来电**;来电全屏体验;主叫回铃音。
> 不在本期:iOS、Web 浏览器推送、拨打电话(P3)、通知栏内直接接听/拒接按钮(P2.5 见 §9)。

## 0. P1 遗留的体验缺口

P1 的振铃完全依赖 WS 在线:被叫 App 被杀 / WS 断时,服务端直接给主叫回
`unreachable`(「对方不在线」),被叫对这次呼叫**毫无感知**(只能事后看
call-log)。P2 把这条路补上:被叫离线 → 走个推唤醒/通知,手机照样响。

## 1. 关键前提(实勘结论)

1. **透传消息到不了冷杀进程**(`push_send.py` 注释记录的线上教训):
   `onReceiveMessageData` 需要 App 进程存活;冷杀后只有**厂商通道的通知消息**
   能投达。这决定了呼叫推送必须**双通道**:
   - 个推通道·透传(`push_message.transmission`)→ 进程活着:代码接管,
     全屏来电 + 铃声,体验最佳;
   - 厂商通道·通知(`push_channel.android.ups.notification`)→ 冷杀:
     通知栏高优通知(来电渠道,响铃),点击拉起 App 进入来电页。
   个推 v2 **单条请求可同时携带两者**,在线走透传、离线走厂商,互斥投达。
2. 现有链路可完整复用:jusi webhook(HMAC)→ Django `ImPushHookView` →
   `push_send.py` → 个推 REST v2。呼叫只是加一种 payload 类型。
3. Go 侧 `handleCall` 目前对离线被叫短路回 `unreachable`
   (handlers_call.go);P2 改为:**Push 已配置 → 触发呼叫 webhook、不回
   unreachable**(主叫继续响铃等推送唤醒的被叫);未配置 → 维持现状。
4. WS 无离线缓冲:被叫被唤醒后,原始 invite 帧已丢——**推送 payload 必须
   自带完整呼叫信息**(call_id/cid/caller/media/room_slug/ts),客户端据此
   直接落入 Incoming 态,不依赖重收 invite。
5. 主叫 invite 有 3s×3 重发:Go 侧呼叫 webhook 必须按 call_id 去重,
   否则一次呼叫触发 4 条推送。

## 2. 端到端时序

```
主叫A            jusi(Go)              Django              个推            被叫B(App杀死)
 |--invite-->  presence(B)==""
 |             按call_id去重 --webhook(type=call)--> 校验HMAC
 |             (不回unreachable)         解析B的User→tokens --双通道push-->
 |                                                            厂商通道通知(来电渠道,响铃)
 |                                                                 |  用户点通知
 |                                                            App冷启,deeplink wemeet://call?...
 |                                                            CallController.seedIncoming(payload)
 |                                                            新鲜度校验(60s-age剩余振铃)
 |                                                            全屏来电页 + 铃声
 |                                                                 |  用户点接听
 |<------------accept(WS,连上后带重试)---------------------------|
 |  进房                                    GET /rooms/{slug} → token,进房
```

进程活着但 WS 恰好断开的中间态:透传直达 `onReceiveMessageData` → 直接
`seedIncoming` + 全屏 intent 通知,不经通知栏点击,体验与在线振铃一致。

被叫接听前主叫取消:cancel 帧对离线被叫会丢。兜底已天然存在——主叫
cancel 时 endRoom,被叫接听 → `resolveCallRoom` 发现房间已关 → 「通话已
结束」。厂商通道的残留通知无法撤回(个推 recall 仅部分厂商支持),接受。

## 3. 推送 payload(个推透传体 与 deeplink 共用同一 JSON)

```json
{
  "type": "call",
  "call_id": "uuid",
  "cid": "direct 会话 id",
  "from": "主叫 jusi uid",
  "from_name": "主叫显示名(Django 解析 User.full_name)",
  "media": "audio | video",
  "room_slug": "83920417",
  "ts": 1720600000000
}
```

- `ts` 为 Go 发起 webhook 的 unix-ms。客户端**新鲜度校验**:
  `age = now - ts`,`age ≥ 55s` 直接丢弃(呼叫早已超时);否则剩余振铃
  时长 = `60s - age`。
- 个推 `settings.ttl = 55000`(55s):过期不补投,杜绝「几分钟后手机才响」。
- 厂商通道通知:`channel_id = "im_calls"`(新渠道,IMPORTANCE_HIGH,系统
  铃声),title「语音/视频通话邀请」,body「{from_name} 邀请你进行语音通话」,
  click_type=intent → `wemeet://call?payload=<urlencoded json>`(与 IM 推送
  同款显式 component intent 写法,注意个推对隐式 intent 静默丢弃的坑)。
- 通知 `notify_id` 用 call_id 哈希:同一呼叫的重复推送互相替换。

## 4. 各仓库改动

### 4.1 jusi-light-im(Go)

1. `push.Service` 增加 `CallInvitePublished(callID, cid, callerUID, calleeUID,
   media, roomSlug string)`:
   - **按 call_id 去重**(带 TTL 的小 map,90s 过期),invite 重发不重推;
   - 构造 `{type:"call", ...上表字段, ts}` webhook,复用现有 HMAC 签名/重试
     /队列(与消息推送同 URL `/api/agent/push-hook/`)。
2. `hub.go` 的 `PushNotifier` 接口加该方法;`handlers_call.go` invite 分支:
   ```go
   if node == "" {
       if h.deps.Push != nil {
           h.deps.Push.CallInvitePublished(...)   // 离线→推送唤醒,主叫继续等
       } else {
           writeFrame(unreachable)                 // 无推送→维持 P1 行为
       }
       return  // 两种情况都不再走 UserChannel 投递
   }
   ```
3. 单测:去重(同 call_id 4 次 invite 只 1 次 webhook)、Push 为 nil 回退
   unreachable、webhook payload 字段。

### 4.2 Django(we-meet)

1. `ImPushHookView` 不变(HMAC 通吃);`notify_offline` 入口按
   `payload["type"]` 分流:缺省/`"im"` → 现逻辑;`"call"` → 新函数
   `notify_call(payload)`。
2. `notify_call`:
   - `callee_uid → User(im_uid) → DevicePushToken`(与现逻辑同构);
   - `from_name`:`caller_uid → User.full_name`(取不到则「对方」);
   - `GetuiClient` 增加 `push_call_to_cid(cid, payload)`:
     `push_message.transmission = <payload JSON>`(在线透传)+
     `push_channel.android.ups.notification`(离线厂商通知,`im_calls` 渠道,
     intent 深链 `wemeet://call?...`)+ `settings.ttl = 55000`。
3. 复用 `PUSH_CONFIGURATION`,无新配置项、无迁移。

### 4.3 Android(we-meet-android)

1. **Manifest**:`USE_FULL_SCREEN_INTENT` 权限;`wemeet://call` 已被现有
   `wemeet` scheme intent-filter 覆盖(确认)。
2. **`WeMeetGtIntentService`**:`"call"` 分支 → 解析 payload → 新鲜度校验 →
   `showCallNotification()`:`im_calls` 渠道(HIGH,系统铃声+震动),
   `CATEGORY_CALL` + `setFullScreenIntent(pending, true)`(锁屏/灭屏直接拉起
   MainActivity;亮屏时 heads-up)。intent = `wemeet://call?payload=...`。
   同时若进程内 ImSession 已存在,直接 `calls.seedIncoming(payload)`
   (透传到达=进程活着,不必等用户点通知)。
3. **`MainActivity.handleDeepLink`**:新增 `wemeet://call` → 写
   `app.pendingIncomingCall`(仿 pendingChatCid);AppNav 收集 →
   `ImSession.get(app).calls.seedIncoming(payload)` —— 之后**复用现有机制**:
   状态进 Incoming → 既有 collector 自动推 IM_CALL 全屏页 → 铃声/接听/拒接
   全部照旧。
4. **`CallController.seedIncoming(payload)`**:
   - 仅 Idle 时接受;call_id 已终结/不新鲜(≥55s)→ 丢弃;
   - 落 Incoming,振铃超时 = `60s - age`;
   - **accept 的 WS 重试**:seed 场景 WS 可能还在连接,accept/ringing 帧
     发送失败时以 1s 间隔重试 ≤5 次(HTTP 的 resolveCallRoom 不受影响);
   - 收到迟到的真 invite(主叫重发)→ 现有幂等分支已回 ringing,天然补上
     主叫侧的「等待接听」回执。
5. **通知清理**:seedIncoming 后取消 call 通知;终态(cancel 超时/接听)
   同步取消。

### 4.4 回铃音(主叫侧,Android + Web)

- 国标回铃音:**450Hz,响 1s / 停 4s** 循环。
- 开始:`waitingAnswer == true`(收到被叫 ringing 回执后);结束:离开
  Outgoing 态。离线推送场景被叫未上线前无 ringing 回执 → 主叫静默等待,
  符合直觉(对方还没响铃)。
- Android:`ToneGenerator(STREAM_VOICE_CALL, TONE_SUP_RINGTONE)` 或
  AudioTrack 450Hz 正弦,挂在 CallScreen Outgoing 的 DisposableEffect;
- Web:CallOverlay 现有 WebAudio 基建加 `RingbackSound`(450Hz 起停包络)。

## 5. 多端语义(本期边界)

推送**仅在被叫全端离线**(presence 为空)时触发。「手机 App 被杀但 Web
在线」→ WS 正常振铃 Web,手机**不响**——飞书是全端都响,本期不做
(需要 Go 把每次 invite 都旁路一份推送 + 客户端对「已在别端处理」撤通知,
复杂度显著上升),列为 P2.5 候选。

## 6. 边界与竞态

1. **推送到达时用户已在通话中**:seedIncoming 非 Idle → 丢弃(通知也清)。
2. **通知点击时呼叫已超时**:新鲜度校验丢弃 + toast「通话已结束」,App 正常
   打开落在消息页。
3. **双设备都离线**:两台都收到推送、都响;先接听者 accept,后接听者
   resolveCallRoom 仍会成功(trusted 房)→ 三人同房?否——被叫两端同
   call_id,后接的那端在 accept 前会收到先接端 accept 的回声(若 WS 已连)
   → answeredElsewhere;若 WS 未连收不到回声,则确实可能双端都进房。
   接受为已知边界(概率低,房间行为也无害),P2.5 可在服务端记 call 终态拒
   第二个 accept。
4. **Getui 冷杀可达性**:依赖厂商通道配额/机型策略,不保证 100% 送达
   (无 FCM 兜底是既有架构约束)。推送失败的呼叫回落为 P1 行为(超时+
   call-log),无新增故障面。

## 7. 测试计划

- Go 单测:webhook 去重 / Push nil 回退 / payload 字段。
- Django 单测:type 分流、from_name 解析、双通道消息体。
- 实机矩阵(Android 被叫):
  ① App 前台在线(对照,走 WS 不推送);② App 后台进程活+WS 断(透传→
  全屏来电);③ App 冷杀(厂商通知→点击→来电页→接听进房);④ 冷杀+主叫
  中途取消(接听→「通话已结束」);⑤ 冷杀+不理会(55s 后通知不再响,主叫
  超时 call-log);⑥ 回铃音:Android/Web 主叫在被叫响铃后听到 450Hz 回铃。
