## 0. 本次变更范围

| 仓库 | 分支 @ 提交 | 变更 | 部署动作 |
|---|---|---|---|
| `we-meet` | `aliyun-dev` @ `96428351` | **后端**：管理端 serializer 暴露预订限制、列表筛选、`retrieve`；C 端房间可见性按预定范围过滤；日历 serializer 校验时长/提前天数/范围。**前端**：运营台会议室列表页重做、会议室详情页、设施字典管理弹窗 | build `backend frontend` → rollout 两个 deploy（**无 helm upgrade**） |
| `we-meet-android` | — | 无变更 | **无需操作** |
| `jusi-light-im` | — | 无变更 | **无需操作** |

**顺序依赖：后端必须先于前端就绪。** 新前端的详情页要 `GET /admin/meeting-rooms/{id}/`，
旧后端没有 `RetrieveModelMixin`，会返回 **405**；预订限制字段在旧后端也不存在，
详情页会把空值当「无限制」显示。反过来「新后端 + 旧前端」是安全的（纯新增字段）。

## 3. 阶段 B — 生产 ECS：rollout（后端先，前端后）

生产 values 是 `tag: latest` + `pullPolicy: Always`，`rollout restart` 会重新拉取
刚推上去的 latest，不需要改 tag。

- [ ] 先滚后端，**等它 ready 再滚前端**（见第 0 节的顺序依赖）：

  ```bash
  kubectl -n meet rollout restart deploy/meet-backend
  kubectl -n meet rollout status  deploy/meet-backend --timeout=180s
  ```

- [ ] 后端就绪后再滚前端：

  ```bash
  kubectl -n meet rollout restart deploy/meet-frontend
  kubectl -n meet rollout status  deploy/meet-frontend --timeout=180s
  ```

- [ ] 确认没有意外的待落迁移（应为空，纯保险）：

  ```bash
  kubectl -n meet exec deploy/meet-backend -- python manage.py showmigrations core | grep -c "\[ \]"
  # 期望：0
  ```

## 4. 后端冒烟（约 2 分钟）

用 org admin 账号取 `<access_token>`：

```bash
TOK=<access_token>
BASE=https://meet.we-meet.online/api/v1.0
ROOM=<任意一间已存在会议室的 uuid>

# 新增的 retrieve 端点（P9 首发时是 405）
curl -s -o /dev/null -w "%{http_code} admin-room-detail\n" \
  -H "Authorization: Bearer $TOK" "$BASE/admin/meeting-rooms/$ROOM/"

# 详情响应里应带上四个预订限制字段
curl -s -H "Authorization: Bearer $TOK" "$BASE/admin/meeting-rooms/$ROOM/" \
  | python -m json.tool | grep -E "booking_scope|bookable_departments|max_booking_minutes|advance_booking_days"

# 新增的列表筛选
curl -s -o /dev/null -w "%{http_code} filter-active\n"   -H "Authorization: Bearer $TOK" "$BASE/admin/meeting-rooms/?is_active=1"
curl -s -o /dev/null -w "%{http_code} filter-capacity\n" -H "Authorization: Bearer $TOK" "$BASE/admin/meeting-rooms/?capacity_min=10"

# 顺带修掉的 500：非 uuid 的 node 参数
curl -s -o /dev/null -w "%{http_code} bad-node(期望200)\n" \
  -H "Authorization: Bearer $TOK" "$BASE/admin/meeting-rooms/?node=not-a-uuid"

# 既有 C 端接口不受影响
curl -s -o /dev/null -w "%{http_code} c-rooms\n" -H "Authorization: Bearer $TOK" "$BASE/meeting-rooms/"
```

- [ ] retrieve 200、四个字段都在、两个筛选 200、`bad-node` **200 而非 500**、C 端 200

## 5. ⚠️ 本次最大的回归面：C 端会议室可见性

C 端 `/meeting-rooms/` 的 `get_queryset` 新增了「按预定范围过滤」。既有房间的
`booking_scope` 默认是 `org`，理论上可见性零变化——但这是全体员工选会议室的入口，
**值得单独核一眼**，别让一次运营台改动把订房功能悄悄关掉。

- [ ] 确认存量数据确实都是 `org`：

  ```bash
  kubectl -n meet exec deploy/postgresql -- \
    psql -U meet -d meet -c \
    "SELECT booking_scope, count(*) FROM meet_meeting_room WHERE deleted_at IS NULL GROUP BY 1;"
  # 期望：只有一行 org | N
  ```

- [ ] 用**普通员工**账号（非 admin）建日程 → 「添加会议室」→ **能看到全部会议室**，
      数量与上线前一致

任一不符 → `kubectl -n meet rollout undo deploy/meet-backend`，不放行。

## 7. 三条预订限制的端到端验证（约 10 分钟）

挑一间**测试用**会议室做，验完记得改回不限。

- [ ] **时长上限**：详情页设「单次可预定时长上限 = 60 分钟」→ 保存 →
      C 端建一场 2 小时的会并选这间 → **保存被拒**；改成正好 60 分钟 → **能订上**（闭区间）
- [ ] **最早可提前**：设为 7 天 → 建一场 30 天后的会选这间 → **保存被拒**
- [ ] **可预定范围**：设为「指定部门」并只勾一个部门 →
      - 该部门（**或其下级部门**）的员工：**看得到也订得上**
      - 其它部门的员工：选择器里**根本看不到这间房**（不是能选但报错）
- [ ] 验完把三项都清空（时长/天数留空 = 不限，范围改回「全部成员」）

> **已知行为，不是 bug**：范围限制**没有管理员豁免**。若把某间房限定给某部门，
> 而管理员自己挂在组织级（无部门），管理员在 C 端也会看不到那间房——运营台是改
> 规则的地方，不是坐在规则外面的地方。要「会议室预定管理员」那种高权限角色，
> 是独立一档权限模型，另行排期。

## 8. 观察面（上线后 24h）

- [ ] `/api/v1.0/meeting-rooms/` 的返回条数：若某个组织突然掉到 0，查是不是有人
      误把房间设成了部门限定
- [ ] 日历创建接口的 400：新增了三类校验，`meeting_room_id` 字段上的 400 是正常
      业务信号（用户撞到了限制），不是错误
- [ ] `/admin/meeting-rooms/?facilities=` 带多个设施时走了 `distinct()`，房间数上来
      后留意该查询耗时

## 9. 回滚预案

| 对象 | 方式 |
|---|---|
| 后端 | `kubectl -n meet rollout undo deploy/meet-backend` |
| 前端 | `kubectl -n meet rollout undo deploy/meet-frontend` |
| **迁移** | **不涉及**——本次无迁移 |
| 已配置的限制数据 | 回滚后旧代码不读 `max_booking_minutes` 等列，限制**自动失效**但数据不丢；重新上线即恢复 |

回滚顺序与上线相反：**先回前端，再回后端**（旧前端配新后端是安全的，反过来会 405）。
