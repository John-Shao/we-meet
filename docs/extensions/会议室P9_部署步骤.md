## 1. 迁移画像（已用 `sqlmigrate` 核对，风险极低）

| 迁移 | 实际 SQL | 风险 |
|---|---|---|
| `0063_btree_gist_extension` | `CREATE EXTENSION IF NOT EXISTS "btree_gist";` | 幂等；`btree_gist` 自 PG 13 起是 **trusted extension**，生产是 PG 16.4，且同一 DB 用户在 `0002` 已建过 `pg_trgm`——**无新增权限要求** |
| `0064_meeting_rooms` | 6 张新表（4 模型 + 2 张 M2M）+ 索引 + 约束，排斥约束内联在 `CREATE TABLE` 里 | **纯新增**，不改任何既有表结构（只从新表向既有表加 FK），无表重写、无锁等待 |
| `0065_alter_auditlog_action_meeting_rooms` | `-- (no-op)` | choices 只是 Django 校验层，`max_length` 未变，**数据库层零动作** |

⇒ 无需停机、无长事务、无数据回填。

## 3. 阶段 B — 生产 ECS：pull → **helm upgrade** → rollout

- [ ] 拉代码：

  ```bash
  cd /opt/we-meet && git pull origin aliyun-dev
  ```

- [ ] **helm upgrade（触发 migrate hook，必须先跑）**：

  ```bash
  helm upgrade --install meet ./src/helm/meet \
    -n meet \
    -f ./src/helm/env.d/common.yaml.gotmpl \
    -f ./src/helm/env.d/aliyun-prod/values.meet.yaml \
    -f ./src/helm/env.d/aliyun-prod/values.secrets.yaml \
    --wait --timeout 15m
  ```

  > 生产是 `tag: latest`，只 `rollout` 不 `helm upgrade` **不会跑迁移**，
  > 访问会议室相关接口会报 `relation "meet_meeting_room" does not exist` 500。

- [ ] 再 rollout（新代码才服务）：

  ```bash
  kubectl -n meet rollout restart deploy/meet-backend deploy/meet-frontend
  kubectl -n meet rollout status  deploy/meet-backend  --timeout=120s
  kubectl -n meet rollout status  deploy/meet-frontend --timeout=120s
  ```

- [ ] **确认迁移已落**：

  ```bash
  kubectl -n meet exec deploy/meet-backend -- python manage.py showmigrations core | tail -5
  # 期望三行都是 [X]：
  #   [X] 0063_btree_gist_extension
  #   [X] 0064_meeting_rooms
  #   [X] 0065_alter_auditlog_action_meeting_rooms
  ```

  若仍是 `[ ]`（hook 没跑成），**在新后端 pod 就绪后**手动兜底：

  ```bash
  kubectl -n meet exec deploy/meet-backend -- python manage.py migrate --no-input
  ```

- [ ] **确认排斥约束真的建上了**（这是防重订的全部依仗，值得单独看一眼）：

  ```bash
  kubectl -n meet exec deploy/postgresql -- \
    psql -U meet -d meet -c "\d meet_meeting_room_booking" | grep -i exclude
  # 期望：\"mrbooking_no_overlap\" EXCLUDE USING gist (room_id WITH =, tstzrange(...) WITH &&) WHERE (...)
  ```

  > 若这行不存在（例如 `btree_gist` 建失败被吞），**防重订就是失效的**，
  > 表面功能正常但会出现两个人订到同一间。必须修复后再放行。

## 4. 后端冒烟（约 3 分钟）

用 demo 手机号取 `<access_token>`：

```bash
TOK=<access_token>
BASE=https://meet.we-meet.online/api/v1.0

# 新端点应 200（此时数据为空，返回空列表是正确的）
curl -s -o /dev/null -w "%{http_code} nodes\n"      -H "Authorization: Bearer $TOK" "$BASE/meeting-room-nodes/"
curl -s -o /dev/null -w "%{http_code} facilities\n" -H "Authorization: Bearer $TOK" "$BASE/meeting-room-facilities/"
curl -s -o /dev/null -w "%{http_code} rooms\n"      -H "Authorization: Bearer $TOK" "$BASE/meeting-rooms/"

# 参数校验应 400（证明 availability 走到了业务逻辑而非 500）
curl -s -o /dev/null -w "%{http_code} availability-no-window(期望400)\n" \
  -H "Authorization: Bearer $TOK" "$BASE/meeting-rooms/availability/"

# 既有日历不受影响
curl -s -o /dev/null -w "%{http_code} calendar\n" -H "Authorization: Bearer $TOK" "$BASE/calendar-events/?page_size=1"
```

- [ ] 五项均符合预期（前三 200、第四 400、第五 200）

## 8. 端到端冒烟（真机 + Web 对端，约 15 分钟）

按顺序走，每一步都是一个曾经出过问题的点：

- [ ] **正常预订**：Web 建日程 → 选会议室 → 保存 → 详情显示「🏢 会议室: xxx · 层级」
- [ ] **防重订（核心）**：另一账号建**同一时段同一间** → 应弹「已被订走」，且**日程没有被创建**
- [ ] **背靠背不算冲突**：10:00–11:00 已订，建 11:00–12:00 同一间 → 应能成功
- [ ] **改期跟随**：把已订房的日程改到别的时段 → 时间轴上的块跟着移动
- [ ] **编辑不自撞**：编辑已订房的日程但**不改时间**（只改标题）→ 不该报会议室冲突
- [ ] **清空预订**：编辑 → 点会议室 chip 的 ×→ 保存 → 详情不再显示会议室，时间轴释放
- [ ] **删除释放**：删掉日程 → 时间轴上该时段变空
- [ ] **重复日程**：建每周重复 + 选会议室 → 保存成功；等 beat 物化后（或手动
      `kubectl -n meet exec deploy/meet-backend -- python manage.py send_due_reminders`）
      看子场次是否也占上房
- [ ] **全天日程**：勾「全天」→ 会议室区块变成灰字说明，不可选（服务端也会 400）
- [ ] **时间轴**：会议室 Tab → 看到房间行与占用块；当天有红色当前时间线；点空档能带着时段开建日程
- [ ] **隐私**：把日程设为 private，用**非参与人**账号看时间轴 → 只显示「已预订」+ 组织者，不显示标题
- [ ] **App 端**：建日程 → 「添加会议室」sheet →「可用/全部」分段、筛选、点行即选 → 保存 → 详情显示
- [ ] **App 撞车**：App 上选一间 Web 已订走的 → 提示「刚被他人订走」而非泛化的保存失败

任一失败 → 记 `kubectl -n meet logs deploy/meet-backend --tail=200` / `adb logcat`，不放行。

## 9. 观察面（上线后 24h）

- [ ] 后端日志里 `meeting room %s unavailable for event` 是 **INFO 级正常业务信号**（重复日程
      跳过冲突场次），不是错误，不必告警
- [ ] `409` 响应量：正常业务信号（有人抢同一间）。若异常高，多半是某间热门会议室，不是 bug
- [ ] `timeline` 的 400：窗口 >7 天或房间 >200 会拒绝。若前端触发了，说明筛选没收窄
- [ ] 慢查询：`meet_meeting_room_booking` 上的范围查询走 `mrbooking_room_start_idx`；
      房间数上来后留意 `availability` 的响应时间

## 10. 回滚预案

| 对象 | 方式 |
|---|---|
| 后端 | `kubectl -n meet rollout undo deploy/meet-backend` |
| 前端 | `kubectl -n meet rollout undo deploy/meet-frontend` |
| **迁移** | **不需要回滚**。`0064` 是纯新增表，旧代码根本不认识它们；`0065` 数据库层是 no-op；`0063` 只是装了个扩展。旧代码跑在新库上完全正常 |
| App | 停止分发，重发上一版 APK |

> 反过来说：**已经产生的预订数据在回滚后会失去入口**（旧代码不读那些表），但数据不丢，
> 重新上线即恢复。若要彻底清场再来一遍，`0064` 是可逆的（`migrate core 0063`）。

## 11. 已知风险

| 风险 | 应对 |
|---|---|
| 只 `rollout` 没 `helm upgrade` → 漏迁移 | 第 3 节 `showmigrations` 三行必须 `[X]` |
| `btree_gist` 建失败但迁移被吞 → **防重订静默失效** | 第 3 节最后一步单独 `\d` 确认 EXCLUDE 约束存在 |
| 上线后没人建层级/会议室 → 用户以为功能坏了 | 第 6 节运营初始化，建议与发布同一时间窗完成 |
| App 先于后端分发 | 旧后端静默忽略 `meeting_room_id`，选了等于没选 → 严格按 3 → 7 顺序 |
| 重复日程超出 60 天物化窗口的场次没占上房 | 已知语义（见设计文档），非缺陷；必要时向用户说明「超出范围需重新预订」 |
| 设施字典无 Web 管理界面 | M1 过渡走 Django admin；M2 补 |
