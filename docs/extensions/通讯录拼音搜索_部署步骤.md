## 1. 为什么能覆盖所有入口而不用改前端

`q` 这个参数已经被 Web 通讯录筛选、Web 全局搜索的联系人分类、Web 选人器、App 搜索、
App 选人器**全部**在用了（同一个 `/directory/members/?q=`）。所以这次只改**服务端**把
`q` 的匹配面扩大一行,以上入口自动获得拼音搜索 —— 前端唯一要做的是把占位文案改对,
别让「输入拼音」这个能力没人知道。

## 2. 迁移画像

`core/migrations/0145_user_search_key.py`:

1. `AddField`：`User.search_key`（`max_length=255`、默认空串）；
2. `RunPython(backfill_search_keys)`：整表回填（`bulk_update`，500/批）。算法是冻结副本，
   与 `core/services/pinyin.py` 的 `pinyin_search_key` 一致（有对齐测试）。

**为什么没有索引**（写在这里是为了不让后人「好心」补上）：`?q=` 是一条跨 5 列的 OR
（姓名/简称/邮箱/职位/部门名）+ 新加的这一支；而且 `icontains` 在 Postgres 上是
`UPPER(col) LIKE …`,列上的 btree/trigram 索引都用不上。实测（5000 人 + 5000 条主
membership，热缓存，20 次平均）：

| 查询 | 结果 | 耗时 |
|---|---|---|
| `q=ye`（拼音前缀） | 20 条 | 10.97 ms |
| `q=ylx`（首字母） | 1 条（夜来香） | 10.89 ms |
| `q=夜`（汉字，老路径） | 20 条 | 10.85 ms |
| `q=noluck`（无命中） | 0 条 | 10.81 ms |
| 对照：老查询（不带 search_key）`q=ye` | 1 条 | 10.37 ms |

**拼音搜索没有让这条查询变慢**（±0.6 ms 是噪声）—— 它加在一条本来就全表过滤的
OR 上。为一个省不下来的开销再加 GIN 索引（每次保存用户都维护）不划算；组织规模上
一个数量级、或进慢查询日志，再补 `UPPER(search_key)` 的表达式 trigram 索引。

### 2.1 发布窗口会留下「旧格式」的行 —— 发布后跑一次 `rebuild_pinyin_keys`

回填是**一次性**的，而这两列是**旧代码也会写**的列。migrate 是 pre-upgrade hook：它跑完
之后、旧 Pod 全部退场之前，旧镜像仍在服务，而它

- 不认识 `search_key`（新建/改名那一行留空串）→ 拼音搜索搜不到这个人；
- 写出的 `full_name_pinyin` **没有桶类前缀**（`zhangsan` 而不是 `0zhangsan`）→ 目录是
  `ORDER BY full_name_pinyin, full_name`，`en_US.utf8` 下数字排在字母前，**这个人会排到
  整个名册的第一行**。

迁移已经标记为已应用，没有任何代码会回头修它们；唯一会自愈的路径是「有人再保存一次这个
用户」。所以留了 `manage.py rebuild_pinyin_keys`（幂等、只写算错了的行、按批 `bulk_update`）：

```bash
# 生产机（backend 容器里）
kubectl -n meet exec deploy/meet-backend -- \
  python manage.py rebuild_pinyin_keys --check     # 只报告；有残留则以退出码 1 结束
kubectl -n meet exec deploy/meet-backend -- \
  python manage.py rebuild_pinyin_keys --dry-run   # 看具体是哪些行（最多列 20 条）
kubectl -n meet exec deploy/meet-backend -- \
  python manage.py rebuild_pinyin_keys             # 修
```

窗口很窄（通常残留 0～个位数），所以 `--check` 多数时候直接绿。**若 §3.1 的最后一条 SQL
查出 `search_key = ''` 的行，或名册第一行是个明显不该在那儿的名字，就跑一次正式修复。**

顺带记一条迁移的锁语义（不是功能问题）：`0145` 没有 `atomic = False`，整段迁移是一个事务，
`AddField` 在 `meet_user` 上拿到的 ACCESS EXCLUSIVE 会把回填也罩在里面——**回填期间对这张表
读也会阻塞**，「500/批」只减少往返、不缩短持锁。几千行时是亚秒级，可以接受；长到上万行应改成
`atomic = False` + 逐批 `transaction.atomic()` + `AddIndexConcurrently`，并单独挑窗口。

### 3.1 验收（后端，一条 `curl` 就够）

```bash
TOK=<access_token>
BASE=https://meet.we-meet.online/api/v1.0
# 找一个纯中文姓名,比如「夜来香」;下面三个词都该命中同一批人
curl -s -H "Authorization: Bearer $TOK" "$BASE/directory/members/?q=ye"   | python -m json.tool
curl -s -H "Authorization: Bearer $TOK" "$BASE/directory/members/?q=ylx"  | python -m json.tool
curl -s -H "Authorization: Bearer $TOK" "$BASE/directory/members/?q=夜"   | python -m json.tool
```

- [ ] `ye`（全拼前缀）、`ylx`（首字母）、`夜`（汉字）三者的结果**包含同一个人**；
- [ ] 老行为不回归：`q=alice`（邮箱/姓名子串）、`q=销售总监`（职位）、`q=人事部`（部门名）照旧；
- [ ] 别组织的人搜不出来（`q` 始终 org 内过滤）；
- [ ] 回填完整：`SELECT count(*) FROM meet_user WHERE coalesce(full_name,'') <> '' AND search_key = '';` → 0；

## 5. 回滚预案

| 对象 | 方式 |
|---|---|
| 后端 | `kubectl -n meet rollout undo deploy/meet-backend` |
| 前端 | `kubectl -n meet rollout undo deploy/meet-frontend` |
| **迁移 0145** | **不回滚**。`search_key` 是纯派生列,旧代码不读它;留着无害 |
| 顺序 | 与上线相反:先回前端,再回后端(旧前端配新后端也安全) |

- 只回后端 = 拼音搜索消失（`ye` 搜不到人），其余照旧。
- 只回前端 = 占位文案退回「姓名或邮箱」，拼音搜索仍可用（只是不提示）。

## 6. 未交付项（别在验收时找）

- **拼音搜索不覆盖「职务/部门名的拼音」**：`q=gaoji` 找不到「高级工程师」。搜索键只收
  姓名与简称的拼音；职位/部门名仍按**汉字/原文**匹配（`title__icontains` /
  `department__name__icontains`）。要做就把职位也进词袋 —— 那是另一个决定（涉及
  Membership 字段,搜索键得从 User 挪到 Membership 才能跟职位一起物化）。
- **不覆盖工号** `E1042`：同上,`employee_no` 没进搜索面,也没进词袋。
