# we-meet 客户端多端策略 — 对标飞书 (to-B)

> 立项日期：2026-06-23 · 范围由产品负责人拍板 · 本文是《[企业协同套件路线图_对标飞书](企业协同套件路线图_对标飞书.md)》的**客户端落地侧**：路线图管"做什么功能"，本文管"功能在哪些端、用什么技术落地"。

## 端命名约定

沿用项目约定（见路线图「M 端」节）：

- **C 端**：面向全体员工的客户端（浏览器 Web、桌面、移动）。
- **M 端**：运营管理端（management console），面向管理员（IT/HR/行政），Web。**不用 "A 端"**（易与代理商 Agent 混）。
- **平台端**：we-meet 自管的跨租户运营层，多租户铺开后再说。

## Context（为什么做这件事）

we-meet 要对标飞书做全平台覆盖：桌面（Windows / macOS）、移动（Android / iOS）、Web。规划的第一原则不是"选 Electron 还是 Flutter"，而是**围绕现有家底做复用最大化**——任何脱离"已有 React Web + 原生 Kotlin Android"去谈技术选型都是空中楼阁。

**现有客户端家底（2026-06-23 实测）**：

| 端 / 平台 | 现状 | 技术栈 |
|---|---|---|
| C 端 · 浏览器 Web | ✅ 完整 | React 18 + Vite 7 + panda-css + wouter + react-query；`livekit-client`(JS)；`@jusi/light-im-sdk`(TS) |
| C 端 · Android | ✅ 完整 | 原生 Kotlin + Jetpack Compose + Material3；多模块(`app`/`feature-im`/`feature-assistant`)；Retrofit/Moshi/OkHttp；LiveKit Android；`com.jusi.lightim:sdk-im`(原生 Kotlin)；CameraX；minSdk 29 |
| C 端 · iOS | ⛔ 无 | 净新增 |
| C 端 · 桌面 Win/macOS | ⛔ 无 | 净新增 |
| M 端 · Web | 🟡 过渡 | 组织/部门/成员管理暂在 Django admin（见路线图「M 端」节）；独立 Web M 端延后 |

**关键事实**：`jusi-light-im` 已有 **TS（Web）+ Kotlin（Android）两套 SDK**，缺 Swift；后端是统一 Django REST + LiveKit token + jusi-im WS/HMAC。

**对标飞书自身的客户端架构**：飞书/Lark 出 **原生 iOS + 原生 Android + Electron 桌面（Win/macOS/Linux）+ Web**，**不用 Flutter**，桌面是 Electron 外壳 + 重 Web + 少量原生模块。Slack / Teams / Discord / VSCode 桌面同样 Electron。标杆直接验证了下面的选型。

## 载荷决策（先定不再讨论）

1. **桌面端 = Electron 包裹现有 React，不用 Flutter。** 决定性因素是**复用现有 React 前端**：会议/IM/AI/通讯录整套 UI 零重写直接装进 Electron，`livekit-client`(JS) 在 Electron 捆绑的 Chromium 里原生可用、媒体行为与 Web 完全一致。**Flutter 对我们零协同**——它要用 Dart 重写整个 UI，既不能复用 React Web、也不能和原生 Kotlin Android 共享（Flutter 只有在"移动端也是 Flutter"时才划算，不是我们的情况）。行业 + 飞书标杆一致用 Electron。

2. **iOS = 纯原生 Swift / SwiftUI。** 与 Android 原生对称，LiveKit iOS SDK、APNs 推送、相机/媒体、后台都走原生最优路径。
   - **KMP（Kotlin Multiplatform）已评估、暂不采用**：理论上能把 Android 的 Kotlin data/domain 层共享到 iOS，但需把现有 Android 代码重构成 KMP 模块、引入 KMP 工具链与团队心智成本；为"最快最稳上线 iOS"，先纯 Swift，**不**为了省一层逻辑而拖慢/复杂化首版。（将来若 iOS/Android 业务逻辑重复严重，再回看 KMP。）

3. **Android 沿用原生 Kotlin / Compose。** 已是健康的多模块原生应用，不动技术栈，持续演进。

4. **M 端 = Web（独立 React entry）。** 管理员用浏览器即可，对标飞书管理后台 `admin.feishu.cn`（纯 Web）。不做桌面/移动包装。详见路线图「M 端」节。

5. **共享内核优先于各端重复造轮子。** 协议/契约层（jusi-im、后端 OpenAPI、LiveKit token）和设计 token 收敛到单一源，UI 各端用原生最优实现。

## 分平台落地

### 桌面端（Electron）—— 最高 ROI，优先做

**复用**：renderer 直接用 `src/frontend` 的 React 应用（浏览器 Web / Electron / M 端是同一代码库的不同 entry）。

**净新增工作量（是外壳 + 适配，不是 UI 重写）**：
- Electron `main` 进程 + `preload`（`contextBridge` 安全桥），renderer 复用现有 React
- **OIDC 适配**：Keycloak Authorization Code + PKCE 走**系统浏览器 / loopback 或自定义 scheme**（`wemeet://`），**禁用内嵌 webview 登录**（Keycloak/安全要求）
- 路由适配（HashRouter 或自定义协议拦截）
- 桌面能力：系统托盘、原生通知、开机自启、**全局快捷键**、**会议独立窗口**（多 `BrowserWindow`）、屏幕共享（`desktopCapturer` 接 LiveKit）
- **打包/签名/更新**：`electron-builder`（Win `nsis` / macOS `dmg`）+ Win EV 证书 + macOS notarization + `electron-updater` 自动更新（自建/对象存储 feed）
- CI 出 Win + macOS 双平台产物（含 Apple Silicon / Intel）

**备选（暂不选）**：**Tauri**（Rust + 系统 webview）包体更小（~10MB vs Electron ~100MB+），但系统 webview（WebView2 / WKWebView）在 WebRTC/LiveKit 一致性上不如捆绑 Chromium——媒体密集型应用风险高。留作"以后优化包体"候选，MVP 用 Electron（飞书/Slack 同量级包体可接受）。

### iOS（纯 Swift / SwiftUI）—— 唯一的真增量投入

- **UI**：SwiftUI（对标 Android 的 Compose 声明式）
- **会议**：LiveKit iOS SDK（Swift）
- **IM**：`jusi-light-im` 出 **Swift SDK**（或 iOS 直连 WS/REST 协议，参照已有 TS + Kotlin 两版）；放到 `John-Shao/jusi-light-im` 仓库的 `sdk/ios`
- **推送**：**APNs**（注意：iOS APNs 国内可用，与 Android 国内推送路径不同——见 [项目记忆 FCM 搁置 / HMS 不集成]；后端需把推送做成统一抽象，按平台分发 APNs / 国内通道）
- **网络/DTO**：OpenAPI 生成 Swift client，与 Android/Web 共享契约

### Android（沿用原生）

不动技术栈。持续演进；作为 token / OpenAPI 共享源的受益方之一。

### M 端（Web）

见路线图「M 端」节：独立 React entry / 部署，`org_role` 守卫，立项时腾 `/admin` 路径（Django admin 移走）。复用 C 端 Web 全套（OIDC / `fetchApi` / panda / i18n）。

## 共享内核策略（跨端复用什么）

| 层 | 共享方式 |
|---|---|
| **IM 协议** | `jusi-light-im`：TS(Web/Electron) + Kotlin(Android) 已有，**补 Swift(iOS)**；协议/WS/HMAC 单一权威 |
| **后端 API** | OpenAPI codegen 各端 client（TS / Kotlin / Swift），收敛 DTO 与错误码 |
| **设计系统** | panda tokens 一份源 → **Style Dictionary 生成** Web / Compose / SwiftUI 三套主题，三端视觉统一 |
| **Web ↔ Electron** | 同一 React 代码库，~95% 复用；差异仅在 OIDC/路由/桌面能力的薄适配层 |
| **LiveKit** | 各端官方 SDK（JS / Android / iOS）；token 签发后端统一 |

## 分期 rollout（按 ROI 排序）

依据：**Electron 边际成本最低（吃现有 Web），iOS 是最大净增量**。小团队优先级：桌面 → M 端 → iOS。

1. **P1 · 桌面端 Electron**：包 React + OIDC 适配 + 托盘/通知/自启/独立窗口 + 屏幕共享 + 双平台签名打包 + 自动更新。
2. **P2 · M 端独立 Web**：见路线图「M 端」节（产品对外发布前）。
3. **P3 · iOS 纯 Swift**：SwiftUI + LiveKit iOS + jusi Swift SDK + APNs。
4. **并行（贯穿）**：① 设计 token 单一源（Style Dictionary）② OpenAPI codegen——给三端打统一地基，越早越省。

---

## 跨阶段风险（排序）

1. **OIDC 在桌面/移动**：必须系统浏览器 + PKCE，**禁内嵌 webview 登录**；Electron 用 loopback/自定义 scheme，iOS 用 `ASWebAuthenticationSession`。
2. **推送国内化**：Android 已知国内 FCM 不可用走保活/个推；iOS APNs 国内可用——后端推送需做成按平台分发的统一抽象，别和某一端耦合。
3. **代码签名 / 分发**：Win EV 证书、macOS Apple Developer + notarization、App Store 审核、国内 Android 多商店。
4. **媒体一致性**：Electron 捆绑 Chromium 保证 LiveKit/WebRTC 与 Web 一致——这正是不选系统 webview / Tauri 的核心理由。
5. **自动更新**：Electron 走 `electron-updater` + 自建 feed；移动走商店。
6. **维护面从 2 端 → 5 端**：Electron 边际成本低（复用 Web），iOS 是真增量；小团队按上面的 ROI 优先级推进，别同时铺开。
7. **设计 token 不统一会越拖越贵**：三端主题尽早收敛到单一源，否则后期对齐成本指数上升。
