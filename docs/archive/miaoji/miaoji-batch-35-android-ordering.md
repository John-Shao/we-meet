# 第三十五批：Android 记录库与纪要库创建时间排序

G4 中服务端/Web 已支持全局创建时间排序，Android 仍缺少选择入口。本批补齐 App 的这一差异，Android 提交 `ce1fcead`（已推送）。

## 行为与实现

- 记录库、纪要库顶部排序菜单支持“创建时间从新到旧 / 从旧到新”，菜单标示当前选择；默认从新到旧。
- 请求发送 `ordering=-created_at` 或 `created_at`，由服务端在分页前排序。没有对当前页进行客户端重排。
- 切换排序重新从第一页加载，并清除旧页显示和滚动位置；归属、来源、标题、日期范围保持不变。继续翻页携带原排序和筛选。
- 进行中与历史仍分区，分别使用选择的排序；纪要库继续限定 `has_summary=true`。排序不等于会议开始时间，列表原有来源时间仍保留。
- 日期和排序共用 `filteredRecords` 请求；保留无筛选调用的兼容接口。没有改动 ACL 或服务端数据模型。

## 验证

- 30 项单元测试通过：包含两个新增排序请求契约用例，覆盖两方向、日期/归属/来源/标题/纪要过滤及游标传递。
- 31 个不同仪器用例最终通过：历史第二页切换排序回第一页、来源/日期保留、两个分区请求排序一致、纪要库范围不变，以及原有列表/详情回归。首轮 30/31 通过，新纪要排序用例误等记录库空态，修正为纪要库空态后补跑通过；两个截图场景同时补跑，不重复计数。
- 设计规范检查通过；记录库/纪要库截图已查看，排序入口、分区和原有操作均可见。新版 debug APK 已安装在 Pixel 8，尚未正式分发。
- 生产 `85c0291d6` API：既有两条 miaoji 导入记录在日期 × owned × upload × 标题条件下，升序/降序完整结果互为逆序；两次均无下一页。只读查询，没有新增记录或分享。

## 发布与剩余边界

本批仅 Android 运行代码变化。后端依赖第 23 批已有排序能力，当前生产满足，不需重新部署 backend/frontend 或迁移。尚需正式 App 分发、物理设备和生产多页/进行中样本验证；API 的两条记录不代表 App 生产 UI 或多页验收。

G4 的任意所有者筛选、标签/文件夹、保存筛选仍未实现；G6 可靠全媒体时长/人工历史版本精确导航、G7 回收站等保持原排期。大文件恢复、长原文跨页继续按用户要求延后。
