# P1-9：全天日期语义与跨设备时区

> 状态：已实现（2026-08-12）
>
> 迁移：`0094_calendar_all_day_preferences`
>
> 本文是全天日程日期语义、日历显示时区和跨设备设置同步的唯一事实来源。

## 1. 目标与边界

P1-9 把两类时间明确拆开：

- **定时日程是时间点**：服务端继续用 tz-aware `start_at/end_at` 保存绝对时间，`timezone` 记录创建或编辑时采用的 IANA 事件时区；查看者切换显示时区只改变墙上时间，不改变实际时刻。
- **全天日程是民用日期**：服务端以半开区间 `start_date/end_date` 为事实源，例如单日 8 月 12 日保存为 `[2026-08-12, 2026-08-13)`。它不随浏览器、设备或查看者时区换日。

`CalendarEvent.start_at/end_at` 对全天日程仍然非空，用作旧客户端兼容、排序、提醒和既有外键联动；它们只是按事件时区生成的当地午夜锚点，不能再反推或改写全天日期。

本期实现 Web 与 Android 的 `自动（跟随当前设备）/ 固定时区`、日程级时区选择和账号设置同步。会议室层级时区仍服务于会议室地点与占用 API；跨时区工作时间重叠计算、浮动时间、CalDAV/Exchange 导入规则不在本期。

## 2. 数据模型与不变量

### 2.1 CalendarEvent

新增两个可空字段：

| 字段 | 含义 |
|---|---|
| `start_date` | 全天日程包含的首日 |
| `end_date` | 全天日程不包含的结束日 |

数据库约束 `calevent_all_day_dates_consistent` 保证：

- `all_day=true` 时两个日期都非空，且 `end_date > start_date`；
- `all_day=false` 时两个日期都为空；
- `start_at/end_at` 对全部日程仍满足既有的 `end_at > start_at`。

全天重复日程按民用日期递推，再在该事件的 IANA 时区重建每一场的当地午夜锚点。夏令时切换周可能不是 24 小时，但日期跨度和当地 00:00 必须保持不变。

### 2.2 CalendarPreference

新增账号级一对一模型 `CalendarPreference`：

- `timezone_mode=auto|fixed`；
- 固定模式下的 IANA `timezone`；
- 每周首日、新建默认时长、默认提醒；
- 淡化已过日程、是否显示周末；
- 工作时间起止、日历和会议室的工作时间/全天范围。

`User.timezone` 不承担固定日历时区。它继续表示账号/设备侧通用时区，用于既有通知等能力；日历固定显示时区是独立偏好，避免一台设备改变另一台设备的系统语义。

`initialized` 区分“服务器默认值”和“已有客户端本地设置尚未导入”，`revision` 用于乐观并发控制。Web 的 `localStorage` 与 Android 的 `SharedPreferences` 只作为离线缓存，不再是跨设备事实源。

## 3. REST 协议

### 3.1 日程读写

`CalendarEvent` DTO 增加向后兼容的可选字段：

```json
{
  "all_day": true,
  "start_date": "2026-08-12",
  "end_date": "2026-08-13",
  "timezone": "Asia/Shanghai",
  "start_at": "2026-08-11T16:00:00Z",
  "end_at": "2026-08-12T16:00:00Z"
}
```

新客户端创建或移动全天日程必须发送 `start_date/end_date/timezone`。服务端生成兼容锚点；非法 IANA 时区、缺少日期或非正日期跨度返回 400。

兼容期内，旧客户端仍可用 `start_at/end_at` 创建全天日程，服务端只在事件时区中确定性派生一次日期。已有规范全天日程编辑普通字段时，旧客户端回传完全相同的时间锚点仍可接受；试图只用时间点移动它会返回 400 `all_day_dates_required`，防止另一时区的设备把日期静默改掉。

列表和个人日历 feed 在原有 `start/end` 时间点窗口外增加 `date_start/date_end` 民用日期窗口。定时日程按时间点相交，全天日程按日期区间相交，服务端不混用两种语义。

IM `event-card` v1 同步增加可选 `start_date/end_date`；全天改期卡另带可选 `old_start_date/old_end_date`。新客户端优先按日期渲染新旧全天范围，旧客户端继续忽略新字段并使用兼容锚点。

### 3.2 跨设备设置

`GET /api/v1.0/calendar-preferences/me/` 获取当前账号设置；不存在时按需创建未初始化默认行。

`PATCH /api/v1.0/calendar-preferences/me/` 更新设置，请求携带 `expected_revision`：

- 版本匹配时保存、`initialized=true` 并把 `revision` 加一；
- 版本过期时返回 409 `calendar_preference_conflict`，客户端重新获取服务器版本；
- 固定模式必须提交有效 IANA 时区；自动模式在服务器清空固定时区值；
- 工作时间使用 30 分钟步长，跨度限制为 6–12 小时。

首次升级时，若服务器记录尚未初始化，最先同步成功的新版客户端把本地有效设置整体导入。此后服务器版本优先；离线修改保留在本地缓存，恢复连接且服务器基线版本未变化时再同步。若另一设备已先更新，客户端收到 409 后拉取服务器新版本，不静默覆盖远端设置。

## 4. 双端体验

- 日历设置可选择跟随当前设备或固定时区；固定模式显示常用 IANA 时区列表。
- 日/周/月/列表、迷你日历、当前时间线、消息列表日程提醒、忙闲和详情统一按有效日历时区投影。
- 切换固定时区不会修改定时日程的 UTC 时间点；如果当前选中的是旧时区的“今天”，视图跟随跳到新时区的“今天”。
- 新建/编辑定时日程可单独选择事件时区，表单墙上时间按该时区转换成 UTC 提交。
- 新建/编辑全天日程表单显示含首尾日期，提交时把表单的末日加一天形成 API 半开区间；编辑不增减原跨度。
- 全天日程在任意查看时区都显示同一组日期；详情、卡片和提醒优先使用规范日期字段。

自动模式刻意按每台设备自己的系统时区显示，因此两台位于不同时区的设备可以显示不同的定时墙上时间；固定模式则跨设备保持同一显示时区。

## 5. 迁移与兼容

迁移 `0094_calendar_all_day_preferences`：

1. 添加可空 `start_date/end_date`；
2. 对历史 `all_day=true` 行，在其已保存的事件 `timezone` 中把旧锚点确定性转换成日期；无效时区回退 UTC，非正跨度至少保留一日，并记录迁移告警；
3. 加上全天日期一致性约束；
4. 创建 `meet_calendar_preference`，不预先批量创建用户偏好行。

迁移不会依据部署机器、浏览器或执行迁移者的时区猜测，也不会修改历史时间锚点。对旧数据只能选择一个可重复的解释；发现非午夜或无效时区时写告警，后续如需人工纠正应按具体事件处理，不能批量平移全部历史数据。

协议是读取侧加法兼容，但全天日程移动存在刻意的写入收紧：旧客户端可继续读取、创建和编辑普通字段，不能仅靠 UTC 锚点可靠改期。部署窗口应尽量缩短，并在后端迁移后发布 Web、再发布 Android。

## 6. 安全与正确性不变量

- 所有客户端和任务必须把全天日期字段作为事实源；兼容锚点不能覆盖日期。
- IANA 时区由服务端校验，不能信任客户端任意字符串。
- 设置同步要求登录，并按当前用户一对一隔离；客户端不能指定目标用户。
- 409 冲突不能静默覆盖另一设备的新版本。
- 自动模式不把某台设备时区写成账号固定时区。
- 日程显示时区不改变日程可见权限、来源会话权限或视频会议入会权限。

## 7. 验收清单

- 单日/多日全天日程在上海、洛杉矶和 UTC 查看时日期完全一致；普通字段编辑不改变跨度。
- 全天重复日程跨夏令时后仍落在同一民用日期和当地 00:00。
- 定时日程切换显示时区只改变显示；在事件时区编辑墙上时间后提交正确 UTC 时间点。
- `date_start/date_end` 能查到位于 UTC+14 或 UTC-12、但民用日期落在窗口内的全天日程。
- Web 修改固定时区后 Android 同步生效，反向亦然；自动模式各自跟随设备。
- 两台设备用同一旧 `revision` 更新时，后一请求收到 409 且不会覆盖先写值。
- 迁移后历史全天日程都有正的日期区间，日志可识别异常回填，旧客户端普通字段编辑仍兼容。
