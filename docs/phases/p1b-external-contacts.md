# P1b — 外部联系人（External Contacts）

**状态**：🟡 M1 主链已实现并通过定向测试（2026-08-12）；M2–M5 为规划，**尚未实现**。
**范围**：we-meet 后端、Web、Android；M1 复用现有 jusi-light-im 协议，不修改 jusi 服务端。
**前置**：[P1 组织架构](./p1-organization-foundation.md)、[P2 日历](./p2-calendar-scheduling.md)、[P1-8b 日历共享权限](./p2b-calendar-visibility-sharing.md)、[P8 IM × 日历](./p8-im-calendar-integration.md)。

> 竞品依据：[飞书《添加或删除外部联系人》](https://www.feishu.cn/hc/zh-CN/articles/360043505973-%E6%B7%BB%E5%8A%A0%E6%88%96%E5%88%A0%E9%99%A4%E5%A4%96%E9%83%A8%E8%81%94%E7%B3%BB%E4%BA%BA)。
> we-meet 参考的是“先在通讯录建立真实账号关系，再进入聊天、日历和会议协作”的产品边界，不照搬飞书的 UI、商业版本或后台配置。

## 一、背景：外部邮箱不是外部联系人

P1-8 曾把“外部参与人”实现成日历表单里直接输入邮箱。该方案只能产生一行没有账号身份的 `EventAttendee.email`：对方无法在自己的日历看到邀请、不能 RSVP，无法稳定接收变更卡，也没有可复用的 IM 和会议权限。

本设计纠正身份入口：**手机号/邮箱只是通讯录里的账号发现方式，不是日程参与人类型**。只有双方建立外部联系人关系后，对方的真实 `User.id` 才能进入日历、IM 和会议权限链。

### 四类身份必须分开

| 身份 | 建立方式 | 能否浏览我方通讯录 | 日历/IM/会议身份 | 当前状态 |
|---|---|---|---|---|
| 组织内部成员 | 与调用者共享当前组织的 active membership | 按内部通讯录权限 | 内部真实账号 | ✅ 已有 |
| 外部联系人 | 两个不同组织的真实账号，由一方申请、另一方接受 | 不能；只见最小外部名片 | 外部真实账号 | 🟡 M1 主链已实现 |
| 信任组织成员 | 两家组织的管理员建立组织级互信并配置可见范围 | 只见对方授权范围 | 受信任组织账号，不要求逐人加好友 | ⛔ M4 规划 |
| 匿名访客 | 通过公开会议链接临时入会 | 不能 | 会议临时身份，不进入通讯录和日历 | ⛔ M5 仅定义边界 |

外部联系人是**个人之间的双向关系**，不是组织成员关系，也不是信任组织的简化版。信任组织落地时不得批量生成 `ExternalContact` 行；匿名访客也不得因为参加过会议而自动成为联系人。

## 二、产品与安全不变量

1. **真实账号优先**：新日程参与人必须有 `user_id`；邮箱不能直接创建可 RSVP 的外部身份。
2. **双方确认**：申请发出后只有接收方可接受或拒绝；双方同时申请等价于双方表达意愿，可自动接受。
3. **服务端鉴权**：客户端展示外部联系人不是授权依据。日历、忙闲与 IM 每条写路径都要重新检查 accepted 关系。
4. **最小名片**：M1 只对外返回姓名、头像和组织名；不返回手机号、邮箱、部门、职位、员工编号或对方组织树。
5. **不可枚举**：账号发现只接受完整手机号或完整邮箱的精确匹配，不提供模糊搜索和“推荐外部联系人”。
6. **安全强标识**：外部联系人在联系人列表、选人器、日程详情和后续会议成员列表中必须带“外部”标签。
7. **关系与历史解耦**：删除联系人关系不删除历史会话、既有日程和 RSVP；但不能再从通讯录、新日程或“新建私聊”入口发起新的联系人受控协作。
8. **私密日程不降级**：外部联系人只有在成为真实参与人后才能查看私密日程详情；其他人仍只看到脱敏忙碌时间窗。
9. **治理集中化**：M3 上线后，是否允许对外协作必须由一个统一服务判定，不能在日历、IM、会议各自维护一套开关。

### 3.2 数据模型与迁移

迁移 `0092_external_contacts` 新增 `ExternalContact`（`meet_external_contact`）：

| 字段 | 含义 |
|---|---|
| `user_a` / `user_b` | 一对真实用户，按 UUID 字符串顺序规范化存储 |
| `requested_by` | 当前申请发起人，必须是关系中的一方 |
| `status` | `pending` / `accepted` / `declined` |
| `responded_at` | 接受或拒绝时间；重新申请时清空 |
| `created_at` / `updated_at` | 申请创建时间与最近状态变化时间 |

约束与索引：

- `unique(user_a, user_b)`：同一用户对只有一行，避免双向重复；
- `user_a != user_b`：不能添加自己；
- `requested_by ∈ {user_a, user_b}`：申请方向不能指向第三人；
- `(user_a, status)` 与 `(user_b, status)` 索引：加速双方的联系人和申请列表。

M1 的关系是**用户级全局关系**，不是 `(用户, 组织)` 关系。发现账号时，以调用者当前 active/primary 组织判断“内部/外部”；对方名片选择一个不等于调用者当前组织的 active 组织展示。多组织用户的组织上下文细化留到真正支持组织切换时处理。

### 3.3 状态机

| 当前状态 | 操作人 / 操作 | 新状态 | 备注 |
|---|---|---|---|
| 无关系 | 任一方发送申请 | `pending` | `requested_by` 记录发起人 |
| `pending` | 接收方接受 | `accepted` | 双向关系建立 |
| `pending` | 接收方也发送申请 | `accepted` | 交叉申请自动接受 |
| `pending` | 接收方拒绝 | `declined` | 发起方不能替对方接受/拒绝 |
| `declined` | 任一方重新申请 | `pending` | 更新 `requested_by`，清空 `responded_at` |
| `pending` | 任一方删除 | 无关系 | 撤回申请或删除申请记录 |
| `accepted` | 任一方删除 | 无关系 | 双方联系人列表同时移除 |

`accept` 对已接受关系幂等返回成功。关系删除采用硬删除；既有 jusi 会话历史和既有 `EventAttendee` 不级联删除。删除后创建新私聊、向新日程添加对方等入口重新受 accepted 关系限制。

### 3.4 通讯录 API

所有端点均要求登录，不分页：

| 方法与路径 | 行为 |
|---|---|
| `GET /directory/external-contacts/` | 返回当前用户的 accepted 联系人 |
| `GET /directory/external-contacts/search/?q=` | 按完整手机号或邮箱精确发现其他组织账号 |
| `GET /directory/external-contacts/requests/` | 返回双方与当前用户有关的 pending 申请 |
| `POST /directory/external-contacts/requests/` | `{target_user_id}` 发送申请；交叉申请自动接受 |
| `POST /directory/external-contacts/{relationship_id}/accept/` | 仅接收方可接受 |
| `POST /directory/external-contacts/{relationship_id}/decline/` | 仅接收方可拒绝 |
| `DELETE /directory/external-contacts/{relationship_id}/` | 任一方删除关系、撤回申请或清理申请记录 |

最小名片契约：

```jsonc
{
  "relationship_id": "uuid | null",
  "id": "真实 User UUID",
  "full_name": "Partner Person",
  "short_name": "Partner",
  "avatar_url": "短时效预签名 URL",
  "organization": {"id": "uuid", "name": "Partner Ltd."},
  "status": "none | pending | accepted | declined",
  "direction": "none | incoming | outgoing | accepted | declined",
  "requested_at": "ISO-8601 | null"
}
```

搜索不创建数据库状态。空查询、非精确查询、组织内部成员、设备账号、无 OIDC 身份账号以及没有其他 active 组织的账号均不返回。直接向同组织账号、自己或不存在的用户发送申请会返回 400/404，不泄露额外身份信息。

### 3.5 日历闭环

- 新写协议为 `attendee_entries=[{user_id, role}]`，`role` 仅允许 `required | optional`；提交任何 `email` 字段返回 400，并提示先添加外部联系人。
- 旧 `attendee_ids` 继续兼容；`EventAttendee.email` 只用于读取存量历史行。编辑时显式提交完整参与人列表，会清理不再存在于列表中的历史 email-only 行。
- 服务端只同步本组织 active 成员和组织者的 accepted 外部联系人。未建立关系的跨组织 `user_id` 不会获得参与人或 Room 权限；M1 沿用既有兼容语义静默忽略，后续可收紧为字段级 400。
- 外部联系人成为真实 `EventAttendee` 后，可以在自己的跨组织日历列表看到日程、RSVP、参与忙闲查询，并获得视频会议 `ResourceAccess`。
- 创建邀请、RSVP、改期、参与人变化、移除和取消继续走 P1-7 的日程助手个人卡；来源群提醒和私密日程脱敏规则不变。
- 事件响应的参与人增加 `external: true` 标识。历史 email-only 行也按外部身份展示，但不因此获得账号能力。

### 3.6 IM 与客户端

`POST /im/conversations/direct/ {peer_user_id}` 允许：

1. 与调用者共享当前组织的 active 成员；或
2. 与调用者存在 accepted `ExternalContact` 的真实账号。

任意其他跨组织 ID 返回 400，不会被客户端 ID 注入绕过。该路径只放宽 we-meet bridge 的账号解析与新建私聊鉴权，不修改 jusi-light-im 协议和会话存储。

Web 通讯录增加“外部联系人”视图，支持申请处理、删除和发消息；日历选人器合并 accepted 联系人并显示组织名与“外部”标签。Android 增加同等的联系人管理面板和日历选人能力，但联系人面板直达私聊尚未实现。

## 四、安全、隐私与 M1 已知缺口

| 主题 | M1 现状 | 后续要求 |
|---|---|---|
| 搜索防枚举 | 只做精确匹配和最多 20 条结果；没有独立 throttle | M2 增加按用户/IP 的独立 scope、失败统一响应和申请冷却 |
| 对外名片 | 固定返回姓名、头像、组织名 | M3 改为管理员可配置白名单，默认仍为这三项 |
| 日程参与人邮箱 | 兼容 DTO 仍返回 account-backed `attendees[].email` | 下一阶段按查看者身份脱敏，并推动双端停止依赖该字段 |
| 对外沟通权限 | 所有 active 组织成员都可申请 | M3 支持全员、指定部门/人员、完全禁止 |
| 申请通知 | 仅通讯录申请列表 | M2 增加站内/推送通知，且不泄露搜索关键词 |
| 操作审计 | 无专用外部联系人审计动作 | M3 记录申请、接受、删除、策略变化和信任组织变化 |
| 外部群安全提示 | 无 | M3 群头部持续显示外部标识，成员列表逐人标记 |
| 会议外部权限 | accepted 联系人按真实 Room 成员进入 | M3 增加外部身份元数据、等候室与音视频/共享模板 |
| Android 私聊入口 | 后端支持，联系人面板没有按钮 | M2 补齐 |
| 未授权日历参与人 | 静默忽略非法跨组织 ID | 后续改为结构化 400，便于客户端解释 |
| 关系留痕 | 删除关系行后只能依赖外围日志 | M3 审计日志保留动作元数据，但不保存搜索邮箱/手机号 |

通讯录外部联系人端点永远不能返回对方组织的部门树、内部成员列表、手机号、邮箱、职位或内部应用。M1 日历响应仍因历史 DTO 兼容返回参与人邮箱，这是已明确记录的隐私债务，不代表外部联系人获得了通讯录字段权限。云文档、机器人等协作能力必须由各自资源授权单独放行，不能因为 `ExternalContact=accepted` 自动继承。

## 五、完整蓝图（均未实现）

### M2 — 发现入口与申请通知

1. **个人二维码/个人链接**：服务端签发可撤销、可轮换的不透明凭证，不把 `User.id`、手机号或邮箱编码进二维码。打开链接必须登录，只回显最小外部名片，再复用现有申请状态机。
2. **外部群成员名片入口**：用户从自己所在会话的成员卡发起申请；服务端验证双方确实共享该会话，不能只信任客户端传入的成员 ID。
3. **申请通知**：收到申请、申请被接受/拒绝时进入站内通知与设备推送；通知体只含最小名片，不包含搜索使用的手机号/邮箱。
4. **滥用防护**：精确搜索使用独立 throttle scope；发送申请按 `(发起人, 接收人)` 冷却并限制每日上限，错误响应不得成为账号枚举 oracle。
5. **Android 对齐**：accepted 联系人行增加“发消息”，复用现有 `peer_user_id → cid` 路径。

### M3 — 组织治理、审计和安全 UI

新增组织级 `ExternalCollaborationPolicy`，由持 `org.external_collaboration.write` 的组织级管理员维护。该权限属于 `UNSCOPABLE`：策略影响整个组织，不能把“管理某部门”误解为只能修改策略的一部分。

策略至少包含：

- `mode = all | selected | disabled`；
- selected 模式下的部门和人员授权名单；
- 对外名片字段白名单；
- 外部联系人入会时的等候室、麦克风、摄像头、发言和共享屏幕默认模板；
- 是否允许创建外部群、邀请外部联系人进入已有群。

服务端提供统一的 `can_collaborate_externally(user, organization, capability)` 判定，通讯录搜索/申请、IM 新建私聊/外部群、日历邀请和会议授权全部复用；策略关闭后不删除既有数据，但阻止新的受控操作。

外部群需在列表、会话头部和成员列表持续标识“含外部人员”，并展示信息安全提示。会议 token/participant metadata 需携带内部、外部联系人、信任组织、访客四类身份，主持人才能应用不同权限模板。

审计动作覆盖：申请发送/接受/拒绝/删除、管理员策略变更、外部群创建、信任组织建立/撤销。审计日志只记录主体、对象和结果，不记录用户输入的完整搜索手机号/邮箱。

### M4 — 信任组织（独立模型）

新增组织对组织的 `OrganizationRelation`：规范化组织对、发起组织、`pending | accepted | declined | revoked` 状态，以及双方各自配置的可见部门/人员范围。必须由两家组织管理员确认，单方可撤销。

信任组织成员通过单独的“受信任组织目录”解析器进入选人器，可以按对方授权范围搜索、聊天、邀请和开会；**不得**为每对员工批量创建 `ExternalContact`。个人外部联系人与组织互信并存，任一关系都不能扩大另一关系的可见范围。

### M5 — 匿名访客边界

匿名访客只通过会议链接进入现有 lobby/等候室流程：没有通讯录卡片、日历账号、RSVP 和长期 IM 身份。默认要求主持人核验，并使用最严格的音视频、发言和共享权限模板。

访客后来注册账号也不会自动变成外部联系人；必须重新走通讯录申请与双方接受。这样可以避免“一次入会永久进入企业协作圈”的隐式授权。

## 六、测试与验收基线

### M1 已覆盖

- 精确邮箱搜索、模糊查询为空、同组织成员排除；
- 申请、incoming/outgoing 方向、接受、拒绝、删除；
- 未接受跨组织账号无法成为日程参与人，accepted 后可邀请并出现在对方日历；
- email-only 写入返回 400，历史 email 行仍可读取和清理；
- 任意跨组织账号不能新建私聊，accepted 联系人可以；
- 通讯录旧权限与私密日程脱敏不回归；
- Web API、全量 Vitest、TypeScript 构建、lint；Android 单测与 Debug 构建。

### 后续里程碑验收原则

- M2：二维码不暴露账号 ID，撤销后立即失效；群名片入口校验会话共同成员；搜索和申请达到限流时统一返回 429/通用错误。
- M3：全员/selected/disabled 三种策略在通讯录、IM、日历、会议四条写路径结果一致；对外名片字段和审计日志不泄露敏感信息。
- M4：双方管理员接受后仅授权范围可见；撤销互信不删除个人联系人和历史协作记录。
- M5：访客不能访问通讯录和日历，默认进入等候室；注册后仍需单独添加联系人。

## 七、发布与兼容

`0092_external_contacts` 是加法迁移，不覆盖历史 `EventAttendee.email`。发布顺序为：

1. 后端与 `0092`；
