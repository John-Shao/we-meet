# P1-8b：日程公开范围与个人日历共享权限

> 状态：已实现（2026-08-12）
>
> 迁移：`0093_calendar_sharing_visibility`
> 本文是该能力的唯一事实来源。P2 日历总览和企业协同路线图只保留摘要并链接到这里。

## 1. 目标与边界

we-meet 采用“个人日历共享权限 + 单条日程公开范围”的两层模型：

1. 个人日历权限决定某个账号是否有权订阅，以及基础上能看忙闲还是完整详情；
2. 单条日程的 `visibility` 决定该日程沿用、放宽或收紧上述基础权限。

这套可见权限只控制日程资料读取，不控制视频会议入会。`public` 也不是互联网公开、组织内全员公开或“知道 event id 即可查看”；读取者仍须是组织者/参与者、有效订阅者，或来源会话成员。

本期只实现个人日历。团队日历、公共日历、信任组织日历、匿名访客日历账号和基于部门的批量授权均未实现。

当前组织上下文仍沿用 P1 的单 active/primary 组织假设；多组织用户的显式组织切换和“同一账号选择哪份组织日历”留待组织切换能力落地后处理。

## 2. 核心概念

### 2.1 个人日历

每个有效的“组织 + 用户”组合拥有一份 `PersonalCalendar`。日程不复制到日历关联表，而是动态投影到：

- 组织者的个人日历；
- RSVP 不是 `declined` 的真实账号参与者个人日历。

同一日程因此可以出现在多个账号的个人日历里，但仍只有一个 `CalendarEvent` 事实对象。

### 2.2 基础共享权限

`PersonalCalendar.organization_default_access`：

| 值 | 含义 |
|---|---|
| `none` | 同组织成员默认不能订阅 |
| `free_busy` | 同组织成员可订阅，但默认只看忙碌时间段 |
| `details` | 同组织成员可订阅并查看日程详情 |

`CalendarAccessGrant` 是日历所有者对单个账号的显式覆盖，只允许 `free_busy | details`。同组织授权覆盖组织默认值；跨组织授权必须同时满足“已接受的双向外部联系人关系”。

`CalendarSubscription` 只表示订阅者是否把一份已经获权的日历显示在自己的视图中，并可保存颜色。订阅不是授权，取消订阅也不会改变所有者的共享设置。

### 2.3 单条日程公开范围

`CalendarEvent.visibility`：

| 值 | 产品文案 | 规则 |
|---|---|---|
| `default` | 默认的公开范围 | 沿用个人日历的基础共享权限 |
| `public` | 公开 | 对已有权的订阅者放宽为完整详情 |
| `private` | 私密 | 对非组织者、非参与者收紧为仅显示忙碌 |

组织者和日程参与者始终可查看完整详情。私密日程不影响被邀请人处理 RSVP 或入会。

## 3. 访问判定矩阵

| 查看者路径 | `default` | `public` | `private` |
|---|---|---|---|
| 组织者或参与者 | 完整详情 | 完整详情 | 完整详情 |
| `free_busy` 订阅者 | 仅忙碌 | 完整详情 | 仅忙碌 |
| `details` 订阅者 | 完整详情 | 完整详情 | 仅忙碌 |
| 来源会话成员 | 完整详情 | 完整详情 | 仅忙碌 |
| 无任何有效路径 | 404 | 404 | 404 |

忙碌投影保留事件 ID、状态和起止时间供日历网格去重与占用展示，返回 `details_redacted=true`；标题、描述、组织者、参与人、会议室和入会信息全部脱敏。会议室占用时间线也复用同一判权，未获详情权限时不泄露标题、事件 ID 或组织者。

来源会话判定严格调用 IM 花名册：明确不是成员返回 404；当来源会话是唯一可能的读取路径且 IM 无法完成验证时返回 503。网络故障不能被误判成“已退群”。

## 4. 数据模型与迁移

迁移 `0093_calendar_sharing_visibility`：

- 新建 `PersonalCalendar`、`CalendarAccessGrant`、`CalendarSubscription`；
- `CalendarEvent.visibility` 增加 `public`，形成 `default | public | private`；
- 为迁移时所有有效组织成员回填个人日历，默认权限为 `free_busy`；
- 不复制、不改写历史日程，无需日程数据回填。

唯一约束分别是 `(organization, owner)`、`(calendar, grantee)` 和 `(calendar, subscriber)`。模型禁止给自己创建授权或订阅。

外部联系人关系删除时，同时撤销双方跨组织的日历授权和订阅；历史日程、已有会话和参与记录继续保留。任意跨组织用户 ID 本身不能获得日历访问能力。

## 5. REST API

所有路径位于 `/api/v1.0/`，均要求登录。

| 方法与路径 | 作用 |
|---|---|
| `GET personal-calendars/mine/` | 获取或按需创建当前组织的个人日历 |
| `PATCH personal-calendars/{id}/` | 所有者修改 `organization_default_access` |
| `GET personal-calendars/{id}/events/?start=&end=` | 获取自己的或已订阅日历的时间窗事件 |
| `GET/POST calendar-access-grants/` | 列出授权；按 `grantee_user_id` 创建或覆盖授权 |
| `PATCH/DELETE calendar-access-grants/{id}/` | 修改或撤销授权；撤销时同步删除对应订阅 |
| `GET/POST calendar-subscriptions/` | 列出订阅；按 `owner_user_id` 订阅已获权日历 |
| `PATCH/DELETE calendar-subscriptions/{id}/` | 启停、改色或取消订阅 |

`GET /calendar-events/{id}/` 统一走服务端 `NONE / BUSY / DETAILS` 判定。知道 UUID 不形成权限；`public` 日程在没有订阅、参与或来源会话成员关系时同样返回 404。

创建和编辑日程使用 `visibility=default|public|private`。Web/App 编辑请求同时发送只写字段 `visibility_explicit=true`。兼容期内，旧客户端编辑一个现存 `public` 日程并隐式提交 `default` 时，后端保留 `public`；只有带显式标记的新客户端才能主动降级为 `default`。

## 6. Web 与 Android 体验

- 新建/编辑日程均提供“默认的公开范围 / 公开 / 私密”三态选择和含义提示；
- 日历设置提供共享管理入口，可配置组织默认权限、点对点授权和订阅；
- 选人继续复用通讯录，跨组织目标只能来自已接受的外部联系人；
- 日/周（Web）或三日（Android）/月/列表视图合并自己的投影和已启用订阅，按 event id 去重，并优先保留完整详情版本；
- 忙碌投影统一显示“忙碌”，私密忙碌投影显示私密提示，不提供分享、参与人和入会详情；
- 单个订阅源读取失败不会隐藏自己的日程或其他正常订阅源。

## 7. 安全不变量

- 客户端不负责最终判权，所有读取入口复用服务端策略；
- `public` 只覆盖获权订阅者的详情层级，不绕过订阅和身份关系；
- 外部联系人不会自动获得日历权限，必须由所有者显式授权、对方显式订阅；
- 对方组织通讯录和部门结构不会因日历共享而暴露；
- 日程可见性、会议入会权限、来源群发消息身份是三套独立能力；
- 取消订阅只影响显示，撤销授权才终止读取能力；
- 外部联系人关系失效后，跨组织授权和订阅立即失效。

## 8. 发布顺序与验证

发布顺序固定为：

1. 发布后端并执行 `0093_calendar_sharing_visibility`；
2. 发布 Web；
3. 发布 Android。

协议为加法兼容。迁移前不得发布依赖个人日历 API 的双端版本。旧客户端不能选择 `public`，但后端会防止普通字段编辑把已有 `public` 日程静默降级。

上线至少验证：三种日历基础权限、三种事件公开范围的矩阵；无权凭 ID 访问 404；来源群成员/非成员/IM 故障；同组织和外部联系人授权订阅；删除联系人后立即失权；参与者仍能读取私密日程；会议室忙闲不泄露标题；双端创建、编辑、订阅和取消订阅。
