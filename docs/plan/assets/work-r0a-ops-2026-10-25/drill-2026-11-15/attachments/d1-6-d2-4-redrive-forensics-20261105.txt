Three facts this establishes, and one it retracts:
  1. #56-A holds: attempt 2 was scheduled at 4m06s (11:35:13 -> 11:39:19), not at the old 16-minute
     boundary. The parking window that D1-6/D2-4 recorded on 11-04 is gone.
  2. The provider exchange continued without the worker: work-egress finished 2m17s after the
     cancel (137,216 ms), and the parent kept issuing capabilities until 11:37:09 (generation 7).
     A stopped work-worker therefore does NOT stop the fragment - it only orphans the activity.
  3. Attempt 2 could not take over. The only codes it could get were runtime_execution_expired
     (active + elapsed lease) mapped by node/src/lease.mjs NOT_CLAIMABLE_CODES to
     lease_not_claimable. There is no other exit: revoke => state 'revoked' (not claimable),
     register => same execution_id returns the existing state, a new row => dispatch_gate_exists,
     late heartbeat => state 'expired' (not claimable).
  RETRACTED: the earlier note "重驱动判定得比租约释放得早" and the resulting fix sketch
     "release the previous execution before claim on attempt >1". Revoking first cannot make a
     row claimable, so that prescription would have changed nothing. This file is the evidence
     for the retraction.

== E. what increment 0028 changes, and what it deliberately does not ==

  changes: claim_runtime_execution accepts state='active' + lease elapsed + different holder,
           takes the fragment over (new holder, new lease, heartbeat_seq reset to 0) and writes
           audit action runtime.execution_taken_over with previous_holder_id,
           previous_lease_until, previous_heartbeat_seq.
           runtime_execution_guard allows that one shape (holder move and the accompanying seq
           reset) and still refuses every other holder move or sequence decrease.
  unchanged: same-holder replay of an elapsed lease -> runtime_execution_expired (as before),
           live lease + foreign holder -> runtime_execution_holder_mismatch,
           passed hard deadline -> runtime_execution_expired,
           completed/revoked/expired -> runtime_execution_not_claimable,
           run no longer current -> run_not_current,
           dispatch_delivery (gate) semantics -> untouched; its guard still pins holder_id, so
           the send right cannot move.
  consequence for the drill: attempt 2 will no longer die in the claim. It claims, the gateway
  answers observed/not_sent, node/src/child-pi.mjs maps a non-success outcome to
  WAITING_RECONCILE, the run parks on wait_reason='reconcile', and FinishAdvance resolves the
  receipt from dispatch_delivery plus the content reference registry. A durable answer therefore
  finishes the run; a missing one stays an unknown for the operator.
