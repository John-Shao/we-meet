## 2. 不需要重新讨论的部分（已定，不重开）

- 编排语义：`RunWorkflow` 契约、取消四时点、派发后失败一律 unknown、对账器只走领域命令——与托管方式无关，两种答案下都不变。
- 业务终态在 Work PostgreSQL，不在 Temporal：workflow 完成标志不是业务终态，history 不作审计/计费来源。因此 **Temporal 不可达只影响推进速度，不影响账本正确性**；这点已由切片与冒烟验证（见 §5）。
- outbox relay 属"义务作业"：kill switch 与组织停用期间不得停投递；这条不因托管方式调整。
- 因此：**U3 的答复不阻塞 E1–E3**（数据层、API、outbox/SSE）继续推进；它只决定 E4 能否从契约与本地切片走到真实部署。

## 5. 证据边界（请勿据此认为"已验证"）

**已在本地验证**（Temporal CLI 1.9.1 / dev server 1.32.0 in-memory、Node 22、PG16、faux model）：

- 编排故障切片 10/10，连续 3 次稳定（含启动前取消、claim 前取消、心跳超时→unknown、跨组织单 relay）。
- S1 参考演练 R01–R05 通过：worker 重启续跑、DB 终态优先、执行开关阻断、outbox backlog 抑制新提交、`patched` 版本切换。
- 逻辑备份/恢复烟雾计数一致。

**尚未验证，只有真实环境能证明**：

- 多节点拓扑；**在途** workflow 的 server 重启（R06 只在 file-backed dev server 上验证过"已完成" workflow，且为修订前结果，未复跑）。
- worker drain 与升级窗口；生产规模下的 sticky cache/PG 争用；真实时钟偏差下的租约接管。
- 全部 SLO 仍为 `not_measured`：告警规则已通过 promtool 校验并带单测，但没有真实序列。
