# 任务模块功能完善实施计划

> 状态：Active（阶段 D 已完成）
> 制定日期：2026-08-26  
> 事实来源：当前代码、数据库迁移及 `docs/features/task_*.md`  
> 关联文档：[当前功能说明](../features/task_module_minimum.md)、[功能缺口与增量路线图](../features/task_module_gap_analysis.md)、[长期规划](../research/long-term-plan.md)、[ADR-0001：有界递归子任务层级](../adr/0001-bounded-recursive-task-hierarchy.md)

## 1. 背景与目标

任务模块已经形成团队任务闭环：任务创建与删除、多人负责人、关注人、任务清单协作、列表/看板/统计、表内编辑、评论附件、通知提醒、会话分享、操作历史，以及会议行动项状态双向同步。全局任务搜索也已交付，可按标题和说明检索，并按人员、状态和截止日期筛选。

下一阶段的重点不是复制完整项目管理套件，而是解决任务数量增长后的日常效率问题，并逐步补齐工作拆解、周期执行和提醒个性化能力。

本计划的目标是：

1. 让用户能够保存常用任务视图，并对大量任务执行安全的批量操作。
2. 支持有界递归子任务，使任务可以按最多 5 级子任务进行拆解和分派，并允许以后通过服务端配置提高深度上限。
3. 支持重复任务，覆盖周会、值班、巡检和周期报表等场景。
4. 支持个人提醒偏好，在保证可靠投递的同时降低通知噪音。
5. 为后续自定义字段、依赖、里程碑、任务图和 AI 员工打下稳定的数据与权限基础。

## 2. 实施原则

- **代码与迁移是事实来源**：计划和功能文档必须随实现同步更新。
- **服务端权限优先**：前端能力字段只用于展示，任何写操作都必须由服务端逐项校验。
- **渐进增强**：先交付个人视图、有界递归子任务和有限重复规则，不首期引入共享视图、无边界层级或完整甘特图。
- **保持兼容**：现有任务 URL、搜索契约、会议行动项同步和通知账本不得被破坏。
- **默认可恢复**：批量操作、重复任务生成和提醒投递必须具备幂等、审计和失败重试能力。
- **真实场景验收**：除单元测试外，关键能力必须进入 PostgreSQL、Redis、Keycloak 和 Chromium 组成的真实 E2E。

## 4. 阶段 A：保存视图

> 状态：Completed（2026-08-29）

### 4.1 产品范围

首期只提供**个人保存视图**。视图保存“如何查看任务”，不复制任务，也不改变任务归属。

保存内容：

- 任务范围：我负责的、我关注的、我创建的、全部相关。
- 状态、日期、优先级和任务清单筛选。
- 排序字段与方向。
- 列表或看板模式。
- 列表显示列及列顺序；若首期列配置尚未稳定，可作为同阶段后续增量。

管理能力：

- 保存当前视图、命名、重命名和删除。
- 固定到任务侧栏并调整顺序。
- 设置一个默认视图；进入任务模块时优先打开它。
- 点击保存视图后，将配置写入现有 URL，刷新与前进/后退行为保持一致。

首期不包含：

- 团队或组织共享视图。
- 视图订阅和通知。
- 保存全局搜索关键字。
- 复杂 AND/OR 条件编辑器。

### 4.2 建议数据契约

新增个人视图模型，建议字段如下：

- `id`、`organization`、`owner`、`name`。
- `config`：版本化 JSON，只接受白名单字段。
- `position`、`is_pinned`、`is_default`。
- `created_at`、`updated_at`。

`config` 首版建议使用以下结构：

```json
{
  "version": 1,
  "scope": "assigned",
  "status": "open",
  "time": "all",
  "priority": "all",
  "task_list": "all",
  "ordering": "due_date",
  "view": "list",
  "columns": ["title", "assignees", "priority", "start_date", "due_date"]
}
```

建议 API：

- `GET|POST /api/v1.0/task-saved-views/`
- `GET|PATCH|DELETE /api/v1.0/task-saved-views/{id}/`
- 排序、固定和默认状态通过 `PATCH` 更新；如后续需要一次移动多条，再增加专用 reorder 端点。

服务端必须：

- 强制按当前用户和组织隔离，不接受客户端传入 `owner`。
- 校验枚举、排序字段、列名和配置版本，拒绝任意 JSON。
- 确保每位用户最多只有一个默认视图。
- 保存清单 UUID 时不扩大清单权限；清单失效、归档或不可见后，打开视图应安全回退并提示用户更新。

### 4.3 前端交互

- 在任务侧栏增加“保存视图”分组和新增入口。
- 当前筛选与已保存配置不一致时，显示“保存更改”或“另存为”。
- 系统快捷入口继续保留，不允许删除或覆盖。
- 删除当前视图后回到“全部相关”或系统默认入口。
- 默认视图失效时回退到现有默认任务页，不能阻止任务模块加载。
- 低于 1024px 的移动设备由移动 App 承接，不在 Web 保存视图范围内。

### 4.4 测试与验收

- 后端：所有权、组织隔离、名称和配置校验、默认唯一性、清单失效、数量上限。
- 前端：URL 与配置双向序列化、保存/重命名/删除、默认视图、失效回退、浏览器前进后退。
- E2E：创建视图、刷新恢复、设为默认、删除后回退；第二个用户不可看到该视图。
- 性能：加载任务页最多增加一次轻量查询；视图数量建议首期限制为每人 50 个。

验收标准：用户可以把“我负责的、本周到期、紧急、按截止日期排序”的任务页保存为命名视图，刷新或重新登录后仍能一键恢复。

### 4.5 收尾记录

- 新增 `TaskSavedView` 与 `/api/v1.0/task-saved-views/` REST 资源；配置采用版本化白名单 JSON，按当前用户和主组织隔离，名称不区分大小写唯一，每个用户/组织最多 50 条且只有一个默认视图。
- Web 任务侧栏支持保存、恢复、覆盖、重命名、删除、固定、默认和排序；未固定视图仍可从管理面板恢复。选择视图会把完整配置及 `saved_view` 标识写回 URL，刷新和浏览器前进/后退沿用既有状态机制。
- 清单在归档、删除或失去访问权限后，服务端响应会将该视图安全降级到全部清单，并由 Web 明示降级原因；不会借保存视图扩大清单权限。
- 首版保存范围、状态、日期、优先级、清单、排序及列表/看板/统计模式。列表列配置尚未形成稳定的用户状态模型，按原计划作为阶段 A 后续增量，不阻塞本次闭环。
- PostgreSQL API 回归 `68 passed`（其中保存视图 6 项），任务前端单元回归 `119 passed`；TypeScript、ESLint、Prettier、Ruff 与迁移漂移检查通过。生产 E2E 仍需部署迁移后执行创建、刷新恢复、默认和第二用户隔离场景。

## 5. 阶段 B：批量操作

### 5.1 首期能力

- 列表视图支持多选、全选当前页和清除选择。
- 单次最多选择 50 条任务。
- 支持批量完成/重开、修改负责人、优先级、任务清单和删除。
- 看板批量操作、跨页全选和“选择全部查询结果”延后。

### 5.2 服务端契约

建议增加统一批量端点：

```text
POST /api/v1.0/tasks/bulk/
```

请求包含 `task_ids`、`operation` 和对应 `payload`；响应明确区分：

- `succeeded`：已成功任务及更新后的必要摘要。
- `failed`：任务 ID、稳定错误码和可展示原因。

批量处理按任务执行权限判断。单条失败不回滚其他合法任务，但同一任务的字段更新、活动记录和通知账本必须在一个事务中完成。重试相同请求不得重复生成通知或活动。

### 5.3 交互与验收

- 批量工具栏固定显示已选数量和可用动作。
- 危险操作二次确认；删除结果展示成功数和失败数。
- 对权限不同的任务不得只按第一条任务推断操作能力。
- 操作完成后只更新受影响缓存，保留仍然有效的选择。

验收标准：50 条以内任务可一次修改；混合权限时返回部分成功，失败项可定位、可重试，操作历史和通知不重复。

## 6. 阶段 C：有界递归子任务/检查项

> 状态：Completed（2026-08-27）

### 6.1 ADR 先行

迁移 `0112_task_parent` 曾引入 `parent`，又由 `0124_remove_task_parent` 删除。模型与 API 实现前必须先评审 [ADR-0001：有界递归子任务层级](../adr/0001-bounded-recursive-task-hierarchy.md)，并以该 ADR 明确以下边界：

- 数据模型使用可空的递归 `parent_id`，不在数据库中固化“只允许一级”或固定最大深度。
- 产品首期根任务 `depth=0`，其下最多 5 级子任务；深度上限由服务端配置，提升上限不需要数据库迁移。
- 每个父任务最多 100 个直接子任务，单棵任务树最多 500 个节点。
- 父子任务删除、移动、归档和恢复策略，以及整个子树的影响提示。
- 循环引用、跨组织挂载、父子可见性、清单成员权限和会话分享边界。
- 统计、搜索、提醒、批量操作及会议行动项同步口径。
- 历史数据和旧迁移不直接恢复的原因。

### 6.2 数据模型与服务端约束

- `Task.parent_id` 指向同表任务；根任务为 `NULL`，任意非根任务仍可作为其他任务的父任务。
- 默认 `TASK_MAX_SUBTASK_DEPTH=5`，根任务深度为 0，允许的子任务深度为 1—5。深度由服务端按父链计算和校验，不使用固定深度的数据库 `CHECK` 约束。
- 创建和移动必须在事务内同时校验目标父链与待移动子树：目标不能是自身或任一后代，父子必须属于同一组织，移动后的最深节点不得超过配置上限。
- 创建和移动后，每个节点的直接子任务不得超过 100 个，目标任务树不得超过 500 个节点；移动子树时按整棵子树计数。
- 父子关系不扩大任何读取或写入权限。查询子任务前仍需按任务自身及完整父链逐项鉴权；任何不可见祖先都不能通过面包屑、搜索摘要、统计或会话分享间接暴露。
- 删除和移动父任务前，服务端返回受影响子树的节点数和层级摘要；前端必须展示明确确认提示。删除按整棵子树执行，移动则保持子树内部结构不变。

### 6.3 产品与查询行为

- 子任务拥有独立标题、负责人、状态、优先级和日期。
- 父任务只展示子任务完成进度，首期不因子任务全部完成而自动完成父任务，也不因父任务状态变化而改写子任务状态。
- 列表默认折叠子任务，详情面板可创建、排序、移动和快速完成；达到深度或数量上限时禁用入口并展示原因。
- 保存视图默认同时匹配根任务和各级子任务。搜索或筛选命中任意子任务时，结果必须展示从根任务到命中节点的完整父链，并对父链上的每个节点执行可见性校验。
- 统计接口显式区分仅顶层与包含子任务，避免无意重复计数。

### 6.4 测试与验收

- 后端覆盖深度 0—5、配置提升、100 个直接子任务、500 个树节点，以及创建和移动的边界值。
- 并发测试覆盖互相移动导致的循环、移动期间的配额竞争，以及跨组织父节点伪造。
- 权限测试覆盖创建人、负责人、关注人、清单角色和会话分享；不可见子任务或祖先不得出现在详情、搜索、筛选、统计和通知中。
- E2E 覆盖五级创建、独立完成状态、完整父链展示，以及删除或移动父任务时的整棵子树影响提示。

验收标准：用户可以把根任务继续拆解到第 5 级并分别指派；第 6 级、循环引用、跨组织挂载、超过直接子任务或整树配额的写入均被服务端稳定拒绝；子任务状态保持独立，搜索和筛选展示完整可见父链，删除与移动提示及结果符合 ADR。

### 6.5 收尾记录

- 模型、迁移、服务端配置、递归查询、稳定错误码、整树移动/删除和完整父链鉴权均已落地；组织级稳定事务锁覆盖并发创建与互相移动竞争。
- 详情面板支持子任务就地编辑、负责人、截止日期、完成/重开、逐级进入和直接子任务排序；排序支持专用拖拽把手与上移/下移按钮，并通过原子 reorder 接口提交完整同级快照。任务列表的分组移动也仅从专用把手发起，把手可通过键盘或触控打开目标分组菜单。
- 列表与详情已完成层级 UX 收尾：详情打开时列表收敛为标题、负责人、优先级和截止日期四列，树节点支持键盘展开、收起、移动焦点和完成；父任务存在未完成子项时，完成动作会明确确认，已完成父任务继续展示剩余子项提示。筛选区可识别并逐项清除生效条件，空结果和请求失败提供恢复操作，行操作入口与详情属性分组也已统一。完成/重开、负责人修改和任务移动提供统一 Toast，并以服务端反向写入实现有限撤销；重复任务完成和删除不提供语义不完整的前端撤销。Web 视觉验收覆盖 1024、1366、1439、1440 和 1600 像素宽度；1439px 及以下使用居中的全屏详情，1440px 起恢复右侧详情面板。低于 1024px 的移动设备由移动 App 承接，Web 不保留小屏降级实现或视觉基线。
- 加载体验已使用与最终内容结构一致的骨架占位：首屏按列表或看板模式展示对应骨架，详情预留标题、属性分组和协作区高度，子任务、评论、附件及操作历史各自保留稳定区域；错误态和空态保持独立，无障碍状态继续播报加载文本，减少异步数据到达时的布局跳动。
- 通知在入队、领取和到期提醒阶段均复核完整父链，清单成员和会话分享不能造成子任务越权暴露。
- PostgreSQL 后端层级与任务回归测试 `84 passed`，任务模块前端单元测试 `95 passed`；TypeScript、ESLint、Prettier 和 Ruff 检查通过。
- 真实 Keycloak、PostgreSQL、Redis、后端和 Chromium 环境的任务 E2E 覆盖核心任务、重复任务、递归层级和桌面响应式视觉；桌面视觉基线验证列表与详情在 Web 支持宽度内的稳定切换。

## 7. 阶段 D：重复任务

> 状态：Completed（2026-08-27）

### 7.1 模型原则

采用“重复规则 + 当前实例”模型，完成或到达生成窗口时创建下一实例，不无限预生成未来任务。

首期支持：

- 每日、每周、每月。
- 每 N 天/周/月。
- 可选结束日期或生成次数。
- 按规则所有者时区计算。

实例继承标题、说明、负责人、关注人、清单、优先级和日期跨度；不继承评论和操作历史。附件采用引用还是复制必须在实现前明确，首期建议不自动复制附件。

### 7.2 一致性与边界

- 通过规则 ID 与周期键保证生成幂等。
- 修改时明确“仅本次”和“本次及以后”；“全部历史实例”首期不支持。
- 月末、闰年、夏令时、规则停用、清单归档和负责人失效均需确定行为。
- 会议行动项生成的任务默认不可设置重复，直至同步语义单独评审。

验收标准：调度器重复执行不会生成重复实例；月末、时区和失败重试测试稳定通过。

### 7.3 收尾记录

- 新增 `TaskRecurrenceRule` 与任务实例的 `recurrence_rule`、`recurrence_key`、`recurrence_sequence`，通过规则 ID + 周期日期唯一约束保证幂等。
- 支持每日、每周、每月与每 N 周期，以及结束日期或生成次数；规则时区由所有者配置快照确定。
- 完成任务会立即生成下一实例，既有提醒定时命令会按所有者本地日期补建到期实例；两条路径共用事务锁和幂等生成器。
- 实例继承标题、说明、负责人、关注人、清单、分组、优先级和日期跨度，不复制评论、历史或附件；月末规则保持月末语义。
- 模板字段修改支持“仅本次 / 本次及以后”，规则可停止但不改写历史；会议行动项任务和层级节点首期禁止重复。
- 清单归档、所有者或负责人失效时规则停止并记录稳定错误；调度失败回滚后可安全重试。
- PostgreSQL 阶段 D 测试 `7 passed`；任务 API、层级和重复任务联合回归在完整本地凭据下 `91 passed`。任务前端单元测试 `69 passed`，并新增真实 OIDC + Chromium 重复任务场景；TypeScript、ESLint、Prettier 与 Ruff 检查纳入收尾验证。

## 8. 阶段 E：提醒偏好

### 8.1 首期范围

- 每个用户可选择截止日当天、提前 1 天或提前 3 天提醒。
- 用户可关闭某一任务对自己的日期提醒。
- 多位负责人分别保存偏好，互不影响。
- 逾期提醒仍为一次性，不首期提供每日催办或稍后提醒。

### 8.2 技术要求

- 继续复用 `TaskImDelivery` 的收件人、事件和参考日期幂等约束。
- 偏好变化只影响尚未投递的提醒，不撤回已发送消息。
- 负责人增删、任务完成/重开和日期变化必须重新计算有效提醒。
- “截止具体时刻”会改变当前纯日期语义，应单独立项。

验收标准：同一任务的不同负责人可以收到不同提前量的提醒；关闭提醒后不会新建对应投递记录，重试不会重复发送。

实施状态（2026-09-02）：阶段 E 已完成。系统设置提供不提醒、截止当天、提前 1 天和提前 3 天四档个人默认值；任务详情允许每位参与者独立跟随系统设置、覆盖提前量或关闭该任务提醒，任务级选择始终覆盖系统设置。提醒扫描按参与者时区和任务级覆盖生成幂等投递，偏好变化会作废尚未发送的跟随项，并在新的有效触发日安全重激活；无参与角色的用户不能读取或修改任务级提醒偏好。

## 9. P1：轻量项目管理增强

P0 稳定后，根据真实使用数据逐项立项：

1. **清单模板**：支持会议待办、发布检查、入职和巡检模板；复制字段、分组和任务骨架，不复制成员与历史。
2. **自定义字段与高级筛选**：先支持文本、数字、日期、单选和人员字段；标签如需恢复，应纳入统一字段模型。
3. **依赖、里程碑与时间线 MVP**：先实现阻塞关系和里程碑，再提供只读时间线，最后评估拖拽排期。
4. **日历视图与日历联动**：复用现有日历模块，不复制日期编辑和时区逻辑。
5. **会议行动项字段同步扩展**：逐字段评估标题、负责人和截止日期同步，保留人工覆盖优先和冲突审计。

依赖、里程碑和时间线必须成套设计；不先交付只有外观、没有约束能力的甘特图。

## 10. P2 与长期方向

以下能力需要在客户需求、使用频率和商业价值明确后再建设：

- 自动化规则、表单收集和审批节点。
- 工作量、容量、工时和人员排期。
- 多清单归属、项目组合和目标管理。
- 外部协作者、跨组织负责人和开放 Webhook。
- 第三方任务导入导出与日历订阅。

长期规划中的“AI 员工、把任务分配给 AI 员工、任务图”依赖稳定的任务层级、依赖关系、权限和活动审计：

- AI 员工必须作为可识别、可审计且权限受限的执行主体接入，不能绕过现有任务能力字段。
- AI 进展应写入结构化活动和评论，允许人工暂停、接管和撤销授权。
- 任务图应建立在有界递归子任务与显式依赖之上，不能仅从标题或自然语言推测关系作为事实。
- 上述能力均需单独 ADR 和安全评审，不纳入当前 P0。

## 11. 质量、性能与发布门槛

每个阶段都必须满足：

- 后端权限、参数校验、幂等、分页稳定性和查询数测试。
- 前端序列化、空态、失败重试、键盘操作和 ARIA 测试。
- 至少一条真实 OIDC Chromium 主流程；涉及协作权限时增加第二用户场景。
- 迁移可向前部署，旧前端在滚动发布期间不会调用失败。
- 更新功能说明、API 文档、缺口路线图和 Changelog。

规模基准：

- 500 条可见任务下，列表和保存视图首屏无明显退化。
- 5,000 条组织任务下，任务查询和统计不得出现负责人、关注人或清单关系导致的 N+1。
- 批量操作上限 50 条，响应必须给出逐项结果。

发布策略：

1. 数据模型和只读接口先部署。
2. 写接口与前端入口通过功能开关逐步开放。
3. 观察错误率、查询耗时、批量部分失败率和通知重试量。
4. 验收通过后移除临时开关；异常时关闭入口，不回滚已合法写入的数据。

## 12. 推荐执行顺序与里程碑

1. **M1：个人保存视图**——先交付保存、恢复、重命名、删除、固定和默认视图。
2. **M2：批量操作**——完成列表多选及五类首批动作。
3. **M3：有界递归子任务**——ADR 评审通过后实现模型、权限、UI、搜索和统计。
4. **M4：重复任务**——实现规则、生成器、时区与幂等保障。
5. **M5：提醒偏好**——开放个人提前量和单任务关闭能力。
6. **M6：P1 决策点**——依据视图使用、批量操作、子任务和重复任务数据，选择自定义字段或依赖/里程碑方向。

每个里程碑独立上线、独立验收，不等待后续阶段打包发布。阶段 C 必须先完成计划与 ADR 评审，再进入模型和 API 实现。
