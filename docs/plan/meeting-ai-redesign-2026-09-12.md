## 1. 产品方向

会议 AI 的核心产出是：**有依据的结论、经过确认的行动项、可以继续跟进的任务**。

用户会后打开会议，首先回答三个问题：决定了什么、我需要做什么、哪里还没有定。AI 问答作为查证和追问入口，会中提供安静的跟进辅助，会前复用历史结论准备议程。

默认采用「纪要优先」布局；行动密集的项目例会可以探索「行动项优先」，首期不增加用户必须配置的布局选项。

## 3. 信息架构与入口

### 会议列表

会后列表的一行代表一次场次，显示标题、实际日期/时长、参与人，以及「整理中 / 待核对 / 已确认 / 部分失败」中最需要用户处理的状态。状态不只靠颜色表达。

无纪要、生成失败的会议也能进入详情，不以“已有纪要”作为会议历史的存在条件。同一固定房间的多次会议按时间区分，标题相同也能定位。

### 会后详情

- 标题区：会议名、场次日期与时间、参会人、材料更新时间；会议属性按需展开。
- 一级页面：**纪要 / 行动项 / 原文**。默认进入纪要；来自任务或引用的链接直接定位目标。
- 纪要顺序：一句话概览 → 已达成的决定 → 待解决问题 → 讨论摘要。无结论时明确“本场未形成明确决定”，不补造内容。
- 行动项在纪要底部给出少量预览及待核对数量，完整管理在行动项页；共享同一数据状态。
- 原文页整合章节目录、说话人、时间和搜索。录制存在且有权限时支持播放；否则仍可定位文字。
- 右侧上下文区在“问本场会议”和“查看依据”之间切换，一次只展示一种；窄屏改为顺序展开或全屏面板，保留阅读位置。
- 已结束会议主操作随状态变化：整理中查看原文；待核对确认纪要；已确认查看行动项。分享是独立动作。

### AI 问答入口

会中与会后均使用「问本场会议」，清楚显示范围和材料截止时间。会后增加“决定为什么改变”“有哪些未解决问题”等建议问题；不以空白聊天框作为详情首屏。

跨会议问题进入已有全局问答，显示「我有权访问的会议」及当前筛选条件。切换范围开启新上下文，避免把先前问题和引用悄悄带进新范围。会议内不默认引入聊天、日历等其他数据源。

## 4. 关键流程

### A. 会前：准备可使用的议程（P2）

创建会议时保留议题、资料和 AI 记录设置。仅在有关联上次会议或用户选择历史会议时，生成议程建议：上次未解决问题、尚未完成的关联任务、本次需决策事项。

建议由用户选择后加入议程。历史会议和任务分别执行权限检查；不能因加入新会议而获得历史材料权限。无历史数据时提供普通议程编辑。

### B. 会中：跟上进度（P1，范围修复先做）

工具栏保留清晰的「AI 记录」状态，进入会议时能知道是否正在转写、谁能查看材料。设置控制与个人字幕显示分开：隐藏自己的字幕不等于停止会议记录。

面板优先提供三个动作：「帮我跟上进度」「刚才有什么决定」「查看原文」。回答标注覆盖区间及转写更新时刻，未覆盖部分不冒充全场总结。长会采用分段检索与聚合，不能只截取最近文本后称为完整会议。

问答默认本人可见；写入共享纪要或转成任务必须经过相应编辑流程。AI 识别到行动项可以进入共享待核对区，不自动指派，不反复弹窗打断讨论。语音 AI 如保留，作为显式邀请的可选模式，启动/停止权限与文字私有问答分开设计。

### C. 会后：核对并确认纪要（P0）

1. 场次结束后显示“正在收齐转写”，随后分项显示纪要和行动项处理状态。等待最后字幕的截止水位必须可追踪，晚到数据标记为增量。
2. 生成草稿立即可读，展示“AI 草稿 · 尚未确认”。转写不完整时明确缺失区间；全文无材料时提供手写纪要入口。
3. 关键决定和行动项附可点击的来源，打开同场次原文片段及上下文。发言内容与 AI 推断分开，不能以生成的时间戳伪造引用。
4. 有权管理会议的人编辑草稿并确认纪要，记录确认人和版本。不要求所有行动项都已分派才能确认纪要；未确认事项继续标为待核对。
5. 重新生成产生新候选版本；对比并采纳，不覆盖已确认内容、人工修改或关联任务。有人同时编辑时提示版本变化并允许合并。

**分发行为的提议变更**：现有代码生成后就尝试推送文档和 IM。建议生成时发送一次“纪要草稿已就绪”的入口提醒，确认后更新同一入口指向的正式版本，避免重复推送全文。这需要调整后端分发与文档同步，不是更换按钮名称。

“确认纪要”只改变内容版本状态，不自动扩大可见范围。主动“分享”展示接收范围与所分享版本；原文、录音访问仍单独校验。首期不新增匿名公开链接。

### D. 行动项：从建议到任务（P0）

每条包含：要做什么、负责人、截止时间、来源、当前状态。缺失值写成“待指定 / 未约定”，AI 原话里的“小王”“尽快”不能自动解析成已确认身份或日期。

操作顺序：查看依据 → 补充或修改 → 确认行动项 → 按需创建任务。把“确认”与“创建任务”保留为不同动作，用户可只记录会议承诺。

- 负责人候选按服务端授权范围提供，同名显示组织/身份辅助信息；未解析访客只保留文本，不凭显示名绑定账户。
- 截止时间允许不填；把相对日期建议转换为明确日期时展示会议日期和时区，让用户确认。
- 创建任务展示内容、负责人、日期、目标清单以及该清单的可见范围。只列出有创建权限且未归档的清单；使用默认清单也要可见。
- 创建请求幂等；失败保持“已确认 · 尚未创建任务”，可重试。成功显示任务链接，重复点击进入同一任务。
- 完成/重新打开沿用现有双向同步与人工覆盖保护，显示最近来源，例如“随任务完成”；同步失败给出重试入口和可理解原因。
- 创建后任务作为执行信息的主要编辑入口；纪要保留确认时的承诺快照。负责人、截止时间、标题的双向同步不在首期隐式新增。
- 忽略建议保留记录；重新生成不能把已忽略或语义重复事项反复当成新建议。
- 会议阅读权限不自动授予关联任务访问权；任务链接无权限时只显示当前用户有权看到的会议承诺信息。

## 5. 权限与数据范围

以下为目标规则；现有 ACL 与新增场次访问政策必须在实现时逐项对齐，不能只靠前端隐藏。

| 操作 | 目标权限 |
| --- | --- |
| 查看纪要/原文、问本场会议 | 具有对应场次、对应材料读取权限的用户；问答检索与引用打开均重新校验 |
| 编辑、确认纪要、重新生成 | 会议 owner/admin，首期沿用现有纪要编辑角色；重新生成接口必须显式对齐此限制 |
| 编辑行动项、调整负责人、忽略建议、创建任务 | 会议管理者；创建任务还需目标清单创建权限 |
| 确认、完成、重新打开自己的行动项 | 被指派人，在已授权范围内保留现有能力；不能借此修改其他字段 |
| 分享纪要、调整可见范围 | 复用现有会议分享权限；发布确认不能顺带扩权 |
| 启停共享转写/语音 AI | 建议由会议管理者控制，普通成员可申请；此为需实现的产品规则，不能宣称现有 token 鉴权已保证 |

“实际参会”用于识别本场参与人，但不等同于无限期的材料访问授权。访客入会令牌不自动授予历史会议材料和跨会搜索权限。持久成员新增/移除后对历史场次的影响应通过明确的场次授权策略决定，迁移时保持已有可见范围并审计差异，不静默放开或回收。

问答输入、回答和临时草稿默认个人可见；只有用户明确保存到共享纪要才成为会议材料。缓存键包含用户、组织、场次和范围；退出登录、切换组织与范围时清理或隔离缓存。处理转写中的指令性内容时视为被引用的数据，不允许它改变权限或触发任务/消息操作。

## 6. 状态与异常

| 状态 | 用户看到什么 / 可以做什么 |
| --- | --- |
| 未启用记录 | “本场未开启 AI 记录”；仍可手写纪要，不展示空白加载 |
| 转写进行中/有延迟 | 显示已记录到的时间；查看已有原文，问答提示覆盖区间 |
| 场次结束、材料收集中 | 显示正在收齐转写，不把离开房间或共享房间关闭混为本场结束 |
| 纪要成功、行动项失败 | 已有纪要可读；行动项区域显示失败并独立重试，不能写“无行动项” |
| 未提取到行动项 | “未发现明确行动项”，允许人工添加 |
| AI 不可用/额度不足 | 保留原文、人工编辑与任务入口；说明稍后重试，避免无限转圈 |
| 原文无支持/检索覆盖不足 | 明确未找到依据，显示覆盖范围，不编造结论 |
| 已确认后有晚到转写/新生成内容 | “有新增材料待核对”，已确认版本继续可读 |
| 原文删除或权限改变 | 引用显示不可用，不回退展示缓存片段；其他有权限材料仍可用 |
| 文档或 IM 分发失败 | 纪要仍是成功状态，单独显示同步失败；重试不生成另一份任务/纪要 |

## 7. 实现拆分与数据契约

### 第一阶段 P0：会后完整闭环

先完成场次范围基础，再做会后 UI 和证据链。交付：场次列表/深链、三页信息架构、分项处理状态、可核对草稿、带来源行动项、确认/任务创建、版本保护与分发状态。

建议契约（待实现，不表示已有接口）：

- 用显式 `session_id` 访问材料、问答、重生成和操作结果；旧房间入口作为兼容适配，先解析一次确定场次后再跳转，不能每个请求各选“最新”。
- 统一来源对象：`session_id, transcript_ids, start_offset_ms, end_offset_ms, quote`；服务端验证 ID 归属和引用文字，展示时间由原始数据计算。无来源输出保持待核对。
- 处理状态按 transcript/summary/action_items/chapters/delivery 分开，失败项可独立重试。`pending/success/failed` 不承担“已确认”语义。
- 增加确认版本、确认人/时间、输入材料水位和并发版本号；AI 输出、人工编辑、正式确认保留关联关系。
- 行动项保留稳定 ID、人工修改标记与来源；重生成按版本追加/比对建议。复用现有任务关联、幂等与同步服务。
- 任务目标清单选择是现有无请求体转任务接口的扩展，必须先核对任务创建服务的权限、默认清单与通知契约。
- 文档/IM 分发按场次与内容版本幂等；既有已发送消息不回撤，历史纪要标记为旧版材料，不自动伪装成“人工确认”。

### 第二阶段 P1：会中辅助与会后追问

修正现有 RoomAI 的 room 级检索可以先于完整 P1 发布。随后交付：本场材料检索、来源可点击的流式回答、跟上进度、覆盖时间提示、会后同场追问、失败可取消/重试。优先复用 GlobalAsk 的检索和引用能力，但必须新增硬性的场次过滤及对应授权，不能仅在提示词里写“只问本场”。

### 第三阶段 P2：会前与连续会议

交付：选择关联会议、生成议程建议、回顾未完成任务、跨场次决策变化比较。跨会结论逐场引用并显示时间；先验证使用需求和质量，再评估语音主动参与或更复杂自动化。

首期不扩展通用人格聊天、AI 自动代替主持人决策、自动跨范围分享、无需核对的批量派任务。现有通用/语音 AI 服务无需在本次规划中直接删除。

## 8. 验收与评估

发布门槛使用可复现样例，行为性门槛要求全部通过：

1. 同一房间连续开两场会：详情、原文、问答、重新生成、分享均保持选定场次，不混入另一场材料。
2. 关键结论/行动项点击来源可定位正确原文；错误 ID、跨场次 ID、删除及权限撤销均安全降级。
3. 纪要生成成功但行动项失败时，界面显示部分失败并可单独重试。
4. 人工修改未确认建议、确认纪要、创建任务后再生成，人工内容与原任务均保留，不产生重复执行项。
5. 同名参会人、未登录访客、模糊日期、无负责人、无截止时间均可明确处理；模型不静默指派。
6. 创建任务重复点击、超时后重试、清单已归档或权限中途变化，都不会重复创建或越权写入。
7. 完成/重新打开同步遵守人工覆盖规则，能解释状态来自哪里；部分失败可以恢复。
8. 普通成员不能编辑纪要或管理他人行动项；有任务权限但无会议权限者不能通过任务来源读取会议原文。
9. 晚到转写、并发编辑、模型失败、IM/文档失败不会破坏可读版本或触发重复分发。
10. Web 键盘操作和主要断点可完成来源核对、确认及转任务；Android 需在单独实现中验证等价流程，不能以 Web 原型代替验收。

上线前用真实授权、去标识化的短会/长会/跨语言/无明确决定样本测量：结论事实准确率、引用支持率、行动项负责人/日期误填率。先建立现状基线再确定目标，不能将原型示例视为质量评估。

上线后观察：进入会后页到首次确认的中位耗时、建议采纳/编辑/忽略比例、转任务成功率、重复任务数、问答无依据回答比例、引用打开成功率、生成延迟 P50/P95。耗时下降需同时满足事实和权限质量，不单独追求更多生成或更多任务。

## 9. 评审焦点

本提案默认推荐：纪要优先、会后闭环先行、管理者确认纪要、个人问答不自动共享、生成提醒与正式内容分开。最值得评审的是“确认纪要”的组织习惯以及默认任务清单；两者会影响操作成本与实际协作方式。

本次交付为规划与本地交互草案，没有修改运行时代码，没有连接 AI、创建任务或发送通知。实施时应按上述阶段分别提交并验证，不能将原型中的成功反馈当作后端能力已完成。
