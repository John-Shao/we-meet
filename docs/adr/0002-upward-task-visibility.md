# ADR-0002：子任务向上可见

> 状态：Accepted  
> 实现状态：Completed  
> 日期：2026-08-28  
> 决策范围：任务可见性、协作权限、会话分享边界  
> 修订：[ADR-0001](0001-bounded-recursive-task-hierarchy.md) 第 4 节「权限不沿父子关系自动扩大」  
> 关联文档：[任务模块现状说明](../features/task_module_minimum.md)

## 背景

ADR-0001 第 4 节规定：父任务与子任务各自独立鉴权，任何一方都不得因为父子关系获得另一方的读取权限；返回子任务前必须确认调用者能查看**完整父链**，任一祖先不可见时该子任务不得出现在任何结果中。

该规则在实现上产生了一个比预期更强的后果：它不只是"看不到父任务"，而是**子任务的协作者连自己那条子任务也看不到**。详情返回 404，列表、搜索、统计为空，通知被抑制。原因是被调用链上的 `filter_visible_task_hierarchy` 与 `visible_task_ancestor_path` 要求整条父链可见，而父链对子任务的负责人往往不可见。

同时，写入侧的 `validate_parent_visibility_for_collaborators` 会拒绝"把子任务指派给看不到父链的人"，因此"子任务负责人看不到父任务"这个状态在正常 API 流程中无法产生，只能由管理脚本或历史数据造成。这使系统既不能表达飞书式的"子任务负责人可以查看父任务"，也无法让用户自行修复这类数据。

飞书任务的产品约定是：子任务负责人**可以查看父任务，但不能编辑父任务**。这是"上下文授权"而非"权限继承"——它只向上、只读，不下传、不外扩。

## 决策

### 1. 可见性向上闭合，且仅向上

一条任务对调用者可读，当且仅当满足任一条件：

- **直接可见**：调用者是创建人、负责人、关注人、所属任务清单的成员，或通过 `shared_via` 读取其被分享到的会话；或
- **向上可见**：调用者对其**某个后代**直接可见。

祖先链是传递的：若调用者对深度 k 的节点直接可见，则其 0…k-1 层祖先全部可读。兄弟节点不在链上，因此**不因该规则变得可见**。

### 2. 上调只授予读取，不授予任何写入能力

这是本 ADR 的关键边界，也是它可以安全落地的前提：所有能力字段（`can_edit`、`can_update_status`、`can_delete`、`can_comment`、`can_manage_attachments`、`can_manage_followers`、`can_manage_reminder`、`can_create_subtasks`）都**独立于可见性**计算，继续只依据创建人、负责人、关注人、任务清单角色和会话分享。

因此一个通过向上可见打开的父任务，仍然稳定返回 `can_edit: false`，`PATCH`/`DELETE`/评论/附件上传/关注人管理全部返回 403。无需为此新增任何权限判断。

可见的内容是父任务的详情、评论、附件元数据与活动历史；附件**下载**沿用既有规则（要求内容管理权限），只读访问者同样无法下载。

### 3. 会话分享不参与向上可见

`shared_via`（会话分享）只授予**直接**可见性，不向上传播。原因：会话成员是一个可能很大的受众，如果分享一条子任务卡片就能让整个会话读到未分享的祖先，ADR-0001 第 4 节「会话分享只作用于明确分享的任务，不递归分享祖先或后代」就被推翻了。

写入侧继续由 `validate_conversation_ancestor_chain` 保证：把任务分享进会话前，其整条父链必须已分享进同一会话。由于当前没有"取消分享"接口，该不变量在读取时始终成立；`_filter_visible_ancestor_chain` 仍会在 `shared_via` 路径上显式走一遍祖先链作为纵深防御。

### 4. 写入侧不再为父子可见性设限

`validate_parent_visibility_for_collaborators` 对协作者（负责人、关注人、清单成员）的检查被移除：既然协作关系本身就带来向上可见，这个状态不再"坏"，该检查只会阻止合法操作。

保留的检查：

- `validate_task_parent_change`：循环、跨组织、深度、直接子任务数、整树节点数。
- `validate_conversation_ancestor_chain`：父链必须与分享目标同会话。
- `validate_subtree_parent_visibility`：移动子树时，子树中每个节点的所有分享会话仍须包含目标父链。

### 5. 提供部署级开关

`TASK_UPWARD_VISIBILITY`（默认 `True`）关闭后回到 ADR-0001 第 4 节的严格行为。关闭时读取路径会重新启用祖先链校验，因此列表、详情、搜索、统计、活动与通知不会出现"可见子任务但父链不可见"的泄露。

## 结果与权衡

收益：与飞书任务的产品语义对齐；子任务负责人总能看到自己任务的上下文；ADR-0001 留下的"可见性漂移导致子任务静默消失"问题一并消除。

代价是**读取面显著扩大**：任何能读到子树中任一节点的人，都能读到整条祖先链。具体地，把一个子任务放进一个 100 人的任务清单、或指派给一名外部协作者，会让这些人都能读到此前不可见的父任务标题、说明、评论与附件元数据。这是"上下文授权"模型的固有代价，飞书接受该代价；本 ADR 通过只读约束、会话分享豁免和部署开关限制其影响面。

默认任务列表的 `scope` 为 `assigned`，所以祖先不会进入用户的任务中心；只有显式 `scope=all` 才会包含祖先。`statistics` 与 `activity` 沿用同一可见集，口径一致。

## 不采用的方案

- **保留 ADR-0001 的严格规则**：实现上最省事，但子任务负责人看不到自己的任务，且无法通过产品流程修复。
- **向上可见同时授予编辑**：会让子任务负责人改写自己无权负责的父任务，覆盖父任务负责人的决策。
- **向上可见同时授予评论**：评论会产生通知与活动记录，属于写入面，先保持只读；如产品需要，应另立 ADR。
- **让会话分享也向上传播**：等于推翻了"分享不递归"的不变量，泄露面无法界定。
- **把祖先加入 `scope=assigned`**：会让用户的任务中心塞满自己并未负责的任务，掩盖真正的待办。

## 实现验证

- 可见性谓词集中在 `core/services/task_hierarchy.py`：`apply_task_visibility`（直接 + 向上）与 `directly_visible_task_ids`（仅直接，用于进度与只读判定）。
- 向上部分以深度为界生成固定数量的 `parent_id` 索引子查询，不依赖递归 SQL，也不受循环数据影响。
- 后端层级测试覆盖向上可见、兄弟不可见、只读拒绝、无父权限指派的放行、会话分享不泄露、开关关闭回退。
