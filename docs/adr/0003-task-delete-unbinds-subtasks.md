# ADR-0003：删除任务解绑子任务

> 状态：Accepted  
> 实现状态：Completed  
> 日期：2026-09-11  
> 决策范围：任务删除、父子引用、删除确认与清理  
> 修订：[ADR-0001](0001-bounded-recursive-task-hierarchy.md) 第 7 节「删除和移动按整棵子树提示与执行」  
> 关联文档：[任务模块现状说明](../features/task_module_minimum.md)

## 背景

ADR-0001 第 7 节规定：删除任意父任务会删除其整棵子树，执行前必须返回受影响节点总数并要求二次确认。该决策把删除当作"整棵树的操作"，并据此设计了 `confirm_subtree_node_count` 快照校验。

它与飞书任务的产品约定相反：飞书里删除父任务**不会**删除子任务，只清除父子引用，子任务变成独立任务继续存在。差异的后果不是体验问题而是数据丢失问题——子任务有独立负责人、独立状态、评论、附件和历史，删除父任务等于替所有子任务的协作者做了一次他们从未同意的不可逆删除。

同时该规则产生了一个难以解释的副作用：删除要求调用者能删除子树中**每一个**节点，因此一个自己看不见的子任务会阻止自己删除自己的任务，且为了避免泄露规模，服务端只能返回一个不带节点数的 403。

## 决策

### 1. 删除只影响被点名的那一条任务

`DELETE /api/v1.0/tasks/{id}/` 删除且仅删除该任务。它的**直接**子任务被解除父子引用（`parent` 置空），成为独立根任务；这些子任务各自的子树、负责人、关注人、评论、附件与历史完全保留。更深层的后代父链不变。

### 2. 在模型层保证该不变量，而不是只在删除接口里

`Task.parent` 的 `on_delete` 由 `CASCADE` 改为 `SET_NULL`（迁移 `0142_alter_task_parent`）。层级删除语义因此对**所有**删除路径成立，而不只是任务接口：任务清单的 `delete_unassigned` 清理、管理后台、组织级联、任何管理脚本都不会再连带摧毁子树。

Django 的 PostgreSQL 后端不在 DDL 里生成 `ON DELETE` 子句，`on_delete` 完全由 ORM 收集器实现，因此该迁移的 `sqlmigrate` 输出是 `(no-op)`：它不重写线上外键约束，只改变 Django 的删除行为。

### 3. 删除权限只看任务本身

删除要求调用者是任务创建人或任务清单编辑者，与 `can_delete` 能力字段一致。子任务不再参与鉴权，因此：

- 解绑不是破坏性操作，不需要被解绑节点的授权；
- "看不见的后代阻止删除"这条规则消失；
- 服务端不再有机会通过 403 泄露自己子树里存在不可见节点。

### 4. 取消服务端子树节点数确认，保留移动的确认

删除的爆炸半径恒为一条任务，`confirm_subtree_node_count` 这类"确认的规模与实际的规模一致"的保护失去了保护对象，因此删除不再要求任何确认参数。客户端仍然弹出确认对话框（不可逆操作），但文案从"将删除整棵树"改为"子任务会保留并成为独立任务"。

`subtree-impact` 接口与**移动**的 `confirm_subtree_node_count` 校验保持不变：移动父任务仍然原样搬走整棵子树，仍然需要整棵树可见并确认节点数。移动的爆炸半径没有变，保护也不应改变。

### 5. 被提升的子任务留下层级变更记录

每个被解绑的直接子任务都会写入一条 `HIERARCHY_CHANGED` 活动（`parent` 由原父任务变为 `null`），操作者记为删除发起人。父链消失是用户可见的层级变更，必须可审计。

`position` 刻意保留，使被提升的任务保持原有同级顺序。

### 6. 其余清理仍只作用于被删除的任务

行动项解绑、重复规则停用、附件与文件清理、删除通知都只针对被删除的那一条任务。原实现为整棵子树逐节点执行这些清理，现在子树不再被删除，也就不再需要。

## 结果与权衡

收益：与飞书任务的产品语义对齐；删除不再造成用户未同意的数据丢失；"删不掉自己的任务"和"403 泄露子树规模"两个问题一并消除；任务清单级的批量清理顺带获得了同样的安全性。

代价：删除不再是"清理一棵树"的快捷方式。希望整棵树消失的用户必须逐个删除，或未来由产品提供一个显式的"删除整棵子树"选项。同时，父任务被删除后，原子任务与父任务的关联事实只存在于被提升任务的活动历史里——这也正是第 5 条要求记录活动的原因。

另外，删除父任务不再减少"任务总数"以外的统计：子任务转为根任务后仍计入列表与统计，`roots_only` 口径下的根任务数会增加。

## 不采用的方案

- **保留整树级联删除**：与飞书语义相反，且会造成不可逆的数据丢失。
- **保留级联但强化确认**：确认只能让用户知情，不能挽回子任务协作者未参与决策的事实。
- **把子任务重新挂到原父任务的父任务上**：会改变用户没有要求改变的树形结构，并可能让子任务继承一个新的上级。
- **仅在删除接口里解绑，不改模型**：任务清单批量清理、管理后台等路径仍会级联摧毁子树，不变量无法保证。
- **服务端继续要求解绑子任务数确认**：爆炸半径不再随之变化，确认只是噪音；且真实子任务数对调用者未必可见，强求一致反而会泄露不可见子任务的数量。

## 实现验证

- `core/api/tasks.py` 的 `destroy` 只删除被点名的任务；`_unbind_direct_subtasks` 解绑直接子任务并记录层级变更活动。
- 迁移 `0142_alter_task_parent` 将 `parent` 改为 `SET_NULL`，`makemigrations --check` 无漂移。
- 后端层级测试覆盖：删除父任务后子任务与孙任务仍存在且父链只解除一层、被提升任务记录 `HIERARCHY_CHANGED`、同级顺序保留、不可见后代不再阻止删除、`subtree-impact` 仍为移动保留整树口径。
