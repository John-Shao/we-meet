# ADR 0006：Work 逐步吸收 Task

> 状态：Accepted
>
> 实现状态：Not started
>
> 日期：2026-10-24
>
> 决策范围：Work 与任务模块的入口、数据关系、权限边界与迁移节奏
>
> 关联：[Work 方案](../plan/work-module-product-architecture-agent-plan-2026-09-21.md)、[ADR-0001](0001-bounded-recursive-task-hierarchy.md)、[ADR-0002](0002-upward-task-visibility.md)、[ADR-0005](0005-work-two-layer-access.md)

## 背景

产品里同时存在两个相邻概念：

| 入口 | 数据模型 | 语义 |
|---|---|---|
| 任务 | `core.Task`（`core/models.py:5196`） | 人际协作：创建人、负责人/协负责人、关注人、父子层级、任务清单、开始/截止日期、优先级、重复规则、提醒、手动完成 |
| 工作 | `work.WorkTask`（`work/models.py:62`） | 个人向 Agent 交代目标：owner + organization、目标、背景、来源、run、成果 |

`core.Task` 已经有一套成熟的协作与可见性规则（ADR-0001、ADR-0002），`WorkTask` 则是 owner 范围内的一次执行请求。两者当前互不相通：用户要记一件事去“任务”，要 AI 做一件事去“工作”，同一件事可能被重复创建两次。

用户已决定 **Work 逐步吸收 Task**。本 ADR 定义“逐步”的边界，避免在能力尚未对齐时做高风险的单表合并。

## 决策

### 1. 对外只保留一个入口：我的工作

- Work 二级导航中的“我的工作”成为唯一用户面向的工作列表；独立“任务”入口在阶段 4 前保留但指向同一读模型，阶段 4 后下线并重定向。
- 中文界面统一用“我的工作”作为页面名，“任务”作为条目的一个类型；不引入第三个名词。
- 入口统一不等于数据合并。阶段 1–3 期间 `core.Task` 与 `WorkTask` 继续分表。

### 2. 用链接表表达关系，不合并表

新增 `WorkTaskLink`（Work app）：

- `work_task`：OneToOne → `work.WorkTask`。
- `task`：FK → `core.Task`，索引。
- `relation`：`created_from`（从任务发起执行）/ `attached`（执行结果挂到既有任务）。
- `created_by`、`created_at`；唯一约束在 `work_task` 上。

一个任务可以有多条 WorkTask（多次执行、不同目标），但一条 WorkTask 只能挂一个任务。链接不复制权限，也不改变任一对象的可见性。

### 3. 统一读模型，不合并权限

新增聚合读接口（建议 `GET /api/v1.0/work/items/`），把两类条目合并为稳定排序、游标分页的列表。每条带 `item_type = task | run` 和 `source_id`。

权限规则：

- `item_type=task`：使用 `core.Task` 自己的可见性谓词（创建人、负责人、关注人、任务清单、会话分享、ADR-0002 的向上可见）。
- `item_type=run`：使用 Work 的 owner + organization + ADR-0005 的组织/成员授权。
- 两个来源**各自过滤后再合并**，禁止用一个来源的可见性推断另一个来源。
- 用户能看到任务但看不到其关联 WorkTask 时，只返回任务，并显示“无权限查看执行”，不泄露 run 的存在与状态。

### 4. 状态映射

`core.Task` 只有 `todo / completed`，`WorkRun` 有 `queued / running / waiting_device / succeeded / failed / canceled / disconnected`。统一显示按以下优先级：

| 条件 | 显示状态 |
|---|---|
| 任务已完成 | 已完成（人工完成优先） |
| 存在 running / queued / waiting_device 的 run | 执行中 / 排队中 / 等待设备 |
| 存在 succeeded 但任务未完成 | 待确认完成 |
| 仅有 failed / canceled / disconnected | 待处理（附失败原因） |
| 无 run 的待办任务 | 待处理 |

执行成功**不自动完成**任务；用户确认后才写入 `completed_at`。自动完成如要做，必须是组织级可选策略并另立 ADR。

### 5. 分阶段实施

**阶段 1：入口与读模型（不改写路径）**

- 上线 `WorkTaskLink` 与聚合读接口；“我的工作”渲染任务 + 工作条目。
- 任务创建、编辑、完成仍走原 `core/tasks` API，行为不变。
- 开关 `WORK_TASK_SURFACE` 控制新读模型；关闭时回到两个独立入口。
- 退出标准：混合列表的权限测试通过；任务写路径零改动；可一键回滚入口。

**阶段 2：双向创建与统一提醒**

- 从任务发起执行、从 Work 成果创建/关联任务。
- 共用通知与提醒基础设施；避免同一截止日期发两份提醒。
- 退出标准：双向创建幂等；链接唯一；通知去重。

**阶段 3：能力补齐**

- 指派人、截止日期、优先级、重复规则、关注人、手动完成进入 Work 域。
- 此时再决定是给 `WorkTask` 加列，还是抽共享基表/读模型；**不在本 ADR 预先承诺单表合并**。
- 退出标准：人际协作功能与现任务模块等价；迁移脚本可回放；旧数据可按链接回查。

**阶段 4：退役旧入口**

- 任务导航下线并重定向到“我的工作”；`core/tasks` HTTP API 保留一个发布周期做兼容，之后标记弃用。
- 退出标准：无前端调用旧入口；外部集成有迁移说明；数据保留策略明确。

### 6. 不改变现有任务语义

- 不修改 ADR-0001 的层级上限、跨组织约束和删除解绑规则。
- 不修改 ADR-0002 的向上可见与只读边界。
- 不把 Work 的 owner + organization 过滤套到任务上；任务仍按协作关系授权。
- 不把任务数据复制进 Work 表；聚合接口是读时组合。

## 后果

**正面**

- 用户只有一个工作入口，AI 执行与人际任务不再分裂。
- 不需要一次性迁移 `core.Task` 的层级、协作、提醒数据，风险可控。
- 权限模型各自保持，避免合并列表扩大可见范围。

**代价**

- 阶段 1–3 存在两个写模型和两套状态词汇，读模型要持续做映射。
- 通知、提醒、搜索需要在两个来源之间去重。
- 阶段 3 的能力补齐是主要工作量，且最终形态（加列 vs 共享基表）仍未定。
- 旧任务 API 的兼容周期会延长维护面。

**风险**

- 混合列表最容易出权限漏洞；必须为“可见任务 + 不可见执行”和反向组合写专门测试。
- 双重通知与重复条目会直接损害体验，阶段 2 必须先解决。
- 若阶段 1 的读模型不稳定，阶段 3 会反复返工。

## 不采用的方案

- **现在就把两张表合并**：`Task` 的协作者、层级、重复规则会迫使 `WorkTask` 增加大量可空列，且要重写 ADR-0001/0002 的权限路径，收益不足以覆盖风险。
- **永久保留两个入口**：用户重复建条目，AI 能力无法进入既有任务流。
- **把 Task 重写成 WorkTask**：丢失父子层级、协作者和向上可见语义。
- **执行成功自动完成任务**：会替用户做业务判断，且失败重试场景容易误完成。
- **聚合接口复用 Work 的 owner + organization 过滤**：会让任务协作者看不到自己参与的任务，或让 Work 条目越权可见。

## 验收

- 阶段 1：同一用户同时有任务与 Work 条目时，列表顺序稳定、分页不重不漏；关闭开关后两个旧入口行为不变。
- 权限：任务可见但执行不可见时只显示任务；执行可见但任务不可见时不反向暴露任务标题；跨组织不串数据。
- 状态：人工完成后即使有 succeeded run 仍显示已完成；failed run 不显示为成功；等待设备有明确原因。
- 阶段 2：从任务发起执行只产生一条链接；重复点击复用同一幂等键；提醒只发一次。
- 阶段 4：旧入口无调用、重定向生效、兼容 API 有弃用日期。
