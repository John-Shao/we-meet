## 0. 结论摘要

1. **豆包的扩展不是三个并列市场，而是三层任务能力。** 工作伙伴解决「谁来做」：角色、指令、默认能力；技能解决「怎么做」：方法、流程、输出要求；连接器（产品导航中称「插件」）解决「用什么数据和工具」：读取或写入外部系统。三层最终都汇入同一个任务输入框。
2. **新建任务页是组合面板，不是设置页。** 截图中的输入框下方同时出现运行环境（本地电脑）、项目、按需确认、技能、插件；右侧是模型与推理强度。已选能力会与目标一起出现在输入框上方。工作伙伴则通过「召唤」或 `@` 进入任务，并可以继续追加技能、插件、项目和文件。
3. **安装、授权、调用是三个不同状态。** 技能安装/启用后通常即可被任务选择；连接器安装后还必须完成账号授权；工作伙伴可以把技能和连接器设为默认能力，但默认能力不等于已经授权。三者不能用一个 `enabled` 布尔值表达。
4. **工作伙伴是「可复用的角色 + 默认能力包」。** 截图显示伙伴有指令（`IDENTITY.md`、`USER.md`、`SOUL.md`、行为准则）、能力（技能/连接器开关）、管理（默认允许/部分限制），以及任务/自动化/资源主页。它的价值是复用配置，不是新的执行引擎。
5. **技能与连接器的边界最值得借鉴：技能管方法，连接器管数据。** 豆包官方帮助中心的描述（转述）是「技能负责分析和执行方法，插件负责获取或写入外部数据」。这个分层让安装、授权、调用和审计可以分别设计。
6. **we-meet 当前执行层明确不支持扩展。** 云端与本地 dsh 都关闭了 `--no-mcp`、`--no-skills`、`--no-extensions`；模型可用工具只有 `read,bash,write,edit`；`work-agent/v1` 与 `work-local/v1` 都是严格字段白名单，新增字段会被旧执行器拒绝。先做扩展 UI 会变成假入口。
7. **推荐按 E1 → E2a → E2b → E3a → E3b → E4 落地。** E1 方法型技能：服务端把技能说明组合进目标，不需要改执行器；E2a 套件模板：有序技能 + 快捷命令 + 输出标准；E2b 可选工作伙伴：同一个 `WorkPreset`，只增加短 `instructions`/组织共享；E3a 只读 SaaS 连接器；E3b 本机/MCP/写入；E4 链式上下文与富成果。E3b/E4 不能和 E1/E2a/E2b 同批。
8. **组合必须由服务端解析并冻结。** 客户端只提交 `preset_id`、`quick_command_id`、`skill_ids`、`connector_ids` 等选择；服务端按组织策略、preset 默认值、任务追加项解析，生成 `capability_snapshot`，并纳入幂等比较。界面展示「本次任务计划」，不展示原始提示词。
9. **不要新增「扩展中心」左栏入口，直到目录、安装、授权、管理和审计都真实可用。** E1 增加「技能」；E2a/E2b 增加「套件/工作伙伴」；E3a 增加「连接器」；E4 再增加项目上下文与富成果。产品阶段仍用 P0/P1/P2，扩展阶段统一用 E 编号，避免混淆。
10. **现有产品/技术方案需要修订。** 产品方案中「伙伴未核验」已经过时；技术方案把 P3 扩展估为 15–25 人日，只覆盖注册表/授权/审计。统一路线图为 E1 8–12、E2 10–16、E3 40–70、E4 60–95+、设计/幻灯片工作台 30–50+；E3b/E4/工作台均需单独排期。`capabilities.skills` 当前是执行器标识，不是技能注册表。

### 0.1 待验证假设

竞品与代码分析不能替代用户验证；以下三条在立项前需要小样本验证：

1. **套件优先 vs 伙伴优先**：5–8 位目标用户，3 个任务场景（写报告、分析数据、整理材料），观察首次配置耗时、能力理解度、是否愿意复用；如果用户更偏好角色人设而非技能包，E2b 应提前。
2. **可见计划与只读连接器是否提升信任**：用原型对比「自动匹配」与「提交前展示本次任务计划」，观察授权完成率和放弃率。
3. **E4 的链式/富成果是否有真实需求**：如果用户只需要一次性文本成果，E4 不应启动；如果用户愿意为连续工作流等待/付费，再投入项目上下文与富成果。

## 2. 豆包工作的扩展模型

### 2.1 三层结构

```text
任务目标
├── 工作伙伴：谁来做
│   ├── 角色/身份/行为准则
│   ├── 默认技能
│   └── 默认连接器
├── 技能：怎么做
│   └── 方法、流程、输出要求、边界
└── 连接器（插件）：用什么数据和工具
    └── 外部系统、账号、范围、读取/写入
```

| 层 | 回答的问题 | 典型例子 | 安装 | 授权 | 任务内形态 | 复用范围 |
|---|---|---|---|---|---|---|
| 工作伙伴 | 谁来做 | 产品经理、高级开发工程师、PPT 制作专家 | 伙伴市场「召唤」/创建 | 伙伴本身无账号授权；其连接器仍需授权 | 输入框上方已选能力、`@` 伙伴 | 个人/团队 |
| 技能 | 怎么做 | 论文排版、代码库变更方案设计、系统化 Bug 诊断 | 技能市场「安装」 | 通常不需要外部账号 | `/`、`@`、技能按钮、自动匹配 | 个人/企业 |
| 连接器 | 用什么数据/工具 | GitHub、Notion、飞书任务、飞书妙记、企业微信 | 插件市场「连接」 | 必须完成账号与范围授权 | `/`、`@`、插件按钮、自动匹配 | 个人/企业 |

三者的关系不是「三选一」，而是：

- **伙伴能力里可以配置技能和连接器**（截图 7、12、13）；
- **任务可以在伙伴默认值之上追加技能和连接器**（官方文档：任务对话框 `@` 伙伴/小队，可加文件、技能、插件、项目）；
- **技能和连接器也可以不经过伙伴直接使用**（截图 5 的工具栏和官方插件文档）。

### 2.2 工作伙伴：可复用的角色与默认能力包

官方定义：工作伙伴是面向专业场景的企业智能体；支持内置伙伴和自定义伙伴；在任务对话框中通过 `@` 伙伴或小队分派任务。

截图中的伙伴结构：

| 区域 | 内容 | 产品含义 |
|---|---|---|
| 伙伴档案 | `IDENTITY.md - 我是谁`：身份、风格、签名 | 角色设定 |
| 用户档案 | `USER.md - 关于你的人类`：用户偏好、协作方式 | 持久用户画像/记忆 |
| 行为准则 | `SOUL.md - 你是谁`：证据优先、小步、边界等 | 工作原则 |
| 能力 | 技能、连接器，各自可开关 | 默认能力包 |
| 管理 | 授权模式：默认允许 / 部分限制 | 粗粒度权限策略 |
| 主页 | 任务、自动化、资源 | 伙伴自己的工作空间 |

关键事实与边界：

- 伙伴详情显示「内置技能 13」，说明伙伴可以预置一组技能，而不是只靠任务临时选择；
- 伙伴主页的输入框比「新建任务」页更简洁，只有 `+`、语音、发送；环境、项目、技能、插件等控件不出现，看起来**伙伴主页把能力选择收进了伙伴配置**；截图不足以证明其内部实现；
- 伙伴可以被「召唤」到对话/任务中，也可以通过 `@` 调用；
- 官方文档补充：团队伙伴可共享群上下文；自定义模型限企业订阅；导入伙伴仅当前用户可用；小队至少 2 人，在 `aily.feishu.cn` 创建（来源：[使用豆包工作伙伴](https://www.feishu.cn/hc/zh-CN/articles/790732948604)）；
- 截图 14 的「默认允许 / 部分限制」是伙伴级授权模式，不是任务级逐项确认；这正是 we-meet 不应照搬的地方（见 4.3）。

**设计判断：**

- 伙伴的本质是**配置复用**，不是新的执行引擎；如果把伙伴做成第二个任务系统，会与现有历史、详情、预算、审计重复。
- 豆包的 `IDENTITY/USER/SOUL/行为准则` 是强大的提示词工程，但对用户不透明、对记忆和隐私要求高；we-meet 首版应使用「一句角色说明 + 默认技能 + 环境/审批偏好」，不做持久记忆、不做用户画像文件。
- 豆包伙伴的优势在角色、默认能力和配置复用；we-meet 统一收口到 `WorkPreset`：首版做 `kind='suite'`（技能 + 快捷命令 + 输出标准），E2b 才把短 `instructions` 作为 `kind='partner'` 加入。不再单独建 `WorkPartner`，也不把「工作伙伴」作为唯一模型。

### 2.3 技能：可复用的方法包

官方定义：技能封装特定领域的知识、方法和工作流程，扩展豆包工作的能力边界；系统会根据任务描述或需求详情自动匹配，也可以在对话框中手动指定。

截图中的技能结构：

- 市场卡片带「安装」，分类浏览，显示使用人数；
- 详情页有启用开关、描述、目标、使用边界；「完整内容暂不支持展示」；「在对话中试用」；
- 伙伴能力里的技能带「开源 / 官方 / 内置」来源标签；
- 任务输入框支持 `/` 或 `@` 搜索技能，或点「更多技能」。

技能与连接器的分工（官方帮助中心的表述，转述）：

> 技能负责分析和执行方法，插件负责获取或写入外部数据。

从能力边界上应理解为：

- 技能可以声明「需要什么数据」，但不能自己获得账号或凭据；
- 连接器可以提供数据/工具，但不决定分析方法；
- 组合时，技能定义步骤和输出，连接器提供输入/输出通道；
- 技能的安装通常不等于授权；企业技能的可见范围由管理员配置。

限制与未核验：

- 官方任务模式文档称云端与本地隔离，技能不互通（商店及 `user_skills` 除外）；具体边界未在截图中验证；
- 自动匹配时用户是否能看到、能否取消，官方文档未说明；截图未覆盖；
- 技能「完整内容暂不支持展示」意味着用户无法审查完整提示词，这是透明度缺口；
- 自建技能支持对话创建或上传含 `skill.md` 的文件；企业技能范围由管理员配置。

**设计判断：**

- 技能应被建模为**版本化的方法包**：名称、说明、适用场景、输入要求、输出格式、边界、版本、内容哈希；
- 技能不能携带密钥、不能直接发起外部调用；需要数据时声明依赖，由连接器授权解决；
- 对用户展示「做什么、需要什么、产出什么、边界是什么」，而不是只显示一个名字；
- 首版不建议开放任意用户上传提示词；先由组织管理员策展，降低提示词注入和质量风险。

### 2.4 连接器（插件）：受授权的外部数据与操作

官方定义：插件用于连接外部系统与数据源，让豆包工作在授权范围内查询或操作外部系统的数据。

接入形态：

| 形态 | 说明 | 典型场景 | 风险 |
|---|---|---|---|
| OAuth / 账号连接 | 连接 SaaS，授权账号与范围 | GitHub、Notion、飞书、企业微信 | 范围过宽、令牌泄露、撤权不及时 |
| 自定义 HTTP | 云端程序，填 URL、Headers、鉴权 | 企业内部 API | SSRF、出网、密钥保管 |
| STDIO / CLI | 本地程序，填命令、参数、环境变量 | 本地工具、MCP server | 本机命令执行、路径与凭据 |
| MCP | 通过协议暴露工具/资源 | 标准化工具生态 | 工具描述不可信、越权调用 |

截图中的连接器：

- 市场卡片带「连接」；GitHub 弹窗要求确认账号与数据共享范围；
- 伙伴能力 > 连接器可以逐项开关（豆包语音合成、图片生成、飞书任务、飞书妙记）；
- 伙伴管理有「默认允许 / 部分限制」的授权模式；
- 官方文档：连接成功不等于拥有全部权限，权限由连接账号及权限设置决定；授权时确认账号、操作范围、结果保存位置。

关键限制：

- 连接器可能读取或写入外部系统；写入的风险远高于读取；
- 连接器运行在云端还是本机，决定凭据存放位置、出网路径和数据可见性；
- 撤销授权、令牌过期、范围不足、外部系统限流都是常态，不是异常；
- 官方文档未详细说明撤销入口和审计视图，截图未覆盖；本文标记「未核验」。

**设计判断：**

- 连接器不是一张市场卡片，而是**安全边界**；首版只做只读、策展、云端，先证明权限和审计，再考虑写入和本机；
- 不应向普通用户暴露任意 HTTP/STDIO 配置；企业版可以由管理员配置 MCP/HTTP，但必须有出网白名单和工具白名单；
- 连接器的授权必须逐范围、逐任务可见，不能用伙伴级「默认允许」一把梭。

### 2.5 小队与企业版

官方文档与截图补充：

- 小队由多个工作伙伴组成，至少 2 人，在 `aily.feishu.cn` 创建，包含队长与协作模板；
- 团队伙伴可共享群上下文；自定义模型限企业订阅；导入伙伴仅当前用户可用；
- 企业版与飞书深度集成，连接消息、日历、文档、表格、知识库，权限遵循飞书原有体系。

本文不展开小队，因为：

- we-meet 当前一次 run 只对应一个执行器/一个模型循环，没有多 Agent 编排、共享上下文、角色分工、预算拆分和冲突裁决；
- 小队不是「多选几个技能」，而是新的编排层；在没有调度器和审计前加入口会制造错误预期。

### 2.6 哪些不是扩展

| 能力 | 为什么不是扩展 | 应归属 |
|---|---|---|
| 本地电脑 / 云电脑 | 决定执行位置，不改变方法或数据权限 | 执行环境（P0） |
| 项目 | 任务与文件的上下文容器 | 项目模型（P2） |
| 企业知识 | 组织内知识与权限继承 | 企业知识/检索，独立权限模型 |
| 按需确认 | 风险动作的审批策略 | 权限/审批，不是能力 |
| 模型 / 推理强度 | 质量、成本、时延档位 | P1 档位 |
| Pi 复核 | 运行后的独立复核策略 | 详情页/复核，不进任务能力选择器 |

把环境、项目、权限、模型塞进「扩展」会让用户无法判断「我到底授权了什么」。豆包把它们放在同一行，是为了操作效率；we-meet 应在视觉上分组，在语义上分开。

## 3. 新建任务时的组合方式

### 3.1 两个入口

豆包有两类入口：

| 入口 | 截图 | 能力选择 | 适合 |
|---|---|---|---|
| 通用新建任务 | 5 | 环境、项目、审批、技能、插件、模型/强度；已选能力与目标同排 | 目标明确、需要临时组合能力 |
| 伙伴主页 | 8 | 只输入目标；能力看起来由伙伴配置承载；下方任务/自动化/资源 | 长期使用同一角色/默认能力 |

通用新建任务的能力行（截图 5）：

```text
[已选：◇ 产品经理] 帮我设计一个技术博客网站
[+] [本地电脑] [项目] [按需确认] [技能] [插件]            [自动 低] [发送]
```

伙伴主页（截图 8）：

```text
[为老年健康应用设计首页和用药提醒页，交付可运行原型与设计说明。]
[+]                                                        [语音] [发送]
任务 | 自动化 | 资源
```

**设计判断：**

- we-meet 首版只做通用新建任务；伙伴主页会分裂任务历史，且「自动化/资源」依赖调度与文件模型，不应在 E2 一起做；
- 伙伴在 we-meet 中是「预填器」：选中后把默认技能、环境、审批偏好填进通用 composer，用户仍能看到并修改；
- 不复制「伙伴主页」的独立任务列表；后续如果要做，只做筛选视图，不新建任务存储。

### 3.2 组合面板拆解

| 控件 | 所属层 | 选项 | 是否多选 | 是否需授权 | 任务内可见性 |
|---|---|---|---|---|---|
| `+` | 资料 | 文件/云盘等 | 未核验 | 否 | 附件列表 |
| 本地电脑 / 云电脑 | 环境 | 执行位置 | 单选 | 本机需目录授权 | 环境标识 |
| 项目 | 上下文 | 项目/文件夹 | 单选 | 继承项目权限 | 项目名 |
| 按需确认 | 权限 | 风险动作确认策略 | 单选 | 否 | 权限摘要 |
| 企业知识 | 上下文 | 组织知识 | 未核验 | 继承组织权限 | 知识范围 |
| 技能 | 方法 | 已安装/已启用技能 | 官方未说明；建议多选 | 通常否 | 技能 chip / 名称 |
| 插件/连接器 | 数据/工具 | 已连接连接器 | 官方未说明；建议多选 | 是 | 连接器 chip / 数据范围 |
| 模型 / 推理强度 | 质量/成本 | 自动、Turbo/Pro、低/中/高 | 单选 | 否 | 模型标识 |
| `@` 伙伴/小队 | 角色/默认能力 | 内置/自定义伙伴 | 官方称可 @ 伙伴/小队 | 伙伴本身否；其连接器是 | 伙伴标识 |

未核验项：

- 技能/插件是否真的支持多选、最多几个；
- 选中后如何取消、是否能在提交前移除；
- 自动匹配的技能是否显示、能否拒绝；
- 任务执行中能否追加能力或修改权限；
- 连接器撤销后正在运行的任务如何处理。

这些不影响本文的方向判断，但会影响具体交互细节；实现前需要一次真机走查。

### 3.3 组合顺序与优先级

推荐的服务端解析顺序：

```text
组织策略（硬约束：允许/禁用、上限、范围）
  ↓
preset 默认值（软默认：套件技能/快捷命令，或伙伴的短说明、环境、审批偏好）
  ↓
任务显式选择（追加技能、连接器、环境、审批）
  ↓
服务端校验（存在、启用、授权、范围、环境、预算、长度）
  ↓
冻结 capability_snapshot（ID、版本、内容哈希、范围）
  ↓
生成执行计划 / agent_payload
```

规则：

1. **组织策略优先于 preset 和任务。** 组织禁用某技能/连接器时，preset 默认值和任务选择都不能绕过；界面显示「组织已禁用」，不静默丢弃。
2. **preset 默认值是预填，不是锁定。** 用户可以在任务里移除未被组织锁定的默认技能；被锁定的显示锁标识和原因。
3. **任务选择是追加。** 同一技能按 ID 去重；同一连接器按 ID + 范围去重；重复选择不重复执行。
4. **连接器永远需要授权。** 伙伴携带连接器只代表「默认想用」，不代表已授权；任务选择也不能扩大授权范围。
5. **环境决定可用集合。** 云端与本机能力不互通；环境切换后，不兼容的能力要显示原因，不能静默保留。
6. **服务端解析并冻结。** 客户端不发送原始提示词、不发送凭据；任务历史展示快照，不重新解释当前配置。
7. **提交前可见。** 用户应看到「本次使用哪些能力、访问什么数据、在哪个环境、需要哪些确认」，而不是提交后才发现。

### 3.4 直接使用与组合使用

- **直接使用**：只选一个技能、一个伙伴或一个连接器，任务用这一层能力执行；
- **组合使用**：伙伴提供角色和默认能力，技能追加方法，连接器提供数据/工具；环境、项目、审批、模型是正交配置，不属于扩展层；
- 组合不是三者必须同时出现：伙伴可以单独用，技能可以单独用，连接器也可以单独用；组合只是允许在同一个任务里叠加。

| 场景 | 选择 | 执行 | 用户确认 | we-meet 分期 |
|---|---|---|---|---|
| 只用一个方法 | 技能 A | 目标 + A 的方法说明 | 看到技能名与输出要求 | E1 |
| 只用一个角色 | 伙伴 P | P 的 instructions + 默认技能 | 看到 P 与默认技能 | E2b |
| 角色 + 追加方法 | 伙伴 P + 技能 B | P 的默认技能 + B | 看到 P、默认技能、B，可移除 B | E2b |
| 角色 + 数据 | 伙伴 P + 连接器 C | P + C 的只读工具 | 看到 C 的账号、范围、数据去向 | E3a |
| 角色 + 方法 + 数据 | P + B + C | 角色说明 + 方法 + 工具循环 | 看到完整计划；C 需授权；写操作逐次确认 | E3a（写操作 E3b） |
| 多个方法 | 技能 A + B | 按确定顺序组合；冲突时提示 | 看到顺序/冲突 | E1（建议上限 3） |
| 多个连接器 | C1 + C2 | 工具集合；受上下文和配额限制 | 分别授权、分别显示范围 | E3a（建议上限 2；E3b 另立） |

注意：

- 豆包官方文档说插件可以「指定或自动匹配」，因此「只选连接器、不选技能」在豆包是可能的；we-meet E3a 只支持「只读 SaaS 连接器 + 明确任务目标」，不承诺自动规划。
- 伙伴 + 连接器的组合不意味着连接器自动获得写权限；写操作必须另行走审批。
- 技能 + 连接器不是「技能调用连接器」的任意编程关系；首版只允许技能声明「需要某类连接器能力」，由服务端在解析时检查，不允许技能代码直接拿到凭据。

### 3.5 自动匹配与显式选择

豆包：

- 技能：系统根据任务描述自动匹配；也可 `/`、`@` 或技能按钮手动指定；
- 连接器：任务中可指定或自动匹配；
- 伙伴：通过 `@` 或「召唤」显式选择。

we-meet 建议：

| 能力 | 自动建议 | 自动启用 | 理由 |
|---|---|---|---|
| 技能 | 可以（按关键词/场景） | 不建议 | 技能改变输出方法和格式；静默启用会让结果不可复现 |
| 伙伴 | 可以推荐 | 不建议 | 伙伴改变角色和默认能力，必须让用户看到 |
| 连接器 | 不建议 | 禁止 | 涉及账号、数据和外部副作用；必须显式授权 |
| 环境 | 可以默认 | 不自动切换 | 执行位置是硬边界；不能因能力不可用而静默换环境 |

推荐交互：

- 输入目标后，显示「可能适用：技能 A / 伙伴 P」的**建议 chip**，用户点击才加入；
- 已加入的能力在输入框上方显示，可移除；
- 提交前展开「本次任务计划」，列出能力、环境、数据访问、审批、预算；
- 任何自动匹配都必须在提交前可见，且不改变用户未确认的权限。

### 3.6 组合限制与冲突

豆包公开文档未给出技能/连接器数量上限；不要假设「可以无限叠加」。we-meet 首版建议：

| 限制 | 建议值 | 原因 |
|---|---|---|
| WorkPreset（套件或伙伴） | 1 | 多角色/多套件会互相冲突；小队另立项 |
| 技能 | 3 | 控制提示词长度、冲突和可解释性 |
| 连接器 | 2 | 控制工具数量、上下文、授权面和审计复杂度 |
| 组合后执行目标长度 | ≤ 8000 字符（当前 `work-agent/v1` 上限） | 不改执行器契约的硬约束 |
| 单技能说明 | ≤ 1200 字符 | 给目标/背景/其他技能留空间 |
| 技能说明合计 | ≤ 2000 字符 | 与目标/背景合计不超过 8000 |
| 伙伴说明 + 默认技能 | ≤ 2000 字符 | 6000（目标+背景）+ 2000 = 8000 |

冲突类型：

| 冲突 | 表现 | 处理 |
|---|---|---|
| 重复技能 | 同一 ID 多次选择 | 去重，保留一次 |
| 输出格式冲突 | 技能 A 要求 Markdown，B 要求 JSON | 提交前提示，让用户移除一个；不静默择一 |
| 缺失连接器 | 技能声明需要 C，但 C 未授权 | 阻止提交，提示先连接；不自动换技能 |
| 组织禁用 | 技能/连接器被管理员禁用 | 显示禁用原因；不允许伙伴/任务覆盖 |
| 环境不匹配 | 本机任务选了仅云端连接器 | 显示「此环境不可用」；不自动切环境 |
| 预算不足 | 组合后超出日预算 | 提交前提示；不降级到更便宜模型 |
| 令牌过期 | 连接器授权过期 | 阻止调用；提示重新授权；不自动用旧令牌 |
| 版本变化 | 技能/伙伴在任务创建后更新 | 任务使用快照；不静默升级 |

### 3.7 尚未核验的交互

- 技能/插件多选上限与取消方式；
- 自动匹配技能是否可拒绝；
- 执行中能否追加技能/插件或修改权限；
- 连接器撤销入口与撤销后运行中任务的行为；
- 伙伴的团队共享范围、导入伙伴的能力边界；
- 云端与本机技能/连接器的实际互通范围；
- 伙伴「默认允许」具体覆盖哪些飞书操作、是否有审计。

这些应在立项前用真实账号走查，不应在 PRD 中写成已确认。

## 4. 权限、治理与安全

### 4.1 四个状态

| 状态 | 含义 | 谁控制 | 界面 |
|---|---|---|---|
| 可见 | 用户能在市场/列表看到 | 组织策略、市场配置 | 卡片/列表 |
| 已安装/已启用 | 加入当前用户或组织的可用集合 | 用户/管理员 | 「已安装」「开关」 |
| 已授权 | 连接器获得账号、范围和凭据 | 用户/管理员 | 「已连接」「范围」 |
| 可调用 | 本次任务实际选择并通过校验 | 任务 + 服务端 | 任务计划/执行事件 |

常见错误是把「已安装」当成「可调用」。技能通常不需要外部授权，但连接器必须；伙伴的默认连接器也必须单独授权。

### 4.2 身份与范围

- 个人能力：仅创建者可用；
- 组织能力：管理员发布，组织成员可见/可用；成员不能自行扩大范围；
- 团队伙伴：共享群上下文；导入伙伴仅当前用户；
- 公开市场：we-meet 首版不做；没有审核、签名、责任主体之前，公开市场会带来质量和安全风险；
- we-meet 现有 `owner + organization` 双重作用域必须延续；扩展的安装、授权、调用都不能跨组织。

### 4.3 连接器授权与凭据

推荐模型：

```text
连接器目录（组织/内置）
  → 用户连接（OAuth/管理员配置）
    → 授权记录（范围、账号、到期、状态）
      → 任务选择（本次允许的范围）
        → 运行时短期令牌（由 broker 注入，不进模型上下文）
          → 调用审计（谁、何时、哪个连接器、哪个范围、结果状态）
```

要求：

- 凭据只存加密引用，不存明文；云端用 KMS/Secret Manager，桌面用系统安全存储；
- 任务 payload、日志、埋点、事件、错误信息都不含令牌；
- 连接器授权显示：账号、范围、数据去向、保存位置、到期/撤销方式；
- 读与写分开授权；首版只读；写操作逐次确认，不支持「全部允许」；
- 撤销后：新任务不能再选；运行中任务在下次调用前检查授权，失败即停止，不自动换连接器；
- 企业管理员可以禁用连接器、限制范围、查看调用审计；成员不能绕过；
- 连接器结果可能进入模型上下文，必须向用户说明数据会被发送到模型服务。

对豆包「默认允许 / 部分限制」的评价：

- 作为消费级体验，它减少了确认次数；
- 作为组织可控执行，它过于粗糙：默认允许常用飞书操作，不等于用户理解每次写入的范围；
- we-meet 的差异化是「可控、可验收」，应坚持逐范围、逐任务、写操作逐次确认，而不是复制默认允许。

### 4.4 技能内容供应链

- 首版只允许内置/组织策展技能；管理员审核内容、版本、输出要求；
- 技能内容视为不可信指令：不能覆盖系统安全策略、不能获得凭据、不能绕过审批；
- 技能声明依赖连接器时，只声明能力 ID/范围，不包含令牌；
- 版本化 + 内容哈希；任务快照固定版本；更新不回溯已创建任务；
- 个人自建技能后续再做，需要审核、签名、可见范围和使用审计；
- 提示词注入防护：分隔用户目标、技能说明、连接器结果；连接器结果按数据处理，不按指令执行。

### 4.5 执行隔离与出网

云端：

- 每任务容器只挂载当前任务目录；不注入业务数据库凭据、供应商真实 key；
- 连接器需要出网白名单；不能任意 URL；
- 工具循环在 Gateway/任务容器内；模型只看到工具 schema 和结果，不看到令牌；
- 连接器调用有次数、token、超时、并发限制。

本机：

- 只在用户授权目录内工作；绝对路径不出设备；
- 命令逐次审批；连接器如果在本机执行，必须复用现有审批与目录授权；
- 本机连接器的凭据只在本机安全存储；服务端只记录别名和审计元数据；
- 本机失败不自动转到云端；云端失败不自动转到本机。

### 4.6 审计与计量

至少记录：

- 谁在何时安装/启用/禁用了哪个技能、伙伴、连接器；
- 谁在何时授权/撤销了哪个连接器的哪些范围；
- 哪个任务使用了哪些能力（快照）；
- 连接器调用的连接器、操作、范围、状态、耗时、错误码；
- token/调用次数/费用；
- 管理员的策略变更。

不记录：

- 连接器令牌、OAuth code、模型密钥；
- 本机绝对路径；
- 技能/伙伴的完整提示词（可记录内容哈希和版本）；
- 任务正文、成果正文、连接器返回的原始数据（除非用户明确同意用于审计）。

### 4.7 失败模式

| 失败 | 行为 | 禁止 |
|---|---|---|
| 未授权 | 阻止提交/调用，提示连接 | 自动用匿名/共享账号 |
| 范围不足 | 提示缺少的范围 | 自动申请更大范围 |
| 令牌过期 | 提示重新授权 | 自动刷新失败后继续调用 |
| 连接器不可用 | 提交前阻止；运行中失败则保留原任务，由用户决定是否新建无连接器任务 | 静默改用其他连接器，或自动降级 |
| 限流 | 重试有上限，保留用量 | 无限重试 |
| 部分写入 | 记录已发生的副作用，人工处理 | 自动回滚/重复写 |
| 执行结果未知 | 保留原任务，查询同一记录 | 自动重放付费调用 |
| 撤权 | 停止新调用，保留审计 | 删除历史或继续调用 |
| 技能冲突 | 提交前阻止 | 运行时静默择一 |
| 上下文超限 | 提交前提示，要求减少能力 | 截断用户目标 |

### 5.2 关键发现：执行层不支持扩展

这是本文最重要的可行性结论：

1. **云端和本机都显式关闭了扩展。** `drivers.py` 固定传入 `--no-extensions`、`--no-mcp`、`--no-skills`、`--no-prompt-templates`、`--no-context-files`；非复核任务只开放 `read,bash,write,edit`。
2. **agent 契约是严格白名单。** `validate_request` 只允许 `contract/run_id/goal/files/timeout_seconds` 加可选 `limits/operation`；新增 `skills`/`connectors` 字段会被旧 Gateway 直接拒绝，不能假设「加字段就兼容」。
3. **本地契约同样严格。** 适配器 `submit` 只允许 `run_id/workspace_id/goal`；桌面主进程只允许四个键；新增能力字段需要桌面、适配器、服务端同步升级。
4. **执行器自己声明不支持业务工具。** `limitations` 明确 `no_business_tools`、`no_user_files`；云端容器虽然有网络，但没有连接器工具循环、凭据 broker 和出网白名单。
5. **因此不能先做 UI。** 在 composer 里放「技能」「连接器」而执行层不能执行，会制造假能力和错误预期，违反「未实现不渲染」的既有原则。

### 5.5 术语修正：`office_agent` 不是技能

当前 `capabilities.skills = ["office_agent"]` 和 `WorkTask.kind = "office_agent"` 表达的是**执行器/任务类型**，不是方法型技能。建议：

- `executor`：`cloud_agent` / `local_agent`（执行环境与运行器）；
- `skill`：方法包；
- `preset`：`WorkPreset`，`kind='suite' | 'partner'`；
- `connector`：外部数据/工具。

`skills` 字段保留一个版本做兼容，但不要再扩展它；新增 `task_skills`、`presets`、`connectors` 或统一的 `capabilities` 数组。

### 5.6 上下文预算：最容易被忽略的硬约束

当前链路：

```text
goal ≤ 2000 + background ≤ 4000 = 6000 字符
work-agent/v1 / work-local/v1 goal 上限 = 8000 字符
可用余量 ≈ 2000 字符（严格说还要扣除背景前缀和分隔符，实际略小）
```

这意味着：

- E1 所有技能说明合计必须 ≤ 2000 字符，否则组合后会被执行器拒绝；
- E2 伙伴说明 + 默认技能也必须 ≤ 2000 字符；一个长 `SOUL.md` 就会超限；
- E3a/E3b 连接器工具 schema 也消耗模型上下文，且模型上下文窗口 32768、输出 4096，工具太多会挤压任务本身；
- 如果要支持长伙伴说明，必须：
  - 扩展 agent 契约，增加独立的 `instructions` 字段（推荐，v2）；或
  - 提高 goal 上限到 16000/24000（需要执行器与桌面同步升级）；或
  - 限制 preset 说明/技能长度（E1/E2a/E2b 首版推荐）。

这个约束直接影响产品：**不能把豆包的 `IDENTITY/USER/SOUL` 原样搬过来**。we-meet 首版伙伴应是「短说明 + 默认技能」，不是长提示词文件。

## 6. 推荐方案

### 6.1 设计原则

1. **未实现不渲染。** 没有注册表、没有执行能力、没有授权/审计，就不放 chip、不放导航。
2. **方法与数据分离。** 技能是方法，连接器是数据/工具；技能不能持有凭据，连接器不能决定方法。
3. **安装、授权、调用分离。** 三个状态分别建模、分别 UI、分别审计。
4. **服务端解析并冻结。** 客户端只提交 ID/选择；服务端解析、校验、生成快照；任务历史按快照解释。
5. **目标优先，能力渐进。** 默认只写目标；能力是可选、可移除、可解释的。
6. **最小权限。** 连接器只读优先、逐任务授权、写操作逐次确认；不复制「默认允许」。
7. **组织策略优先。** 组织禁用/限制不能被 preset 或任务覆盖。
8. **环境边界清晰。** 云端/本机能力不互通；不自动切换、不自动降级。
9. **可复现。** 版本 + 内容哈希 + 快照；同键同选择返回同任务，同键不同选择冲突。
10. **可核验。** 显示「做什么、用什么数据、产出什么、边界是什么」，不只显示名字。

### 6.2 概念模型

```ts
type CapabilityKind = 'skill' | 'preset' | 'connector'

type WorkSkill = {
  id: string
  slug: string
  name: string
  description: string
  version: number
  scope: 'builtin' | 'organization'
  enabled: boolean
  output: 'markdown' | 'text' | 'json'
  requires?: {
    environment?: ('cloud' | 'local')[]
    connector_kinds?: string[]
  }
  content_sha256: string
}

type PresetKind = 'suite' | 'partner'

type WorkPreset = {
  id: string
  kind: PresetKind
  name: string
  description: string
  version: number
  scope: 'builtin' | 'organization' | 'personal'
  enabled: boolean
  instructions?: string         // partner 模式 ≤ 800 字符；suite 可为空
  skill_ids: string[]           // 有序；suite 定义工作流顺序
  quick_commands: {
    id: string
    label: string
    prompt_template: string
    skill_id: string
  }[]
  output_standard?: {
    format: 'markdown' | 'json'
    schema?: string
    template?: string
  }
  connector_ids?: string[]
  preferred_environment?: 'cloud' | 'local'
  approval_mode?: 'ask' | 'read_only_auto'
  requires?: {
    connector_ids?: string[]
  }
  content_sha256: string
}

type WorkConnector = {
  id: string
  name: string
  provider: string
  version: number
  scope: 'organization'
  enabled: boolean
  authorized: boolean
  grant_id?: string
  scopes: {
    id: string
    label: string
    access: 'read' | 'write'
    risk: 'low' | 'medium' | 'high'
  }[]
  environments: ('cloud' | 'local')[]
}
```

`approval_mode` 说明：`ask` = 所有风险动作确认；`read_only_auto` = 只读自动、写入确认。首版 preset 只允许 `ask`，连接器出现后再考虑 `read_only_auto`。

任务创建时只提交选择：

```ts
type TaskCapabilityInput = {
  preset_id?: string
  quick_command_id?: string
  skill_ids?: string[]          // ≤ 3
  connector_ids?: string[]      // ≤ 2
  connector_scopes?: Record<string, string[]>
  environment: 'cloud' | 'local'
}
```

`environment` 只在统一提交入口（P2-A）后进入任务 API；E1/E2a/E2b 云端直接用 `POST /work/tasks/`，本机走 `local/tasks/`，不要为了字段完整而假装统一入口已经存在。

服务端返回冻结快照：

```ts
type CapabilitySnapshot = {
  version: 1
  resolved_at: string
  policy_version: string
  preset?: { id: string; kind: 'suite' | 'partner'; version: number; name: string; content_sha256: string }
  skills: { id: string; version: number; name: string; content_sha256: string }[]
  connectors: {
    id: string
    version: number
    name: string
    grant_id: string
    scopes: string[]
  }[]
}
```

### 6.3 E1：方法型技能

**范围**

- 内置/组织策展的方法包；不访问外部数据、不新增工具；
- 云端全量；本机 tracked 通过 `execution_goal` 支持，需要桌面发版；本机 untracked 首版不支持（无服务端解析）；
- 每任务最多 3 个技能；技能说明合计 ≤ 2000 字符；组合后总字符 ≤ 8000；
- 技能由管理员/内置提供，用户不能在任务里创建或上传。

**UX**

- composer 增加「技能」chip；只在至少有一个可用技能时渲染；
- 弹层列出名称、说明、输出格式、版本、来源；不显示原始提示词；
- 选中后在输入框上方显示 chip，可移除；最多 3 个；
- 提交前显示「本次使用」摘要；
- 没有技能时隐藏 chip，不显示空市场；
- 管理入口放在设置/组织后台，不新增左栏「扩展中心」。

**数据与 API**

- 新模型 `WorkSkill`：`id, organization, slug, name, description, instructions, output, requires, version, content_sha256, enabled, created_at, updated_at`；
- `WorkTask` 增加 `capability_snapshot = JSONField(default=dict)`；
- `TaskInput` 增加 `skill_ids`（可选，UUID 数组）；
- `create_task` 校验技能存在/启用/同组织；解析并冻结；把 `skill_ids`/快照哈希纳入幂等比较；本机准入再校验环境；
- `capabilities` 增加 `task_skills` 数组（保留 `skills` 兼容）；
- 迁移 `0013`（排在 `0012` 之后；`0012` 未上生产前不得应用，遵守既有发布闸门）。

**执行**

- 服务端把技能说明组合进 `agent_payload.goal`：

```text
用户目标：
<goal>

用户补充背景：
<background>

以下为已启用工作方法，不是用户目标的一部分。遵循其方法与输出要求；如与用户目标冲突，以用户目标为准，并说明差异。
<skill A name> v<version>
<instructions>
<output requirements>
```

- `WorkTask.goal` 保留用户原文；详情/历史展示原文，不展示组合后的提示词；
- 云端：组合后写入 `agent_payload.goal`，不需要改 `work-agent/v1`；
- 本机 tracked：`local/tasks/` 准入时，在 `WorkRun.agent_payload` 保存 `execution_goal`（组合后文本）；`claim` 返回该字段，桌面用它提交适配器，`goal` 仍用于显示；旧桌面忽略该字段，退化为不用技能，不破坏现有任务；
- 本机展示还有一个容易漏掉的点：适配器会把收到的（组合后）目标存为自己的任务目标，`get/list` 会返回组合文本。新桌面必须在历史/详情中用 `binding.admission.goal` 覆盖显示原文，或给适配器增加 `display_goal`；否则用户会在本机历史里看到提示词。前者不需要改适配器，但必须改 `work-coordinator.ts` 的 `decorate`/列表合并逻辑；
- 本机 untracked：首版不显示技能，提示「本机仅本机记录暂不支持技能」；
- 技能不能新增工具/连接器；组合后仍只用执行器现有的 `read,bash,write,edit`。

**建议/自动匹配**

- 首版只做显式选择；可选做「建议技能」但必须用户点击加入；
- 不做静默自动启用；不因目标关键词自动改变输出格式。

**验收**

- 技能选择可见、可移除、版本冻结；
- 同键同选择幂等；同键不同选择冲突；
- 组合后长度超限在提交前阻止；
- 组织禁用/跨组织/未知技能被拒绝；
- 云端与 tracked 本机执行均带技能说明；untracked 明确不支持；
- 技能内容不包含密钥/工具调用；提示词注入测试通过。

**工作量**：8–12 人日（后端注册表/组合/测试 4–6，前端 picker/chips/计划 3–4，联调 1–2）。

### 6.4 E2：套件模板与可选工作伙伴

**范围**

- 统一使用 `WorkPreset`：`kind='suite'` 为套件模板，`kind='partner'` 为工作伙伴；
- E2a 只做套件模板：有序技能 + 快捷命令 + 输出标准；不读链式上下文、不引入连接器、不产出富成果；

- 每个 preset 最多 5 个技能；每任务最多 3 个；preset 说明 + 技能说明 + 快捷命令模板 ≤ 2000 字符；
- E2a/E2b 输出只支持 Markdown/JSON；HTML/Office/PDF/图片是 E4；
- 首版只做内置/组织 preset：管理员发布、成员只读；个人 preset 字段保留但不开放创建；
- 没有 `instructions` 的 preset = 套件模板；有 `instructions` = 轻量伙伴。

**UX**

- composer 增加「套件」chip；E2b 后同一入口可切换「套件/工作伙伴」；
- 选中后：显示 preset 名、快捷命令列表；点击快捷命令预填模板；默认技能自动填入但可移除；显示「预设模式，暂不支持链式上下文」；
- preset 选择器显示名称、简介、技能数、输出标准、来源、版本；
- 管理页创建/编辑/复制/停用；不展示原始 `SKILL.md`，只展示结构化摘要；
- 不新增独立套件/伙伴工作台；导航等 CRUD/列表/权限完成后再说。

**数据与 API**

- 新模型 `WorkPreset`：`id, owner, organization, kind, name, description, instructions, skill_ids, quick_commands, output_standard, preferred_environment, approval_mode, visibility, version, content_sha256, enabled, created_at, updated_at`；
- `WorkTask` 增加 `preset_id`（nullable）与快照中的 preset；
- `TaskInput` 增加 `preset_id` + `quick_command_id`；
- `create_task` 解析 preset → 有序技能 → 快捷命令模板 → 冻结；幂等比较 preset/quick command/skills；
- 组织 preset 由管理员创建；个人 preset 首版不开放；
- 迁移 `0014`（E2a/E2b 共用，不新增 `WorkPartner` 表）。

**执行**

- 服务端组合：preset 工作说明 + 有序技能说明 + 快捷命令模板 + 用户目标；
- E2a 只做提示词层面的顺序：告诉模型按顺序执行；不保证技能之间通过 schema 传递上下文；
- E2b 同样不读项目文件；伙伴的 `instructions` 只影响角色/风格，不新增工具；
- 云端与 tracked 本机支持；untracked 本机不支持；
- E2 不引入连接器。

**组合规则**

- preset 默认技能是预填；任务可移除未锁定项；
- 任务追加技能优先保留，冲突时提示；
- 组织策略可以锁定/禁用 preset 或技能；
- preset 版本更新不影响已创建任务；任务快照固定版本。

**验收**

- preset 版本/内容哈希冻结；同键不同 preset 冲突；
- 组织 preset 只读；个人 preset 字段保留但首版不开放创建；
- 无链式上下文/无连接器/无富成果入口；
- 云端/tracked 本机执行一致；untracked 明确不支持。

**工作量**：E2a 8–12 人日；E2b +2–4；E2 合计 10–16 人日（含组织共享与审计）。

### 6.5 E3：连接器（E3a / E3b）

**范围**

- **E3a：只读 SaaS 连接器。** 云端优先；OAuth/API key + HTTP/OAuth；不含 MCP、本机、写入、公开市场；每任务最多 2 个；逐 scope 授权。
- **E3b：本机连接器、MCP、写操作。** 单独立项；必须桌面/适配器 v2、系统安全存储、目录/命令审批；不复用云端凭据。
- E3 管理/审计/安全评审作为独立工作项，可与 E3a/E3b 并行。

**UX**

- composer 增加「连接器」chip；只在有已连接/可连接连接器时渲染；
- 选择器显示：名称、提供方、已授权/未授权、可读范围、数据去向、环境；
- 未授权时提供「连接」按钮，走 OAuth/管理员配置；授权弹窗显示账号、范围、保存位置；
- 选中后显示 chip；提交前「本次任务计划」列出连接器、范围、只读/写入、审批；
- 任务详情增加「数据访问」区块：调用了哪个连接器、什么操作、状态、耗时；不显示返回数据正文；
- 撤销入口在设置/管理页；撤销后新任务不可选；
- 不显示「默认允许」；所有连接器调用显式选择。

**数据与 API**

- `WorkConnector`：`id, organization, provider, name, kind, config_schema, scopes, environments, enabled, version`；
- `WorkConnectorGrant`：`id, user, organization, connector, encrypted_token_ref, scopes, status, expires_at, revoked_at`；
- `WorkConnectorCall`：`id, run, connector, operation, scope, status, started_at, finished_at, error_code`；
- `TaskInput` 增加 `connector_ids` 与 `connector_scopes`；
- `capabilities` 增加 `connectors` 数组，只返回已启用且当前用户可见的；`authorized` 按 grant 计算；
- E3a 迁移 `0015`；E3b 迁移 `0016+`。

**执行**

- E3a 需要 Gateway v2、工具循环、HTTP 客户端、凭据 broker、出网白名单；**不引入 MCP**；
- E3b 才引入本机连接器、MCP/STDIO 和写入；
- `work-agent/v1` 的严格校验无法直接加字段；建议新增 `work-agent/v2`，或先升级所有 Gateway；
- job payload 只传连接器 ID、grant 引用、scope、操作白名单；不传令牌；
- Gateway 在调用前向 broker 换取短期令牌；按 scope 校验；记录调用；
- 工具描述/结果不可信；只允许白名单工具；结果按数据处理；
- 每任务限制调用次数、token、超时、并发；失败不自动换连接器/不自动扩大范围。

**授权与治理**

- OAuth：state/nonce、回调校验、scope 最小化、令牌加密、刷新、撤销；
- 企业管理员：连接器目录、可用范围、禁用、审计导出；
- 数据说明：连接器结果可能进入模型上下文；向用户说明数据去向和保留；
- 写操作：E3a 不做；E3b 才做，逐次预览 + 审批 + 幂等键 + 审计。

**验收**

- E3a：只读连接器可授权/调用/撤销；
- 未授权、过期、范围不足、限流、外部不可用均有明确状态；
- 令牌不出现在 payload/日志/事件/埋点；
- 跨组织、跨用户、越权 scope 被拒绝；
- 旧 Gateway 兼容路径明确（升级或 v2）；
- 任务详情可看到调用审计；撤销后停止新调用；
- 不自动调用、不自动写入、不自动降级。

**工作量**：E3a 20–35 人日（暂定，需按同一范围 bottom-up 重估）；E3b 15–25 人日；管理/审计/安全评审 5–10 人日；E3 合计 40–70 人日。E3b 不与 E3a 同批。

**成果边界（P1）**：当前 Work 只支持 `.txt/.md/.csv/.json`；Markdown 编辑/采纳版本上限 40,000 字符，执行器单次最多 20 个文件/400,000 字节。HTML/Office/PDF/图片/画布属于 E4/Workbench，详见千问篇 6.2。因此 E2a/E2b 首版只做文本型套件，不承诺设计稿、PPT 或富文件成果。

### 6.6 组合语义（跨期）

| 规则 | 行为 | 失败 |
|---|---|---|
| 组织策略优先 | 禁用/限制覆盖 preset 默认和任务选择 | 显示原因，阻止提交 |
| preset 默认可移除 | 未锁定项由用户移除 | 锁定项显示锁和来源 |
| 技能追加去重 | 按 ID 去重，保留顺序 | 冲突提示，不静默择一 |
| 连接器逐任务授权 | 选择后检查 grant/scope | 未授权则阻止，提供连接入口 |
| 环境过滤 | 只显示当前环境可用能力 | 不自动换环境，不自动换能力 |
| 版本冻结 | 任务使用创建时快照 | 技能/伙伴更新不回溯 |
| 幂等包含选择 | 同键同选择返回同任务 | 同键不同选择 409 |
| 预算前置 | 组合后超预算在提交前提示 | 不降级模型、不缩减用户目标 |
| 撤回 | 连接器撤权停止新调用 | 不删除历史，不自动换连接器 |
| 失败不扩权 | 失败/未知保留原任务 | 不自动重试更大范围 |

说明：

- 云端任务 API 当前不接受 `environment`；本机 tracked 走 `local/tasks/` 准入。统一入口接受环境是 P2-A 的工作，不应在 E1/E2a/E2b 假装已经存在。

任务响应增加：

```json
{
  "capability_snapshot": {
    "version": 1,
    "preset": null,
    "skills": [{ "id": "uuid", "version": 3, "name": "会议纪要", "content_sha256": "..." }],
```

**幂等**

`runs.create_task` 当前比较 `organization/kind/goal/background`（`src/backend/work/runs.py:89-113`）。扩展后必须比较：

- 用户目标/背景；
- `preset_id` + `quick_command_id`；
- 规范化后的 `skill_ids`；
- `connector_ids` + `connector_scopes`；
- 环境（如果同一 API 接受环境）。

同一 `Idempotency-Key` + 相同选择返回原任务；不同选择返回 `idempotency_conflict`。

**WorkRun.agent_payload（E1/E2a/E2b，不新增 wire 字段）**

以下是数据库记录，不是发给 Gateway 的完整 job。`AgentClient.submit` 仍只发送 `goal/files/timeout_seconds/limits`；`capability_snapshot_hash` 只存数据库，不发送给执行器。

```json
{
  "goal": "组合后的目标 + 工作方法（云端）",
  "execution_goal": "组合后的目标 + 工作方法（本机 tracked，可选）",
  "files": {},
  "timeout_seconds": 180,
  "limits": { "max_model_calls": 6, "max_total_tokens": 80000, "max_output_tokens": 3000 },
  "capability_snapshot_hash": "..."
}
```

云端使用 `goal`；本机 tracked 使用 `execution_goal`，由 `claim` 返回给桌面；两者都只存在业务记录/数据库，`work-agent/v1` 的 wire 字段不变。

E3a/E3b（需要新契约/升级）：

```json
{
  "contract": "work-agent/v2",
  "goal": "...",
  "files": [],
  "timeout_seconds": 180,
  "limits": { "...": "..." },
  "capabilities": {
    "connectors": [
      {
        "id": "uuid",
        "grant_ref": "opaque",
        "scopes": ["read:projects"],
        "operations": ["list_projects"]
      }
    ]
  }
}
```

**本机**

- `work-local/v1` 的 `submit` 仍是严格白名单；E1/E2a/E2b 不直接加字段，而是通过服务端 claim 返回 `execution_goal`，桌面用它提交；
- 新桌面使用 `claim.execution_goal ?? claim.goal` 提交适配器；旧桌面忽略该字段，退化为原目标；
- 新桌面历史和详情必须显示原目标（`binding.admission.goal` 或服务端 `task.goal`），不能直接显示适配器返回的组合目标；否则本机历史会泄露组合提示词；
- E3b 本机连接器需要新的 `work-local/v2` 或扩展字段 + 桌面/适配器同步升级；
- 本机 untracked 首版不支持技能/preset/连接器，避免出现「界面有、执行没有」。

**迁移顺序**

- `0012` 当前仅在本地验证，未应用到生产；任何扩展迁移都排在它之后；
- E1 `0013`；E2a/E2b `0014`；E3a `0015`；E3b `0016+`；E4 `0017+`；
- E2a/E2b 共用 `0014`，不新增 partner 表；每期独立开关、独立回滚。

### 6.9 环境支持矩阵

| 能力 | 云端 | 本机 tracked | 本机 untracked |
|---|---|---|---|
| E1 方法技能 | 支持（服务端组合） | 支持（`execution_goal`，需新桌面） | 首版不支持 |
| E2 套件/伙伴 | 支持（服务端组合） | 支持（同上；需新桌面） | 首版不支持 |
| E3a 连接器（只读 SaaS） | 支持（Gateway v2） | 不做 | 不支持 |
| E3b 连接器（本机/MCP/写入） | 不做 | 另立 E3b | 不做 |
| Pi 复核 | 支持 | 支持（既有） | 不支持（既有） |

原因：

- 云端任务一定经过服务端，最适合解析/冻结/审计；
- tracked 本机经过准入，服务端可以返回执行目标；但需要桌面发版；
- untracked 本机不经过服务端，没有技能注册表、授权和审计；强行支持会绕过组织策略；
- 本机连接器涉及本机凭据和命令执行，风险更高，单独立项；
- 远程派发（设备 A → 设备 B）首版不携带技能/preset/连接器选择；需要扩展 `work-device/v1` 的派发请求，另行立项。

### 6.10 与 P0/P1 的关系

- P0 的统一 composer、会话、历史、注意项不受影响；E1 只使用 composer 的 `tools` 插槽增加一个 chip；
- E1 可以与 P1 档位并行，因为 E1 不改模型/预算解析；但如果团队只能做一件事，优先 P0，再做 E1；
- E2a/E2b 依赖 E1 的技能注册表；
- E3a 依赖执行器 v2、凭据保管、出网和审计；E3b 依赖桌面/适配器 v2；两者都不能与 P0/P1 同批；
- E4 依赖 P2 项目；云端只使用 `project_id` + 文件别名/哈希，本机绝对路径不出设备，本机 context 只在授权目录内读写；
- 扩展工作不应阻塞 P0 上线；P0 的 composer 插槽先留好，但不渲染未实现能力。

### 7.2 工作量

> 估算假设：以 1 名前端 + 1 名后端/桌面为主；不含视觉设计、QA、发布值守、运维、法务/合规评审、存储与模型调用成本。数字为规划区间，不是交付承诺；E3b/E4/Workbench 必须单独排期。

| 阶段 | 内容 | 估算（人日） | 说明 |
|---|---|---|---|
| E1 | 注册表、组合、快照、API、前端 picker/chips、测试 | 8–12 | 不改 Gateway/适配器 wire；claim 加可选字段；tracked 需桌面小改 |
| E2a | 套件模型、快捷命令、输出标准、解析、前端预填、测试 | 8–12 | 仅预设，不含链式 |
| E2b | 伙伴 instructions、组织共享、审计 | +2–4 | E2 合计 10–16 |
| E3a | 云端只读 SaaS：OAuth/HTTP、凭据、工具循环、审计、UI | 20–35 | 暂定，需按同一范围 bottom-up 重估 |
| E3b | 本机连接器、MCP/写入、桌面运行时 | 15–25 | 单独立项 |
| E3 管理/安全 | 管理员目录、策略、审计导出、合规、威胁建模、渗透 | 5–10 | 可与 E3a/b 并行 |
| E4 | 项目上下文、服务端确定性编排、富成果 | 60–95+ | 需按千问篇 7.6 二次估算 |
| Workbench | 设计/幻灯片画布 | 30–50+ | 独立工程，需重估 |
| 未来小队 | 多 Agent 编排、共享上下文、预算拆分 | 20–35 | 不建议近期 |

对照：

- 技术方案原估 P3-能力 15–25 人日，只够「注册表 + 授权 + 审计」；统一路线图 E1 8–12、E2 10–16、E3 40–70、E4 60–95+、工作台 30–50+；
- E1+E2 约 18–28 人日（按 E1 8–12 + E2 10–16），是可控增量；
- E3b/E4/工作台均需独立排期，不能按前端需求同批上线。

### 7.3 验收标准

**E1**

- 只显示已启用、同组织、当前环境可用的技能；
- 选中/移除/上限/超长/冲突均有明确状态；
- 服务端组合顺序确定（不保证模型执行顺序）；技能说明不覆盖用户目标/安全策略；
- 任务快照固定版本/哈希；同键同选择幂等，不同选择冲突；
- 云端与 tracked 本机执行带技能；untracked 不显示技能并说明原因；
- 技能内容不含密钥/工具调用；提示词注入测试通过；
- 组织禁用/跨组织/未知技能被拒绝。

**E2a/E2b**

- preset/快捷命令/默认技能正确预填，可移除未锁定项；
- 技能选择顺序确定；执行顺序不保证（E4 才保证）；
- preset 版本/内容哈希冻结；组织 preset 只读；个人 preset 字段保留但首版不开放；
- 套件模板无链式/连接器/富成果入口；伙伴模式无记忆、无主页、无自动化、无小队入口；
- preset + 技能组合不超限；冲突提示正确；
- 云端/tracked 本机一致；untracked 明确不支持。

**E3a/E3b**

- E3a 只读 SaaS 可连接/授权/调用/撤销；E3b 本机/MCP/写入另立验收；
- 授权弹窗显示账号、范围、保存位置、数据去向；
- 未授权/过期/范围不足/限流/不可用状态明确；
- 令牌不在 payload/日志/事件/埋点；跨组织/越权 scope 被拒绝；
- 任务详情可审计调用；撤销后停止新调用；
- 旧 Gateway 兼容路径明确；不自动调用/写入/降级。

### 7.5 发布与回滚

- E1：`WORK_SKILLS_ENABLED`；迁移 0013；关闭后隐藏技能选择，已创建任务保留快照；
- E2a/E2b：`WORK_PRESETS_ENABLED`；迁移 0014；关闭后不能新建/选择 preset，已创建任务保留快照；`WORK_PARTNERS_ENABLED` 不再新增，必要时做别名；
- E3a/E3b：`WORK_CONNECTORS_ENABLED` + 按连接器/租户 kill switch；撤销 grant；保留审计；Gateway v2 回滚前先排空任务；
- E4：`WORK_CONTEXT_ENABLED` / `WORK_RICH_ARTIFACTS_ENABLED` 独立开关；E4 详见千问篇；
- 旧客户端：E1/E2a/E2b 的 `execution_goal` 是可选字段，旧桌面忽略并退化为无技能；E3a/E3b 不承诺旧 Gateway 兼容，必须升级或 v2；
- 迁移：`0012` 未上生产前，不应用 `0013+`；E1 0013、E2a/E2b 0014、E3a 0015、E3b 0016+、E4 0017+。

### 7.6 指标与埋点

指标：

- 能力采用率：使用技能/preset/连接器的任务占比；
- 组合率：使用 2 个以上能力的任务占比；
- 提交转化率：打开能力选择 → 提交；
- 首次提交耗时：加入能力后是否变慢；
- 任务成功率/返工率：按能力组合分组；
- 连接器授权完成率、调用成功率、撤销时延；
- 预算/上下文：组合后 token、失败原因、超限率；
- 信任：用户移除建议技能的比例、查看「本次任务计划」的比例。

埋点（不采集正文/路径/令牌/连接器返回数据）：

- `work_capability_view`（kind）
- `work_capability_select`（kind、id、source）
- `work_capability_remove`（kind、id）
- `work_capability_resolve`（counts、blocked_reason）
- `work_submit`（environment、skill_count、preset、connector_count）
- `work_connector_authorize`（connector_id、scope_count、status）
- `work_connector_call`（connector_id、operation、status）
- `work_capability_revoke`（kind、id）

## 9. 风险与开放问题

| 问题/风险 | 影响 | 建议 |
|---|---|---|
| WorkPreset 的可见范围？ | 决定权限、共享、审计和 UI | E2a 内置/组织、成员只读；E2b 组织伙伴只读；个人 preset 后置 |
| 是否要持久记忆/用户画像？ | 隐私、提示词膨胀、不可解释 | 首版不做；未来单独设计可查看/可删除的记忆 |
| 技能自动匹配还是显式选择？ | 可复现性、信任、提示词长度 | 首版显式；建议可提示但必须用户确认 |
| 连接器先做 MCP 还是策展 HTTP？ | 生态 vs 可控性 | E3a 只做 OAuth/HTTP SaaS；MCP 放 E3b |
| 连接器在云端还是本机执行？ | 凭据归属、数据出境、出网 | E3a 云端；E3b 本机另立 |
| 是否支持写入外部系统？ | 副作用、审计、回滚 | E3a 不做；E3b 逐次预览 + 审批 + 幂等 |
| 本机 untracked 是否支持能力？ | 隐私模式 vs 组织策略 | 首版不支持；避免绕过服务端授权/审计 |
| 远程派发是否携带能力选择？ | 设备 A→B 的能力一致性 | 首版不带；需要 `work-device/v1` 扩展与设备能力协商 |
| 上下文 8000 字符上限 | 长 preset/多技能无法组合 | E1/E2a/E2b 限制长度；需要长说明时升级 agent 契约 v2 |
| 技能质量与提示词注入 | 结果不可控、越权 | 组织策展、版本/哈希、评审、注入测试 |
| 连接器数据进入模型上下文 | 数据泄露/合规 | 明确告知、最小化、企业策略、必要时不做 |
| 旧 Gateway/旧桌面兼容 | 新字段被拒绝/行为不一致 | E1/E2a/E2b 用可选 `execution_goal`；E3a/E3b 用 v2 或先升级 |
| 计费与配额 | 连接器调用成本不透明 | 按连接器/任务计量；提交前预算提示 |
| 管理员界面与审计导出 | 组织无法管控 | E1 起就做组织范围；E3a 前完成管理/审计 |
| 与项目/企业知识的关系 | 概念混淆 | 项目是上下文；企业知识是组织数据；连接器是外部集成 |

需要产品拍板的事：

1. **首版 WorkPreset 范围**：E2a 套件模板（推荐），E2b 工作伙伴是否同批？
2. **技能的首版来源**：内置/组织策展（推荐），还是允许个人上传（后置）；
3. **连接器的首版边界**：E3a 云端只读 SaaS（推荐）；E3b 本机/MCP/写入是否立项？
4. **是否投入 E4**：项目上下文 + 链式 + 富成果（决定能否做千问式完整专家套件）。

## 11. 一句话结论

**豆包的扩展体系值得学的是「任务内组合 + 方法/数据分层 + 安装/授权/调用分离」，不值得直接照搬的是「伙伴级默认允许」和「完整提示词文件」。we-meet 统一用 `WorkPreset`：先做 E1 方法技能和 E2a 套件模板，E2b 再做短说明伙伴，E3a 只读 SaaS 连接器，E3b/E4 单独立项；在 E2a 之前，不新增扩展中心入口。**
