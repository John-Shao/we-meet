# 独立日志容量与提交耗时走查

日期：2026-10-11（Asia/Shanghai）。分支：`feature/speaker-identity-voiceprint`。接续[日志门禁](voiceprint-journal-gate-review-2026-10-11.md)及[完整 RTC 回归](voiceprint-journal-rtc-review-2026-10-11.md)。本阶段完成独立日志容量测量，减少业务提交中的重复读取和合并；功能仍默认关闭。

## 改动及不变量

原运行路径先读取、验证并合并完整状态，再由 `publish` 重新读取、验证和合并一次。新增 `Journal.prepare_publication()`：读取一次已认证的状态，返回头信息的副本和持有原状态的发布闭包。原状态不暴露给调用者；修改返回头信息不会改变 CAS 前提。闭包合并新状态一次，在原头上追加；外部已经有较新提交时，数据库仍拒绝 CAS，不刷新旧快照或盲目重试。

`runtime.mutation` 使用该路径。普通无变化调用不追加；麦克风声明等临时隐私变更仍强制追加。累计撤销证明、元数据容量限制、签名加密、提交前发布、主库检查点及失败关闭规则保持。原 `publish` 接口继续支持首次初始化和离线调用，持久化格式及 SQL schema 不变。

## 探针与测量范围

新增 `voiceprint_journal_capacity_probe.py`，由现有隔离启动器的 `--mode capacity` 启动。使用真实 PostgreSQL 16、TLS `verify-full`、主节点要求、最小权限角色和非 root 后端；主库地址不可达，并显式拒绝任何主库连接。

每个合成作用域有一条权限、一条删除下限、一条来源失效及三条贡献失效证明，每条贡献引用一个模板证明。三个规模分别为 100／1,000／3,000 个作用域，合计 600／6,000／18,000 行。没有声音、向量、真人账号或模型调用。作用域数量不是生产用户容量；实际多组织、来源和模板引用密度会改变大小。

发布耗时包含读取和认证旧状态、合并、签名加密、TLS 及数据库 CAS。原路径保留两次读取／合并，优化路径使用一次；两者在同一运行中对同一完整状态强制发布。数字不包含主库捕获、业务 SQL、全局事务锁等待、进程间竞争或配置文件加载。

## 实际结果

Docker Desktop Linux x86_64，后端限制 2 CPU／1 GiB、日志 PostgreSQL 限制 1 GiB；Docker 总可用为 32 CPU、约 15.44 GiB。每条发布路径每个规模仅 3 次，最新头 5 次。下表为本次中位数，不计算 P95 或生产 SLA。

| 合成作用域 | 净元数据 JSON（字节） | 日志封装（字节） | 最新头读取 | 完整认证读取 |  原发布路径 | 优化发布路径 |
| ---------- | --------------------: | ---------------: | ---------: | -----------: | ----------: | -----------: |
| 100        |               168,877 |          225,565 |    9.77 ms |     18.35 ms |   109.92 ms |     71.77 ms |
| 1,000      |             1,688,077 |        2,251,165 |    9.93 ms |     97.37 ms |   800.10 ms |    439.20 ms |
| 3,000      |             5,064,077 |        6,752,501 |   10.12 ms |    273.81 ms | 2,347.83 ms |  1,315.42 ms |

在 1,000／3,000 规模，本次中位发布耗时分别下降约 45.1%／44.0%。优化路径最大耗时为 75.80／445.31／1,400.35 ms。初始独立基线的原路径为 114.95／830.58／2,443.37 ms，中位变化量不能解释为跨机器稳定性统计。

6,500 个相同构成的作用域产生 10,972,077 字节净元数据，超过 8 MiB 明文上限，被明确拒绝；日志头不变，先前 3,000 作用域的所有行保持，没有截断。每表 100,000 行的限制未变；本次先触及字节上限，不代表支持 100,000 个作用域。

另以两个已经准备好的快照验证真实 SQL CAS：第一个成功追加，第二个在较新头存在时被拒绝，最新状态保持。最终 sequence 为 22，实际保留 22 条记录；entries 数据／TOAST／索引占用合计 74,137,600 字节。重启后全部当前元数据保持。约 6.75 MB 的请求绑定签名恢复包成功导出和校验，导出本次 372.49 ms。进程峰值 RSS 为 318,144 KiB，包含 fixture、Django 和最大被拒绝数据，不能视为生产 worker 的内存上限。

## 剩余容量与发布要求

全局事务锁仍串行发布，等待上限仍为 3 秒。1.315 秒只是本次独立日志部分的中位数，生产事务更长；并发到达会排队或拒绝，不能据此给出“支持 3,000 人并发”的配置建议。需要主库事务、实际增长分布、峰值声明／撤销和长时间并发验收。

每次发布仍追加全量封装。按本次最大封装粗算，1 万次发布约 67.5 GB 净封装，不含数据库页、WAL、副本及备份。历史保留、压缩与容量预警须落实；当前累计失效证明须覆盖所有可能恢复的备份和在途写入，不得静默丢弃。多引用的贡献证明还可能使较少作用域就达到上限。

超限会拒绝新的业务提交；该行为不能替代“立即撤销”的容量保障。生产启用前必须验证增长预算及处理流程，避免进入无法发布新撤销的状态。本阶段没有提高上限、裁剪证明、取消 CAS、延长锁等待或开放生产。

独立日志 HA、自身恢复／可信最新头、密钥轮换、实际设备、授权真人评测和生产部署验收仍待完成。Qwen 优先路线不变，本阶段不进行模型切换或真人效果声明。
