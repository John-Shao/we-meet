## 1. 结论

**基础链路已经具备，后续重点应从新增栏目转为补齐来源覆盖、修正交互承诺和提高复核效率。当前不需要推翻架构，也不需要照搬飞书的文档编辑器。**

优先做四件事：

1. 修复 Web 被分享者误读所有者转写控制接口，以及普通上传/单次直传的取消和进度语义。
2. 开放上传说话人区分，补齐服务端全局排序；这两项已有部分底座，但用户获得的能力不完整。
3. 增加批量校对、可复用热词、发言时间轴和清楚的记录信息，让用户能高效核对与复用结果。
4. 为已完成的上传件/录音件提供记录级删除与恢复；团队协作需要进一步设计媒体权限和协作校对，不能将只读分享等同于完整协作。

当前最明确的遗漏不是“没有纪要、章节、分享、导出”，而是下列具体问题。

## 2. 优先补齐：现有流程中的真实问题

优先级：P1 表示下一阶段应做；P2 表示核心流程稳定后增强。没有证据将这些项目定为生产全站阻断 P0。

| ID / 优先级 | 当前事实与用户影响 | 最小补齐范围与验收 |
|---|---|---|
| G1 / P1 | **Web 被分享者可能看到误导性转写错误。** 上传详情只判断来源为 upload，就挂载 `UploadedRecordingStatus`；组件请求所有者专用接口，被分享者得到 404 后显示错误。Android 第十九批已修复，同类修复未同步到 Web。静态调用链已确认，实际 Web UI 尚未复测；这不是越权泄漏。 | Web 用 `upload.can_control` 决定是否读取控制状态；只读用户使用授权元数据/正文状态。验收所有者、仅纪要、仅全文、撤权四种身份路径，不为消除错误而放宽服务端接口。 |
| G2 / P1 | **普通上传与单次直传的取消不完整，进度反馈不足。** Web 的取消按钮在 busy 时均显示，但 AbortController 只在分片路径设置；Android 取消按钮修改的标志也仅由分片路径消费。非分片路径缺少字节进度。分片恢复机制已存在，不能把所有上传统称为不可恢复。 | 三条路径统一可取消网络请求、进度/阶段反馈和结果未知处理。取消发生在传输、合并、登记三个阶段时，分别有清楚结果，不能把已登记成功误报为取消。单次直传可以说明重试需重传，无须所有路径都实现断点续传。 |
| G3 / P1 | **上传分人能力没有交付到用户。** 后端及供应商适配支持 diarization，默认 false；Web/Android 上传配置只传 context、hotwords，用户不能开启说话人区分。已有发言人页和身份绑定不能弥补输入阶段缺失。 | 双端提供分人选项，贯通普通上传、直传、分片及重试配置。用真实多人样本验证说话人标签、手动归属、统计；“区分声音”不承诺自动识别真实姓名。 |
| G4 / P1 | **Web 排序只是当前页排序。** 服务端已有按 origin_at/id 的全局倒序，但 UI 创建时间升降序只重排当前页。不是“没有排序”，而是 UI 选择与全局结果不一致。 | 把可选排序放到服务端、使用稳定次序及匹配游标，切换排序重置分页。用跨页数据验证全局单调性；随后增加时间范围/所有者等组合筛选，不在当前页假过滤。 |
| G5 / P1 | **校对仍以单段为单位，热词只用于一次上传。** 已有版本校对/恢复，但未找到批量术语替换预览、统一提交和回退；未找到个人/组织可复用热词库。专业名词反复出错时仍需逐段、逐次处理。 | 先做单记录批量查找替换：预览命中、冲突检测、一次操作记录、可恢复；再做个人词表复用。组织词表继承和审批可后置。延续有效原文投影，不能破坏旧引用快照。 |
| G6 / P1 | **记录信息与纪要文档导航偏弱。** 双端信息页主要是来源、时间、保留方式；owner 已在接口中，详情却没有完整呈现。已有纪要导出到 Docs 的工作流和文档链接，但入口不等于信息页中稳定可见的关联产物。 | 展示所有者、可靠的时长、来源及处理状态，提供已有纪要文档的浅层入口和版本关联。没有真实参会关系时只显示识别发言人，不能把 speaker 当 participant；不新增双向同步文档编辑器。 |
| G7 / P1 | **缺少统一的记录级删除/恢复入口。** canonical 记录接口为 ReadOnlyModelViewSet 加自定义动作，未见完整的录音/上传记录回收站流程；上传取消、媒体保留策略、旧云录制文件删除均不等于删除整条记录。 | 先覆盖个人上传/录音的移入回收站、恢复、保留期及永久清理规则；明确原文、纪要版本、共享、搜索、媒体及外部导出文档各自的处理。企业所有权转移和管理员批量治理后置。 |

G1、G2 是当前代码行为缺陷，优先于新增竞争功能；G3、G4 是现有能力交付不完整。G5–G7 是高频使用时会持续产生操作成本的缺口。

## 7. 对架构与 UX 的判断

保留统一 `MeetingRecord`、按来源接入媒体、原始转写与修订分离、版本化纪要/引用、能力字段控制操作的方向。这些边界已经支撑上传、采集和线上来源共用读取与产物；分源采集和独立 Docs 都合理。

目前架构问题主要在边界落地：Web 未遵循已有 `can_control`（G1）、上传取消契约只覆盖一种传输（G2）、来源能力尚未全覆盖（G11/G12），以及列表排序没有服务端契约（G4）。优先修正这些，避免仅增加入口、继续扩大双端不一致。

UX 不必复制飞书的固定两栏或横向多 Tab。要一致的是任务链：导入时能选分人并看见状态；回看时能定位原文和发言片段；校对能批量处理术语；信息页能看懂所有者和产物；分享者能知道自己能读、能听、能否校对；记录不再需要时能安全清理。

## 8. 建议下一轮批次

1. **正确性批**：G1 + G2。补 Web 只读状态调用与双端上传取消/进度，并进行对应路径回归。
2. **分人与列表批**：G3 + G4。贯通分人选项与真实多人样本，完成服务端排序；均无需等待被延后的大文件/长录音验收。
3. **复核效率批**：G5 + G6 + G8。先批量校对/个人热词，再记录信息与可点击发言时间分布；内容关键词可随此批小步加入。
4. **记录管理批**：G7。先个人记录回收站，明确导出文档和共享的生命周期，避免误删其他系统中的独立产物。
5. **按产品场景推进**：团队协作优先 G10；线上会议主场景优先 G11；跨语言优先 G12；知识检索优先 G14。G9 的词级时间和 G13 的片段协作后置。

Android 正式发布准备与上述工作并行。每一批均应分别记录实现、测试、推送、部署和端到端验收，不再以“按钮存在”作为完成依据。本文件只重排建议，本次没有开始这些运行代码变更。
