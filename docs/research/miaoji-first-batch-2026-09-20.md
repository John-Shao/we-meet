## 版本契约

三个版本含义分别为：

- 原文行 `revision`：原始 ASR 段版本，保持不可变。
- `correction_revision`：该段最新人工修订号，未修订为 0；保存和恢复时传入这个值。
- `record_revision`：整份实录版本，成功变更时递增；写入响应返回提交后的值。

保存请求保持 PATCH 路径，JSON 增加必填 `expected_revision`。恢复请求保持 DELETE 路径，通过查询参数 `?expected_revision=N` 提交校对版本。两种请求缺少版本均返回 400，过期版本返回 409。

成功响应返回有效文字、原文、校对标记以及上述两个可变版本。兼容保留 `revision` 响应字段；它在无新修订时仍为 null，因此客户端后续编辑必须使用 `correction_revision`。

新建的纪要输入快照使用「原始段版本 + 校对版本」作为 `segment_revision`。保存过的旧输入快照不重写，历史引用仍指向当时的文字。校对不会自动启动付费纪要生成。

## 实现入口

- `src/backend/core/services/effective_transcripts.py`：当前发布批次、最新校对文字、校对版本和显示名的统一查询投影；查询不连接多行修订结果，也不逐段读取修订。
- `src/backend/core/services/transcript_corrections.py`：在同一实录行锁内完成版本比较、修订追加及记录版本递增。
- `src/backend/core/api/meeting_records.py`：查询投影、权限提示、写入版本契约。
- `src/frontend/src/features/meetings/components/TranscriptSegment.tsx`、`CaptureTranscriptionPanel.tsx`：编辑草稿、失败状态及缓存刷新。
- Android `MeetingRecordRepository.kt`、`RecordSegmentCorrection.kt`：写入后版本核验、版本传递、权限入口和编辑状态。

## 验证

- 后端两组测试分别通过 64 项和 105 项，交集 4 项，共 165 项不同测试。覆盖真实 PostgreSQL 写入、恢复历史、版本冲突、旧纪要快照、新输入、搜索、导出、重新转写、实时转写、阶段纪要和发言人归属。最后对增强后的 4 项核心回归再次验证通过。
- Web 50 项测试通过，含连续两次编辑后恢复原文、保存期间不退出、网络失败保留草稿、刷新期间保留原校对版本。
- Web TypeScript 构建检查、修改文件 ESLint、120 个 JSON 解析、多语言结构检查通过。
- Android 46 项 `MeetingRecord*Test` 通过，包含 Retrofit PATCH JSON 和 DELETE 查询参数的真实序列化验证；Kotlin 编译和设计规范检查通过。
- 新增及主要修改的 Python 文件 Ruff 检查通过；`meeting_search.py` 仍有原有的三项 lint 问题（参数数量、局部导入和旧服务私有方法引用），本次没有新增同类问题。
- 本次使用独立本地 PostgreSQL、Redis 测试实例，没有调用真实 ASR 或付费模型；未做浏览器、模拟器或真机人工验收。

## 发布约束与下一批

本批不需要数据库迁移。旧客户端没有提交校对版本，连接新后端时写入会返回 400；Web、Android 需配套升级。新客户端连接缺少 `can_correct` 或 `correction_revision` 的旧后端时隐藏编辑入口。

恢复原文从本次起保留历史；此前已被旧逻辑删除的修订无法由本次变更恢复。编辑草稿仅存在当前界面内存中，账号切换、权限失效、页面退出仍按现有私有数据清理机制处理，不提供离线草稿存储。

下一批继续处理「上传音视频 → 转写 → 生成纪要」的完整链路，并拆分编辑权限与付费 AI 权限。此次 `can_correct` 复用既有服务端授权规则，不扩大上传记录或普通只读成员的编辑权限。播放器、跨页跟随、签名地址续期留在后续媒体回放批次。
