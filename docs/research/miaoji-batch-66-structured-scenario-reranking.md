# 第 66 批：结构化输出与场景歧义对照

日期：2026-09-21。基于 `a2297daf9`；仅改动评测工具、合成控制和报告，不修改生产检索或客户端。用户最近确认的问答 backend 为 `4c5ca713f` / Helm388，其他专项发布独立管理。本批不构建镜像，无部署要求。

## 实验范围

第65批有两种不同失败：返回裸编号不符合输出契约，以及结构合法却将产品上线错配成快递派送。本批拆成两个固定方案：

- `schema_only`：沿用第65批证据选择要求，改成 `decision/selected` 对象，使用严格 JSON Schema，候选编号枚举、必填摘句、禁止额外字段；本地仍验证原文摘句、去重、长度与决策一致性。
- `scenario`：使用同一Schema，额外要求按实体、事件、动作和属性核对候选；当多个同等合理目标无法由问题指代区分时返回 `clarify`，同一目标的冲突证据仍保留。

两者均关闭thinking、temperature=0。根据[百炼结构化输出官方文档](https://help.aliyun.com/zh/model-studio/qwen-structured-output)中对 Qwen3.8-Flash 的支持说明，使用 `response_format.type=json_schema`、`strict=true`，不设置 `max_tokens`，避免人为截断。服务端接受参数不等于语义正确；本地校验继续保留。本次文档核对日期为2026-09-21。

`schema_only`与第65批相比还改变了外层响应结构、增加决策字段并取消输出token上限，且请求为重新单次生成。因此只能评价这个格式约束方案，不能把语义成绩变化全部归因为Schema。两个新方案交替请求顺序，无重试、无中途改提示或改gold。

## 数据与判定边界

复用第65批22个冻结请求（16个检索问题和6个直接控制）及第64批68个冻结向量，不重新生成embedding。另加14个控制：10个基础样例及4个候选反序变体，涉及软件发布/货运到仓、开发负责/报销联系人、明确/含糊/不存在项目预算、冲突、未知原因和材料内伪指令。

新增材料和期望结果在请求前固定；不向模型发送gold、期望决策或题目标签。但这些由同一作者设计，是**合成诊断集，不是独立人工盲测**；反序变体也不是14个独立任务。题库顺序调整只是有限的位置敏感性检查。

旧57题仍按原gold计分，`clarify`在原有证据题中仍算未找到证据，不重新标成通过。新增两道含糊预算题（含反序）才有显式 `clarify` 期望。此决策仅用于离线诊断，没有向App/Web增加澄清流程。

回放通过第65批真实ORM与问答上下文准备链路，核对候选内容、实时引用及实际gold覆盖；原始生成、输入/Schema/请求hash、本地校验结果全部保存。最终回答不生成，不能据此声称最终回答质量完成。

## 关键发现

- 原负责人题的裸编号结构错误本次没有重现。格式方案给出合法摘句“责任人指定为赵明”，按旧gold恢复该题；场景方案返回`clarify`，仍漏证据。
- 原`release_with_noise`中，格式方案仍选择“快递将于明天派送”，场景方案返回`no_evidence`；两者都未选到旧gold的上线日期。
- 重新检查该题的英文问句 `When do we ship the product?`：缺少软件/货物类型与目标项目，`ship`本身可能有不同含义。因此保留其历史错误评分，同时标记为需独立复核的语义歧义；不能把作者预设的gold当成已验证的唯一人类意图。新增明确的software go live与货运到仓问题，两方案均选对，正反序也一致。
- 场景方案把“上次项目经费最终批了多少”和“这次得掏多少银子”也要求澄清，即使输入池只有一条费用预算证据。这使原两套题库分别从23/25、8/8降到22/25、7/8。提示里已要求单一明确目标可保留，仍不能保证执行。
- 费用/牵头类指代问题需要真实用户上下文及人工判定；所有旧题保持原gold不动。新控制用两个明确不同项目检验澄清，避免用“拒答更多”冒充相关性变好。
