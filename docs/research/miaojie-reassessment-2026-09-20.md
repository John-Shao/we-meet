## 1. 判断先行

**保留当前领域架构，优先修复跨模块链路，再补回看体验。现在的主要问题是能力接通与数据一致性，不是缺少足够多的模型或按钮。**

1. **`MeetingRecord` 作为记录身份是合理的。** 线上会议、独立录音、上传文件可以共用记录、阅读、检索、分享与产物关联，不必强行共用采集实现。原始转写不可变、纪要版本与引用快照也应保留。
2. **“已补齐”需要明显降级。** 当前代码已经有校对、身份绑定、字幕格式导出、播放器和分片上传，但上传来源的纪要/编辑权限未贯通，校对内容未进入纪要输入和搜索，Web 跟随接线存在缺陷，Android 校对成功后的版本校验存在冲突。这些比新增关键词或可视化纪要更紧急。
3. **不要把“实录、智能纪要、录音入口分开”本身判为架构错误。** 截图 1/3/8 明确链接独立智能纪要，截图 9 已进入文档页面；官方资料也区分 Minutes、Note、Doc。需要统一的是记录身份、导航和状态，不是把所有产物塞进一张表或一个页面。
4. **上传视频画面与线上会议云录制必须分开。** 已上传的文件已经存在，补视频画面不依赖 LiveKit Egress。线上会议回放则还需要录制产物、存储完成事件与时间轴映射。旧报告将视频回放整体列为“不做”，不适合作为本轮结论。
5. **下一阶段应以“完整的一条记录”验收。** 建议先保证：上传/录音 → 可播放 → 可检索/校对 → 纪要与引用一致 → 可导出/按权限分享。不要以组件存在或测试数量替代这条链路。

## 4. 当前实现中应先处理的问题

下列是代码可以定位的问题，不是根据竞品按钮推测出来的新需求。严重度按核心链路影响排序，不给缺少生产数据的项目虚构事故概率。

### A1. 上传文件未接通纪要生成，并连带阻断校对与说话人绑定（P0）

**用户影响：上传一段像截图里的视频，即使转写成功，也不能沿当前记录链路得到同等的纪要产物。**

- `services/meeting_records.py:109` 的独立记录生成授权只包含 `Source.AUDIO`，不包含 `UPLOAD`。
- `services/capture_summary_source.py:31` 再次要求 `source_type == AUDIO`，并要求已发布的 `CaptureTranscriptionJob`。上传使用另一套 `UploadedRecording` 状态与原文发布逻辑，不能只放开一个枚举。
- `services/uploaded_recordings.py:527` 的 `finish()` 发布原文、修改记录版本并记账，没有在这里接入纪要生成。
- `transcript_corrections.py:92`、`speaker_attribution.py:34` 又复用 `can_generate_summary()` 做编辑授权；上传属主因此也不具备这些编辑能力。
- 后端 `api/meeting_records.py:260` 对上传返回 `capture_id=null`，Web `routes/MeetingRecordWorkspace.tsx` 因而走 `OriginalRead`；该阅读组件没有传入校对处理函数。Android 则按来源显示上传校对，后端仍会拒绝。

**建议：** 增加上传来源的已发布原文适配器，统一形成有效逐字稿快照；把 `edit_transcript`、`attribute_speaker` 与“是否允许消耗 AI 额度生成纪要”分开。不要为通过现有条件而将 upload 伪装为 audio_recording。

**验收：** 同一上传文件在 Web/App 都能完成转写、校对、绑定发言人并生成纪要；共享只读者只得到明确允许的能力。未生成纪要时也应能基于有权限的逐字稿问答，而不是必须先拥有一个纪要版本。

### A2. 阅读、纪要、搜索、导出的内容不一致（P0）

| 消费方 | 当前取值 | 结果 |
|---|---|---|
| 原文阅读 API | `corrected_text_subquery()`、`attributed_name_subquery()` | 展示修订文字和绑定姓名 |
| 独立录音纪要快照 | `capture_summary_source.py:84` 读取 `row.text`、`row.speaker.label` | 重新生成仍读识别原文与旧标签 |
| 记录内搜索 | `api/meeting_records.py:721` 先按原始 `text__icontains` 过滤 | 用户搜刚刚改正的词，可能找不到该行 |
| 跨记录召回 | `meeting_search.py:64` 匹配、返回 `row.text` | 搜索和回答可能继续引用错误内容 |
| TXT/SRT/VTT | `transcript_export.py:196` 校对文本 + 原始 speaker.label | 文字已改，姓名却可能还是“Speaker 1” |
| 单记录问答 | `meeting_record_qa.py:98` 使用指定不可变 snapshot | 历史快照是合理的，但没有解决“当前有效文本”生成与新鲜度提示 |

本轮用真实 `capture_summary_source.source()` 配合隔离的内存输入验证，输出为：

```text
READ_PROJECTION: Corrected word
SUMMARY_INPUT: ASR wrong word
ATTRIBUTED_NAME: Alice
SUMMARY_NAME: Speaker 1
UPLOAD_SUMMARY: Standalone source identity is unavailable.
```

这不是 LLM 质量问题，在调用模型之前输入已经不一致。

**建议：** 一个统一的有效逐字稿读取层决定当前 ASR 代次、修订文字、显示姓名和记录时间。搜索、导出、新快照和 AI 输入共用它。原文完整性校验继续对识别原文及其 hash 执行，校验后再应用人工修订。不要拿修订文字去覆盖原文 hash。

旧纪要/旧引用维持其冻结快照；源修改后标记“来源已更新”，由用户生成新版本。不要自动重写已分发的纪要或协作文档。

### A3. 校对的保存反馈、并发保护与历史回退不完整（P0）

1. **Web 保存后可能仍显示旧文。** `CaptureTranscriptionPanel.tsx:451` 使用 `capture-originals` 查询键；`fetchMeetingRecord.ts:323` 成功后只失效 `meeting-records`。这个原文查询没有轮询，工作区重新取到 record 也不会改变它的查询键。`TranscriptSegment.tsx:219` 提交后立即关闭编辑态，保存结果与可见内容不可靠地联动。
2. **Android 成功保存会遭遇自己的版本递增。** `MeetingRecordRepository.kt:210` 写入后仍以旧 `revision` 调 `originalRecord()`；`:293` 要求记录版本严格相等。后端真实修改会递增记录版本，于是成功 PATCH 后的读校验可抛 `RecordSourceChangedException`，UI 将其报为失败。现有 correction 测试的 record stub 固定返回 revision=3，未模拟真实递增。
3. **冲突参数有定义但 UI 没用。** Web `CaptureTranscriptionPanel.tsx:492`、Android `RecordSegmentCorrection.kt` 都没有传入 `expectedRevision`。列表只返回原始段 `revision`，没有独立的当前 correction revision。接口支持 409，不代表用户编辑已受到并发保护。
4. **“恢复原文”删除整段修订历史。** `transcript_corrections.py:170` 执行 `original.revisions.all().delete()`，DELETE 也不校验期望版本。这与“追加式修订”目标不一致，且会失去本段人工校对历史。已冻结快照不因此被改写，但修订审计与后续版本单调性会受损。

**建议：** 响应返回新 record revision 和 correction revision；成功后精准刷新原文；失败保留草稿；写前必带 correction revision；恢复原文也追加一个修订事件。把“当前记录变了”与“我刚刚成功改变记录”区分开。

### A4. 播放同步有算法和控件，但关键页面没接完整（P0）

- **Web 当前句高亮：** `MeetingRecordWorkspace.tsx:324` 调用 `usePlaybackFollow(EMPTY_ROWS)`，它计算的 `activeId` 恒为 null。`CaptureTranscriptionPanel.tsx:471` 只要存在 follow 就采纳传入 activeId，跳过按自己的 timedRows 计算。上传 `OriginalRead` 也直接使用这个 activeId。因此工作区虽有 position 更新与滚动逻辑，高亮仍未接通。
- **Web 上传逐句回听：** `OriginalRead` 渲染 `TranscriptSegment` 时没有 `onSeek`，时间文本并没有连接上传播放器。
- **Android 上传：** `RecordScreens.kt:113` 的 `canPlay` 只针对 audio_recording；`:167` 只在 canPlay 时向 `RecordOriginals` 传 onSource 和 positionMs。上传播放器存在，但逐字稿既收不到其时钟，也不能逐句跳转。
- **长稿跨页：** 后端 `RecordPagination` 每页 30 行。Web 按当前页构造 timedRows；Android `RecordOriginals.kt:143` 取无筛选的第一页作为 timeline。播放到后续页或从章节跳到未加载行时，没有按时间定位并加载目标窗口的机制。
- **跟随控制仍需磨合：** Web `transcriptSync.ts` 全 window 的 wheel/touchmove 都会抑制跟随；抑制期结束没有独立定时信号，不能保证同一句内恢复。Android 当前只在正在滚动时让出控制，不等于“用户自由阅读后主动回到播放位置”。

**建议：** 播放器只报告 position；列表基于自己的有效时间窗口算 activeId。增加按 record 时间定位的 API/索引或有边界的预取，避免把所有长稿一次装入客户端。搜索/说话人过滤期间暂停自动跟随，提供“回到播放位置”。两端统一 seek 后是否播放的语义。

**验收：** 用超过 30 行的记录，在第一页/后续页/空隙/搜索/手动滚动/章节引用之间切换，验证文字、音频和滚动目标一致。逐句闭环优先；逐词高亮另需词级时间数据，不能用字符长度估算成真实时间。

### A5. 导出没有沿用“当前有效 ASR 代次”（P0）

`transcript_export.rows_for()` 在 `:186` 读取记录下全部 `MeetingOriginalSegment`；正常阅读使用 `capture_transcription.current_originals()`（`:41`），仅取无 job 的原文及 active_transcription 对应代次。重新转写保留旧代次时，导出会混入历史段落，可能出现重复或过期文本。

此外，逐行调用 `corrected_text()` 会为大量段落反复查修订；这在开放大文件后值得一起改为批量投影。格式渲染测试通过并不能证明数据选取正确。

**建议与验收：** 默认导出当前已发布版本，历史导出明确指定 snapshot；使用批量有效投影及显示姓名。至少验证“转写一次 → 再转写 → 校对 → 绑定姓名 → TXT/SRT/VTT”，结果与阅读页同一版本一致。

### A6. capability 契约、共享范围与播放授权不一致（P0 基础契约，P1 扩展）

- `meeting_records.record_capabilities():140` 仍将 play_media/download_media/edit/manage/capture 固定为 False，而 UI 在各处自行推导可用性。记录 API 不再准确描述产品行为。
- `api/meeting_records.py:1055` 媒体读取只支持上传属主。独立录音的 capture_id 也只暴露给属主。读逐字稿不自动意味着可播放，这是可接受的策略，但界面不能误导用户。
- Android 校对按钮按来源显示，不按真实编辑授权显示；共享只读者可能看见注定失败的按钮。
- `meeting_summary_sharing.py` 是“仅纪要”的授予/撤回流程。模型已有 read_transcript 不等于用户已有分享全文或媒体的完整入口。
- TXT/SRT/VTT 目前只校验 read_transcript，没有独立 export_transcript 开关。这可以作为当前明确的简化策略，但若宣称提供“可阅读、不可导出”等档位，就必须补服务端边界。

**建议：** 形成由服务端计算的 read_summary/read_transcript/play_media/download_media/edit_transcript/attribute_speaker/rename/share/generate_summary/export_transcript 能力集。能力与来源状态分开，返回可展示的不可用原因。记录级播放读取与设备采集控制分离，不要为了共享回听而放开 capture 会话的控制权限。

“不向未授权者暴露内容”继续保留；不需要把所有隐藏按钮机械改成禁用态。只对用户合理期待的能力说明“未保留媒体、仍在处理、权限不足、格式不支持”等原因。

### A7. 长文件可用性需要包含媒体链接与上传完成恢复（发布前核实）

**已经实现的部分：** 两端直传、分片、进度、取消、续传；服务端 ListParts 校对已传分片；第三方存储请求不携带应用身份凭证。总体方案合理。仓库生产配置 `values.meet.yaml:197` 已开启直传，不能再把配置开关当作唯一未完成项。

**仍需处理或实测的边界：**

| 边界 | 当前代码证据 | 评估 |
|---|---|---|
| Web 长时播放 URL 续期 | `uploaded_recordings.py:321` 签名 3600 秒；`UploadMediaPlayer.tsx` mount 时取 URL，没有消费 expires_in 做续期 | 在过期后新建 Range 请求/seek 有失败风险；不能直接认定所有播放到 1 小时必断 |
| Android 周期性重签可能打断播放 | `RecordScreens.kt:71` 默认每 15 秒轮询；`:122` 每轮取 media；播放器 `remember(media.url)` 和 `DisposableEffect(media.url)` 重建/释放 engine | 当签名 URL 随时间改变时，会重置播放状态。代码风险明确，需设备验证；应将 ACL 复核、URL 刷新与播放器生命周期分开 |
| 存储已完成，但完成响应/登记丢失 | `recording_upload_sessions.py:310` 服务端调用 CompleteMultipartUpload，再 adopt；resume/complete 先 ListParts | 若存储完成但 DB 未完成，旧 upload_id 可能无法 ListParts，需要以受信任的会话声明和对象 HEAD 恢复登记 |
| “已完整成功”与“存储完成、DB 未登记” | begin 对 COMPLETED 可回放已有 job，但对 OPEN 继续列分片 | 前者已有幂等恢复，不应误称所有完成重试都坏；后者仍需专项恢复分支 |
| 上传体积上限与时长/解码边界 | 6 GiB 配置是字节约束，非等价的 6 小时转写/播放质量承诺 | 用真实长音频、长视频和不同编码验收；明确格式/时长错误，不只显示上传成功 |

旧报告 §5.11 将 multipart 完成调用描述为“客户端直连存储”不符合当前实现；完成调用实际在上述服务端函数中，确实会继承 storage client 的超时/重试设置。既有真实桶探针结果只作为历史证据，本轮没有重跑存储写入或生产端到端。

## 5. 架构评价与建议边界

### 5.1 应保留的设计

| 设计 | 判断及理由 |
|---|---|
| MeetingRecord 独立于会议房间 | 合理。上传与离线录音无需虚构线上会议；记录链接不应依附于可复用房间 |
| 原始识别输出不可变，人工修订另存 | 合理。可追溯错误来自识别还是人工；应补齐修订历史而非取消保护 |
| 纪要版本 + 输入快照 + source_refs | 合理。历史纪要可核对当时的依据；这是我方可靠性基础，但不能据飞书 API 字段少而断言架构优于飞书 |
| 录音分块、上传整文件分开传输 | 合理。录音需要恢复/缺口，上传本来已有完整对象；可统一读取契约，不必强制统一底层存储 |
| 列表先做可见性过滤，后台任务复核授权 | 合理。继续保持公开入会不等于资料权限 |
| 版本/租约/任务幂等保护 | 有必要。具体新增路径仍需端到端验证，不能概括为“所有写操作都幂等且有冲突保护” |
| 纪要输出到已有云文档 | 合理。继续复用文档的编辑协作能力，避免在实录内另造文档产品 |

### 5.2 建议的职责划分

```text
采集入口：线上会议 / AI 录音 / 上传
                ↓
MeetingRecord（身份、来源、权限、生命周期）
  ├─ Media：采集分块 / 上传对象 / 会议录制映射
  ├─ 原始转写与 ASR 代次：保留来源证据
  ├─ 修订与身份归属：人工可维护的有效内容
  ├─ 有效逐字稿读取层：统一代次、文字、姓名、时间
  │    ├─ 阅读 / 搜索 / 导出
  │    └─ 不可变快照 → 纪要、章节、关键词、问答与引用
  └─ 关联：已生成的纪要文档、任务、外部链接
```

这是对现有模块的收口，不建议为本轮再拆一组微服务，也不建议复制存储一套“妙记表”。

需要明确三种版本语义：识别原文代次、人工内容修订、冻结快照版本。它们不能都含糊地叫 revision。身份绑定变更也要进入有效输入指纹/版本策略，否则姓名修改无法可靠触发派生产物新鲜度判断。

### 5.3 线上会议媒体必须使用真实起点

当前 `MeetingMediaSegment` 仍没有生产服务/API读写链路，模型存在不代表映射存在。配置中 storage event 关闭，既有计划记录了 Egress 等部署依赖；本轮没有验证线上集群状况。

[线上媒体时间轴计划](../plan/online-meeting-media-timeline-2026-09-19.md)中 `record_start_ms=0` 的示例以“录制即整场”为前提；若用户入会数分钟后才开始录制，或停止后再开，这个前提不成立。实施时必须依据录制实际开始时间、媒体首帧/采样时间、持续时间与缺口做映射。不能以会议开始时间和文件顺序猜测全部录制边界。

## 6. UX 评价：学习妙记的任务组织，不照搬它的全部控件

### 6.1 当前合理之处

已有统一记录路由、原文/纪要/发言人/信息/翻译分区、引用溯源、来源及留存提示；Android 将工具放入 sheet 也适合小屏。`/meeting/minutes` 用 has_summary 过滤同一记录集合，本身是合理的视图，不应为了消除“重复入口”而丢掉用户常用的纪要聚合页。

### 6.2 应调整的阅读流程

**Web：** 视频记录采用可调整的媒体区 + 内容区，保证观看与阅读同时可见；纯音频可使用紧凑固定播放器，优先给文字空间。顶部集中标题、时长/来源、分享、导出、更多。正文以“纪要 / 文字记录”为主要切换，发言人、信息、片段作为辅助分区。已有内容时默认纪要，转写处理中或无纪要时默认文字/处理状态，并保留用户最近选择。

当前 Web 工作区主要是单列 Tab 与底部音频；导入组件无条件渲染 `<audio>`，即便 `media_type=video` 也不显示画面（`UploadMediaPlayer.tsx:210` 附近）。应按媒体类型渲染；宽屏双栏是建议，不是所有音频页面的硬性要求。

**App：** 视频置顶、正文采用易触达的标签；长文阅读可折叠媒体为紧凑控制条。必要时显示当前发言人和“回到播放位置”。纪要、全文、章节、发言人的状态和定位应等价，但无需复制 Web 房间页的全部六个 Tab。Android 当前 `UploadMediaEngine` 用 MediaPlayer 音频播放且没有视频 Surface，这不是可视视频回放。

**搜索：** “搜到了哪一句”比“列表变短了”更重要。补命中词高亮、结果数、前后命中、点击回听、清除后保留上下文；要先修有效文本搜索，再做高亮装饰。跨记录筛选与单条全文搜索分开表达，列表排序必须在服务端全体结果上执行。

**编辑：** 阅读态克制，进入编辑态再展示校对工具；提供保存中、成功、冲突和保留草稿。可提供批量词替换预览（命中数/范围），再追加逐段修订；普通用户不需要理解 ASR job、snapshot id 或 generation。

**纪要与章节：** 当前 `RecordSummaryPanel.tsx:677` 对空数组直接不渲染，用户难以分辨“没有待办”与“没有生成”。增加独立的 ready_empty/not_applicable/processing/failed 状态；不因短视频没有章节而判定 AI 失败。章节导航应显示时间范围与简述，点击一次完成播放与原文定位，而不是多次打开引用面板。

**信息与关联：** 工作区目前主要显示来源、日期、留存，所有者虽在列表里存在，详情没有完整呈现。应补所有者、总时长、说话人数/参会成员的明确区分、关联纪要文档和相关链接。创建文档后给稳定“打开纪要文档”入口，并说明它来自哪个版本；不要默认为与实录双向实时同步。

**发言人：** 先做发言总时长与可点击的发言时段，再做观点总结。时长统计需定义重叠发言、未知发言、静音/缺失时段的分母；不要为了凑百分比而制造准确性。

## 8. 建议实施顺序与验收门槛

不按页面逐个补按钮，按可交付链路组织。

### 第一批：数据与权限一致性

- 三来源的有效逐字稿适配；接入上传纪要；分离编辑与 AI 消费权限。
- 修复文本/姓名投影、ASR 当前代次、搜索和导出的一致性。
- 修复 Web 缓存刷新、Android 保存后版本校验、冲突参数与追加式恢复。
- 输出真实 capabilities 与来源状态，保留既有 ACL 防线。

**完成条件：** 同一行校对后，阅读、搜索、新纪要、新问答和导出一致；旧快照引用仍保持旧内容；上传属主可以完成整条流程，纯读者没有误导性的写入口。

### 第二批：回看与长内容

- 修复双端高亮/seek，增加按时间加载原文、搜索回听与回到播放位置。
- 上传视频画面；长播放链接刷新与 Android engine 生命周期。
- 处理分片完成结果未知的恢复；验证 >100 MiB 与长时播放。
- 通用改名、时长/所有者、关联文档；清晰的处理/空态/失败说明。

**完成条件：** 从不在当前页的章节或搜索结果一次跳到正确内容；播放越过 30 行后仍同步；跨链接有效期与网络恢复可继续使用。视频可看画面，音频不会浪费大面积空视频容器。

### 第三批：协作与导航完善

- 共享范围与原媒体下载；发言时段/占比；章节导航。
- 批量校对、关键词、可复用热词；服务端全局筛选/排序。
- 线上会议回放另立基础设施里程碑；使用真实录制起点与缺口映射。

**完成条件：** 授权、撤权、当前来源状态和两端可见操作一致；“仅纪要”不会透出全文或媒体；下载权限独立明确；参会/说话人身份不会被混淆。

### 最小验收样本

| 样本/操作 | 必须覆盖的结果 |
|---|---|
| 与截图相当的约 47 秒竖屏上传视频，2 个说话人 | 画面、全文、纪要、可解释的章节空态、名字与文件名 |
| 超过 30 段的多人长录音 | 跨页跟随、跨页 seek、章节跳转、筛选退出后的定位 |
| 改错词、改名字、重新生成/导出/搜索 | 当前投影一致，历史引用不变 |
| 两客户端同时编辑，再恢复原文 | 409 冲突、草稿保留、历史不被删除 |
| 再次转写同一录音 | 阅读与导出只采用当前已发布代次，不混入历史 |
| owner / summary-only / transcript-reader / revoked | 控件、API、媒体、导出权限一致；读者失败有可理解原因 |
| >100 MiB 分片上传，完成响应丢失 | 不重复建记录，能识别存储已完成并恢复登记 |
| 超过签名 TTL 的播放与后段 seek | 受控续期、不重置位置；Android 周期复核不打断播放 |
| 会议中途开始录制，停止后再次开始 | 使用真实媒体起点，缺口明确，不能全部从 0 算起 |
