# 千问办公 / 豆包工作「新任务」设计调研与 we-meet 新建任务优化方案

- 日期：2026-10-25
- 调研对象：千问办公（QwenWork）、豆包工作
- 范围：新任务 / 新工作任务的 UX、功能、配置、扩展、任务生命周期与成果沉淀
- 方法：官方帮助文档 + 用户提供的产品界面截图；未做真人实测
- 用途：为 we-meet Work 模块「新建任务」改版提供依据
- 证据口径：官方文档 > 截图观察 > 第三方报道；截图只代表某一版本，具体以当期产品为准
- 基准代码：`refactor/work-module` 分支，2026-10-25 工作区快照

---

## 0. 结论摘要

1. **两家的新任务页遵循同一个公式**：目标输入 → 执行环境 → 上下文 → 能力 → 权限 → 执行/接管 → 成果沉淀。差异不在“有没有输入框”，而在每个环节暴露多少控制权。
2. **输入框就是控制面板**。千问办公把技能、连接器、模型、默认权限收进输入框底部；豆包工作把本地/云电脑、项目、按需确认、企业知识、技能、插件收进同一行。用户不需要先去设置页配置。
3. **执行环境是第一分支**。千问办公桌面端可直接读本地磁盘、做浏览器自动化；豆包工作把「本地电脑 / 云电脑」做成首屏一等选择。环境决定权限、上下文和成果去向，应该在目标之后、提交之前选择。
4. **推荐任务是新手引导**。两家都用 4–6 个可点击的“任务配方”，点击后填入目标而不是直接提交。配方同时承担能力发现和空白页消解。
5. **扩展体系的关键是“安装/授权”和“调用”分离**。扩展中心负责安装与授权，任务输入框只出现已安装、已授权的能力；调用方式包括手动选择、`/` / `@`、自然语言自动匹配。
6. **we-meet 不应做“功能更全的千问/豆包”**。我们的差异化是可控执行、组织授权/审计/预算、Pi 独立复核和可版本化成果。优化重点应放在把执行位置、能力、权限、结果预期在一屏内讲清楚，而不是补齐项目、市场、云盘、定时任务。
7. **建议先做 P0（纯前端）**：统一 composer 的云端/本机切换、能力/权限/文件夹 chip、任务配方、字数边界校验、任务详情“当前需要你”横幅、历史任务环境标识。项目、扩展、定时任务在真正实现前不进入左栏。

## 2. 竞品拆解

### 2.1 千问办公（QwenWork）

#### 2.1.1 信息架构与新任务入口

截图可见的左栏结构：

- 新任务
- 扩展：专家套件 / 技能 / 连接器
- 定时任务
- 我的网页
- IM 频道
- 任务 / 频道 两个 Tab
- 置顶
- 项目（空状态 + 新建项目）
- 最近（空状态）
- 底部账号、套餐、设置

新任务入口：

- 左栏「新任务」。
- 快捷键：macOS `⌘ N` / Windows `Ctrl N`（官方文档）。
- QuickPick：全局快速任务窗口，不切换主窗口即可提交任务（官方文档）。
- 搜索全部任务 `⌘ G` / `Ctrl G`。

主区域（截图）：

- 问候语「还没休息，Johnshao / 有什么需要我搞定的？」
- 输入框 placeholder：「描述任务，输入/调用技能」。
- 工具栏：`+`、工具/技能图标、「通用」、「默认权限」。
- 右下：「标准」、麦克风、发送。
- 输入框下方：「新建项目」。
- 快捷 chip：钉钉办公、文档创作、数据分析、多人工作台、创意设计、深度调研。

> 截图中的「通用 / 默认权限 / 标准」是同一行三个不同层级的选择：工作台模式、权限、模型或推理档位。官方文档对「工作台模式」和「模型档位」有展开，对「默认权限」的任务级行为描述较少。

#### 2.1.2 新建任务流程

官方 Web 端使用链路：

1. 点击左栏「新任务」。
2. 在输入框描述工作。
3. 添加资料：上传本地文件，或从「我的网盘」选择。
4. 发送并等待执行。
5. 同一任务内多轮对话推进。
6. 查阅、核对、下载或在线编辑成果。

官方建议一条高质量指令包含四要素：

| 要素 | 含义 | 示例 |
|---|---|---|
| 目标 | 最终想得到什么 | 写一份 Q2 项目状态报告 |
| 输入 | 需要参考哪些资料 | 参考附件中的会议纪要和数据表 |
| 要求 | 结构、语气、范围 | 包含进展、阻碍和下一步，面向管理层 |
| 交付 | 结果形式 | 输出为 Word，并附一页摘要 |

#### 2.1.3 功能范围

- 任务：对话式多轮执行，一个任务包含多轮交流、附件和最终产物。
- 文件上下文：上传、我的网盘、桌面端直接读取本地磁盘（文档、表格、图片、视频）。
- 浏览器自动化：桌面端可执行网页点击、输入、信息采集。
- 交付物：PPT、Word、Excel、网页、报告、代码、多媒体；可保存到原路径或指定文件夹。
- 定时任务：按计划在云端运行，结果可推送钉钉消息。
- 网页发布：生成静态/动态网页，默认域名托管。
- IM 集成：钉钉内入口、钉钉消息推送。
- 企业能力：企业后台、安全合规、权限分层、用量可控。

#### 2.1.4 配置设计

| 配置 | 位置 | 说明 |
|---|---|---|
| 模型档位 | 输入框旁下拉 | 高级 / 基础 / 经济 / Qwen3.8-Max；可按任务复杂度选择，任务中可切换 |
| 工作台模式 | 设置 → 扩展与集成 → 工作台 | 通用 / 设计 / 幻灯片 / 写作；可配置新任务默认模式 |
| 默认权限 | 输入框底部（截图） | 任务级默认权限入口；具体策略文档未展开 |
| 系统权限 | 设置 → 通用 → 系统设置 | 完全磁盘访问、录屏与录音、辅助功能、麦克风、自动化、通知、位置 |
| 安全工作环境 | 高级设置 | 在隔离工作环境中运行任务，文件和数据不离开设备；可清理工作环境文件 |
| 提示词建议 | 偏好设置 | 回复后自动生成下一步建议，新会话生效 |
| 工具调用展示 | 偏好设置 | 默认展开工具调用；IM 频道可选择是否展示每步执行 |
| 快捷键 | 设置 → 快捷键 | 新建任务、搜索任务、QuickPick |

#### 2.1.5 扩展体系

官方定义：

| 类型 | 定义 | 典型用途 |
|---|---|---|
| 专家套件 | 针对特定岗位或场景的一组专业能力，可能包含多个技能和连接器 | 一次获得一套完整工作能力 |
| 技能 | 预定义的专业化工作流，处理特定类型任务 | 内容创作、数据分析等重复/复杂任务 |
| 连接器 | 连接外部平台、账号、数据或工具的接口 | 获取外部数据、操作第三方服务 |

调用方式：

1. 在主聊天框「添加资源」列表中手动选择。
2. 自然语言描述需求，由 QwenWork 在合适时机自动使用已安装资源。
3. 部分技能提供预设输入，点击后按提示补充信息快速发起任务。

安装与授权：

- 技能安装后通常可直接使用。
- 专家套件如包含连接器，需要先完成配置或授权。
- 连接器安装后必须填写参数或授权外部账号，完成后才能使用。
- 安装范围限定在当前个人或组织工作空间；企业用户可在组织内共享自建资源，个人用户暂不支持发布到公共扩展。
- 在「我的安装」中修改任务说明不会影响原始资源，资源更新时会覆盖个人修改。

#### 2.1.6 任务生命周期与成果

- 任务创建后进入多轮执行，用户可持续追加修改指令。
- 任务过程中可切换模型，不丢失上下文。
- 成果进入「我的网盘」，可在 Office 文件中在线编辑、下载、重命名。
- 定时任务每次运行生成独立会话，不自动继承其他日常对话的上下文；执行记录可追溯。
- 定时任务支持启用/停用、编辑、立即执行、删除；执行记录含状态、触发方式、耗时和会话链接。

### 2.2 豆包工作

#### 2.2.1 信息架构与新任务入口

截图可见：

- 应用级左栏：消息（11）、豆包工作、视频会议、日历、云文档、多维表格、工作台、通讯录、权益升级、更多、最近文档。
- 工作模块左栏：新工作任务、定时任务、插件·技能·伙伴、云盘；置顶「和豆包工作的对话」；项目 → 创建新项目；最近。
- 主区域：Logo、「今天有什么工作要处理？」。
- 「为你推荐」chip：创意设计 / 做电商促销海报、云文档 / 帮我把图片插到云文档里、Word / 写一份正式的工作简报、新媒体写作 / 帮我写短视频脚本。
- 输入框 placeholder：「发消息或创建任务... / 使用技能 @ 添加资料」。
- 输入框底部：`+`、本地电脑、项目、按需确认、企业知识、更多技能、插件；右侧「自动」、麦克风。
- 工作任务是独立于普通对话的 Agent 执行模式。

#### 2.2.2 核心流程

官方口径：

1. 点击「新工作任务」。
2. 描述工作目标；可添加资料。
3. 在任务配置中选择本地电脑/云电脑、项目、权限、企业知识、技能、插件、模型。
4. 发送后，豆包工作自动拆解目标、分步调用工具、执行任务。
5. 执行过程中可查看进度、局部编辑、通过手机遥控电脑。
6. 结果保存到云盘或推送飞书，可协同分享。

#### 2.2.3 执行环境

| 环境 | 说明 | 适用场景 |
|---|---|---|
| 本地电脑 | 直接使用本机 CPU/内存算力，数据存储在本地；可访问本地文件、软件；默认在安全沙箱内执行 | 涉及本地软件、文件、项目目录的任务 |
| 云电脑 | 在云端隔离环境处理；不访问本地数据 | 需要持续运行、高资源或手机远程查看进展的任务 |

补充：

- 首次使用本地电脑模式会安装本地安全沙箱，默认在沙箱内执行。
- 本地模式读取必需文件时上传云端处理，云端不存储（官方须知摘要）。
- 支持手机远程派发/遥控；关机后任务仍可在后台运行（官方须知摘要）。
- 云端沙箱闲置会销毁；本地模式需要电脑开机。

> 以上“文件上传云端不存储”“关机后后台运行”等属于法律须知摘要，具体边界以豆包当期条款为准。

#### 2.2.4 任务配置

截图与官方摘要中可以确认的配置项：

| 配置 | 选项/说明 |
|---|---|
| 执行环境 | 本地电脑 / 云电脑 |
| 项目 | 创建新项目；只有当前任务运行环境为本地电脑时，才可通过本地文件夹创建项目 |
| 权限 | 始终询问 / 按需确认 / 全部允许 |
| 企业知识 | 任务配置中启用；仅访问用户有权限的内容，不越权 |
| 技能 | 封装特定领域知识、方法和工作流程；系统自动匹配，也可 `/` / `@` 选择 |
| 插件 | 连接外部系统与数据源，在授权范围内查询或操作数据；安装后需完成授权配置 |
| 模型 | 自动 / Turbo / Pro（官方摘要与截图） |
| 资料 | 输入需求时添加文件/资料 |
| 定时 | 自动任务/定时任务，配置资料、环境、项目、权限、技能、模型 |

#### 2.2.5 权限模式

豆包工作《任务功能须知》原文口径：

| 模式 | 行为 |
|---|---|
| 始终询问 | 每次读取授权外文件或使用网络前均需授权 |
| 按需确认 | 仅在潜在风险操作前询问，如删除重要本地文件、修改文件权限、关闭防火墙等；风险判断由安全模型识别结果为准 |
| 全部允许 | 可自主执行指令并快速访问电脑 |

这是竞品中自主性最高的设计。它适合“让 Agent 接管电脑”的场景，但与 we-meet 当前的组织管控、逐次审批和可追责定位不一致。

#### 2.2.6 技能、插件与知识

| 类型 | 解决的问题 | 调用/安装 |
|---|---|---|
| 技能 | “做事方法”：领域知识、方法、工作流程 | 系统自动匹配；或 `/` / `@` 搜索选择；在「插件·技能·伙伴」安装 |
| 插件 | “数据的读取与写入”：连接外部系统与数据源 | 安装后完成授权配置；任务中 `/` / `@` 指定；权限由连接账号及对应权限设置决定 |
| 企业知识 | 组织内的知识与资料 | 新建任务/定时任务时，在任务配置中点击「企业知识」启用；仅访问有权限内容 |
| 项目 | 任务与文件的上下文容器 | 左栏新建项目；本地环境下可由本地文件夹创建；项目内对话可归档 |

技能与插件的边界值得借鉴：**技能管方法，插件管数据**。这比把所有能力都叫“工具”更清晰，也便于权限和授权分开设计。

#### 2.2.7 任务生命周期与成果

- 任务模式自动拆解复杂目标，分步调用工具。
- 执行中可局部编辑、手机遥控、查看进展。
- 结果保存到云盘，或推送飞书；支持协同分享。
- 定时任务支持可视化定时规则，自动拆解流程、执行、归档。
- 限制：云端沙箱闲置销毁；本地模式需要电脑开机；技能/插件在本地与云环境间的可用性未完整核验。

## 3. 竞品洞察

### 3.1 值得借鉴

1. **输入框即控制面板**：能力、环境、权限、模型都在 composer 内完成，不让用户跳设置页。
2. **执行环境前置**：环境决定权限和上下文，应在目标之后立即选择。
3. **任务配方降低空白页焦虑**：推荐任务不是装饰，而是能力发现和提交入口。
4. **扩展的安装与调用分离**：扩展中心管理安装/授权，任务里只出现可用能力。
5. **技能与插件分层**：技能管方法，插件管数据；权限与授权可以分别治理。
6. **任务状态与接管可见**：执行中可看进度、可局部编辑、可远程接管；结果有明确去向。
7. **项目是上下文容器**：豆包的项目由本地文件夹创建，只在本地环境可选；这比抽象的“云项目”更贴近真实工作。

### 3.2 不应照搬

1. **「全部允许」权限模式**：与我们的组织管控和逐次审批冲突。我们可以提供“本次任务内允许同类只读操作”的渐进选项，但不做无限制自主执行。
2. **云盘、应用市场、浏览器自动化**：超出 Work 模块边界，会制造大量空入口和运维负担。
3. **任务中切换模型**：计量、预算、可追溯性都会变复杂；we-meet 更适合任务级“自动/深入”档位。
4. **项目、扩展、定时任务的导航先摆出来**：未实现就不进左栏，这是既有产品原则。
5. **云端材料上传**：我们刚完成日常办公材料能力的删除，不应为了对齐竞品重新引入；文件上下文走本机工作空间。
6. **把“伙伴/IM 频道/网页发布”当成新任务页的一部分**：这些是独立产品面，不应塞进 composer。

### 3.3 对我方的战略含义

- 竞品在“自主性”和“生态广度”上竞争；we-meet 的差异化应放在**可控执行、组织信任、成果可核验**。
- 我们已经有竞品没有明确对标的能力：逐次命令审批、Pi 独立复核、组织预算、审计、版本采纳。问题不是能力缺失，而是**界面没有把它们讲出来**。
- 新建任务页是这些信任能力最好的展示位置：用户在下达任务前就知道“会在哪执行、会碰什么、谁来复核、成果去哪”。

## 5. 优化方案

### 5.1 定位

不做“功能更全的千问/豆包”，做**更可控、可验收的办公任务入口**：

> 一句话交代目标；在哪执行、用什么能力、给多大权限，一眼可见；成果可核验、可编辑、可追责。

### 5.2 设计原则

1. **任务优先，配置后置**：默认只让用户写目标；背景、环境、权限都是可选的渐进披露。
2. **环境先行**：执行位置决定权限、上下文和成果去向，必须在提交前可见。
3. **能力真实**：只展示 capabilities 真正返回的能力；没有实现的能力不渲染入口。
4. **信任可见**：审批、复核、预算、成果去向要在 composer 和任务详情中出现。
5. **结果可预期**：提交前告诉用户会得到什么、保存在哪里。
6. **未实现不占位**：项目、扩展、定时任务在真正实现前不进入左栏。

### 5.3 信息架构

V1 保持：

```
工作
└── 新建任务
    └── 最近任务（侧栏）
```

不新增项目、扩展、定时任务、搜索、置顶。等对应能力有真实后端和用户验证后再逐项加入。

### 5.4 新建任务页布局

```
工作 / 新建任务

今天想完成什么工作？
描述目标，选择执行位置，交付可核验的成果。

┌────────────────────────────────────────────────────┐
│ 例如：整理这份材料的要点，生成一份汇报文档…        │
│                                                    │
│ [云端 | 本机]  [办公助理]  [逐次确认]        [发送] │
└────────────────────────────────────────────────────┘
云端生成 · 不访问本机文件 · 成果保存在当前任务

快捷开始
┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│ 起草文档 │ │ 整理要点 │ │ 制定方案 │ │ 生成清单 │
└──────────┘ └──────────┘ └──────────┘ └──────────┘

最近任务
```

本机模式：

```
[本机]  [选择文件夹]  [逐次确认]  [登记云端 ✓]   [发送]
成果保存到该文件夹内的 WeMeet成果 目录
```

布局要点：

- 顶部不再出现「使用云端/本机」跳转按钮；执行位置只在 composer 内选择。
- 云端/本机是同一个 composer 的两种适配器，切换时保留 goal 和 background（若当前模式支持）。
- 文件夹 chip 显示文件夹名，完整路径放 tooltip。
- 提交按钮旁不堆叠模型名；模型作为能力详情的一部分。

### 5.5 Composer 规格

| 控件 | 云端 | 本机 |
|---|---|---|
| 目标 | ≤2000 字；接近上限显示计数 | 未登记云端 ≤8000；登记后 ≤2000 |
| 补充背景 | 可展开，≤4000 字 | V1 不支持独立背景；提示写入目标，或后续扩展本机契约 |
| 执行位置 | 云端（默认）；桌面端可切本机 | 本机；Web 端不可见 |
| 能力 | 办公助理；来自 `capabilities.skills` | 办公助理 + 本机执行器 |
| 权限 | 只读说明：不访问本机文件 | 逐次确认；展开可见授权范围 |
| 上下文 | 无 | 文件夹选择/更换 |
| 云端登记 | 不适用 | 开关；开启后 goal 限 2000 字并即时校验 |
| 提交 | goal 非空 | goal 非空 + 已授权文件夹 + 执行器就绪 |

交互细节：

1. **切换执行环境不丢草稿**：goal 保留；background 在本机模式下隐藏并提示“本机任务暂不支持独立背景，请写入目标”。
2. **勾选“登记到云端”时即时校验长度**：若 goal 已超过 2000 字，就地提示并禁用提交，不等到后端报错。
3. **权限文案具体化**：本机不是一句“逐次审批”，而是三行：
   - 可读取已授权文件夹；
   - 命令执行前逐次批准；
   - 是否登记到云端任务记录。
4. **能力 chip 展开**：办公助理说明“生成可编辑的 Markdown 成果”；本机执行器说明“在授权文件夹内执行命令，逐次审批”。不出现未实现的能力。
5. **错误前置**：执行器未配置、文件夹未授权、云端登记长度超限，都在 composer 下方就地提示，不通过 toast 或提交后错误暴露。
6. **可访问性**：执行位置用 radio/segmented control 语义；chip 使用 button + aria-expanded；错误使用 role="alert"；字数计数使用 aria-live="polite"。

### 5.6 任务配方

把两个静态 chip 改为 `recipes` 注册表。每项包含：`id`、标题、一句说明、目标模板、适用环境、所需能力、交付物标签。

V1 建议：

| 配方 | 目标模板 | 环境 | 交付物 |
|---|---|---|---|
| 起草文档 | 围绕给定主题撰写一份结构清晰、可直接编辑的文档，包含结论、要点与待确认信息 | 云端/本机 | Markdown/文件 |
| 整理要点 | 整理给定内容的要点、结论与待确认信息，生成结构化摘要 | 云端/本机 | Markdown |
| 制定方案 | 围绕目标制定可执行方案，包含步骤、依赖、风险与待确认信息 | 云端/本机 | Markdown |
| 生成清单 | 把目标拆解为可执行清单，标注负责人、截止时间与验收标准 | 云端/本机 | Markdown |

行为：

- 点击只填入 goal 并聚焦输入框，不自动提交。
- 若配方只适用于某一环境，点击后提示切换，不静默改环境。
- 配方不包含已删除的日常办公能力（材料解析、周报、表格分析等）。
- 配方注册表是前端静态数据，后续可由后端 capabilities 返回，避免前后端两套能力清单。

### 5.7 任务详情闭环

1. **“当前需要你”横幅**：审批、待确认、设备断线、失败四种状态，动作放在页面顶部。
2. **结果轨道**：已提交 → 执行中 → 待验收 → 已完成；标注执行位置、复核状态、用量、成果去向。
3. **Pi 复核前移**：从详情底部独立区块变为结果轨道中的“已复核/未复核”状态；需要用户同意时再展开。
4. **成果去向**：云端“保存在当前任务”；本机“保存在 WeMeet成果 目录，可选择性同步到云端”。
5. **基于此成果新建任务**：复用当前 goal/background 预填新任务；不假装支持多轮追问。
6. **失败可恢复**：保留取消、重试、原任务查询；本机断线显示“请在执行设备恢复”而不是泛化错误。

### 5.8 配置分层

| 层级 | 内容 | 放置位置 |
|---|---|---|
| 任务级 | 执行位置、文件夹、background、是否登记云端、本次审批方式 | Composer |
| 用户/组织默认 | 默认执行位置、默认模型档位、日预算、是否允许远程、审批策略、复核开关 | 设置/组织后台 |
| 扩展级 | 技能、连接器、专家套件 | 未来的扩展中心；安装授权与任务调用分离 |

约束：

- 组织策略优先于用户默认；被策略禁用的能力直接隐藏或显示禁用原因，不在提交后报错。
- 任务级只能缩小组织允许的范围，不能扩大。
- 预算和模型档位在提交前给出预估或上限提示，避免“提交后才知道超预算”。

### 5.9 扩展策略

V1 不做扩展市场，只做“能力透明”：

- 用现有 `capabilities.skills` 渲染已启用能力。
- `skills` 为空时隐藏能力 chip，不显示空市场。
- 能力详情只描述真实能力：办公助理、本机执行器、Pi 复核（如果作为能力展示）。
- 不展示“专家套件/连接器/伙伴”等未实现概念。

未来扩展注册表建议字段：

```ts
type Capability = {
  id: string
  label: string
  description: string
  kind: 'skill' | 'executor' | 'connector' | 'review'
  enabled: boolean
  authorized: boolean
  scope?: string
}
```

扩展中心负责安装与授权；任务 composer 只消费 `enabled && authorized` 的能力。这样不会出现“安装了但没授权”的中间态混乱。

### 5.10 项目与定时任务

**项目**：

- 豆包的项目由本地文件夹创建，只在本地环境可选；这说明项目首先是一个上下文容器，而不是新的任务类型。
- we-meet 已有本机工作空间（文件夹授权 + 标签 + 模型）。建议先把工作空间当作最小项目，不另起一套云项目模型。
- 如果未来要做项目，定义为“文件夹 + 默认指令 + 默认权限 + 任务集合 + 成果集合”，并复用工作空间授权，不重复造权限。
- 项目入口只有在项目模型、任务归集、权限继承都实现后才进入左栏。

**定时任务**：

- 本质是“任务配方 + 触发器 + 通知 + 预算保护”。
- 每次运行生成独立任务/运行记录，不继承其他任务的对话上下文。
- 需要调度器、失败重试、通知渠道、预算上限和组织审计，缺一不可。
- 在这些能力落地前不做入口，也不在新建任务页放“定时”开关。

### 5.11 响应式与桌面差异

- Web 端：只提供云端执行；不显示本机执行位置，避免用户点了才发现需要桌面端。
- 桌面端：显示云端/本机切换；本机需要执行器就绪和文件夹授权。
- 移动端：以查看任务、审批、同步为主；新建任务可保留云端目标输入，不提供本机文件夹选择。
- 远程待办：本机页已有「远程待办」，但入口在侧栏且依赖授权状态；后续可在任务列表中以来源标识呈现，不单独新增导航。

## 6. 分期落地

| 阶段 | 范围 | 后端影响 | 退出标准 |
|---|---|---|---|
| P0 | 统一 composer 执行位置切换、能力/权限/文件夹 chip、任务配方、字数边界校验、任务详情“当前需要你”横幅、历史任务环境标识、文案统一 | 无 | 云端/本机切换不丢草稿；所有禁用态有原因；本机未授权无法提交；前端测试通过 |
| P1 | 每任务「自动/深入」档位、预算预估、统一创建入口（云端/本机同一提交路径） | 小：请求字段、模型 allowlist、计量 | 档位与实际模型/预算一致；超预算前置提示；用量可追溯 |
| P2 | 项目（文件夹 + 指令 + 权限 + 任务集合）、基于成果新建任务、远程待办前置 | 中：项目模型/权限继承 | 项目内任务共享上下文；权限不越权；导航只在功能可用后出现 |
| P3 | 技能/连接器注册表、定时任务、组织级审批策略 | 大：调度、通知、审计、授权 | 扩展安装/授权/调用分离；定时任务有预算和失败保护；组织策略可审计 |

优先级判断：

- P0 解决“看不懂、不敢点、切换丢草稿”，投入最小、收益最直接。
- P1 解决“成本/质量不可选”，但会触碰计量和模型治理，需与后端一起设计。
- P2/P3 是平台化能力，必须等真实需求和运维能力，否则会变成空入口和长期负债。

## 7. 验收指标

| 指标 | 定义 | 目标方向 |
|---|---|---|
| 新任务页提交转化率 | 访问新建页 → 成功提交任务 | 上升 |
| 首次提交耗时 | 进入页面到首次提交 | 下降 |
| 环境选择正确率 | 提交后未因环境/文件夹错误失败的比例 | 上升 |
| 本机授权完成率 | 选择本机 → 完成文件夹授权 → 提交 | 上升 |
| 审批等待时长 | 命令审批请求到用户处理 | 下降 |
| 任务完成率 | 成功成果 / 已提交任务 | 上升 |
| 复核开启率 | 开启 Pi 复核的成功任务占比 | 上升 |
| 成果采纳率 | 采纳版本 / 生成成果 | 上升 |
| 7 日内复用率 | 7 天内再次创建任务的用户占比 | 上升 |

## 8. 非目标

- 云端材料上传、文件解析、材料引用。
- 全盘访问、无限制自主执行、「全部允许」权限模式。
- 云盘、应用市场、浏览器自动化、网页发布、IM 频道。
- 任务中切换模型。
- 项目、扩展、定时任务的导航占位。
- 多轮追问式任务（在现有 `WorkTask` 模型下不假装支持）。
- 组织多租户切换（沿用既有 P1-A 取舍）。

## 9. 风险与待确认问题

1. **本机 background 是否要支持？** 当前桌面提交契约不接受 background。若统一 composer 要保留背景输入，需要扩展 `work-local/v1` 契约、桌面校验和服务端字段；否则本机模式必须明确提示“写入目标”。
2. **模型档位是否值得做？** 需要确认模型 allowlist、计量口径、预算预估和失败重试是否都能按档位追溯；否则只展示当前配置模型，不做假选择。
3. **云端文件上下文是否是硬需求？** 我们刚删除云端材料能力；如果用户强烈需要“上传文件再生成”，应重新评估产品边界，而不是在新建页偷偷加回上传。
4. **项目是否真的有复用需求？** 先用本机工作空间验证多任务共享上下文的使用频率；没有数据前不建项目模型。
5. **审批策略能否分级？** 例如“本次任务内允许同类只读操作”，需要组织策略、审计和风险评估共同设计；不能直接照搬豆包的“按需确认”。
6. **移动端新建任务的范围？** 云端目标输入可以支持；本机文件夹选择和命令审批是否上移动端，需要单独评估安全和交互。
7. **竞品版本变化**：本文基于 2026-10-25 可访问的文档和截图；项目、伙伴、权限模式等细节可能随版本变化，实施前应复核。
