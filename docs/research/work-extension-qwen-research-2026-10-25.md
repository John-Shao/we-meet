## 0. 结论摘要

1. **千问办公的扩展是「工作方案包」体系，不是「角色人设」体系。** 专家套件把多个技能、数据连接、工作流和输出标准打包成一个可安装、可分享、可版本的完整方案；技能是单个方法包；连接器负责外部数据与工具。三者最终汇入新建任务。
2. **专家套件是三层中的最高层。** 截图中的「产品设计」套件为 `v0.5.10`，包含 28 个技能、28 个快捷命令、知识技能说明、输出模板和链式工作流；每个技能自动读取前序产出，避免重复填写项目信息。它解决的是「团队统一使用同一套 AI 工作方案」，而不只是「让 AI 多一个工具」。
3. **技能是透明的方法文件，不是隐藏提示词。** 技能本质是包含 `SKILL.md` 的文件夹，安装在 `~/.qwenworkcn/skills/`；可以自动触发、`/` 快捷调用或点名使用；`@` 用于补充文件/文件夹上下文，不是调用技能。截图中的技能详情直接展示 `SKILL.md` 原文，并给出独立 / 链式 / 增强三种运行模式。
4. **链式与增强是千问最值得研究的设计。** 「动效规划」技能在独立模式下引导用户补全目标；在链式模式下检测 `spark-output/context/brief.json`、`flow-web.json` 等前序文件，自动跳过基础提问；在增强模式下读取已安装的 `SparkDesign` 或 `motion-apply.md`，让输出直接对接组件库。三种模式产出同一份 JSON schema，差别只在上下文来源。
5. **连接器默认关闭，必须显式授权，开启后要新建任务才生效。** 千问提供系统级连接器（浏览器、计算机控制、Microsoft 365）、协作类（钉钉、飞书、企业微信、LINE）、设计/数据类（Figma、MySQL）以及自定义 MCP（HTTP/SSE/STDIO）。这比豆包的 SaaS 连接器更强大，也更高风险。
6. **新建任务页把「套件 · 技能」直接放在输入框内。** 截图显示「产品设计 · 动效规划」与预填提示词一起出现；工具栏有 `+`、技能/工具入口（截图图标未标注）、工作台模式「通用」、权限「默认权限」、模型档位「标准」、语音和发送；下方还有「新建项目」和快捷场景。这是「先选方案，再补目标」的入口，而不是先写目标再找能力。
7. **千问的完整专家套件不是纯前端功能。** 它的链式工作流依赖项目级上下文文件、技能输出 schema、下游技能读取、连接器增强和富成果（HTML/代码/PPTX/PDF/Office）。这些都需要执行器、上下文存储和成果管线支持。
8. **we-meet 当前有三道硬约束。** 执行层关闭了 Skills/MCP/外部写入，只开放 `read,bash,write,edit`；`work-agent/v1` 与 `work-local/v1` 是严格字段白名单；成果只接受 `.txt/.md/.csv/.json` 文本；Markdown 编辑/采纳版本上限 40,000 字符，执行器单次最多 20 个文件、总文本 400,000 字节。没有项目级上下文，也没有富文件预览/编辑。
9. **推荐统一路线图：E1 方法技能、E2a 套件模板、E2b 可选工作伙伴、E3a 只读 SaaS 连接器、E3b 本机/MCP/写入、E4 链式上下文与富成果。** E1/E2a/E2b 只能做「预设 + 提示词组合」，不能对外宣称完整专家套件；E4 才是千问式专家套件的完整形态。E4 依赖 P2 的项目/工作区模型与成果管线，不能和 P0/P1 同批。
10. **产品概念应以「套件」为主、伙伴为辅。** 千问的专家套件更适合 we-meet 的办公任务定位；豆包的工作伙伴更偏角色人设。建议用一个 `WorkPreset` 统一承载：有 `instructions` 时是伙伴，没有时是套件；首版先做套件，不做记忆、不做独立伙伴工作台。
11. **不要照搬千问的危险能力。** 原始 `SKILL.md` 全量展示、用户文件系统安装、任意 MCP/STDIO、浏览器接管、计算机控制、套件更新覆盖个人修改，都不适合直接进入 we-meet。首版应服务端策展、签名、只读、逐任务授权、审计、快照冻结。
12. **工作量远高于「加一个扩展入口」。** E1 8–12 人日；E2a 8–12、E2b +2–4（E2 合计 10–16）；E3a 只读 SaaS 20–35、E3b 15–25、管理/安全 5–10（E3 合计 40–70）；E4 链式上下文 + 富成果 60–95+，约 12–20 周；设计/幻灯片工作台另估 30–50+。E1+E2 约 18–28 人日，是可控增量；E4 是独立平台工程。

### 0.1 待验证假设

竞品与代码分析不能替代用户验证；以下三条在立项前需要小样本验证：

1. **套件模板是否比“角色伙伴”更容易上手**：5–8 位目标用户，3 个任务场景（写作、分析、整理），观察首次配置耗时、能力理解度、复用意愿；如果用户更偏好角色人设，E2b 应提前。
2. **可见计划与只读连接器是否提升信任**：用原型对比“自动匹配”与“提交前展示本次任务计划”，观察授权完成率、放弃率和错误率。
3. **E4 的链式/富成果是否有真实需求**：如果用户只需要一次性文本成果，E4 不应启动；如果用户愿意为连续工作流等待/付费，再投入项目上下文与富成果。

## 2. 千问办公的扩展模型

### 2.1 三层结构

```text
任务目标
├── 专家套件：整套工作方案
│   ├── 快捷命令（/命令）
│   ├── 知识技能（多个 Skill）
│   ├── 数据连接（连接器）
│   ├── 工作流（链式顺序）
│   └── 输出标准（模板/schema）
├── 技能：单个方法包
│   ├── SKILL.md
│   ├── 触发条件
│   ├── 执行步骤
│   └── 输出格式/辅助文件
└── 连接器：外部系统与工具
    ├── 系统级：浏览器、计算机控制、Microsoft 365
    ├── SaaS：钉钉、飞书、Figma、MySQL 等
    └── 自定义 MCP：HTTP/SSE/STDIO
```

| 层 | 回答的问题 | 典型例子 | 安装 | 授权 | 任务内形态 | 复用范围 |
|---|---|---|---|---|---|---|
| 专家套件 | 整套工作怎么做、团队怎么统一 | 产品设计、合同管理、企业法务 | 套件市场 `+` / 上传 ZIP | 套件本身启用；内含连接器仍需授权 | `套件 · 技能` 预填、`/命令` | 个人/企业空间 |
| 技能 | 某件事怎么做 | 动效规划、docx、pdf、pptx、find-skills | 技能市场/对话/GitHub/上传 | 通常不需要外部账号 | `/`、自动触发、点名使用 | 个人/企业 |
| 连接器 | 用什么数据/工具 | 浏览器、钉钉、Figma、MySQL、MCP | 连接器市场/自定义 MCP | 必须显式授权 | 任务中启用、自然语言调用 | 个人/企业 |

三者的关系：

- **专家套件可以包含技能和连接器**，并且定义技能之间的顺序、上下文文件和输出标准；
- **技能可以独立安装和使用**，不必依附套件；
- **连接器可以独立安装和授权**，也可以作为套件的「增强项」；
- 安装不等于启用，启用不等于授权，授权不等于每次任务自动使用。

### 2.2 专家套件：完整工作方案包

官方定义：专家套件解决的是「如何让团队统一使用同一套 AI 工作方案」——把多个 Skill、数据连接、工作流和输出标准整合为一个完整方案包，一键安装即可在团队内统一使用。

截图中的「产品设计」套件：

| 组成 | 截图/文档证据 | 产品含义 |
|---|---|---|
| 版本与来源 | `v0.5.10`、`@QwenWork`、套件市场 | 套件有版本、作者、市场入口 |
| 技能数量 | 28 个 Skill | 套件是技能集合，不是单技能 |
| 快捷命令 | 28 个 `/命令`，每个带输入示例 | 套件把「怎么开始」也封装了 |
| 知识技能 | 动效规划、动效开发、读需求、工单分析、竞品拆解、可用性测试、启发评估、设计度量、设计复盘、用户旅程、用户研究、站点地图、mobile/Web 页面设计等 | 覆盖岗位工作流，不是零散工具 |
| 链式工作流 | 「28 个 Skill 串成链式工作流，每个 Skill 自动读取前序产出，避免重复填写项目信息」 | 技能之间通过上下文文件衔接 |
| 输出标准 | 设计简报 HTML、用户旅程 HTML、design-tokens、Flow、PRD、dashboard.html 等 | 套件承诺交付物形态 |
| 连接器增强 | SUPERCHARGED：Figma → design tokens；designLang → 线上站点 tokens；WebSearch → 竞品信息 | 连接器不是门禁，而是增强 |
| 启用/编辑 | 右上角启用开关、编辑、更多 | 套件可启用/停用/定制 |
| 分享 | 官方文档：分享套件下载 ZIP，同事上传即可使用 | 团队分发 |
| 更新 | 官方文档：更新以创作者最新版本为准，会覆盖个人修改，更新前提示风险 | 版本治理 |

截图中的快捷命令包括 `/动效规划`、`/动效开发`、`/读需求`、`/工单分析`、`/竞品拆解`、`/可用性测试`、`/启发评估`、`/设计度量`、`/设计复盘`、`/设计简报`、`/设计提案`、`/设计提取`、`/设计验收` 等。从套件说明看，每个命令更像是「套件方法 + 输入字段 + 输出模板」的入口，而不是单纯的提示词。

说明：`v0.5.10`、28 个技能/快捷命令来自截图 1/2（资产见 1.4），不是官方文档固定数字；官方文档只确认套件由多个 Skill、数据连接、工作流和输出标准组成。创建与定制（官方文档）：

- 在专家套件页右上角「+ 添加」→「通过 QwenWork 创建」，用自然语言描述套件功能和场景，自动生成套件结构和技能配置；
- 已安装套件可「定制此套件」，打开新任务并预加载 `plugin-creator` 与该套件配置目录；
- 手动上传 `.zip`，需包含 `.qwen-plugin/plugin.json` 或 `.claude-plugin/plugin.json`，且 `plugin.json` 必须有 `name` 字段；
- 企业空间内可共享，不自动发布到公共扩展；个人用户当前不能把自建技能上传到公共扩展。

**设计判断：**

- 专家套件不是「一个角色 + 几个默认技能」，而是**完整工作方案**：入口（快捷命令）、方法（技能）、数据（连接器）、顺序（工作流）、交付（输出标准）都被打包；
- 它最适合「团队统一产出」的场景，而不是个人一次性任务；
- 它比豆包的工作伙伴更重、更结构化，也更适合 we-meet 的「可验收」定位；
- 但它对执行器的要求也更高：需要上下文文件、技能输出 schema、按顺序执行、富成果交付。

### 2.3 技能：透明的 SKILL.md 方法包

官方定义：技能是一份提前写好的工作指南，告诉千问办公在面对某一类任务时遵循什么步骤、输出什么格式、注意哪些细节；每个技能本质是一个包含 `SKILL.md` 的文件夹。

关键事实：

- **存储位置**：`~/.qwenworkcn/skills/`，每个技能一个文件夹，可直接在文件系统增删改；
- **格式**：`SKILL.md` 用自然语言描述名称、触发条件、执行步骤；可选辅助文件；
- **安装渠道**：技能广场、对话中 `find-skills` 搜索安装、GitHub 仓库链接、手动上传 `SKILL.md`；
- **触发方式**：自动语义匹配、`/` 快捷调用、对话中明确点名；`@` 是补充文件/文件夹上下文，不是调用技能；
- **内置技能**：create-skill、docx、find-skills、media-generation、media-read、pdf、plugin-creator、pptx、qwenwork-guidance、xlsx 等；
- **交互式 UI**：部分技能支持在对话流中渲染 HTML 表单、图表、配置面板；
- **透明度**：截图 9 直接展示 `SKILL.md` 原文；用户可以看到完整方法；
- **更新/卸载**：可通过文件系统删除技能文件夹；套件更新会覆盖个人修改（官方提示风险）。

截图 5 的「动效规划」技能是本轮最重要的证据：

| 模式 | 触发条件 | 产出特征 |
|---|---|---|
| 独立模式 | 无前序上下文，直接调用 | Phase 1 引导用户口述目标元素 + 期望调性 → 完整动效规范 JSON |
| 链式模式 | 检测到 `spark-output/context/brief.json`，或 `flow-web.json` / `flow-mobile.json` / `avatar.json` | 跳过基础信息追问；自动从 `brief.strategy_dimensions` / `avatar.style_profile` 推荐 Personality 候选；从 flow 提取 `target_elements` |
| 增强模式 | 项目已装 `SparkDesign`，或已存在 `spark-output/profile/motion-apply.md` | Personality 与已有组件库主调风格对齐；输出可直接被「动效开发」消费 |

三种模式产出同一份 `spark-output/context/motion-plan.json` schema，差别只在「Personality 来源」。这带来三个关键结论：

1. **技能不是一次性提示词**，而是有输入契约、输出 schema、上下游消费关系的「方法模块」；
2. **链式能力依赖上下文文件**，不是把多个技能名称拼在一起；
3. **增强能力依赖项目/工具状态**，不是连接器自动授权。

**设计判断：**

- 技能应被建模为版本化的方法包，包含名称、说明、适用场景、输入要求、输出 schema、辅助文件、版本、内容哈希；
- 链式技能需要上下文契约；没有上下文存储和 schema 校验，只能做「提示词顺序」，不能做真正的链；
- 透明是优点，但原始 `SKILL.md` 不适合直接暴露给所有终端用户：它可能包含内部方法论、长提示词、敏感示例；应提供结构化摘要 + 管理员原文视图。

### 2.4 连接器：默认关闭的外部系统与工具

官方定义：连接器是千问办公与外部系统（浏览器、日历、邮件、钉钉等）之间的桥梁；所有连接器默认关闭，需明确授权与配置后才获取访问权限。

分类（截图与官方文档）：

| 类别 | 例子 | 能力 | 风险 |
|---|---|---|---|
| 系统级 | 浏览器、计算机控制、Microsoft 365 | 网页自动化、桌面操作、邮件/日历/OneDrive | 高：可接管当前 Tab、操作桌面、读取个人数据 |
| 沟通协作 | 钉钉、飞书、企业微信、LINE | 消息、日历、联系人、群、审批 | 中高：企业数据、发送/写入 |
| 设计/数据 | Figma、MySQL | 设计稿/组件、数据库查询 | 中高：令牌、数据泄露、写操作 |
| 物流/行业 | 数联宝、亿贸AI、数可捞、口岸高质量数据集 | 行业数据查询 | 中：数据授权与合规 |
| 知识文档 | cue、深知可信工作台、百晓智能 | 知识检索 | 中：数据来源与权限 |
| 自定义 MCP | HTTP/SSE/STDIO | 任意 MCP 工具 | 高：任意命令、任意网络、工具描述不可信 |

安装与授权：

- 连接器市场点击 `+` 安装；
- 需要账号的连接器走 OAuth/登录；需要令牌的（如 Figma）填个人访问令牌，可设置 1–600 秒超时；
- 浏览器连接器需要安装 Chromium 扩展，AI 会托管当前 Tab；仅支持 Chrome/Edge，不支持 Safari/Firefox；
- MCP 支持粘贴 JSON 或手动填写：Streamable HTTP/SSE（URL、Headers）或 STDIO（命令、参数、环境变量）；
- 默认关闭；开启/关闭后需要新建任务才生效，旧任务中追问无效；
- 已安装列表可开关、编辑、删除；企业管理员可限制钉钉等连接器的可用范围；
- 官方文档：遇到验证码、扫码登录等 AI 无法独立完成的步骤，用户可手动接管，AI 在登录成功后继续。

任务中的调用：

- 自然语言驱动，不需要写代码；
- 可以同时开启多个连接器，在一个 Prompt 中组合使用（官方示例：查日历 → 浏览器搜参会公司 → 生成会前简报 → 保存到备忘录）；
- 连接器与技能的关系：技能固化方法；复杂连接器流程建议先跑通再固化为技能；
- 连接器与专家套件：套件可以预配置数据连接；连接器未授权时，套件对应能力不可用或需先配置。

**设计判断：**

- 连接器不是「安装后就能用」的插件，而是**默认关闭的权限边界**；
- 浏览器接管、计算机控制、自定义 STDIO 是高风险能力，不适合作为首版通用能力；
- 连接器的价值在于「增强技能」，而不是「替代技能」；这与截图 6 的 SUPERCHARGED 模型一致。

### 2.5 工作台模式与成果形态

千问的新建任务不仅是「聊天」，还可以切换工作台模式：

| 模式 | 官方说明 | 产出 |
|---|---|---|
| 通用 | 默认；日常文档、分析、调研 | 文本、表格、网页、报告等 |
| 设计 | 「设计即代码」；无限画布、圈选标注、Nudge 微调、预览 | HTML/CSS/JS 或 React 组件（shadcn/ui、Spark Design、Ant Design），可绑定本地目录 |
| 幻灯片 | HTML 画布，默认 16:9；大纲确认、逐页生成、追加指令 | HTML 幻灯片；可导出 PPTX/PDF/HTML |
| 写作 | 写作工作台（本文未展开） | 文档类成果 |

这不是扩展层，但它决定了专家套件的「交付物」：

- 「产品设计」套件承诺设计简报 HTML、用户旅程 HTML、design-tokens、Flow、PRD、dashboard.html 等；
- 这些成果需要画布、代码文件、HTML 预览、PPTX/PDF 导出等能力；
- 如果 we-meet 只有 Markdown 成果，就无法复刻「产品设计」这类套件，只能做文本型专家套件。

### 2.6 哪些不是扩展

| 能力 | 为什么不是扩展 | 应归属 |
|---|---|---|
| 通用/设计/幻灯片/写作 | 决定产出形态与画布 | 工作台模式 |
| 标准/旗舰（基础/高级） | 模型质量与成本档位 | 模型档位 |
| 默认权限 | 风险动作审批策略 | 权限/审批 |
| 新建项目 | 任务与上下文的容器 | 项目模型 |
| `+` 添加文件/网盘 | 任务输入 | 资料/上下文 |
| 快捷场景（钉钉办公、文档创作等） | 任务发现入口 | 配方/快捷开始 |
| 定时任务 | 触发器与调度 | 调度系统 |

把工作台、模型、权限、项目都叫「扩展」，会让用户无法判断「哪些是能力、哪些是执行配置」。

### 3.2 直接使用与组合使用

- **直接使用**：选一个技能、一个套件或一个连接器，直接发起任务；
- **组合使用**：套件提供工作流和默认技能，任务选择具体技能/快捷命令，连接器增强数据和工具，项目提供上下文；
- 组合不是必须三层同时出现：技能可以单独用，套件可以只用默认技能，连接器可以单独用（如浏览器任务）。

| 场景 | 选择 | 执行 | 用户确认 | we-meet 分期 |
|---|---|---|---|---|
| 单技能 | 技能 A | 独立模式；A 的步骤与输出 | 看到技能名、输出要求 | E1 |
| 套件 + 技能 | 套件 P + `/命令` | P 的工作流 + 当前技能；E2a 不读取项目上下文 | 看到套件、技能、输入模板 | E2a（仅预设） |
| 套件 + 技能 + 连接器 | P + A + Figma/WebSearch | 连接器增强；链式上下文需 E4 | 看到连接器、范围、数据去向 | E3a（只读） |
| 多个技能 | A + B（同一套件） | 按套件顺序；输出 schema 串联 | 看到顺序/依赖 | E4（真链式） |
| 多个套件 | 合同管理 + 企业法务 | 官方示例支持组合使用 | 看到套件组合与冲突 | E4 |
| 仅连接器 | 浏览器/计算机控制 | 多步骤外部操作 | 看到 Tab/桌面控制与接管范围 | E3b（不建议首版） |
| 项目 + 套件 | 新建项目 + P | 项目级上下文供技能读取 | 看到项目、上下文文件 | E4 |

### 3.3 组合顺序与优先级

千问的实际顺序（从截图与文档推断）：

```text
工作台模式（通用/设计/幻灯片/写作）
  → 套件/技能选择（`/命令` 或技能入口）
  → 快捷命令模板预填
  → 连接器授权/增强
  → 任务执行（技能可读取前序上下文）
```

推荐的 we-meet 解析顺序：

```text
组织策略（允许/禁用、范围、上限）
  → 套件默认值（技能顺序、输出标准、快捷命令、连接器建议）
  → 任务显式选择（技能、连接器、上下文、环境）
  → 服务端校验（存在、启用、授权、环境、预算、上下文长度）
  → 冻结 capability_snapshot
  → 生成执行计划
```

规则：

1. 组织策略优先于套件和任务；
2. 套件默认技能是预填，未锁定项可移除；
3. 任务追加技能按 ID 去重，顺序由套件定义 + 用户追加顺序决定；
4. 连接器必须显式授权；套件的连接器建议不等于已授权；
5. 工作台模式、模型、权限、环境是正交配置，不进入能力快照的能力列表，但进入任务快照；
6. 服务端解析并冻结；客户端不发送原始提示词/凭据；
7. 提交前展示「本次任务计划」。

### 3.4 链式与增强：千问真正的差异化

截图 5 的三种模式，可以抽象为：

| 模式 | 输入 | 处理 | 输出 | 依赖 |
|---|---|---|---|---|
| 独立 | 用户口述目标/调性 | 引导补全 | `motion-plan.json` | 无 |
| 链式 | `brief.json` / `flow-*.json` / `avatar.json` | 跳过基础提问，提取项目调性/目标元素 | 同一 schema | 前序技能产出、上下文目录 |
| 增强 | 上述 + `SparkDesign`/`motion-apply.md` | 对齐组件库风格 | 同一 schema，可直接被下游消费 | 项目/组件库/连接器状态 |

套件说明（截图 6）进一步给出「基础 + 增强」：

- ALWAYS（独立工作）：设计简报、用户旅程、视觉情绪板、Flow、异常态、动效规划、WCAG 审计、度量蓝图、PRD、dashboard.html；
- SUPERCHARGED（连接工具后增强）：+ Figma → design tokens；+ designLang → 线上站点 tokens；+ WebSearch → 竞品实时信息。

这说明千问的组合不是「多个技能随机叠加」，而是：

1. **套件定义工作流顺序**；
2. **技能定义输入/输出契约**；
3. **上下文文件在技能之间传递**；
4. **连接器只增强，不替代基础能力**；
5. **输出标准由套件统一**。

对 we-meet 的含义：

- 只做「技能多选 + 提示词拼接」无法复刻链式；
- 需要项目级上下文目录、技能输出 schema、下游读取、版本/来源追踪；
- 需要决定「链」是在单任务内还是跨任务/项目；千问截图显示项目级文件（`spark-output/...`），更像跨任务的项目上下文；
- 需要富成果管线，才能交付 HTML/PRD/dashboard/PPTX 等。

### 3.5 未核验的交互

- 套件/技能/连接器是否支持多选、最多几个；
- 选中后如何取消、是否能在提交前移除；
- 自动匹配技能是否显示、能否拒绝；
- 执行中能否追加能力或修改权限；
- `默认权限` 的具体选项与默认值；
- `通用` 工作台的具体选项与切换影响；
- `新建项目` 的数据模型与权限继承；
- 套件更新覆盖个人修改的提示与回滚；
- 企业空间成员能否创建/上传/共享，取决于什么权限；
- 平台级连接器（浏览器/计算机）在任务中的审批与审计细节。

这些应在立项前用真实账号走查，不应在 PRD 中写成已确认。

## 4. 权限、治理与安全

### 4.1 四个状态

| 状态 | 含义 | 谁控制 | 界面 |
|---|---|---|---|
| 可见 | 在扩展市场/详情页可见 | 平台/企业 | 卡片/详情 |
| 已安装/已启用 | 加入个人/企业可用集合 | 用户/管理员 | 安装、启用开关 |
| 已授权 | 连接器获得账号、范围、令牌 | 用户/管理员 | 已连接、配置参数 |
| 可调用 | 本次任务实际选择并通过校验 | 任务 + 服务端 | 任务计划/执行事件 |

千问明确：安装资源不代表每次对话自动使用；连接器默认关闭；开启/关闭后需新建任务才生效。这三条都值得 we-meet 直接借鉴。

### 4.2 技能供应链

千问的做法：

- 技能是文件系统里的 `SKILL.md` 文件夹，用户可直接查看、编辑、删除；
- 支持从 GitHub 安装、手动上传、对话创建；
- 套件是 `.zip` + `plugin.json`，可分享、上传、企业空间分发；
- 套件更新会覆盖个人修改，更新前提示风险；
- 个人用户不能把自建技能发布到公共扩展；企业空间资源不自动公开。

风险：

- **提示词/方法论泄露**：原始 `SKILL.md` 全量可见，可能包含内部方法论、示例、敏感信息；
- **供应链篡改**：公开文档未说明文件系统安装/编辑是否有签名校验；在未验证前，应视为技能可能被替换的风险；
- **任意辅助文件**：技能可以带辅助文件，若执行器读取/执行，可能扩大攻击面；
- **更新覆盖**：个人修改被创作者新版本覆盖，可能导致任务行为突变；
- **公共市场质量**：技能质量、版权、责任主体不清晰。

we-meet 建议：

- 服务端策展/组织审核，技能内容签名 + 版本 + 哈希；
- 终端用户看结构化摘要（做什么、输入、输出、边界、版本、来源），管理员可看原文；
- 任务快照冻结版本，更新不回溯；
- 不支持用户文件系统直接安装；本地缓存只读、校验签名；
- 个人自建技能后置，先做组织策展。

### 4.3 连接器安全

千问的默认策略：

- 所有连接器默认关闭；
- OAuth/账号/API key/令牌授权；Figma 需个人访问令牌；MCP 可配 Headers/环境变量；
- 浏览器连接器安装 Chromium 扩展，AI 托管当前 Tab；仅支持 Chrome/Edge；
- 计算机控制允许 AI 操作桌面；
- 自定义 MCP 支持 STDIO 任意命令；
- 开启/关闭后需要新建任务才生效；
- 钉钉可用范围受企业管理员配置限制；
- 已安装列表可开关、编辑、删除。

风险矩阵：

| 能力 | 主要风险 | 建议 |
|---|---|---|
| 浏览器接管 | 当前 Tab 被 AI 操作、登录态、页面数据、误操作 | 首版不做；若做，逐 Tab 授权 + 操作预览 + 可中断 |
| 计算机控制 | 桌面/文件/应用级操作 | 首版不做；本机只保留目录授权 + 逐命令审批 |
| OAuth SaaS | 范围过宽、令牌泄露、写入副作用 | 只读优先；逐 scope；写操作逐次确认 |
| API key/个人令牌 | 明文存储、日志泄露 | 加密保管；不进入任务 payload/日志；撤销 |
| 自定义 MCP HTTP/SSE | SSRF、出网、工具描述注入 | 管理员白名单；出网 allowlist；工具白名单 |
| 自定义 MCP STDIO | 任意本地命令、环境变量、文件访问 | 首版不做；仅管理员签名运行时 |
| 多连接器组合 | 数据跨系统流转、权限叠加 | 逐连接器授权；展示数据流向；审计 |

we-meet 建议：

- 默认关闭；逐任务显式选择；逐 scope 授权；
- 只读优先；写操作逐次确认；不支持「全部允许」；
- 新授权/新启用只影响新任务；撤销是安全覆盖，运行中任务在下一次调用前停止使用该连接器，已产生的结果保留；
- 令牌只存加密引用；broker 注入；模型上下文不见令牌；
- 企业管理员可禁用/限制/审计；成员不能绕过；
- 公开市场和任意 STDIO 首版不做。

### 4.4 企业空间与共享

千问官方：

- 企业空间用于组织内资源协作；成员可创建/上传技能等资源并在组织内共享；
- 企业空间资源不会自动发布到公共扩展；
- 成员能否创建/上传/查看/使用取决于企业是否开通能力及组织权限；
- 分享套件以 `.zip` 下载，同事上传使用；分享链接仅指向公共扩展原始详情，不包含个人修改/账号配置/授权信息；
- 钉钉数据即使通过钉钉登录，也需额外连接器授权。

we-meet 建议：

- 延续 `owner + organization` 双重作用域；
- 组织套件由管理员发布，成员只读；个人套件仅自己可见；
- 套件分享后不携带连接器授权/凭据；
- 组织禁用/撤权是终态；任务快照保留审计，但不能继续调用。

### 4.5 失败模式

| 失败 | 千问行为/文档 | we-meet 建议 |
|---|---|---|
| 连接器未授权 | 套件对应能力不可用/需配置 | 阻止提交，显示缺失范围 |
| 连接器开启后旧任务 | 需新建任务才生效 | 运行中任务不变；新任务才用新授权 |
| 令牌过期 | 外部系统拒绝 | 提示重连；不自动用旧令牌 |
| 浏览器被手动操作 | 可能冲突 | 若做，显示接管状态；允许中断 |
| MCP 命令失败 | 工具调用失败 | 保留错误；不自动换工具 |
| 技能更新 | 覆盖个人修改 | 任务快照冻结；更新只影响新任务 |
| 链式上下文缺失 | 退化为独立模式（截图 5） | 明确提示缺失上下文；不假装已链式 |
| schema 不匹配 | 下游无法消费 | 服务端校验；阻止或降级并提示 |
| 富成果不支持 | 可能无法预览/编辑 | 首版限制成果格式；E4 再扩展 |
| 企业权限不足 | 看不到企业空间 | 显示原因；不绕过 |

### 4.6 审计与计量

本轮检索到的千问公开文档未详细展开扩展的审计/计量；截图只显示使用人数、启用状态。这不代表千问没有内部审计，只是本文未获得证据；we-meet 应补齐：

- 谁安装/启用/停用了哪个套件/技能/连接器；
- 谁授权/撤销了哪些连接器 scope；
- 哪个任务使用了哪个套件/技能版本、哪些上下文文件、哪些连接器调用；
- token/调用次数/费用；
- 技能输出 schema 校验结果；
- 不记录令牌、绝对路径、任务正文、成果正文、连接器返回原始数据。

## 5. 千问 vs 豆包：两种扩展模型

| 维度 | 千问办公 | 豆包工作 | 对 we-meet 的含义 |
|---|---|---|---|
| 最高层 | 专家套件：完整工作方案包（技能 + 数据连接 + 工作流 + 输出标准） | 工作伙伴：角色 + 指令 + 记忆 + 默认技能/连接器 | we-meet 应优先做「套件」，伙伴后置 |
| 技能形态 | `SKILL.md` 文件夹；内容可见；文件系统安装；可带辅助文件 | 技能市场安装；完整内容不展示；自动匹配/`/`/`@` | 透明是优点；但终端用户只需结构化摘要 |
| 技能执行 | 独立 / 链式 / 增强；上下文文件；输出 schema | 自动匹配 + 任务内选择；未见公开的文件级链式契约 | 真链式需要上下文/schema，不是多选 |
| 连接器 | 系统级（浏览器/计算机/M365）+ SaaS + 自定义 MCP；默认关闭 | SaaS 为主（GitHub/Notion/飞书等）+ OAuth/CLI/MCP；伙伴级默认允许/部分限制 | we-meet 只读 SaaS 优先；不做系统控制 |
| 新建任务 | 套件 · 技能内联 + 快捷命令模板；`/` 调用；工作台/权限/模型 | 伙伴/技能 chip + 技能/插件工具栏；`@` 伙伴 | 两者都把能力放进 composer；we-meet 用 chip 更清晰 |
| 上下文 | 项目级 `spark-output/context/*.json`；技能读取前序产出 | 伙伴有记忆/用户档案；未见公开的链式文件契约 | we-meet 需要项目上下文才能做链式 |
| 成果 | HTML/代码/PPTX/PDF/Word/Excel/图片/网页 | 本轮截图未覆盖任务成果形态与链式，不作比较 | we-meet 当前只支持文本，差距最大 |
| 治理 | 企业空间；套件 ZIP 分享；更新覆盖个人修改；连接器默认关闭 | 团队伙伴共享；导入伙伴仅本人；伙伴级授权模式 | we-meet 需版本/快照/组织策略 |
| 透明度 | 原始 SKILL.md 可见 | 完整技能内容不展示 | we-meet 取中间：摘要 + 管理员原文 |
| 风险 | 任意 MCP/STDIO、浏览器/桌面控制、文件系统安装 | 默认允许、数据共享范围、隐藏提示词 | we-meet 应更保守 |

**最重要的差异：**

1. **千问套件是「团队工作方案」，豆包伙伴是「角色代理」。** 如果 we-meet 的目标是「可验收的办公任务」，套件比人设更契合。
2. **从公开材料看，千问把链式上下文做成了产品能力，豆包更依赖伙伴指令/记忆。** 链式是更高门槛，也更可复用。
3. **千问的成果形态远丰富于 we-meet 当前能力。** 这不是扩展 UI 能补的，是成果管线。
4. **两家都把「安装/授权/调用」分开，但千问更明确地默认关闭、要求新建任务生效。** 这一点应直接借鉴。
5. **两家都允许自动匹配，但 we-meet 应坚持「建议可见、连接器不自动」。** 这是信任定位。

### 6.3 项目与上下文

当前：

- `WorkTask` 没有 project 字段；`WorkRun` 属于单个 task（`src/backend/work/models.py:10-32`、`:67-108`）；
- 每个 run 的成果只属于该 run；没有跨任务共享的上下文目录；
- 云端执行器只挂载当前任务目录，不读取其他任务/项目文件；
- 本机有工作空间，但没有「项目上下文」抽象；
- 没有 `brief.json`/`flow-*.json` 这类跨技能 schema。

千问的链式套件依赖：

- 项目级上下文目录（`spark-output/context/`）；
- 技能输出 schema；
- 下游技能读取前序产出；
- 连接器增强；
- 输出标准。

**结论：we-meet 当前无法做真正的链式专家套件。** 最多做「套件模板 + 提示词顺序」，不能承诺 schema 串联和跨任务上下文。

### 6.6 上下文预算


- 链式上下文不应塞进 goal，而应作为文件/上下文引用，否则必然超限。

## 7. 推荐方案

### 7.1 设计原则

1. **未实现不渲染。** 没有套件/技能/连接器注册表、执行能力和成果管线，就不放入口。
2. **套件优先，伙伴后置。** 千问的套件更符合办公任务的可复用、可验收；豆包的人设/记忆不是首版重点。
3. **方法与数据分离。** 技能是方法，连接器是数据/工具；技能不能持有凭据。
4. **安装/启用/授权/调用分离。** 四个状态分别建模、分别审计。
5. **链式需要上下文，不靠提示词硬拼。** 没有项目上下文/schema，就不承诺链式。
6. **套件输出标准优先。** 套件应声明交付物格式、schema、验收标准；没有输出标准的只是技能包。
7. **服务端解析并冻结。** 客户端只提交 ID/选择；服务端生成 `capability_snapshot`。
8. **最小权限。** 连接器默认关闭、只读优先、逐任务授权、写操作逐次确认。
9. **环境边界清晰。** 云端/本机能力不互通；不自动切换/降级。
10. **富成果是独立工程。** HTML/Office/PDF/图片需要存储、预览、编辑、安全，不是扩展 UI 的附属品。

### 7.2 概念模型

```ts
type PresetKind = 'suite' | 'partner'

type WorkPreset = {
  id: string
  kind: PresetKind
  name: string
  description: string
  version: number
  scope: 'builtin' | 'organization' | 'personal'
  enabled: boolean
  instructions?: string            // 伙伴模式；套件模式可为空或仅工作说明
  skill_ids: string[]             // 有序；套件定义工作流顺序
  quick_commands: {
    id: string
    label: string
    prompt_template: string
    skill_id: string
  }[]
  output_standard?: {
    format: 'markdown' | 'json'   // E1/E2a/E2b 仅支持文本
    schema?: string
    template?: string
  }
  connector_ids?: string[]        // E3a 才可用；E2a/E2b 只作为建议，不授权
  preferred_environment?: 'cloud' | 'local'
  approval_mode?: 'ask' | 'read_only_auto'
  requires?: {
    connector_ids?: string[]
  }
  content_sha256: string
}

type WorkSkill = {
  id: string
  slug: string
  name: string
  description: string
  version: number
  scope: 'builtin' | 'organization'
  enabled: boolean
  instructions: string
  input_schema?: string
  output_schema?: string
  output: 'markdown' | 'json'
  requires?: {
    environment?: ('cloud' | 'local')[]
    connector_kinds?: string[]
    context_files?: string[]
  }
  content_sha256: string
}

type WorkConnector = {
  id: string
  name: string
  provider: string
  version: number
  scope: 'organization'
  enabled: boolean
  authorized: boolean
  grant_id?: string
  scopes: { id: string; label: string; access: 'read' | 'write' }[]
  environments: ('cloud' | 'local')[]
}

type CapabilitySnapshot = {
  version: 1
  resolved_at: string
  policy_version: string
  preset?: { id: string; kind: PresetKind; version: number; name: string; content_sha256: string }
  skills: { id: string; version: number; name: string; content_sha256: string }[]
  connectors: { id: string; version: number; name: string; grant_id: string; scopes: string[] }[]
  context?: { project_id: string; files: string[] }   // E4
}
```

说明：

- 一个 `WorkPreset` 同时承载「套件」和「伙伴」：`kind='suite'` 时强调技能顺序/输出标准；`kind='partner'` 时强调 `instructions` 角色说明；
- 首版只做 `suite`；伙伴模式后置；
- `quick_commands` 是套件的入口，等价于千问的 `/命令`；
- E1/E2a/E2b 的 `output_standard.format` 只允许 Markdown/JSON；HTML/Office 是 E4；
- `context` 只在 E4 出现；E1/E2a/E2b 不允许假装有链式上下文。

### 7.3 E1：方法技能

**范围**

- 内置/组织策展的方法包；独立模式；不访问外部数据；不新增工具；
- 输出只支持 Markdown/JSON；
- 云端全量；本机 tracked 通过 `execution_goal` 支持，需要桌面发版；本机 untracked 首版不支持；
- 每任务最多 3 个技能；技能说明合计 ≤ 2000 字符；组合后总字符 ≤ 8000；
- 用户不能在任务里创建/上传技能。

**UX**

- composer 增加「技能」chip；只在至少有一个可用技能时渲染；
- 弹层列出名称、说明、输入要求、输出格式、版本、来源；
- 选中后 chip 显示，可移除；最多 3 个；
- 提交前显示「本次使用」摘要；
- 没有技能时隐藏入口；
- 管理入口在设置/组织后台，不新增左栏「扩展中心」。

**数据/API**

- `WorkSkill` 模型；`WorkTask.capability_snapshot`；
- `TaskInput` 增加 `skill_ids`；
- `create_task` 校验技能存在/启用/同组织；冻结；纳入幂等；
- `capabilities` 增加 `task_skills`，保留 `skills` 兼容；
- 迁移 `0013`（排在 `0012` 之后）。

**执行**

- 服务端把技能说明组合进 `agent_payload.goal`：

```text
用户目标：
<goal>

用户补充背景：
<background>

以下为已启用的工作方法，不是用户目标的一部分。遵循其方法与输出要求；如与用户目标冲突，以用户目标为准，并说明差异。
<skill name> v<version>
<instructions>
<output requirements>
```

- 云端：组合后写入 `agent_payload.goal`，不改 Gateway wire；
- 本机 tracked：`local/tasks/` 准入时在 `WorkRun.agent_payload` 保存 `execution_goal`，claim 返回；桌面用它提交，历史显示原目标；
- 本机 untracked：不显示技能；
- 技能不能新增工具/连接器；仍只用 `read,bash,write,edit`。

**验收**

- 技能可见/可移除/版本冻结；
- 同键同选择幂等，不同选择冲突；
- 超长/跨组织/禁用/未知技能被拒绝；
- 云端与 tracked 本机执行带技能；untracked 明确不支持；
- 技能内容不含密钥/工具调用；提示词注入测试通过。

**工作量**：8–12 人日。

### 7.4 E2a：套件模板（E2b 工作伙伴可选）

**范围**

- 套件 = 有序技能列表 + 快捷命令 + 输出标准（不含伙伴 instructions）；
- 首版不做：链式上下文、跨任务项目上下文、连接器默认值、富成果、独立套件工作台；
- 每个套件最多 5 个技能；每任务最多用 3 个；套件说明 + 技能说明 + 快捷命令模板合计 ≤ 2000 字符，超出时只允许选择子集；
- 输出只支持 Markdown/JSON；
- E2a 只做内置/组织套件：管理员发布、成员只读；个人 preset 字段保留但暂不开放创建；
- E2b 才做工作伙伴：同一 `WorkPreset` 增加短 `instructions`、默认环境/审批偏好、组织共享；不新增 `WorkPartner` 表；
- 没有工作说明、只有技能/输出标准的 preset，就是「套件模板」；有工作说明时是 `kind='partner'`。

**UX**

- composer 增加「套件」chip；选中后：
  - 显示套件名；
  - 列出快捷命令（`/` 菜单）；
  - 点击快捷命令 → 预填提示词模板；
  - 默认技能自动填入，可移除；
  - 显示「本套件为预设，暂不支持链式上下文」；
- 套件选择器显示：名称、简介、技能数、输出标准、来源、版本；
- 管理页：创建/编辑/复制/停用；不展示原始 `SKILL.md`，只展示结构化字段和摘要；
- 不新增独立套件工作台；如果要导航，等 CRUD/列表/权限完成后加「专家套件」，不提前占位。

**数据/API**

- `WorkPreset`：E2a `kind='suite'`；E2b `kind='partner'`；同一模型、同一 `0014` 迁移；
- `WorkTask` 增加 `preset_id` 与快照；
- `TaskInput` 增加 `preset_id` + `quick_command_id`；
- `create_task` 解析 preset → 有序技能 → 快捷命令模板 → 冻结；
- 组织 preset 权限；E2b 组织共享；迁移 `0014`。

**执行**

- 服务端组合：套件工作说明 + 有序技能说明 + 快捷命令模板 + 用户目标；
- **只做提示词层面的顺序**：告诉模型按顺序执行；不保证技能之间通过 schema 传递上下文；
- 如果模型需要前一步结果，只能依赖同一 run 内的上下文，不能读取项目文件；
- 云端/tracked 本机支持；untracked 不支持；
- 不引入连接器。

**命名建议**

- 如果没有 E4，对外称「工作方案模板 / 技能包」，不要称「完整专家套件」；
- 如果产品坚持叫「专家套件」，必须在详情页明确：「当前版本支持套件内技能预设与顺序提示，暂不支持项目级链式上下文与富成果」；
- 真正的「专家套件」留给 E4。

**验收**

- preset/快捷命令/默认技能正确预填；
- 技能选择顺序确定；执行顺序不保证（E4 才保证）；冲突/超限提示；
- preset 版本/内容哈希冻结；同键不同 preset 冲突；
- 组织 preset 只读；个人 preset 字段保留但首版不开放创建；
- 无链式上下文/无连接器/无富成果入口；
- 云端/tracked 一致；untracked 明确不支持。

**工作量**：E2a 8–12 人日；E2b +2–4；E2 合计 10–16 人日（含组织共享与审计）。

### 7.5 E3a：只读 SaaS 连接器（E3b 另立）

**范围**

- **E3a：只读 SaaS 连接器。** 云端优先；OAuth/HTTP；不含浏览器/计算机控制/自定义 MCP/STDIO；
- **E3b：本机连接器、MCP、写入。** 单独立项；桌面/适配器 v2、系统安全存储、目录/命令审批；
- OAuth 或 API key；默认关闭；逐任务显式选择；逐 scope 授权；
- 每任务最多 2 个连接器；
- E3a 不做写入；不做自动调用；不做公开市场。

**UX**

- composer 增加「连接器」chip；只在有可用连接器时渲染；
- 选择器显示：名称、提供方、已授权/未授权、可读范围、数据去向、环境；
- 未授权提供「连接」；授权弹窗显示账号、范围、保存位置；
- 提交前列出连接器、scope、只读/写入、审批；
- 任务详情显示调用审计，不显示返回正文；
- 撤销在设置/管理页；撤销后新任务不可选；
- 不显示「默认允许」。

**数据/API**

- `WorkConnector`、`WorkConnectorGrant`、`WorkConnectorCall`；
- `TaskInput` 增加 `connector_ids`/`connector_scopes`；
- `capabilities` 增加 `connectors`，按 grant 计算 `authorized`；
- E3a 迁移 `0015`；E3b 迁移 `0016+`。

**执行**

- 需要执行器工具循环、凭据 broker、出网白名单；
- `work-agent/v1` 严格校验不能直接加字段：新增 v2 或先升级所有 Gateway；
- job payload 只传连接器 ID/grant 引用/scope/操作白名单，不传令牌；
- Gateway 调用前向 broker 换短期令牌；按 scope 校验；记录调用；
- 连接器结果按数据处理，不按指令执行；
- 每任务限制调用次数/token/超时；失败不自动换连接器/不扩权；
- 本机连接器/MCP/写入另立 E3b；不复用云端凭据。

**验收**

- 只读连接器可授权/调用/撤销；
- 未授权/过期/范围不足/限流/不可用状态明确；
- 令牌不在 payload/日志/事件/埋点；
- 跨组织/越权 scope 被拒绝；
- 任务详情可审计；撤销后停止新调用；
- 不自动调用/写入/降级。

**工作量**：E3a 20–35 人日（暂定，需按同一范围 bottom-up 重估）；E3b 15–25；管理/审计/安全评审 5–10；E3 合计 40–70 人日。

### 7.6 E4：链式上下文与富成果

这是千问式完整专家套件的必要条件。

**E4-A 项目上下文**

- 新增项目/工作区模型（复用 P2 项目）；
- 每个项目有上下文目录/文件存储；
- 技能可以声明读取/写入的上下文文件；
- 任务创建时冻结项目 ID + 上下文版本；
- 技能输出 schema 校验；下游技能按 schema 读取；
- 记录上下文文件来源、版本、哈希、读写者；
- 云端任务容器挂载项目上下文（只读或受控读写）；本机使用授权目录；
- 安全不变量：云端只使用 `project_id` + 文件别名/哈希；本机绝对路径不出设备；本机 context 只在授权目录内读写；跨设备只传内容/别名，不传路径。

**E4-B 链式执行**

- 套件定义技能顺序、依赖、输入/输出 schema；
- **E4-B 基线是服务端确定性编排器**：按套件顺序逐步创建子 run/模型调用，每步做输入/输出 schema 校验，不依赖模型自行决定顺序；
- 单个 agent run 内用工具写读 context 只用于探索型/独立技能，不作为套件链式路径；
- 每一步产出写入 `context/<artifact>.json`；
- 下游技能读取上游产物；缺失/不匹配时失败或降级并提示；
- 支持独立/链式/增强三种模式；
- 任务快照包含套件版本、技能版本、上下文版本。

**E4-C 富成果管线**

- 支持 HTML/CSS/JS/React 工程文件、PDF、PPTX、DOCX、XLSX、图片；
- 对象存储/MIME/大小限制/病毒扫描；
- HTML 预览沙箱；Office 在线预览/编辑或下载；
- 设计/幻灯片工作台（画布/PPT 编辑器）另立；
- 成果版本、采纳、下载、审计；
- 当前 `MAX_ARTIFACT_CHARS=40_000`、`.txt/.md/.csv/.json`、20 文件/400KB 的限制必须扩展。

**E4-D 连接器增强**

- 套件声明「增强型连接器」；未授权时基础能力仍可用；
- 授权后技能读取增强数据（Figma tokens、WebSearch 竞品等）；
- 新授权/增强只影响新任务；撤销停止运行中任务的新调用；
- 增强来源在成果中标注。

**不建议首版做的能力**

- 浏览器接管、计算机控制、任意 MCP/STDIO、公开市场、用户文件系统安装、原始 SKILL.md 全量展示；
- 这些能力风险高，且与 we-meet 的「可控、可验收」定位冲突。

**工作量**：60–95+ 人日（项目上下文 20–30、链式执行 10–15、富成果 20–30、连接器增强 5–10、测试/安全 5–10）；这是起步估算，富成果/Office 在线编辑需 bottom-up 重估并加 20–30% 缓冲。1–2 人约 12–20 周。依赖 P2 项目、存储、前端预览/编辑器、安全评审。设计/幻灯片工作台另估 30–50+ 人日。

**估算边界**：60–95+ 只覆盖 E4-A/B 与 E4-C 的基础存储/预览/下载、E4-D 增强；E4-B 的 10–15 人日仅指最小确定性编排器，不含多子 run 重试/取消/审计；不含完整 Office 在线编辑、设计画布/PPT 编辑器（Workbench 30–50+）。如果要把 Office 在线编辑纳入 E4-C，需再加 15–25 人日并重新排期。

### 7.7 UI 方案

**E1 技能**

```text
[目标输入]
[已选：技能 A ×] [技能 B ×]
[+] [技能] [环境] [权限]                 [发送]
本次使用：技能 A（输出 Markdown）、技能 B（输出清单）
```

**E2a/E2b 套件/工作伙伴**

```text
[目标输入]
[已选：套件「产品设计」×] [快捷命令：动效规划 ×] [技能 A ×]
[+] [套件] [技能] [环境] [权限]          [发送]
本次使用：套件「产品设计」· 动效规划（预设，暂不支持链式上下文）
```

**E3a 连接器**

```text
[目标输入]
[已选：套件 P ×] [技能 A ×] [连接器 C ×]
[+] [套件] [技能] [连接器] [环境] [权限]  [发送]
本次访问：C（只读：项目、任务）；账号已连接；数据将发送到模型服务
```

**E4 完整套件**

```text
[目标输入]
[已选：套件 P ×] [快捷命令 /动效规划] [连接器 Figma ×]
[+] [套件] [技能] [连接器] [项目] [环境] [权限]  [发送]
本次计划：项目「会员改版」· 读取 brief.json / flow-web.json · 输出 motion-plan.json
```

入口与导航：

| 层 | 任务内 | 管理 | 左栏 |
|---|---|---|---|
| 技能 | composer「技能」chip | 设置/组织后台 | 不新增 |
| 套件 | composer「套件」chip + `/` 命令 | 「专家套件」管理页 | CRUD/列表/权限完成后可加 |
| 连接器 | composer「连接器」chip | 设置/组织后台 | 不新增 |
| 项目 | 新建项目/项目选择 | 项目页 | P2 项目实现后再加 |
| 扩展市场 | 无 | 无 | 不做；首版组织策展 |

状态：

| 状态 | 文案 | 动作 |
|---|---|---|
| 无可用能力 | 不渲染 | 无 |
| 加载中 | 正在加载… | 禁用 |
| 未安装/未启用 | 未启用 | 去设置启用 |
| 未授权连接器 | 未连接 | 连接 |
| 授权过期 | 授权已过期 | 重新连接 |
| 组织禁用 | 组织已禁用 | 不可选 |
| 环境不支持 | 仅云端/仅本机 | 阻止；不自动切换 |
| 套件无链式 | 当前为预设模式，不读取项目上下文 | 显示说明；不假装链式 |
| 上下文缺失 | 缺少 brief.json，将按独立模式执行 | 提示；可继续 |
| schema 不匹配 | 上游输出不符合套件 schema | 阻止/降级并提示 |
| 成果格式不支持 | 当前仅支持 Markdown/JSON | 阻止；不做假下载 |
| 超限 | 最多 3 个技能 | 禁用更多 |

可访问性：

- 套件/技能/连接器选择器用 button + `aria-expanded`；
- 多选用 `aria-pressed`；
- chip 移除按钮有 `aria-label`；

### 7.9 环境支持矩阵

| 能力 | 云端 | 本机 tracked | 本机 untracked |
|---|---|---|---|
| E1 技能 | 支持（服务端组合） | 支持（`execution_goal`，需新桌面） | 不支持 |
| E2a 套件模板 | 支持（服务端组合） | 支持（同上） | 不支持 |
| E2b 工作伙伴 | 支持（服务端组合） | 支持（同上） | 不支持 |
| E3a 连接器（只读 SaaS） | 支持（Gateway v2） | 不做 | 不支持 |
| E3b 连接器（本机/MCP/写入） | 不做 | 另立 E3b | 不做 |
| E4 链式上下文 | 支持（项目上下文 + 挂载） | 支持（本地工作空间，需桌面） | 不支持 |
| E4 富成果 | 支持（对象存储/预览） | 支持（本地文件 + 同步策略） | 有限 |
| 浏览器/计算机控制 | 不做 | 不做 | 不做 |

原因：

- 云端一定经过服务端，适合解析/冻结/审计；
- tracked 本机经过准入，可以返回执行目标；但需要桌面发版；
- untracked 不经过服务端，没有注册表/授权/审计；
- 系统级连接器风险太高，首版不做；
- 富成果需要存储/预览/编辑，是独立管线。

### 7.10 与 P0/P1/P2 的关系

- P0 统一 composer、会话、历史、注意项不受影响；E1 使用 composer 的 `tools` 插槽；
- E1 可与 P1 档位并行；E2a/E2b 依赖 E1；E3a 依赖执行器 v2；E3b 依赖桌面/适配器 v2；
- E4 依赖 P2 项目/工作区、成果管线、存储；
- 扩展工作不阻塞 P0；P0 composer 插槽先留好，但不渲染未实现能力。

### 8.3 验收标准

**E1**

- 技能可见/可移除；独立模式；版本冻结；
- 同键同选择幂等，不同选择冲突；
- 超长/跨组织/禁用/未知技能拒绝；
- 云端/tracked 执行带技能；untracked 明确不支持；
- 技能内容不含密钥/工具调用；注入测试通过。

**E2a/E2b**

- preset/快捷命令/默认技能正确预填；
- 技能选择顺序确定；执行顺序不保证（E4 才保证）；超限/冲突提示；
- preset 版本/哈希冻结；组织/个人权限正确；
- 页面明确「预设模式，不支持链式上下文/富成果」；
- 无连接器/无富成果/无独立套件工作台入口。

**E3a/E3b**

- E3a 只读连接器可连接/授权/调用/撤销；E3b 另立验收；
- 未授权/过期/范围不足/限流/不可用状态明确；
- 令牌不在 payload/日志/事件/埋点；
- 跨组织/越权 scope 拒绝；
- 任务详情可审计；撤销后停止新调用；
- 不自动调用/写入/降级。

**E4**

- 项目上下文可读写；技能输出 schema 校验；
- 链式技能读取前序产出；缺失/不匹配有明确状态；
- 上下文来源/版本/哈希可追溯；
- 富成果可预览/下载/编辑；HTML 沙箱；Office 安全扫描；
- 任务快照包含套件/技能/上下文版本；
- 连接器增强可选，基础能力不依赖连接器；
- 不自动扩权/不自动重放。

## 10. 风险与开放问题

| 问题/风险 | 影响 | 建议 |
|---|---|---|
| 首版要不要做链式？ | 决定 E2a 是否能叫「专家套件」 | 不做链式就称「套件模板」；真链式放 E4 |

| 是否支持 HTML/Office/PDF？ | 存储、预览、编辑、安全 | E4-C；先只读预览/下载，编辑后置 |
| 套件更新策略？ | 覆盖个人修改 vs 冻结 | 任务快照冻结；更新只影响新任务；个人覆盖另存 |
| 是否允许用户自建技能？ | 质量/安全/版权 | 首版组织策展；个人后置 |
| 是否展示原始 SKILL.md？ | 透明度 vs 泄露 | 终端摘要；管理员原文 |
| 自定义 MCP/STDIO？ | 任意命令/出网 | 首版不做；仅管理员签名运行时 |
| 浏览器/计算机控制？ | 高权限/误操作 | 首版不做；本机保留逐命令审批 |
| 连接器写操作？ | 副作用/审计 | 首版只读；写操作逐次确认 |
| 套件市场/分享？ | 质量/责任主体 | 首版组织内策展；公开市场后置 |
| 模型档位与套件耦合？ | 质量/成本 | 套件声明最低档位；服务端解析；客户端不覆盖 |
| 远程派发携带套件？ | 设备 A→B 一致性 | 首版不带；后续扩展 `work-device/v1` |
| 本机 untracked 支持？ | 隐私 vs 组织策略 | 首版不支持；避免绕过审计 |

需要产品拍板：

1. **首版 E2a 套件模板是否足够，E2b 工作伙伴是否同批？**（推荐先 E2a，E2b 后置）
2. **是否投入 E4 的项目上下文/富成果？**（决定能否做千问式完整套件）
3. **连接器边界：E3a 只读 SaaS，还是同时做 E3b 本机/MCP/写入？**（推荐先 E3a）
4. **套件内容来源：组织策展，还是允许个人上传/市场？**（推荐组织策展）

## 12. 一句话结论

**千问办公的专家套件值得学的是「完整工作方案包 + 快捷命令 + 技能链式上下文 + 连接器增强」，不值得直接照搬的是「原始 SKILL.md 全量可见 + 文件系统安装 + 任意 MCP/STDIO + 浏览器/桌面控制 + 套件更新覆盖个人修改」；we-meet 应先做不需要改执行器的技能与套件模板，再做到只读连接器，最后才投入项目上下文与富成果，否则所谓「专家套件」只是更长的提示词。**
