# 飞书企业账号生命周期调研

- 日期：2026-10-24
- 范围：企业租户创建、员工维护、角色与权限管理、注销 / 离职 / 企业解散
- 方法：飞书帮助中心 + 飞书开放平台官方文档
- 用途：为 we-meet Work 组织生命周期方案（ADR-0005 后续）提供对标
- 核验口径：以官方帮助中心与开放平台文档为准；版本、套餐、人数上限等数字以实际合同和当期版本对比页为准

## 0. 结论摘要

飞书没有“企业账号 CRUD API”。企业账号是用户在飞书客户端注册产生的**租户**，开放平台应用只能依附于既有租户；真正可编程的是租户内的**通讯录、用户组、应用授权和事件**。

飞书的生命周期模型可以概括为四层：

1. **租户层**：企业由用户注册创建，创建人自动成为超级管理员；企业不能普通删除，只能由创建人解散。
2. **成员层**：员工通过通讯录维护；“删除用户”本质是离职，默认软删除并支持 30 天内恢复。
3. **角色层**：创建人、超级管理员、自定义管理员角色，配合部门/会议室数据范围。
4. **授权层**：应用可用范围、通讯录权限范围、API 权限、资源 ACL 分层收敛，用户组作为规模化授权单元。

注销也必须分三层看：**成员离职**、**个人账号注销**、**企业解散**，三者的操作主体、可逆性和数据处理完全不同。

## 1. 企业账号创建

### 1.1 创建流程

- 用户在飞书客户端注册账号后创建企业。
- 创建人自动成为**超级管理员**，拥有管理后台全部权限。
- 企业名称、行业、规模等不是强制项；创建阶段不要求完成企业认证。
- 同一手机号“创建 + 加入”的企业总数上限为 **30 个**。
- 企业没有普通“删除”入口。创建人只能通过**解散企业**终止租户；解散是唯一根操作。
- 创建人身份可以转移；未转移前不能被直接移除。

### 1.2 认证与规模门槛

- 飞书认证包括企业法人认证、加盖公章授权书认证、团队认证等，主要面向中国大陆企业、事业单位和其他组织。
- 认证有效期 **1 年**，到期需年审续期。
- **未认证企业成员上限 100 人**；认证后按版本提升。
- 商业版单次购买人数上限 500，企业版更高；具体以当期版本对比和合同为准。
- 认证解决的是租户身份与规模，不等于应用发布审核。应用还有独立的权限申请与发版审核。

### 1.3 开放平台边界

- 开放平台没有“创建企业/租户”的 API。企业由用户侧创建，应用通过安装进入租户。
- 应用分两类：
  - **企业自建应用**：仅本企业可用，通常不需要飞书审核，适合内部系统。
  - **商店应用（ISV）**：服务商开发、上架应用中心、多企业安装；安装时飞书向应用推送 `tenant_key`。
- `tenant_key` 是企业唯一标识；`tenant_access_token` 是应用身份凭证；`user_access_token` 是用户身份凭证。SaaS 多租户必须用 `tenant_key` 做租户隔离，不能只靠域名或邮箱。

## 2. 员工维护

### 2.1 身份标识

飞书同时存在多种用户 ID，不能混用：

| ID | 唯一范围 | 适用场景 |
|---|---|---|
| `open_id` | 单个应用内 | 同一用户在某个应用里的稳定标识 |
| `union_id` | 同一开发者/ISV 的多个应用 | 跨应用识别同一用户 |
| `user_id` | 单个租户内 | 租户内通讯录、管理接口 |
| `tenant_key` | 全飞书 | 企业/租户标识 |

关键原则：**不要拿手机号、邮箱当主键**；它们在换绑、离职、重新入职时都会变化。跨租户数据必须带 `tenant_key`，跨应用识别用 `union_id`，单应用内用 `open_id`。

### 2.2 入职 / 邀请

管理后台支持：

- 单个添加；
- 批量导入；
- 邀请链接 / 二维码；
- 设置邀请有效期、是否需要审批；
- 非管理员邀请是否允许，可由管理员策略控制。

开放接口 `POST /contact/v3/users`：

- 需要通讯录权限（如 `contact:contact`）；
- 支持姓名、手机、邮箱、部门、工号、职位等字段；
- 通过短信/邮件发送邀请；
- 支持 `client_token` 幂等；
- 重复手机号/邮箱返回稳定错误码；
- 受席位和租户人数上限约束；
- 部门权限和字段权限必须提前配置，否则创建会失败或字段不可见。

### 2.3 在职变更

- `PATCH /contact/v3/users/:user_id` 更新姓名、邮箱、手机、部门、自定义字段等。
- 较新的 `directory-v1` 面向“入转调离”和组织架构同步，支持员工状态、冻结/恢复等生命周期字段。
- 部门变更要求应用同时拥有**变更前和变更后部门**的数据权限。
- 已离职员工不能再修改邮箱、手机、部门、上级、冻结状态等字段。
- 冻结（`is_frozen`）与离职是两种不同状态：冻结通常用于临时停用，离职是正式退出。

### 2.4 离职 / 删除 / 恢复

飞书的“删除用户”接口本质上是**员工离职**，不是物理删除：

- 账号被停用，释放席位；
- 可转移的资源包括文档、妙记、日历、部门群、外部群、邮件、应用、服务台、审批等；
- 资源处理方式通常有：转移给接收人、保留、删除；
- 接收人默认为直属上级，也可指定其他成员；
- 需要目标部门的数据权限；
- 30 天内可通过管理后台或 `resurrect` 接口恢复；
- 恢复后聊天、文档等部分数据可恢复，但**已转移的资源、已变更的部门不会自动恢复**；
- 恢复时席位需要重新分配；重复工号/邮箱会报错；
- 超过 30 天不可恢复。

此外还有“待离职”状态：管理员可设置离职日期和原因，成员在正式确认离职前仍可使用飞书；它不是自动执行的定时离职。

### 2.5 用户组

- 用户组分为**普通组**（手工维护）和**动态组**（按规则自动更新）。
- 一个企业最多 **500 个用户组**，单个用户组最多 **10 万成员**。
- 用户组是权限模型里的“连接器”，可用于：
  - 应用可用范围；
  - 组织架构可见范围；
  - 管理后台角色和数据范围；
  - 文档/知识库等资源权限。
- 普通组可通过 API 增删改；动态组通常只读查询。

### 2.6 事件与对账

- 通讯录变更事件覆盖用户创建、更新、删除，部门变更，用户组变更，以及通讯录权限范围变更。
- 事件适合做准实时同步，但不能作为唯一数据源；应配合定期全量/增量对账，避免漏事件、重复事件和乱序。
- 创建用户等接口支持 `client_token` 幂等；事件消费端也应做幂等。

## 3. 角色与权限

飞书不是单一 RBAC，而是多层权限叠加。任何一层不满足，用户就看不到或操作不了。

### 3.1 管理后台角色

| 角色 | 权限 | 限制 |
|---|---|---|
| 创建人 | 全部权限，包括解散企业 | 全企业唯一；不能直接移除，只能转移身份 |
| 超级管理员 | 除解散和部分敏感人事权限外的全部后台权限 | 建议 2–4 人；可增删其他超级管理员，但不能移除创建人 |
| 自定义管理员 | 仅获得所分配角色的权限项和数据范围 | 可多人持有同一角色；是否可管理其他管理员取决于是否授予对应权限 |

自定义角色支持：

- 角色名称、说明、上级角色；
- 权限项：成员、部门、用户组、会议室、应用范围等；
- 数据范围：指定部门、会议室等；
- 分配 / 移除 / 删除角色；
- 变更即时生效；
- 管理后台审计记录操作。

### 3.2 五层权限模型

| 层 | 回答的问题 | 配置方 | 作用 |
|---|---|---|---|
| 管理后台角色 | 管理员能操作哪些后台功能、哪些部门/会议室 | 超级管理员 | 管理动作 |
| 应用可用范围 | 哪些成员可以使用这个应用 | 开发者发版时配置，管理员也可在后台调整 | 用户能否打开应用 |
| 通讯录权限范围 | 应用能读写哪些部门、用户、用户组 | 开发者后台 / 管理后台 | API 能拿到什么数据 |
| API 权限 / 字段权限 | 应用能调用哪些接口、读写哪些字段 | 开发者申请 + 管理员审核 | 接口级与字段级 |
| 资源 ACL | 谁能看/编辑某篇文档、知识库、多维表格 | 资源所有者 / 管理员 | 单资源访问 |

补充：

- 通讯录权限范围的配置对象是部门、用户、用户组；变更会触发 `scope updated` 事件；线上配置通常立即生效。
- 应用可用范围与通讯录范围是两件事：前者决定“谁能用”，后者决定“应用能读谁”。
- 业务应用内部还可以再做 RBAC/ABAC（飞书低代码平台就是典型），这与管理后台角色不是同一套东西。
- 文档、知识库、多维表格的权限是资源 ACL，不要和管理员角色混为一谈。
- 部门负责人、直属主管是组织字段，不等同于管理后台角色。

### 3.3 审计

- 管理后台有管理员操作审计和 OpenAPI 日志。
- 行为审计 API 面向用户行为，可对接自建应用或 SIEM；官方文档标注日志最多保留 **180 天**。
- 审计通常只读，不提供写入/删除能力。

## 4. 注销

飞书的“注销”必须分三层看：

| 对象 | 操作 | 操作主体 | 可逆性 | 数据处理 |
|---|---|---|---|---|
| 成员 | 离职 / 删除用户 | 超级管理员或有权限的管理员 | 30 天内可恢复，且资源未被转移 | 账号停用、释放席位、资源转移/保留/删除 |
| 个人账号 | 注销账号 | 本人 | 不可逆 | 退出企业，账号数据清除 |
| 企业 | 解散企业 | 仅创建人 | 72 小时内可撤回，之后不可逆 | 全员离职，账号、通讯录、邮件、文档、知识库等永久删除 |

### 4.1 成员离职

- 管理路径：管理后台 > 组织架构 > 成员与部门 > 成员 > 操作离职。
- 可转移资源：文档、妙记、日历、部门群、外部群、邮件、应用、服务台、审批等。
- 资源处理方式：转移、保留、删除。
- 账号停用并释放席位；30 天内可恢复。
- 恢复的限制：已转移的资源、已变更的部门不会自动恢复；席位需要重新分配；重复工号/邮箱会报错。
- 超过 30 天不可恢复。

### 4.2 个人账号注销

官方帮助中心列出的条件包括：企业未认证、非创建人、账号状态正常。路径为“头像 > 设置 > 账号与安全 > 账号安全中心”。

- 没有明显冷静期；
- 注销后自动退出企业，账号不可使用，数据清除；
- 创建人不能直接注销，必须先转移创建人身份或解散企业。

### 4.3 企业解散

- 仅创建人可操作；
- 前置条件：没有未结清的付费资产；
- 有 **72 小时**冷静期，期间可撤回；
- 72 小时后正式解散：所有成员自动离职，成员账号、通讯录联系人、邮件、云文档、知识库等永久删除；
- 官方明确说明不可恢复。

### 4.4 数据保留与合规清理

- 旗舰版等版本提供数据保留策略/保留标签，可按在职/离职成员保留或到期删除；
- 管理员可对离职成员数据做匿名化清理；
- 支持合规导出；
- 解散企业时的数据删除是永久性的，不能和普通“成员离职”混为一谈。

## 5. 飞书方案的设计原则

1. **租户身份与成员身份分离**：`tenant_key` 是根，用户 ID 是租户内/应用内标识。
2. **创建人是一个不可删除的根角色**：只能转移，不能直接移除；解散权唯一。
3. **删除即离职，离职即软删除**：30 天恢复窗口，先转移资源再关闭账号。
4. **权限分层收敛**：管理角色、应用可用范围、通讯录范围、API scope、资源 ACL 分别配置，任何一层缺失即拒绝。
5. **用户组作为规模化授权单元**：人和部门先进组，权限尽量授给组，而不是逐人配置。
6. **变更可审计、可恢复、有冷静期**：管理员操作有审计；成员离职 30 天；企业解散 72 小时。
7. **事件 + 对账双通道**：事件负责实时性，全量/增量对账负责最终一致性。

## 6. 对 we-meet Work 的启示

上一轮的组织生命周期方案可以按飞书的三层模型校正：

- **平台租户**：`core.Organization` + 创建人/所有者；
- **Work 开通**：`WorkOrganizationEntitlement`；
- **Work 成员**：`WorkMemberGrant`；
- 再补一层**外部身份映射**（飞书接入时）。

### 6.1 可直接借鉴

| 飞书做法 | 我们的对应设计 |
|---|---|
| 创建人唯一、可转移、不可直接移除 | `Organization` 增加 `created_by`/租户所有者，并支持所有权转移 |
| 删除成员 = 离职 + 资源转移 + 30 天恢复 | 成员 `Membership` 增加离职流程、资源交接、恢复窗口 |
| 企业解散 72 小时冷静期 | 组织归档增加可撤回窗口，而不是立即物理删除 |
| 管理角色 + 数据范围 | 客户侧增加组织管理员角色，权限项与部门范围分离 |
| 应用可用范围 / 通讯录范围分离 | 我们的 `features` 与 `X-Organization-Id` 数据范围继续分层，不合并成一个开关 |
| 用户组作为授权单元 | `WorkMemberGrant` 后续支持按用户组授权，而不是只支持逐人 |
| 外部 ID 映射 | `Membership` 或独立表保存 `tenant_key` / `open_id` / `union_id` |
| 事件 + 定期对账 | 订阅通讯录事件，同时保留定时全量对账，防止漏事件 |

### 6.2 不要照搬

- **100 人未认证上限**是飞书的产品策略，不是我们的租户模型；我们用 `member_limit` 和套餐约束即可。
- **72 小时 / 30 天**是飞书的产品参数；我们的留存窗口应由合规和客户合同决定。
- 飞书管理后台的角色/权限项非常多，不要一次性全建；先做“平台运营 / 客户管理员 / 普通成员”三层。
- 飞书有完整的应用商店审核体系；我们是内部或多租户 SaaS，审核流程可以更轻。
- 不要把 `open_id` 当跨租户主键；跨应用用 `union_id`，跨租户必须带 `tenant_key`。
- 不要把“管理员角色”和业务权限（文档 ACL、Work 功能开关）混成一个字段。

### 6.3 当前设计的缺口

结合现有代码，比较明显的缺口是：

1. **没有租户创建人/所有者**：`core.Organization` 只有 `name/slug/is_active/settings`，没有 creator/owner，也没有所有权转移（[core/models.py:6195](../../src/backend/core/models.py#L6195)）。
2. **没有外部身份映射**：`Membership` 只有内部 `user`（[core/models.py:6324](../../src/backend/core/models.py#L6324)）。接入飞书时需要 `tenant_key/open_id/union_id`，且不能拿邮箱/手机当主键。
3. **没有“待离职 / 离职恢复”状态**：`MembershipStatusChoices` 只有 active/invited/suspended/left，没有离职日期、离职原因、恢复窗口。
4. **Work 数据是 owner-scoped**：`WorkMaterial.owner`、`WorkTask.owner` 都是个人，成员离职后没有类似飞书的资源交接；目前只能保留数据但无人可读。
5. **`member_limit` 没有真正执行**：`WorkOrganizationEntitlement.member_limit` 有字段，但授权创建路径没有校验；飞书是席位/人数硬限制，我们至少要在 grant 创建和激活时校验（[work/models.py:292](../../src/backend/work/models.py#L292)）。
6. **`WorkMemberGrant` 只支持逐人**：飞书的用户组是规模化授权单元，后续应支持组授权（[work/models.py:333](../../src/backend/work/models.py#L333)）。
7. **没有管理员角色与数据范围**：目前只有 `work.manage_tenant` 这种粗粒度权限；飞书的管理员角色可以按部门/会议室限定数据范围。
8. **没有审计留存策略**：`WorkAccessAudit` 目前只保证写入；飞书有 180 天审计查询和合规导出，我们需要定义自己的留存期。

### 6.4 建议的目标模型

```text
Organization (tenant)
  ├─ created_by / owner            # 唯一根身份，可转移
  ├─ Membership                    # active / pending_departure / left
  │    └─ external identity        # tenant_key + open_id + union_id
  ├─ WorkOrganizationEntitlement   # features / budget / member_limit / archive
  ├─ WorkMemberGrant               # user grant（后续 group grant）
  └─ WorkAccessAudit               # 运营审计，独立留存
```

### 6.5 建议优先补齐的四项

如果只做一轮增量，建议优先：

1. **租户所有者/创建人 + 转移**：避免组织没有可负责的管理员，也避免创建人离职后无人能解散/转移。
2. **外部身份映射**：`tenant_key` + `open_id` + `union_id`，为飞书/企微/钉钉接入留统一模型。
3. **成员离职与恢复窗口**：离职立即撤销 Work grant，保留数据和审计，30 天内可恢复；恢复不自动恢复 Work 权限，必须重新授权。
4. **`member_limit` 与 grant 校验**：在创建 grant、激活 Work、批量授权时统一执行，避免“字段存在但不生效”。

## 7. 落地顺序建议

- **P0**：租户所有者/转移、外部身份映射、成员离职/恢复、`member_limit` 校验。
- **P1**：用户组授权、客户侧管理员角色与数据范围、审计留存与导出。
- **P2**：资源交接（Work 成果/材料）、飞书事件订阅与定期对账、按套餐的认证/规模门槛。

## 8. 待复核项

以下内容不阻塞方向判断，但在实现前需要按目标套餐和部署方式复核：

1. 飞书各版本的具体人数上限、席位购买规则和认证要求。
2. 目标企业是否允许使用 `directory-v1`，以及其事件覆盖范围与 contact-v3 的差异。
3. 飞书是否提供满足我们需求的 SCIM/HR 标准同步方式；如没有，需要自建事件 + 对账同步。
4. 我们的留存窗口、审计保留期和合规导出要求，应由合同与法务确认，不直接照搬 30 天/72 小时/180 天。
5. Work 的接入形态：是作为飞书应用安装，还是独立 SaaS；这决定租户创建、身份映射和注销路径。
